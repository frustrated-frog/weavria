# 0154 把来源定位与正文读取编译为两步取证

2026-11-27。[上轮修订验收](0153-修订任务的来源重验与原文引用.md)的安装迁移第二对，两次搜索、两次实际取得正文，最终三次提交均被退回。旧任务声明对每个信息需求都要求 `/paths` 和 `/text`，这两个字段分别来自搜索和读取回执。直接按字段合并会把一个目录的匹配项和另一个目录的同名文件连起来。把它们拆成两个能独立完成的阻塞需求也有同样的问题。

## 决策与执行

保留原问题作为一条信息需求，在其内部编译两步可执行的取证条件。宿主在 `HarnessEvidence.located_reads` 中登记定位器、读取器、两者的版本，以及查询、候选列表、规范标识和正文字段在各自契约中的位置。任务准备先对照可见工具和输入输出 Schema。模型为需求选择读取器与定位查询，例如 `{"located_source":{"reader":"read_document","query":"pyproject"}}`。宿主从登记项派生两个生产者、字段和持久化版本。显式声明与登记项冲突时走已有的有界纠错。这个选择不会扩大可执行工具集合。

例如，归约器先遇到该查询已获准执行的成功回执，回执中唯一的候选是 `one/config.md`。接下来，读取的规范参数和返回原件中的标识都必须恰好是 `one/config.md`，正文还必须有值。这时账本保存两个分别指向定位和正文的 Artifact 地址，各自保留 Run、Call 和内容摘要。共同范围的哈希绑定 Run、完整计划、查询与规范源标识。同查询重复取证保留稳定的范围，不同需求的查询各自判断。随后模型仍需分析材料、作答并通过原有的交付验收。

取证条件同时指导能力选择。缺定位字段时，需要定位器；只缺材料时，需要读取器。一格工具预算也能按阶段切换。执行模型能从任务视图读取当前需求的查询和指针。证据归约按已接受回执的顺序进行，每条两步需求顺序扫描记录；当前定位索引按 Run 保存最近一次匹配查询的唯一结果。两次调用的授权照常由 Runtime 决定。

## 版本、失败与适用范围

- `InformationNeed`、`InformationRequirement` 和注册关系可见的 `CapabilityView` 使用 v3。旧任务帧继续按原版本读取。查询、版本和指针参与需求身份计算。跨 Run 再次使用材料时，须在本轮重建定位与读取的关系。取消沿现有 Artifact 读取边界传播。
- 当前契约用于同一 Run 内拥有稳定规范标识的只读资料，定位和读取各使用一个规范字符串参数。多租户过滤、动态版本和当前时效证明需要更丰富的来源契约。没有匹配、多个候选、错误查询、反向顺序、版本不符、仅后缀相同、额外参数或空正文都不能拼成完整证明。
- 这一机制验证查询与已读材料的结构关系。模型仍可能为用户问题选择了错误查询。两个在接受顺序上吻合的回执也不足以证明模型形成后一个动作时已看到前一个结果。在需要这种因果保证的场景，读取器应显式消费定位 Artifact。
- 当前查询属于已接受的任务计划。若查询太宽、太窄或命名不对，执行时随意换词无法取得该计划的证明。单阶段需求与语义取证策略仍走各自原有路径。

```sh
uv run --offline pytest -q tests/evaluation/test_located_read.py
uv run --offline python -m examples.located_read_replay .weavria/revision-delivery/receipts-20261127/migration-2/verified.db

```

旧数据库中没有模型在准备阶段选择的查询。只读回放取模型当时实际执行的两个查询，分别比较相同回执在原规则与显式两步规则下的结果。`pyproject` 和 `uv.lock.packages.tsv` 均从 `partial` 变为 `acquired`。这验证了原始材料足以建立关联。被拒绝的 Run 保持原终态，回放不重新打分。测试另以两个目录下的 `config.md` 验证错配，并覆盖另一需求的查询、歧义、空正文、别名、读取顺序、工作集切换和取消。

在线对照冻结安装迁移问题、独立评分器、模型和预算。首版完成后复制同一个 SQLite 快照，两种修订策略都可重验旧回执。只在实验组注册定位关系，按重复次数交替先后顺序。实验保留首版失败的配对。早期两对的旧声明要求模型重复填写多个字段，两次准备失败；改用简式声明后的两对成功编译，在目录读取后暴露工具发现裁剪字段导致的契约冲突。用原会话复现后，工具选择改为按当前取证阶段分配。一次额外诊断的首版未通过，没有进入配对。最早一批直接连接报 `ConnectError`，使用本机已有的系统代理后才取得模型响应。

第一对的实验组只读取会话中的历史原件，两次提交的候选答案都通过离线字段判据，本轮的定位和读取条件始终缺失。第三对把查询预定为 `poetry.lock`。执行中模型改搜 `lock` 并读取正确的 `uv.lock.packages.tsv`，任务帧里的查询仍是旧值。账本保留这一缺口，候选答案也因取证不完整被拒绝。两次实验组修订均以 `completion_rejected` 结束，工具选择的运行时异常已消失。结果支持按完整标识核对原件的执行语义，但在这项任务上启用策略增加了成本并降低交付率，因此只显式启用。

真实模型批次在含有既有任务准备与覆盖审计改动的同一工作树运行；配对内使用相同模型、用户输入和首版会话。就任务编排而言，尚待解决的是执行反馈如何修正某条失效的资料定位计划，同时保留其他来源已完成的取证与交付要求。
