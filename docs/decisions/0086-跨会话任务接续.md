# 跨会话任务接续

会话 A 完成一部分只读任务后，宿主可调用 `register_task(task_id, session_id, run_id, access=...)` 登记已落库的成果。会话 B 通过 `continue_task(task_id, session_id, expected_version=..., access=...)` 创建新 Run。任务版本独立于 Run 的执行序列及任务修订号。新 Run 的目标和约束来自任务头的权威 TaskInput，跨会话的版本和来源则来自 SQLite 中的任务登记。

宿主提供绑定已认证主体的 `TaskAccessPolicy`，分别检查目标会话的读写权限和来源会话的读取权限。框架核对结果是否已被原 Run 接受、工具是否为可安全重放的只读工具、当前 Tool Policy 是否仍允许该调用，并校验 Artifact 身份。调用 `read_task_artifact` 时重新执行这些检查。此前已经交付给目标会话的内容仍属于该会话历史。

接续视图包含来源引用、小型原始结果、上一 Run 的需求状态和工作记录。任务理解和执行模型都能消费这份视图，并按现有上下文预算处理。历史需求状态属于低信任上下文，新 Run 仍独立验收。当前资料的时间有效性由新 Run 复核；大型原文通过宿主读取 API 获取。第一版最多保留四个 Run、十二份来源和 12000 字节接续上下文，超限时显式拒绝。

只读分支可以在不同会话并行。提交结果前重查任务授权，然后在一个 SQLite 事务中比较旧任务头并发布新版本。冲突方的 Run 仍留在其会话中，任务头只接受一个分支的结果。运行中断依旧走原有 Run 恢复协议。

运行 `uv run pytest -q tests/harness/test_task_continuation.py` 可复验。会话 A 实际调用工具读取第一份文档，两支接续 Run 分别只读取第二份，并在输出中引用第一份文档的原始 Artifact。测试同时检查来源会话无权限时拒绝接续和原文读取、工具授权撤回、任务版本冲突。脚本模型验证的是授权、上下文和版本契约。
