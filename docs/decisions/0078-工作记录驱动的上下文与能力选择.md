# 0078 工作记录驱动的上下文与能力选择

状态：已实现首个垂直切片，2026-11-01。承接 ADR 0077。目标是让工作进展实际影响后续行动，不是引入独立规划执行器。

## 问题和取舍

TaskFrame 表达需求，NeedLedger 表达证据获取状态；二者不能替代计划、假设、阶段成果和被放弃尝试。只依赖聊天历史会让这些信息随上下文缩减丢失。将它们写入长期记忆又会混淆任务局部推断与长期事实。

选择在已有 SemanticSnapshot 中增加独立、有界的 `working_state` 投影，模型通过 `propose_work` 提交替换提议。工具执行仍经过同一个 Runtime、Policy、Artifact 与 ToolRecorded 链路；工具只产出提议 Artifact，不直接修改状态。TaskAwareSessionPreparer 在工具结算阶段归约已接受结果，将投影持久化，再驱动下一轮选择。

没有另加规划模型、模块路由 Agent 或 DAG 执行引擎。使用现有 ToolBatch 协议，比扩展所有供应商的 ModelTurn 更小；代价是每次工作更新消耗一次工具调用，通常还需要下一次模型决策。允许同批提出工作记录与独立工具调用，但不能引用同批尚未接受的工具结果。

## 工作数据与更新算法

- `WorkNote`：最多 6 条，类型为 plan、hypothesis、result、rejected、issue；摘要最多 240 字符，每条关联最多 4 个需求、2 个来源地址。保存简短的可见进展，不要求模型输出内部推理过程。
- `WorkUpdate`：当前 task_revision、base_revision、完整笔记集合、下一步需求和查询。整个提议输入最多 4000 UTF-8 字节。
- `WorkProposal`：工具验证来源访问与 JSON pointer 后，绑定真实 ArtifactRef。提议工具是无外部写副作用的计算与读取；只有 Runtime 接受的结果才能被后续归约。
- `WorkingState`：显式 `trust=model_inference`；单独的工作修订号、记录消费游标、笔记、来源、下一步意图、最近失效笔记和更新诊断。序列化最多 8192 字节，已替换的历史仍留在原事件和 Artifact 中。

归约从 processed_records 后开始，跳过普通工具和失败提议，只读取新提议 Artifact。按 Runtime 接受顺序依次执行：

1. 检查 task_revision 和 base_revision；不匹配则保留当前记录，显示 stale_revision。
2. 关联需求必须在当前 Frame 中，否则保留原记录，显示 unknown_need。
3. 接受全量替换，工作修订号加一；最后推进消费游标。

同一批两份提议若基于相同修订号，第一份接受，第二份冲突，不按工具完成快慢决定覆盖关系。没有 last-writer-wins。归约使用不可变局部值；中途取消不发布半份工作状态，重放同一已接受流得到相同结果。语义头提交沿用原有 CAS 和事务取消结算，不另写第二份事务状态。

## 工作状态如何改变执行

### 上下文

TaskModelView 的稳定 definition 不随笔记变化，`progress.working_state` 携带当前有界记录。ContextCompiler 仍负责整个请求预算与传输计量，提前为最大工作投影预留空间。原始历史可以缩减，当前记录不会仅因旧工具输出被裁掉而消失；空间不足仍明确失败，不声称可无限压缩。

当前下一步需求获得 2 倍软偏好，最终需求权重仍封顶为 8。next_query 产生单独的 `working:next` ContextDemand，关联笔记的来源成为 EvidenceAnchor，参与已有历史/工具上下文选择与记忆查询。引用只保证来源地址可读取，不保证摘要内容真实。

### 能力

AdaptiveCapabilityPolicy 使用相同的有界需求偏好，再运行原有边际覆盖收益/描述成本贪心与最佳单例比较。其它需求仍保有权重，已满足需求不会因笔记被重新标成未完成，未授权或未发现工具也不能被笔记凭空加入。

本轮不根据自然语言笔记直接封禁工具或发明新需求。被否定尝试供模型下一轮参考；模型提出新的 next_need_ids 后，框架才改变需求资源偏好。若模型选错下一步，偏好可能有害，这是需要真实任务验证的策略风险。

### 完成与进展

工作笔记不是证据准入。result 只是模型声称的阶段成果；写“已完成”不满足任何 NeedLedger 条件，不绕过 TaskObligationCompletionPolicy。工作修订号增加也不自动计为实际任务进展，已有无进展策略和模型/工具次数预算继续生效。

## 用户修订与失效传播

steering 后复用既有任务理解与 Frame patch。比较新旧需求定义，找出完全未变化的需求集合，再迭代移除其依赖了已变化需求的后继，得到可保留的依赖闭包。

关联需求全部位于该闭包中的笔记保留；无关联需求的全局笔记、关联已变化/删除需求的笔记移出活跃集合，并记录其 ID。旧 next_query 和 next_need_ids 总是清空，因为下一步意图依赖当前整体目标，应重新提出。工作修订号加一，旧提议不能在新目标下生效。steering 前的工具事实仍保留，工作记录不接管事实的重新匹配。

这是依赖声明驱动的失效，不是自然语言语义等价判定。模型若漏报笔记依赖，可能保留不再适用的笔记；保守的全局笔记会直接失效。原目标与用户修订始终以原始输入为准，不由工作笔记覆盖。

## 装配与兼容

`AgentHarness(working_records=True, understanding=...)` 成套启用工具、工作归约、上下文偏好和 TaskModelView。默认关闭，方便对照旧策略；启用后框架自动安装标准 TaskModelViewProjector。高级自定义选择器/投影器必须声明 working_records_version=1 并实现对应消费语义，缺失时启动报错。

工作工具与成果读取属于支持工具组，不参加业务工具发现。工作模式从初始决策就展示该组；否则纯文本任务第一次产生工作 Artifact 时，会在业务集合不变的情况下悄悄扩展同一 capability epoch。澄清路径不展示支持组，路由切换推进能力版本。

SemanticSnapshot 新增 v2；v1 不携带 working_state，旧序列化形状保留。工作状态有自己的 v1 Schema。SQLite 仍保存 JSON，不需要表结构迁移；旧数据无需伪造工作记录。TaskFrame、NeedLedger、ModelTurn 的持久化 Schema 不变。Harness 版本为 unified-harness/4，TaskAwareSessionPreparer 为 task-aware-session/11，TaskModelViewProjector 为 task-model-view/2，选择策略为 adaptive-capabilities/2。

本轮工作记录属于当前 Run。新输入开启新工作记录；不自动搬运到新任务、长期记忆或另一会话。持久化与可重建投影不等于自动崩溃续跑，Resume 仍未实现。

## 验证与实验

确定性组合覆盖真实 SQLite、上下文编译和工具运行：大文档读取后业务工具退休，模型仍可提交带来源的工作记录，下一轮看到记录与来源；运行中 steering 后旧记录正确失效；纯文本任务更新记录不改变同一 epoch 的工具集合。归约测试覆盖同基版本冲突、重复读取、未知需求、来源权限、无效 pointer、取消后的纯重放、局部失效与依赖传播，以及旧 Schema 兼容。

`uv run python -m examples.working_records` 冻结两个未满足需求、相同目录与一个工具位置。无工作意图选择 read_alpha；工作记录要求先检查 beta 后选择 read_beta。上下文对应需求权重同步提高。它证明该状态影响资源分配，不能证明真实 Agent 会提出正确计划或任务成功率提高。额外工作工具调用与视图预留有成本，默认不启用。

下一步在这个状态基础上研究阶段摘要和定向回取：减少模型每次手工替换的成本，明确何时将旧历史整理成派生摘要，并用真实长任务比较无工作记录、固定窗口与工作记录的效果。没有将 Skills、沙箱、多 Agent 或 Resume 混入本次实现。

本轮结果：全量 `uv run pytest -q` 1372 项通过（68.72 秒），Ruff、格式检查和 Pyright 全部通过；真实模型 CLI 完成 `--help` 检查，未发起模型调用。固定机制实验中，无记录选择 read_alpha（描述 536 字节），带记录选择 read_beta（描述 534 字节），当前工作投影增加 361 字节。该数字不含工具描述、更新调用、来源材料和最大增长预留，不能当作完整 Token 成本。
