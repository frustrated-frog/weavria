# 历史结账修订与当前库存承诺的对照验收

2026-11-19。保留库存任务作为端到端回归用例，默认使用 `model-task-understanding/16`。扩展时间条件的候选解释器 `/17` 保存在提交 `d199f90`。它消除了本批次历史首版的时效误判，但三次冷启动均未交齐三份结果。

## 问的是哪个时点

上一项双组件升级修订曾因一份补发回执被要求证明现实时效而无法交付。本次用独立编写的库存归档检验同一个问题。补发时间晚于结账时间，只会改变对结账时事实的认识。客户今天还能订多少，取决于之后的预留、发运、入库和放行。

| 请求 | 当轮可访问的来源 | 预先冻结的交付条件 |
| --- | --- | --- |
| 首版，核算 D17 结账时 S4 两仓可用件数 | 含其他日期、货号的账本，以及扣除隔离库存的规则 | 东仓 72 − 5 = 67，西仓 51 − 6 = 45 |
| 历史追问，按补发单修订结账表 | 首版归档加同一张更正单，只改东仓实盘数 | 东仓 63 − 5 = 58，西仓仍为 45 |
| 当前追问，修订数现在还能否承诺给客户 | 和历史追问完全相同的归档 | 明确证据不足，两仓件数均为 null，指出需要当前可承诺库存（ATP） |

归档说明明确写出其覆盖边界。它能证明这些材料不足以确认当前件数。报 0 件也需要当前库存证明。验收器分别检查候选内容、宿主验收和实际交付，要求 JSON 类型正确、字段完整、键唯一。一份正确候选两次被拒仍记为未交付。

每次冷启动先运行首版。只有首版正确交付才在关库后用 SQLite backup 复制两份各自独立的会话，分别接受两个追问。副本继承同一个首版回答、工具记录、工作状态及任务解释，两个追问互不可见。第 2 组先运行当前分支，第 1、3 组先运行历史分支。首版失败的组保留在整组分母中。解释器版本之间分别冷启动，没有共享模型采样。

## 候选改了哪里

`/16` 为声明了版本化材料的连接器提供“指定版本”和“证明现实时效”的选项。普通归档连接器只暴露 `freshness`。`/17` 在首次解释与覆盖审计发起的语义修订中，都让模型为每条信息需求独立选择事实需要成立的时点。指定历史期间（含补发更正）和指定版本映射到现有 `stable`；要求证明此刻外部状态映射到 `current`。宿主拒绝新旧字段同时出现的矛盾声明，旧声明中的 `current` 保持原有强度。

这个设计让模型可以在同一任务里区分归档事实和当前事实。转换发生在任务解释边界。工具、权限、持久化需求、证据账本、完成验收均沿用相同实现。用“昨日”“补发”等词在宿主里强制降级会误伤两个时点并存的请求，因此没有采用按词修正。

## 两批真实模型运行

模型为 `deepseek-flash`，温度 0，推理选项 `none`。每轮窗口 64,000 Token，输出上限 4,096 Token，执行阶段最多 16 次模型调用、24 次工具调用、150 秒，准备最多 60 秒，请求总限时 210 秒。两批的材料与问题摘要、模型配置、预算和审计开关逐项一致。任务数据为合成归档。

| 版本与冷启动组 | 历史首版 | 历史修订 | 当前可承诺库存 |
| --- | --- | --- | --- |
| /16，1 | 正确候选因时效缺口被拒 | 未启动 | 未启动 |
| /16，2 | 正确交付 | 正确交付 | 正确的证据不足候选被拒 |
| /16，3 | 正确交付 | 正确交付 | 正确交付证据不足 |
| /17，1 | 正确交付 | 正确交付 | 正确的证据不足候选被拒 |
| /17，2 | 正确交付 | 重复操作，停止 | 覆盖审计引用类型错误，准备失败 |
| /17，3 | 正确交付 | 重复操作，停止 | 正确的证据不足候选被拒 |

`/16` 第 1 组把“找昨日快照”和“读昨日两仓数量”都标记为 `current`。连续两次候选算对，但账本保留 `$freshness`。这在库存首版复现了升级修订遇到的历史事实误判。`/17` 三个首版都将两仓结账数标记为 `stable`，三个都通过。两个历史追问触发 `no_progress` 时已读到更正单，未产生接受检查的 Finish 候选，终态账本没有时效缺口。

在当前追问中，三个被拒的运行都将当前 ATP 登记为必须取证的实时数值。即使模型最终两次提交了完全符合独立答案的“现有资料不足”，宿主仍要求补齐数值证明。另一次追问在准备阶段止于 `wrong_obligation_reference_kind`。唯一一次交付成功的解释关注归档覆盖范围，最终只报告资料不足。五个已启动的当前追问里，没有向用户交付任何未经证实的件数，其中四个也没有交付可用答复。这个实验没有提供带实时 ATP 的正例，无法据此判断框架验证肯定承诺的能力。

| 版本 | 首版 | 历史修订（已启动） | 当前追问（已启动） | 三份均交付（计划组） | 供应商调用 / 总 Token |
| --- | ---: | ---: | ---: | ---: | ---: |
| /16 | 2/3 | 2/2 | 1/2 | 1/3 | 42 / 214,001 |
| /17 | 3/3 | 1/3 | 0/3 | 0/3 | 60 / 321,258 |

调用和 Token 包含准备与执行。两批实际执行 7 轮和 9 轮，不能直接把总量差解释为单次请求的额外成本。请求列出了允许的状态和所需来源选项，因而只验证模型能否在给定选项中做出并交付正确判断。样本只有一个任务族、一个模型、每版三组，无法把后续的停滞或覆盖审计失败归因于更换词表。现有证据不足以提升默认版本。

## 复现与结束条件

```sh
uv run python -m examples.inventory_time
uv run pytest -q tests/evaluation/test_inventory_time.py
uv run python -m examples.inventory_time --live --repeats 3
```

默认命令只输出输入、材料、标准答案的 SHA-256 和运行配置。真实运行使用现有 `WEAVRIA_MODEL_NAME`、`WEAVRIA_MODEL_BASE_URL` 和供应商所需的凭据，每批创建新目录，每轮写入 `results.json`。整组缺失或失败会返回非零。可在导出的候选版本上重跑完全相同的命令，无需切换工作分支。

```sh
candidate_dir=$(mktemp -d)
git archive d199f90 | tar -x -C "$candidate_dir"
(cd "$candidate_dir" && uv run python -m examples.inventory_time --live --repeats 3)
```

本地原始证据分别保存在 `.weavria/inventory-time/run-3vjt9uc9/` 和 `.weavria/inventory-time/run-iptfm3nv/`。运行数据库与模型响应不进入 Git。如下命令只读数据库，按实际请求与 run ID 核验候选、时效条件、缺口与交付。第一例返回 1，第二例返回 0。两批共 16 个已运行轮次的回放均与原记录核对一致。

```sh
uv run python -m examples.inventory_time --replay .weavria/inventory-time/run-iptfm3nv/1-current.db --branch current
uv run python -m examples.inventory_time --replay .weavria/inventory-time/run-3vjt9uc9/3-current.db --branch current
```

本轮关闭时间词表实验。后续值得单独验证的是完成条件能否区分两种交付：报出具体件数需要当前 ATP；说明指定归档不足以确认件数，需要归档边界的证据。若重新开展这个专题，应冻结一对“有 / 无当前 ATP”的任务，同时验收能否正确报数和能否有据地说明不足。
