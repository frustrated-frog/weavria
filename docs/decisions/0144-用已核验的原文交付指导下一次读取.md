# 0144 用已核验的原文交付指导下一次读取

2026-11-21，已采纳。

## 哪个决定需要经验

一个 Run 提议同时读两份材料。反馈预算只能容纳一份，但两次读取单独执行都放得下。ADR 0137 会按原提案顺序推荐第一份。顺序稍有变化，同一会话就可能重新尝试已经读不到的来源。这里有一个宿主能自行检验的目标：被推荐的读取经过真实执行之后，下一次模型请求能否收到完整原文？

SIM 把同类问题、事前预测和事后观察联系起来。本文把这一思想迁移到任务运行中的一次决策。SoMem 让派生记忆保留通向原始证据的路径。这里的经验保留拒绝事件和后续模型请求的位置，原文由当前工具重新读取。此次采用的是这两项机制思想。论文中的 Harness 编辑优化器、自组织主题文档和跨模型实验均有各自的研究范围。来源为 2026-11-21 查阅的 [SIM 原论文](https://arxiv.org/abs/2611.18856) 和 [SoMem 原论文](https://arxiv.org/abs/2611.11929)。

把历史建议写成自然语言再注入提示词，也能提醒模型尝试某个来源，但每次都会占用上下文，且难以区分“工具成功”和“正文交付”。本设计让工具、权限和模型接口继续负责各自的决定，只在两个可行读取竞争时计算一次分数。

## 从发送请求到形成经验

1. 普通调用方使用 `AgentHarness.from_config(...)` 和 `send()`。推荐配置默认启用 `HarnessConfig.read_retry_experience`。设为 `False` 可复现原顺序。手工装配的 `AgentHarness` 和底层 `SessionEngine` 可显式开启。旧 Run 恢复时沿用启动时的策略。
2. Runtime 先对整个提案执行原有准入。只有反馈预算超限，且整批均为可见、公开、低风险、无需审批、可重放的外部只读调用时才尝试排序。每个工具须声明 `artifact_read_inputs=()`。分页、依赖 Artifact 或混合提案仍使用对应的原有建议。候选逐一重新计算单读预算并按归一化动作去重，至少两个可行候选才查询经验。
3. 索引匹配当前会话、配置、任务目标与约束，以及可行候选的完整集合。动作身份包含工具名、版本和归一化实参，忽略顺序和临时 call ID。每次发送时剩余的墙钟秒数不参与配置摘要。本次预算和可见权限始终重新检查。
4. 每个候选的分数是 `(完整交付次数 + 1) / (已观测次数 + 2)`，采用同一现场最近十六条可用观测。未试候选为 1/2，一次完整交付后为 2/3，一次失败后为 1/3。同分沿用原提案顺序。宿主把一个当前候选放入 `AdmissionNotice.retry_read`。模型仍可重提、调整方案或结束，实际调用重新经过 Policy。
5. `BatchRejected` v2 在动作执行前记录候选顺序、选中的动作、预测的完整交付以及所用来源。原有 v1 拒绝事件保持原序列化格式。历史经验正文和评分快照不进入模型请求。
6. 设拒绝发生在模型调用 N。只有 N+1 在同一任务修订上准入了建议的单个归一化动作，N+2 的持久请求携带了它的反馈且模型返回了已接受的决策，才归因。宿主根据实际交换标记完整原文、节选、引用或工具失败。标记完整原文需要按该调用找到持久 Artifact，校验摘要，并用原件重建完整交换进行比对。模型改选其他来源、任务修订、超时或取消导致链条缺失时，这次预测不计分。

SQLite v11 将预测、准入的 call ID、交付结果与相应 Run 事件原子提交。索引按会话、配置、现场和 Run 次序查找，仅使用先前已结算且模型可见的 Run。预算耗尽或失败的 Run 中可以有已经核验的读取。取消、尚在执行及中断的 Run 均不作为读取经验来源。重复提交同一 input ID 不产生额外试验。查看 `read_prediction.observations` 给出的 Run、拒绝序号和模型调用序号，可以回到对应的 `run_events` 与 `request_views`。分叉会话有自己的经验范围。

## 成对回放

两组先从手册读到 E-172，然后把手册更新为 E-309，归档源持续不可用。第二个 Run 固定提交“归档、手册”两项，候选、预算、任务和先前对话均相同。比较的是宿主在同一个预算拒绝之后改变建议的效果。第二轮只有首个提案由回放器提供。真实模型自主决定如何处理拒绝、选哪个来源、是否继续以及最终回答。一次回放使用各自独立的临时数据库。

```bash
uv run python -m examples.read_retry_experience
uv run python -m examples.read_retry_experience --live --env-file .env.m1-openai
uv run pytest -q tests/harness/test_read_retry_experience.py
```

2026-11-21，在同一固定现场重复三组真实模型对照。执行模型为 `gpt-6-luna`，思考强度为 `medium`。下表只统计第二个 Run 的执行，决策轮数包括固定提交的第一轮。

| 策略 | 第一条实际读取 | 回答含当前编号 | 三次的模型决策轮数 | 三次的实际工具调用数 |
| --- | --- | --- | --- | --- |
| 原提案顺序 | 3 次均为归档 | 0/3 | 5、5、5 | 2、2、1 |
| 按已核验交付排序 | 3 次均为手册 | 3/3 | 3、4、3 | 1、2、1 |

原顺序三次均耗尽预算。经验组第二次运行中，模型重复读取手册后才结束。本地确定性对照还验证了反向更新：首次读取失败后，同一候选集中的未试来源会优先。集成测试覆盖重新打开数据库、任务或候选变化、会话隔离、忽略建议、节选降级，以及模型在收到工具反馈时超时或取消。

## 适用边界

完整交付是窄目标。过时文件、内容为空的合法文档也可能完整返回，任务正确性仍需单独判断。这里验证了建议、实际动作、新版原文与回答之间的关系；三组重复共享一个现场。当前匹配保守，换用同义目标或不同实参会重新积累证据。若后续扩展到跨任务的语义匹配，需单独比较误召回、不当偏好、节选更合适的反例和端到端成本。
