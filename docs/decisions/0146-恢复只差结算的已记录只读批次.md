# 0146 恢复只差结算的已记录只读批次

2026-11-22，已采纳。延伸 [ADR 0145](0145-恢复尚未派发的只读批次尾部.md) 的显式恢复入口。

## 恢复边界

最后一个 ToolRecorded 与 TurnSettled 分开提交。若进程在两次提交之间退出，工具批次的回执已经齐全，下一轮模型仍须等宿主结算。恢复者沿用原 Run，归约已提交的调用事实，并沿用原会话的独占领取、授权、任务修订、期限和原请求摘要核对。

RunState 的恢复判断区分三种情况。无法证明安全时拒绝领取。有尚未启动的尾部时沿用已有派发路径。所有回执已接受时，待执行尾部为空，AgentLoop 直接提交 TurnSettled，再运行正常的语义归约和执行决议。成功和失败回执都保留，模型按原提案顺序收到反馈。此路径不进入工具派发器，也不增加 ToolStarted 或 ToolRecorded。正在等待状态轮询、结果未知或任务修订过期的批次继续受原恢复条件约束。

此改动沿用现有事件和 SQLite Schema。所覆盖的断点紧邻 TurnSettled 提交之前。进程若在 TurnSettled 已提交、但执行决议尚未落盘时退出，该断点仍有独立的边界。

## 真实退出复验

测试让 A 晚于 B/C 落盘。最后一个工具回执提交后，原进程直接退出。新进程在同一数据库中通过 AgentHarness.resume() 恢复，检测到旧 Run 有三个工具回执，尚无批次结算。

| 指标 | 复验观察 |
| --- | --- |
| 恢复后新增工具调用和回执 | 0 |
| 恢复后第一条运行事件 | TurnSettled |
| 新增整批结算和执行决议 | 各 1 |
| 最终模型看到的反馈顺序 | A、B、C |
| 恢复后的模型调用 | 1，消费已结算的反馈 |
| Run ID 和原工具回执 | 保留，回执只按原提案重新排序 |

成功与混合失败现场均执行以上检查。测试还覆盖了工作记录在批次结算时才归约、重发相同输入返回原结果，以及原有未知派发和已有结算边界。测试使用固定模型输出隔离执行恢复和模型质量。
