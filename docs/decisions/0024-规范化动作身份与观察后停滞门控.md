# ADR 0024：规范化动作身份与观察后停滞门控

- 状态：已采纳并实现
- 日期：2026-10-21
- 范围：ToolRegistry、ProgressPolicy、批次准入、冻结机制实验
- 前置：[ADR 0022](0022-语义前沿与有界探索.md)、
  [ADR 0023](0023-进度策略隔离与真实模型对照.md)

## 背景

`semantic-progress/4` 使用工具名、版本和模型原始 `arguments` 生成精确动作身份，但真正的输入
校验、默认值填充与字段规范化发生在 `RegisteredTool.validate_arguments()`。因此 `{}` 与
`{"value": 7}` 可能执行为同一个调用，却被 ProgressPolicy 当成两个探索动作。工具字段校验器若
规范化大小写、空白或路径表示，也会出现相同错位。

另一个问题是同族阈值同时限制已有历史和当前批次。默认阈值为 3 时，第一次提出四个独立来源的
并行读取会在任何结果出现前被拒绝。尚未执行的第四个调用不能证明前三个调用没有进展；批次宽度
已经由 ToolBatch 上限、Tool Budget 和反馈预算约束，ProgressPolicy 不应重复承担资源准入职责。

本轮目标是建立三个明确边界：模型原始提议用于审计和事件回放；工具校验后的参数用于授权和真实
执行；Progress 使用不暴露参数的不透明规范化身份。停滞门控只根据已经接受的历史判断，不把当前
同轮并行意图提前解释为失败轨迹。

## 决策

### 1. ToolRegistry 成为动作身份的唯一生成边界

新增 `ToolActionIdentity` 与 `ToolRegistry.action_identity()`。对合法调用，它先经过注册工具的
`validate_arguments()`，再将包含默认值和字段校验器结果的 JSON 对象编码为规范化摘要。身份包括：

- `canonical_action_sha256`：工具名、版本、规范化状态与完整规范化参数；
- `action_family_sha256`：工具名与版本，不包含参数和 `call_id`；
- `normalization`：`validated`、`invalid_arguments`、`unknown_tool` 或
  `validation_failure`。

`call_id` 只表示一次提议与执行关联，不参与动作语义。参数不会写入 AdmissionNotice；Trace 仍只
暴露摘要。工具输入模型的 Pydantic 字段校验器就是当前工具特定规范化扩展点，Progress 与
ToolExecutor 复用同一个 `validate_arguments()` 契约及同一个 JSON 对象编码函数。

Runtime 将已准入批次的身份按 `call_id` 带到派发边界。ToolExecutor 对实际规范化输入重新生成
身份并与准入快照比较；若第三方校验器不确定、工具版本漂移或规范化结果发生变化，在 Policy 和
Backend 运行前以 `ToolExecutionError` 失败关闭，不能用一组参数通过 Progress、另一组参数执行。

非法参数与未知工具不能生成合法执行输入，但仍需要进入普通工具失败反馈。因此身份生成不会提前
拒绝或授权调用：它以明确状态绑定原始 JSON；ToolExecutor 继续独立校验并产生
`INVALID_TOOL_ARGUMENTS`、`UNKNOWN_TOOL` 或端口故障。第三方校验器异常也不会把 Progress 检查
变成新的 Runtime 失败面。

### 2. ProgressPolicy 不再自行解释工具参数

`semantic-progress/5` 保存 `ToolRegistry`，逐个调用获取 `ToolActionIdentity`。ProgressPolicy 只将
身份与任务语义前沿组合，不再维护另一套工具版本表或直接哈希原始参数。

这保证省略默认值、显式填写默认值和工具声明的等价表示共享精确身份；非法表示与合法执行输入
不会发生摘要碰撞。原始 `TurnDecided`、`ToolRecord.exchange.action` 与授权中的
`normalized_arguments` 仍各自保持原有职责，没有静默重写持久事件 Schema。

### 3. 阈值约束已有停滞历史，而不是当前首次扇出

对每个语义前沿和动作族，检查顺序为：

1. 当前动作是否在已接受历史或本批次中精确重复；若是，整批拒绝；
2. 本批开始前，该动作族已接受的唯一动作数是否达到阈值；若是，整批拒绝；
3. 否则为本批所有唯一动作创建原子预留，本批可以使历史计数跨过阈值；
4. 只有 `BatchAdmitted` 被接受后才提交预留；下一批若前沿仍不变，将看到已经跨过的计数并被拒绝。

例如阈值为 3：首次四路同族调用可以执行；其后同一前沿上的第五个调用被拒绝。`3+2` 仍会在
第二批开始前看到三个既有动作并拒绝；`1+4` 可以执行第二批，因为只观察到一个此前动作没有推进。
后者是有意取舍：ProgressPolicy 根据已发生事实判断停滞，不预测尚未执行的四个独立来源无价值。

`record_admission()` 继续执行两阶段原子检查：前序计数必须与检查时一致、不能与已提交动作相交，
也不能从已经耗尽的历史开始提交。它允许当前预留使计数超过阈值。

## 执行不变量

1. 原始模型参数不是执行语义身份；合法身份必须来自注册工具的校验与规范化边界。
2. 身份计算不授权、不派发、不消费额度，也不改变原始事件。
3. 合法、非法和未知调用使用不同的规范化状态，不能共享精确动作摘要。
4. `call_id` 不参与语义重复判断；工具版本继续参与动作与动作族身份。
5. 批内精确重复始终原子拒绝，不因首次扇出豁免。
6. 停滞阈值只读取批次开始前已经接受的动作；当前批次宽度由独立预算约束。
7. 未接受的检查不记账；并发或重复提交不能部分更新动作族。
8. 参数摘要不进入模型反馈，ProgressPolicy 仍不能替代 Tool Policy 或 CompletionPolicy。
9. 已验证身份必须与派发时重新规范化的身份完全一致，否则属于 Runtime 端口违约。

## 考虑过的替代方案

### 在 ProgressPolicy 中直接调用 JSON Schema 规范化

JSON Schema 不完整表达 Pydantic 字段校验器和宿主自定义规范化，而且会形成第二套输入语义；拒绝。

### 把规范化参数写回 TurnDecided

会抹去模型原始提议，改变事件回放与状态归约契约，还会让审计无法区分模型输入与执行输入；拒绝。

### 当前批次仍严格受阈值限制，只允许宿主手工调大

会让 Progress Policy 重复承担资源宽度控制，并在没有观察反馈前把合理并行探索判为停滞；拒绝。

### 完全取消动作族阈值

会重新允许模型持续改变参数逃逸，只依赖总 Tool Budget 才停止；保留为精确动作基线，不作为默认。

## 影响与迁移

- `ProgressCheck` 新增按 ToolBatch 顺序排列的 `action_identities`。自定义 ProgressPolicy 必须使用
  当前 Registry 生成这些身份；Runtime 校验数量，ToolExecutor 校验实际身份，伪造或错序会失败。
- `SemanticProgressPolicy` 升级为 `semantic-progress/5`，工厂升级为
  `semantic-progress-factory/3`，持久 Run 配置能够区分旧参数语义与新的观察后阈值语义。
- 没有修改持久事件 Schema。旧 Run 日志仍按其已记录事件回放，但不能将 v4 实验结果自动标记为
  v5 结果。

## 验证与证据强度

新增测试验证：

- 省略默认值与显式默认值生成相同精确身份；
- 工具字段校验器的大小写与空白规范化进入身份；
- 非法参数和未知工具拥有明确、互不混淆的身份状态；
- 非确定性工具校验器在授权与 Backend 之前失败关闭；
- ProgressPolicy 将两种等价提议识别为 `repeated_action`；
- 首次四路同族扇出被接受，计数原子提交后下一批被拒绝；
- `3+2` 批次重组、批内重复、Need 进展和替代工具族行为保持不变。

冻结实验增加“首次四路合法并行探索”，`semantic-progress/5` 为 11/11，精确动作基线为 9/11。
这些结果证明身份与准入不变量，不证明阈值能估计信息增益或提高开放任务完成率。本轮没有再次调用
付费模型；ADR 0023 的真实模型结果仍只属于 `semantic-progress/4`，不能改写为 v5 证据。

## 当前局限与下一步

- `validate_arguments()` 必须是无外部副作用的工具边界；同一提议的两次结果不一致会失败关闭，
  但当前 Protocol 尚未用进程隔离阻止校验器执行阻塞或隐藏副作用。
- 对非法参数，身份只能绑定带状态的原始表示，因为不存在合法规范化输入。
- 阈值仍是确定性停滞保护，不衡量来源独立性、证据覆盖、矛盾消解或最终成功概率。
- 一次很宽的首批调用仍可能消耗全部 Tool Budget；这是资源配置取舍，不由 ProgressPolicy 猜测。
