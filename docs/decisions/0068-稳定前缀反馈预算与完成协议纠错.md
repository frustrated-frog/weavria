# 0068：稳定前缀反馈预算与完成协议纠错

状态：已实现并验证，2026-10-31。源码前置：461ca87。

## 本轮能力与两个具体问题

用户要求一起修复 [0067](0067-失败尝试的局部语义与继续获取.md) 留下的两个坏例：

1. 十轮旧历史、12K 窗口下，新工作视图的工具反馈反复被拒绝，无法获取当前 owner / deadline。
2. 任务要求 JSON 时，模型有时直接输出业务对象，缺少 decision / finish / output 外层；
   即使业务字段正确，严格解析仍会拒绝，旧纠错提示不足以让模型修正包络。

本轮改进执行前容量证明、模型目录表示和协议反馈，不提高窗口、调用次数、输出上限或重试次数。
没有把裸业务对象自动升级为 Finish，没有改评分器，也没有改变来源、发布与权限校验。

## 稳定前缀为什么可以节省预算

旧 v5 对未来反馈采用整份规范 JSON 每字节最多一个 Token 的充分上界。
这能保证安全，但将已有任务定义与所选历史也重复当成未知文本计费。
直接套用 v3/v4 固定观察公式又不成立：v5 的来源版本、进度和工具说明都可能变化，
等长替换的 Token 数也可能比当前值大，不能只预留长度增长或使用平均字节比例。

OpenAI 兼容编码现在只调整 v5 task_model_view 内部的 JSON 对象键顺序：
稳定的定义、摘要、投影器及容量字段在前，phase / source / progress 在后。
没有删除来源或进度；解析后的用户数据与原请求具有相同字段和值。
这样，所选 Conversation、Task 和稳定定义成为真实 wire 的固定前缀 P，动态字段及后续工具反馈成为未知后缀。
系统说明仍允许变化，因此只保护固定协议 Q，不把当前 instructions 的实际 BPE 当成未来保证。

记输入 allowance 为 T，聊天 framing 上界为 F，prefix_bound 为既有不稳定分词尾部保护函数：

```text
规范请求字节上限 C = max(0, T - F - prefix_bound(Q) - prefix_bound(P) + UTF8字节数(P))
```

未知余量包括 instructions 的 JSON 编码、动态视图、当前工具历史和 control，均按每字节最多一个 Token 计费。
这比使用当前说明的精确分词保守，能覆盖任意合法的后续说明替换。
prefix_bound 只保留对任意后缀稳定的 BPE Token，其余前缀字节按单字节收费，不能假定 BPE 可加。

HTTP 上限继续独立采用“固定空包络 + 两倍规范 JSON 字节”的充分界，覆盖引号、反斜杠、控制字符、Unicode
及等长替换后的转义增长。最终计量取 Token 充分界与 HTTP 充分界的较小值。
实际请求发送前仍重新执行完整 Token、规范字节及 HTTP 字节准入。

### 证明成立的范围

- 当前所选对话、Task、定义与布局必须保持不变；重新选择历史或修订任务后重新计算，不能复用旧 ceiling。
- 模型视图的来源、进度、阶段、说明仍使用原最大容量与增长预留；没有把它们视为固定内容。
- 既有 Session 水位余量、完整工具反馈、可读祖先闭包及控制反馈预留全部保留。
- 编码器和计量器共用表示函数，并检查实际 wire.startswith(prefix)。布局改变时失败，不静默沿用旧证明。

## 先消除目录中的无关开销

真实第一版复测表明，只有前缀证明仍不足以容纳“当前事实 + 历史导航 + 下一次反馈”的保守上界。
目录重复列出了 Python 类型标题、根模型 Docstring、空默认值及宿主已经绑定的工具版本。
这些内容不是模型选择具体调用所需的校验条件。

新增公开纯表示函数 model_schema_view：复制注册 Schema 后，在明确的子 Schema 位置移除 title、
default=null 以及顶层模型说明。字段 description、非空 default、required、enum、const、数值/长度约束、
额外属性约束及引用全部保留。properties / $defs 中名为 title 的业务键，以及 enum / const / default
对象内的数据不会被当成 Schema 注解删除。工具执行继续使用原注册类型和完整 Schema。

新控制协议的目录不再向模型重复展示其不能选择的注册版本；宿主的工具版本、证据匹配、策略和 Trace 不变。
运行与会话说明合并重复文字，同时保留不可信输入、批次独立、更新优先级、读取原文和完成纠错规则。
两轮必需历史导航仍保留；没有删除冻结的十轮输入或放松历史保留约束来让例子通过。

旧 Journal v1/v2 的目录和指令保留原表示，原冻结执行实验继续通过。新表示用于已有控制协议 v3/v4。

## 完成协议怎样纠错

供应商协议现在明确区分任务的答案格式和 Runtime 外层：任务要求 JSON，含义是 output 内放 JSON 编码字符串，
外层仍必须是 decision.kind=finish，不能把业务对象作为顶层或 object 类型的 output。
同时给出字符串转义示例，并说明 FinishAction 对应这个协议包络。

收到 model_output_repair 时，模型应修正外层、保留已有依据，不重复裸答案，也不为修格式重读工具。
说明始终包含在固定协议 Q 中，已纳入当前及未来请求计量；没有在重试时偷偷追加未预留的系统文本。

裸 JSON 仍先产生 schema_mismatch，Runtime 记录脱敏诊断与 ModelOutputRejected；
同一父预算内的新 ModelStarted 才能再次调用模型。原次数上限、不可重试分类、取消、steering 与完成验收不变。
不保存隐藏推理，也不把未知格式猜成可执行 Action。

## 一次请求的源码流转

1. runtime/agent.py 从宿主 ToolRegistry 构建目录表示；tools/schema_view.py 只投影说明，执行契约不变。
2. sessions/engine.py 根据完整运行工具上限，重新计算说明容量；最大说明必须与实际目录使用相同表示。
3. models/openai_compatible.py 编码 v5 稳定前缀，ContextCompiler 继续联合选择历史、证据与反馈余量。
4. 工具派发前，reserve_feedback 使用同一请求的充分界，支付最坏反馈及因果祖先；不够时拒绝批次，建议减小宽度。
5. 调用结算后，Compiler 实际选择并交付结果；模型提交 Finish 后仍执行完成与应用验收。
6. 若供应商返回裸对象，严格解析拒绝；下一次请求携带原修复通知，模型在同一协议说明下纠正包络。

建议观察顺序：_instructions_for → _session_observations → request_byte_ceiling → reserve_feedback →
_handle_invalid_model_response → 下一次 generate_session → 完成验收。

## 版本与替代方案

计量/编码标识升级为 openai-compatible-session/5，绑定实际 Token 与 HTTP 计量方式。
ControlRequest、TaskModelView、ContextCompilation 和持久事件字段不变，旧报告不重写；
新运行配置及编译报告记录新 counter_version。JSON 键重排只发生在供应商适配器，规范请求摘要仍按 Core 序列化。
model_schema_view 是新公开函数，没有修改 ToolDescriptor 或执行校验的持久 Schema。

没有选择扩大窗口、忽略预算、平均 Token 比例、假定说明永远不变，或自动包装任意业务对象。
前者无法证明后续反馈可交付，后者会混淆非确定模型输入与宿主接受的完成候选。

## 当前限制与下一步

计量依赖宿主明确选择的 BPE 编码和 framing 上界，不宣称等于供应商隐藏分词或账单规则。
更大的工具目录仍可能合法超限；协议纠错也不能保证所有非确定模型都会服从，原有有界失败仍必要。
未新增 Resume、记忆、证据增量投影或供应商原生 Structured Output，未默认启用工作视图。

两个已记录坏例已得到契约回归和真实复测支持。下一步可推进必要证据增量投影，
将工具结算后的事实更新与可选进度分析分离；同时保留这批任务作为后续改动的回归门禁。
