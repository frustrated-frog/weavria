# ADR 0023：进度策略隔离与真实模型对照

- 状态：已采纳并实现，已有小样本真实模型证据
- 日期：2026-10-20
- 修订：2026-10-21，根据真实批次形状修正策略并完成受控复测
- 范围：SessionEngine、ProgressPolicy 生命周期、真实模型评测
- 前置：[ADR 0022](0022-语义前沿与有界探索.md)

## 背景

ADR 0022 用冻结的合成轨迹证明了动作族边界，但没有执行真实模型闭环。下一步不能只把已有策略
塞进一个脚本：`SemanticProgressPolicy` 内部维护每个语义前沿已经接纳的精确动作和动作族计数，
若多个 Run 共享一个实例，后运行的样本会继承先运行样本的控制状态，A/B 结果既不公平，也违反
“父 Run 拥有其执行状态”的生命周期不变量。

真实对照还需要把以下变量分开：

- Task Understanding 是否正确；
- 执行模型如何选择工具和参数；
- ProgressPolicy 是否在 Need 不变时约束参数逃逸；
- Need 真正推进时是否发生误拒绝；
- Provider 是否报告 Token，网络或协议是否失败。

如果同时让模型生成 TaskSpecification，就无法判断差异来自首次语义解释还是执行控制。因此首个
真实闭环实验应先固定已验证的 TaskSpecification，只研究 AgentLoop 行为；任务理解质量继续由
独立的 `live_task_understanding.py` 评测。

## 决策

### 1. SessionEngine 接收版本化 ProgressPolicyFactory

新增 `ProgressPolicyFactory` 协议和 `SemanticProgressPolicyFactory`。SessionEngine 在每次已接受
请求构造 AgentLoop 时调用一次 `create(registry)`，不能缓存或共享返回值。工厂版本写入持久化
Run 配置，使结果能够追溯“用了哪种构造参数”，而不把策略私有可变集合写成权威状态。

默认未注入工厂时保持原有行为：AgentLoop 根据 RunLimits 创建默认策略。这个扩展点只改变策略
构造与实验可替换性，不改变 Tool Policy、完成验收或执行权限。

### 2. 对照只改变同族探索上限

真实模型入口比较两组：

- `semantic_frontier`：同一语义前沿、同一工具版本动作族最多接纳 3 个不同参数动作；批次形状
  不参与动作族身份，每个 Tool Call 分别占用额度；
- `exact_action_only`：使用同一策略实现，但把动作族上限设为 1000。在本实验最多 8 次工具调用
  的预算内，它只会阻止完全相同的规范化动作。

两组共享 Provider、temperature、JSON 协议、Prompt、工具、TaskSpecification、完成策略、模型
和工具预算。复现实验中每个 case/策略使用全新的 SQLite 数据库、工具闭包和 ProgressPolicy；
奇偶 repetition 交替策略顺序，降低固定先后顺序造成的系统性偏差。

### 3. 两类任务分别检查节流和误拒绝

冻结数据集 `progress-control-live/1` 包含两个领域无关场景：

1. `volatile_missing_field`：只读工具每次返回不同 nonce，但永远缺少必需 JSON Pointer
   `/required_marker`。Artifact 摘要不断变化，Need 摘要不应变化。正确结果是不能伪造完成；
   语义策略应能以 `no_progress` 有界终止。
2. `progressive_field_collection`：同一工具按 section 分别返回 title、owner 和 deadline。三个
   Artifact 逐步覆盖必需字段，Need 摘要每次真实推进。策略不得因为反复使用同一工具族而拒绝
   合法收集，最终回答必须通过 Runtime 的必需义务验收并含三个已知值。实验没有注入
   `CandidateAnswerVerifier`，所以 Runtime 应保守保留 `task_outcome=unverified`；冻结答案项只由
   独立评测器判分，不得反向升级 Runtime 的权威性声明。

固定 TaskSpecification 是实验控制，不是预先编排工具调用。真实执行模型仍决定是否调用、调用
哪个 section、是否并行、何时修正和何时 Finish。

### 4. 报告区分结果、机制和成本

`LiveProgressRun` 对每个样本记录：

- Runtime 状态、`task_outcome`、错误类别、安全的异常类型和终止原因；
- Runtime 模型调用、Provider 调用、实际 ToolRecorded 数、无进展拒绝、动作族拒绝和已接纳
  批次的有序工具名形状；
- 每次 Provider 调用的有界 `finish_reason` 类别，不保存响应正文或供应商任意字符串；
- 端到端延迟、Provider HTTP 累计延迟及其报告的 prompt/completion/total Token；
- Provider/协议链路外异常的类型，但不保存异常消息、请求、响应或密钥。

聚合器先验证 case × strategy × repetition 构成完整且唯一的矩阵，再计算结果正确数、
`no_progress` 终止数、平均调用、平均延迟、Token 报告覆盖率和已报告 Token 总数。Provider 未
返回 usage 时保持 `None`，不能把“未知”记成 0。

数据集 SHA-256、模型名、temperature、JSON 模式、输出预算、HTTP 超时、Run 预算、两组动作族
上限和顺序策略全部进入报告。API Key 和 endpoint 不进入报告。

## 2026-10-20 最小真实模型探针

经用户授权，对 `deepseek-flash` 只运行了一次完整 A/B repetition（2 个 case × 2 个策略），随后
停止付费调用。探针使用 JSON 模式、512 输出 Token、最多 6 次模型调用、5 次工具调用、90 秒
Run 时限和 45 秒模型时限；共发生 12 次 Provider 请求，Provider 报告 39,647 Token。

| 策略 | 独立正确数 | 平均模型调用 | 平均工具调用 | 报告 Token | 平均延迟 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `semantic_frontier` | 1 / 2 | 3.5 | 4.0 | 23,920 | 6,014.796 ms |
| `exact_action_only` | 1 / 2 | 2.5 | 4.0 | 15,727 | 4,670.084 ms |

递进取数场景中，两组都用 2 次模型调用和 3 次工具调用得到三个冻结答案项，Runtime 均以
`completed/unverified` 结束。这证明必需证据义务可以闭合，但没有答案验证器时不能宣称答案已经
过 Runtime 验证。v1 评测器错误地要求 `verified`，因此把这两个结果误判为错误；v2 改为独立
答案判分，同时原样保留 Runtime 权威性结果。

缺字段场景中，语义组在 5 次模型调用和 5 次工具调用后、基线组在 3 次模型调用和 5 次工具调用
后都以 `invalid_model_response/model_failure` 结束，没有出现 `no_progress` 或动作族拒绝。因此这次
探针**不能**证明语义策略优于或劣于基线：模型协议失败先于目标终态，而且 v1 报告没有保留已
接纳批次形状和 Provider `finish_reason`，不足以判断模型是否通过改变批次形状跨越了动作族。
这直接促成 v2 诊断字段；遵守成本约束，本阶段不为补数据自动重跑。

## 2026-10-21 批次绕过修订与复测

用户允许继续进行小额调用后，v2 诊断先运行 2 个 repetition。缺字段场景出现以下已接纳批次
形状：同一 `inspect_record` 被组合为 `3+2` 或 `1+4`。旧 `semantic-progress/3` 把有序工具列表
作为动作族、把整批只计一次，因此批次大小变化可以重置动作族，一批四个参数也只消耗一个
探索额度。这不是调参问题，而是计量单位错误。

`semantic-progress/4` 改为按“语义前沿 + 工具名 + 工具版本”归族，每个唯一参数动作分别占用
额度；ToolBatch 仍保持原子准入。确定性实验新增 `3+2` 重组轨迹后，语义策略为 10 / 10，精确
动作基线为 8 / 10。首批超额、批内重复、混合工具族预留和两阶段原子提交也进入 Runtime 测试。

修订后的第一次 512 输出 Token 复测中，语义组只派发首批 3 个工具，但第三次 Provider 响应以
`finish_reason=length` 截断，不能用于判断策略终态。随后只把同一 A/B 的输出上限提高到 1024，
得到以下一次 repetition 结果：

| 场景与指标 | `semantic_frontier` | `exact_action_only` |
| --- | ---: | ---: |
| 缺字段：独立结果正确 | 是 | 是 |
| 缺字段：模型调用 | 6 | 6 |
| 缺字段：实际工具调用 | 2 | 5 |
| 缺字段：动作族拒绝 | 2 | 0 |
| 缺字段：报告 Token | 17,867 | 22,848 |
| 缺字段：终止原因 | `model_calls` | `model_calls` |
| 递进取数：独立结果正确 | 是 | 是 |
| 递进取数：模型 / 工具调用 | 2 / 3 | 2 / 3 |

本日诊断、512 复测和 1024 复测合计 57 次 Provider 请求，成功返回 usage 的调用共报告 187,495
Token；一次超时和一次连接失败没有 usage，因此该数字只是 Provider 已报告用量，不冒充账单金额。

这个样本证明逐动作计量实际改变了真实轨迹：缺字段任务少派发 3 个无效工具调用，报告 Token
减少 4,981，同时没有阻止一次批量读取三个真实字段。它仍不证明通用任务收益，也没有证明
`no_progress` 终态优于预算终态：实验允许两次拒绝反馈，第三次才以 `no_progress` 失败，而 6 次
模型调用预算先耗尽。后续比较停止语义时必须冻结并协调这两个预算，不能把当前
`no_progress_terminals=0` 隐去。

## 执行与失败不变量

1. 每个 Run 获得一个新的 ProgressPolicy 实例，策略状态不得跨 Run 泄漏。
2. A/B 两组除工厂参数和因此产生的后续轨迹外，共享相同实验输入与预算。
3. 缺字段场景的“正确”只表示没有错误完成；`no_progress` 是否按预期触发是独立机制指标。
4. 缺字段场景只接受 `no_progress` 或明确预算边界导致的安全未完成；Provider/Runtime 故障不能
   借“没有错误完成”计为正确。
5. 递进场景的独立正确性必须同时是 `completed` 且包含全部冻结答案项；它与 Runtime
   `task_outcome` 是两条证据链。没有答案验证器时 `unverified` 是正确的保守状态，评测器不得
   将自身答案表冒充 Runtime 验证结果。
6. Harness 级异常不能伪装成 Runtime 失败，也不能产生终止原因或任务结果。
7. 取消不被 `except Exception` 吞掉；Transport 在 `finally` 中关闭，SessionEngine 负责其 Run。
8. 报告 Schema 与评测器版本同步升级为 v2；新增诊断不能静默改变历史 v1 报告的含义。
9. 报告里的本地真实模型样本只能支持该模型、配置、数据集和版本下的结论。

## 考虑过的替代方案

### 向 SessionEngine 直接传入一个 ProgressPolicy 实例

接口更少，但会在持久会话的多个 Run 之间共享可变控制状态，也无法基于最终 Registry 安全构造
策略；拒绝。

### 为基线重新实现一个精确重复策略

会同时改变规范化、指纹和两阶段提交代码，差异不再只有动作族边界。当前用远高于工具预算的
动作族上限关闭该机制，保留相同实现路径。若未来工具预算超过 1000，应改为显式的基线策略，
不能继续依赖这个实验常数。

### 让真实模型同时解释任务和执行

更接近开放任务，但两个模型阶段的误差会混在一起，首轮样本难以归因。先冻结规格建立执行基线；
后续增加联合实验时应保留本实验作为可诊断对照。

### 只统计调用减少

更少调用可能来自过早阻断。必须同时保留递进证据任务、Runtime 验收和答案项检查；拒绝单指标
结论。

## 验证方法与当前证据

离线验证：

```bash
uv run pytest tests/runtime/test_control_loop.py \
  tests/sessions/test_engine.py \
  tests/evaluation/test_progress_live.py
```

它验证工厂实例隔离、工厂版本持久化、严格数据集、完整 A/B 矩阵、Token 未知语义和结果检查，
但不证明真实模型收益。

真实模型实验显式启用：

```bash
uv sync --extra openai-compatible
export WEAVRIA_MODEL_BASE_URL='https://example.invalid/v1'
export WEAVRIA_MODEL_NAME='provider-model-name'
export WEAVRIA_MODEL_API_KEY='...'
uv run python examples/live_progress_control.py --repeats 3
```

本次实现环境未设置 `WEAVRIA_MODEL_BASE_URL`、`WEAVRIA_MODEL_NAME`、
`WEAVRIA_MODEL_API_KEY` 或 `WEAVRIA_MODEL_JSON_MODE`，因此没有运行真实样本，也不报告任务完成、
调用或 Token 收益。入口可用不等于机制已经获得真实模型验证。

## 影响与局限

- `ProgressPolicyFactory` 成为公开 Runtime 扩展契约；工厂必须返回隔离的可变实例。
- Run 配置新增 `progress_policy_version`，不修改数据库 Schema 或已持久化事件 Schema。
- 首个数据集只有两个诊断型任务，适合暴露参数逃逸与误拒绝，不足以估计通用任务完成率。
- baseline 的 1000 上限只在当前 `max_tool_calls=8` 下等价于关闭动作族限制。
- 模型 endpoint 可能不提供 usage；报告会显示覆盖率，不补估 Token。
- 评测尚未覆盖多工具替代路径、工具临时失败、当前时效证据、副作用和长任务恢复。

## 下一步

先用至少一个固定模型和三个以上 repetition 取得原始报告，检查每条 Trace 是否符合预期，再扩展
领域无关的本地文件、HTTP 失败与多来源替代任务。只有观察到稳定的任务/成本差异后，才讨论默认
阈值调整；若误拒绝集中在“Need 有变化但价值很低”或“Need 无变化但探索仍有价值”，再研究可
校准的信息增益或停止价值，而不是继续增加静态次数规则。
