# 覆盖审计的字段级纠错

2026-11-18，已采用。

## 问题与决定

[材料交接实验](0132-从已获取材料形成工作判断.md)的六对运行中，三对因为覆盖审计连续两次返回 `assessment_schema_mismatch`，没有进入执行。旧留证只记录了类别，不能倒推出当时错了哪个字段。覆盖审计的两次调用是独立请求：第二次能看到原任务、候选解释、能力目录和约束，看不到模型的首答。即使把完整 Schema 再说一遍，模型仍不知道上次违反了哪条关系。

`ModelRequirementCoverageValidator` 默认使用 `model-requirement-coverage/11`。首轮保持同一协议。声明失败时，宿主沿**本次实际要求的声明 Schema**投影错误位置，将封闭词表里的修复提示附加到原有的一次重试。`field_feedback=False` 是同一版的类别反馈对照，版本单独标识为 `/11-category-only`。两组的接受条件相同，审计声明、规范化报告和持久化 Schema 均不变。

## 一次错误如何流转

1. `assess` 照常严格解析声明。Pydantic 能定位缺字段、非法枚举和数组项；`ObligationCoverage` 额外校验 `status` 与 `reason_code`、引用索引等关系，`RequirementCoverageAssessment` 校验整张图的 ID 是否一一对应。
2. 例如 `$.findings[4]` 同时给出 `status=underspecified`、`reason_code=missing_completion`。两者各自合法，却表达了“已有部分覆盖”和“完全没有对应交付项”两种判断。宿主从同一张关系表指出两条合法路径：保留原因就使用 `missing`；坚持部分覆盖就使用 `missing_selector`，且仍须提供对应候选索引。宿主不代选哪一种符合任务。
3. `coverage_field_checks` 从前 32 个校验错误中取最多四条不同的提示。路径只能经过宿主 Schema 已知的字段和有界数组下标；额外字段只指出其所属对象。错误值、未知字段名、自由文本和库异常消息不会进入提示或持久诊断。状态冲突只带回已通过枚举校验的两个选择。重审时义务由宿主冻结，旧格式完整报告的义务错误只提示改交 findings。
4. 配置上下文编译器时，`_audit_dispatch` 先编译类别反馈，记录可保留的历史。再从完整提示到较短前缀逐次实测，只有请求能装下且保留相同历史才采用；没有余量则使用类别反馈。未配置编译器时直接使用有界提示。模型调用继续共用原截止时间。
5. 第二次仍须提交完整声明，重新校验引文、冻结义务、引用与证据覆盖。再次失败则停止。错误类别保持稳定，诊断消息保留本次安全提示。如果第二次改为返回 `finish`，诊断归因于这次动作，不沿用首答的字段错误。

直接回填最相近的枚举可能把真实缺口改成“已覆盖”。回传完整错误或完整首答会重新引入模型生成的自由文本，也会增加请求成本。当前选择只传宿主可证明的约束。代价是其余判断由模型重新生成，结构合法仍不代表语义正确。

## 固定输入与真实模型对照

`tests/fixtures/work_recheck/coverage_repair.json` 冻结上一轮公开源码、设计修订和不变契约三个任务的用户请求、候选解释和 `read_source` 能力说明。候选来自每个任务一次已通过准备的公开测试轨迹，保留原解释 SHA-256；不是历史失败响应，也不是独立标注的标准答案。默认离线检查完整候选摘要。

```sh
uv run pytest -q tests/harness/test_requirement_coverage.py
uv run python -m examples.coverage_feedback
uv run python -m examples.coverage_feedback --live --repeats 3 \
  --output .weavria/work-recheck/coverage-feedback-new.json
```

真实实验固定 `deepseek-flash`、温度 0、`reasoning_effort=none`、输出上限 4096 Token，每次审计最多 120 秒。每个样本的两组共享同一个真实首答，各自调用宿主校验；只有重试独立调用模型，交替先后顺序。实验只执行审计，不读材料、不回答任务。报告记录首个请求、首答、数据和实现摘要，以及供应商实测用量，不保存原始响应。

最终一轮本地留证 `coverage-feedback-final-03.json` 中，9 对首答摘要逐对一致，5 对无需重试。实际触发重试的是源码任务三次、不变契约一次；四次都是上例中的状态和原因冲突。

| 只计四个真实重试样本 | 只给错误类别 | 加字段提示 |
| --- | ---: | ---: |
| 交回宿主可接受的审计声明 | 3/4 | 4/4 |
| 判定候选覆盖充分 | 3 | 2 |
| 判定候选覆盖不足 | 0 | 2 |
| 再次校验失败 | 1 | 0 |
| 重试输入 / 输出 Token 合计 | 13,137 / 3,216 | 13,329 / 3,130 |

字段提示每次多用 48 个输入 Token。两次“覆盖不足”均指出第 5 项的 `missing_selector`。审计合法后表达缺口是有效输出，不应算作格式失败；同样，判为“充分”也不能算作端到端成功。这些样本来自三个任务和一个模型，无法由此证明哪组的语义判断更准确。

另在 `code_revision` 上运行一次完整会话对照：

```sh
uv run python -m examples.work_recheck --live --compare-handoff --share-preparation \
  --case code_revision --output .weavria/work-recheck/coverage-fields-e2e-new.json
```

本地留证 `coverage-fields-e2e-01.json` 中，两组的候选解释与覆盖报告摘要相同。开启、关闭材料交接各完成一次，最终 JSON 的两个布尔字段均与独立答案相同。两组都使用本轮的审计器，且共享准备声明；这是链路回归，不是对字段提示的独立因果验证。

确定性用例另覆盖不同 Schema 错误、额外字段去重与隐私边界、二次拒绝、冻结义务以及逐条缩短提示的预算边界。下一步应给“候选已完整覆盖 / 确实缺少某项交付条件”配独立判据，测量修复是否保留正确判断、是否引入漏判和误判，再决定是否需要仅重提有问题的 finding。

## 里程碑收口（2026-11-19）

任务准备与覆盖审计 v1 的机制验收点为 `d02a743`：解释与审计声明分开、由宿主校验、最多纠错一次，失败有明确归因，未通过不能进入执行。语义判断并非总是正确；上述“完整计划 / 缺项计划”配对研究转入待办，不作为继续开发的前置条件。仅在发现可复现的执行正确性缺陷，或多项独立真实任务反复因可定位的审计误判而受阻时重开。后续以[独立用户任务的端到端验收](0134-用安装迁移任务验收工具工作集.md)决定研发重点。
