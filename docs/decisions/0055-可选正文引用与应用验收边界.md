# ADR 0055：可选正文引用与应用验收边界

## 问题

在 ADR 0054 的计量修复后，一次真实运行完成了 20 个工具调用，其中 15 个成功、5 个失败，
并生成了两版答案。运行没有反馈预算拒绝，最终却以 completion_repair_stalled 终止。

FinScopeAnswerPolicy v4 要求答案包含全部成功读取的精确 `[来源:source_id]` 标记；最后两个
模型请求只包含 4 个来源标识，另外 11 个没有进入当前上下文。验收检查能读取全部原始 Artifact，
模型却被要求从当前不可见的结果中补齐标识；收尾模式同时禁止工具调用和上下文回取。修复因此
不可执行。两版答案都留下相同的 11 个缺失标记，触发了重复修复终止。

这不是必须放大预算、重试次数或允许收尾重新取证的问题。根因是把“内部有来源记录”与“正文
必须罗列所有来源”混为一谈，而且把未采用的探索查询纳入了默认发布条件。

## 本次能力与边界

本次调整应用发布策略，使其不再因正文缺少全量来源标记而阻止交付。通用框架继续提供任务义务、
证据身份、Artifact、Trace 与可插拔完成验收，不理解 FinScope 的来源格式。本次没有新增
CitationPolicy、引用配置项、来源抽取框架或持久化 Schema。

FinScopeAnswerPolicy 升级为 v5：

- 取消 missing_source_marker 分支；普通答案可以没有标记，也可以只引用实际采用的来源。
- 继续校验已接受来源的类型化包络、实际所需能力、证据缺失与失败，并保留原有 Market Pulse
  数据质量披露检查。
- 应用检查通过时返回 CompletionAccept(unverified)。来源包络有效、某个标记出现，都不能独立
  证明答案逐句正确；本策略不宣称完成了语义事实核验。
- direct / clarify、无可用必需证据等既有不确定性语义保持。分层验收继续执行通用任务义务，
  不允许应用接受覆盖必需层的 Repair，也不允许把 Unverifiable 提升为 Verified。

应用提示词同步取消“引用每一次成功读取”，改为按用户需要引用实际采用的来源。使用标记时，
要求从可见证据复制标识，禁止编造；不为未采用的探索结果凑引用。用户明确要求的引用格式仍是
任务要求，本轮没有新增其独立语义或格式核验器，不能声称已经机械验证所有此类要求。

## 请求如何流转

工具结果仍经过 ToolExecutor 校验、存为完整 Artifact 并记录 ToolRecorded。Context Compiler
从权威原件构造有限视图，收尾阶段仍只允许 Finish。候选先进入 TaskObligationCompletionPolicy，
再进入 FinScopeAnswerPolicy v5：前者判断当前任务义务和证据状态，后者检查应用来源包络及
保留的市场质量披露。正文引用数量不再参与发布决定。

例如已有 15 个成功来源、答案仅采用并引用 4 个时，应用检查仍读取并绑定原始来源，不要求模型
补齐另外 11 个。若必要任务证据不足，组合结果仍为 finalization_incomplete_evidence；Runtime
可以按原有受限收尾语义交付 Unverifiable 回答，不能声称所有要求均已证实。

如果独立答案核验器发现冲突，或者必要行动未完成，既有 Repair 和终止语义继续生效。
Runtime 重复修复终止的 RunError 现在附带仍未解决的 issue_codes。这些代码经过核心契约校验，
不会包含候选正文或工具内容；用户无需只靠一条笼统英文错误再猜测原因。

## 任务理解修复中的同类信息缺口

本轮显式开启真实服务复测时，首个请求在任务理解阶段返回 502，原因是有界修复后仍有两项
missing_selector，尚未进入 Agent 执行与正文验收。该失败记录只保存了分类计数，无法还原两项
具体缺陷，不能把它当作引用修复失败，也不能据此确定唯一原因。

源码核查另外发现，RequirementCoverageReport 已保存 host_adjustments，ModelTaskInterpreter
在构造修复请求时却只转交合并后的 missing_selector，丢掉了实际主机校验理由。不同的
surface_not_grounded、optional_need_for_required_obligation 等原因因此在修复输入里无法区分。

ModelTaskInterpreter 升级为 v8：每个阻塞项携带 obligation_id、host_adjustment_reasons，
并从当前能力目录复制已经引用的 evidence surface 对应的 capability_name 和 required_fields。
这些是既有主机校验的诊断，不是新的任务范围，也不会为没有选择的证据面自动生成需求。
修复结果仍经过原 Schema、用户范围、能力边界与独立覆盖审计；默认只有一次修复，不增加重试。
最终覆盖失败的安全摘要补充 host 原因计数，既有失败诊断 Schema 不变。

领域无关回归使用报告 summary/details，验证修复模型收到确切主机理由和类型字段，修复后的
规格仍需通过原审计。这证明诊断传递契约，不单独证明真实模型规划成功率提高。

## 设计取舍

1. 强行保留所有 source_id 会让应用字符串要求反过来支配通用上下文分配；即使全部交付，也无法
   证明每次探索查询都值得在答案中引用。
2. 增加重试次数不能提供被移除的标识；在收尾重新开放工具则改变了父预算与执行阶段的约束。
3. 自动给答案拼接所有标记会制造“已经引用”的表象，仍不能建立具体结论与来源的对应关系。
4. 完全跳过完成验收会丢失任务义务和独立核验，故不采用。

当前选择取消错误的默认展示条件，保留权威证据链、真实任务约束与保守结果等级。应用策略 v5
的结果上限为 unverified；未来需要提升事实验证等级时，应明确划分独立答案核验与发布检查的
结果语义，不能把来源字符串检查重新包装为事实验证。

## 验证

- 确定性回归构造 15 个完整来源和 limited 收尾，分别验证正文引用 0、4、15 个来源均可通过
  应用检查，且 15 个验收读取与原始 Artifact 都保留。
- 分层测试验证来源展示不改变 incomplete evidence 的 Unverifiable 结果；现有独立核验拒绝、
  缺失必要行动、取消与收尾工具限制继续作为回归门禁。
- 正式 HTTP / SQLite / Compiler 路径在收尾预留 0 和 2 两种配置下，验证首版无引用答案可以
  直接完成，不再为了补格式多调用一次模型。市场质量披露修复仍经过有界控制通道。
- 重复修复失败的通用 Runtime 测试确认错误携带实际 issue_code，不发布被拒候选。
- 使用此次失败运行的已保存输入、20 个工具记录与原始 Artifact，只读重建完整分层验收。
  两版旧候选均返回 finalization_incomplete_evidence，而非 missing_source_marker。未调用模型
  或工具，未改写原失败记录，也未把用户数据保存为仓库 Fixture。

### 显式真实模型复测

2026-10-29 使用现有 deepseek-flash 配置及原问题执行有限探针，保留相同窗口、模型/工具次数、
父 Deadline 和收尾预留：

- 两次新会话 HTTP 请求在规划阶段返回 502，均为有界修复后 missing_selector=2；没有进入
  工具执行或引用验收。第二次已包含本轮补充的修复反馈，因此不能宣称该补充消除了规划不稳定。
- 隔离规划探针保留结构化规格与审计映射。首次规格缺少具体 required_fields，主机拒绝后，
  单次修复补入声明的 /data 字段并通过相同覆盖审计；未执行数据工具。
- 正式 create_app / HTTP ASGI / SQLite / Compiler / Runtime 路径使用真实模型与真实 FinScope
  后端，约 69.91 秒返回 HTTP 200、completed / unverified。执行 20 个工具调用，其中 17 个成功、

  该探针使用独立临时数据库，输出不进入仓库。

## 当前局限与下一步

本轮证明默认引用门禁与有限上下文之间的冲突已消除，不证明原候选的每句结论正确。未新增逐句
事实校验、未知来源标记检测或通用修复资源交付协议。真实服务复测的结果与上述确定性回归
分开记录，不能把一次规划通过或失败当成稳定成功率。
现有 Market Pulse 质量披露仍使用应用文本规则，其语义验证值得单独评估。

下一步应在领域无关任务上冻结失败案例，评估完成策略是否能给出模型在当前上下文和操作权限内
可执行的修复；确实需要外部原件的检查，再设计显式、有界的修复信息交付机制。不要通过恢复
全量来源字符串门禁或放宽独立核验，让同一类冲突以另一种形式回来。
