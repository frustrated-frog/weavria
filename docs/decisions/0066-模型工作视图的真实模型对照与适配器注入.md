# ADR 0066：模型工作视图的真实模型对照与适配器注入

- 状态：已完成一轮有限真实模型验证；保留显式启用
- 日期：2026-10-31（北京时间）
- Runtime 基线：`b977f8f`，本轮没有修改 Core、Runtime 或 Context 策略
- 前置：[ADR 0065](0065-上下文阶段传递与收尾增长预留.md)

## 结论与本次新增能力

**目前没有证据支持默认启用 TaskModelView。** 它在部分任务上减少输入，但真实模型验证
稳定复现了紧窗口下的反馈准入退化；同时，两种表示都受到提前受限收尾的影响。
这一轮完成了真实模型评测入口、冻结数据、执行留证和 FinScope 的显式投影注入，
没有为得到更好结果而在实验中调整预算、弱化验收或修改 Runtime 策略。

主对照为五类领域无关任务，每类两次、两种表示，共 20 次实际执行：
完整状态组通过 7/10，新视图组通过 6/10。这里只描述本次小样本，不估计通用成功率。
另完成 FinScope 固定周总结的四次真实模型执行，作为适配器接入验证。

## 冻结配置与比较方法

### 哪些部分使用真实模型

通用任务先调用真实模型理解一次，保存已经接受的 TaskSpecification；两组再分别执行，
由真实模型选择工具、参数、批次、纠错和最终回答。没有脚本指定执行动作或预填答案。
复测复用第一次的四份已接受规格；修订任务重新生成两个版本的规格，再在两组间共享。
历史任务的十轮背景记录是冻结输入，使用 Fake 播种；被比较的执行阶段均使用真实模型。

FinScope 使用既有 fixed-understanding 基线，隔离应用执行阶段；它没有调用真实任务理解。
真实模型通过 HTTP 适配器背后的 SessionEngine 执行，业务 HTTP 数据由既有冻结 Fixture
返回，没有访问生产金融服务，也没有把领域规则添加到框架。

### 如何判定成功

通用任务同时要求：Runtime 完成、最终 JSON 的键值正确且无多余字段、所有预期事实实际进入
最后一份模型请求的交付清单。修订题还必须实际应用 steering。单独记录 completed 和
unverified，不把它们直接当作答案正确。评分不会反向升级 Runtime 的核验状态。

同时记录真实供应商 usage、内部 BPE 计量、规范字节、传输字节、重复成功读取、失败工具、
反馈拒绝、非法模型响应和旧决策丢弃。cl100k_base 是内部计量，不是 DeepSeek 的实际分词器；
下表成本使用供应商报告的 prompt_tokens。

### 三类失败的源码与执行证据

**一、部分来源失败被过早解释为可以受限收尾。**

主来源题第一轮同时取得 title 和 owner 的主来源失败。日志随后接受：
`FinalizationStarted(mode=limited, reason=evidence_ready)`。
模型随后返回继续行动的候选，被 `finalization_action_rejected` 拒绝，
错误是 `Finalization only accepts a Finish candidate`，最终没有取得镜像数据。两组四次均复现。
当前持久 Trace 未保存被拒绝候选的完整参数，因此不据此断言具体的下一次工具参数。

此时尚有调用预算，也仍有可选来源。问题不是模型不愿纠错，而是一次读取失败与整个需求
获取结束之间的语义没有充分区分。后续修复应处理尝试失败、可继续获取和收尾时机，
不能在工具层增加 mirror、股票或特定接口的分支。

**二、v5 的充分界阻止本来可能有用的工具反馈。**

紧窗口视图组每轮都收到 `feedback_budget`，两次各四次实际模型调用，零工具派发，
最终为 `context_budget_exceeded`。相同历史和预算下完整状态组均两轮完成。
这复现了 ADR 0064/0065 已披露的局限：视图请求为未知反馈使用整包规范字节的 Token
充分界，比旧路径的已知前缀计量保守。初始实际 BPE 请求可以发送，并不意味着后续反馈
必然能获准。下一步需要证明稳定片段、变化区间及编码边界的容量，而不是直接调高窗口。

**三、最终数据与控制协议的信封仍可能混淆。**

八字段完整状态失败轮已经读取并交付所有八个值。随后三次记录的诊断均为
`schema_mismatch`，响应均为 145 字节，摘要均为
`becb17c7d920dccde14f8abaa35f892c40ac522861d5ddc46464ccddf9a4d289`。
该摘要与冻结答案紧凑 JSON 完全相同：返回了正确的数据对象，却没有放进 Finish 控制信封。
有界修复没有改变这一响应，最后为 `model_output_repair_exhausted`。

不需要保存私有推理就能核查这个问题。它也不意味着应该无条件把任意 JSON 包成 Finish；
后续要明确应用输出与控制协议的边界，并验证纠错反馈是否真正改变了下一次请求。

## FinScope 接入结果及评分局限

使用既有周总结 Fixture，fixed understanding、profile coverage，每种表示两次：

| 表示 | Runtime 完成 | 供应商模型调用 | Prompt Token 合计 | 最大单请求内部输入 Token |
| --- | --- | --- | --- | --- |
| 完整状态 | 2/2 | 4 | 37417 | 21845 / 21797 |
| 新视图 | 2/2 | 5 | 39318 | 12691 / 12652 |

四次均为 unverified、四个需求 satisfied、各读取四个市场切片。新视图的单请求更小，
但其中一次多调用一轮，合计成本没有下降。不能把交付完成等同于整篇分析得到独立核验。

原有 `finscope-weekly-summary/2` 的字面评分四次都为 false：所有回答都缺少固定的
`[来源:market-pulse:2026-10-23]`，完整状态两次还没有逐字包含指定日期范围字符串。
这个旧指标与后来取消正文来源门禁的产品规则不一致。本轮保留原始评分，没有事后删除
要求来制造成功；也不把这四个 false 直接归为执行失败或事实错误率。

内容覆盖仍有值得继续核查的信号：完整状态回答列出五个交易日的宽度数值；新视图的一份
回答称仅取得最近两个交易日的宽度点位，而冻结业务数据包含五天。它可能反映片段选择和
“模型未见”与“源数据没有”的区分问题。现有摘要留证不足以独立核验整段自然语言，
不能据此宣称新视图在这个领域质量相同。后续应先冻结符合当前规则的内容评分及事实交付检查。

## 一次评测在代码中如何流转

1. `examples/live_task_model_view.py` 加载严格校验的数据集，固定数据摘要和模型配置。
   只有显式 `--live` 才会调用真实模型；重复次数限定为 1 或 2。
2. 真实任务理解经过已有 TaskUnderstandingEngine；保存接受的规格和摘要。
   复用规格时核对原数据集和规格收据，不重新手工设计更好的任务解释。
3. 每组通过 SessionEngine 和真实 Provider 执行。修订题在第二份请求边界由独立输入任务
   调用 steer；旧模型响应仍会结算并丢弃，不宣称撤回已经发出的 HTTP 请求。
4. 从持久事件、Artifact 和交付清单取统计，再独立核对最终 JSON。所有后台任务由评测
   调用负责取消与等待，Provider 客户端在 finally 关闭。
5. 每组完成即保存报告；完整准备失败也在计划矩阵中显式保留两组失败项。数据库和原始
   模型输出仅保存在忽略的 `.weavria/`，不进入 Git，不记录密钥或隐藏推理。

FinScope 的 `create_app()` 只新增可选 `task_model_projector` 注入，传给同一个通用
SessionEngine 端口，默认 None。启用后运行指纹使用 `finscope-runtime/2` 并记录投影器版本；
未启用继续保持原 v1 指纹字段。没有新增金融抽象、领域规则或核心反向依赖。
既有 FinScope 评测入口新增对应参数和 CLI 开关，旧默认不变。

## 当前没有实现什么及下一步

没有默认切换模型工作视图，没有引入模型裁判、记忆召回、增量投影或更复杂的规划器。
没有修改旧 FinScope 评分来提高通过率，也没有把合成数据上的小样本推广为生产质量结论。

下一切片优先修复两条已稳定复现的通用边界：部分获取失败与收尾资格的区分、
新视图的反馈容量计量；分别补确定性回归和容量证明，再重跑同一冻结题目。
随后进入必要证据增量更新，继续深化任务状态、上下文、反馈与下一步决策之间的协同。
