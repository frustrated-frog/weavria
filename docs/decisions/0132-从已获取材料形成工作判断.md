# 从已获取材料形成工作判断

2026-11-18，实验策略，默认关闭。承接 ADR 0130 的局部工作补丁与 ADR 0131 的指定版本资料。

## 失败发生在哪一步

在 ADR 0131 的源码修订任务中，账本先后确认取得 original 和 current。模型调用了 14 次 `read_artifact`，13 次成功，一次因读取预算容不下下一个字符而失败，直至无进展退出，期间没有提出工作笔记。检查第二次执行模型请求的交付清单，original 的多个摘录覆盖了相同的字符。一份不到 3 KiB 的源码以带坐标和重叠邻文的摘录出现，模型仍要判断哪些部分值得补读。另一个契约任务终态的陈旧笔记属于 plan，已有完成策略只阻止陈旧的 result。

## 决定与执行过程

宿主可在已有工作记录和材料证据配置上开启 `HarnessConfig(work_material_handoff=True)`。任务投影和上下文编译共同使用已接受快照中的来源地址。

1. 按任务声明顺序查看必需需求，仅处理账本已经取得资料、且工作分析仍为 `analysis_pending` 的需求。检查来源所属材料计划、证明强度、时效和当前 Run。每个需求选一个已绑定的资料字段，每轮最多两个，提示总量上限 768 个 UTF-8 字节。缺口、冲突与已有发现继续按各自状态处理。
2. 模型的决策视图显示 `material_for_analysis`。每条含需求 ID、原始 Artifact ID 和字段指针。模型可在已交付的正文里选取精确引文，通过 `propose_work` 提交自己的判断。地址仅表明原文在哪里。交付清单记录本次请求实际带入哪些内容，运行时继续检查读取权限，工作工具继续核对引文。
3. 同一来源成为 `ContextFocus.prefer_complete` 中的软偏好。编译器先执行原来的分配，再对已选摘录试算完整原文。它匹配生产 Run、调用和内容摘要，固定其他来源、依赖和预留预算，用同一计量器重算整个请求。仅当 Token 与请求 JSON 字节都不增加，且通过现有容量与传输检查时替换。每次尝试计入原分配步数上限。成本更高、搜索预算耗尽、仅有引用或已经省略的来源维持原分配。
4. 已接受的、引用对应需求原文的结果笔记，使下一轮的提示退出。用户修订、资料失效、结论撤回后重新按当前快照投影。没有新增持久化状态。旧配置继续使用原投影与分配，启用后的策略由任务投影版本、准备策略版本、编译报告及交付清单标识。

固定要求每读一份资料就写笔记，会让本可直接回答的问题多付出一次工具调用。无条件发送整份文档又可能挤掉其他需求的证据。这项策略只改善可见的来源与可选操作。模型仍决定是否需要补读、形成什么结论及如何修订依赖。一个需求涉及多个字段时，提示只提供一个入口，多来源分析仍须回看需求和正文。

## 真实模型对照

沿用冻结的三项源码与设计资料、独立答案、局部工作补丁与版本取证配置。每项每组运行两次，第二次交换先后，deepseek-flash，温度 0，reasoning_effort 为 none，执行上限 16 次模型调用、24 次工具调用、180 秒。正确交付要求运行完成且每个布尔字段与答案一致。

| 对照方式 | 基线正确交付 | 启用后正确交付 | 观察 |
| --- | --- | --- | --- |
| 独立完成准备和执行 | 3/6 | 2/6 | 基线两次准备失败，启用组四次准备失败 |
| 配对复用准备声明 | 0/6 | 2/6 | 三对在准备阶段均失败，其余三对的任务声明、覆盖评估摘要各自相同 |

配对对照中的三对执行均使用真实执行与审查模型。启用组 3/3 在首次读取 current 前已提交一条带来源的结果，基线 1/3。两组在这三对中均未调用 `read_artifact`。原源码失败任务在启用组两次都先形成了判断，一次正确交付，一次仍以 `no_progress` 退出。比较说明提示可把工作记录提前，端到端成功率仍受任务准备和后续修订影响，独立运行的结果也没有显示总体收益。

独立运行两组供应商调用合计分别为 47 和 29 次，375636 和 160196 Token。配对运行均为 31 次，分别为 256830 和 276947 Token。准备失败会提前退出，共享声明也会减少第二组的供应商调用，这些总数不能独立表示分析成本。

```sh
uv run python -m examples.work_recheck --live --compare-handoff --repeats 2 \
  --output .weavria/work-recheck/material-handoff-sources-new.json
uv run python -m examples.work_recheck --live --compare-handoff --share-preparation --repeats 2 \
  --output .weavria/work-recheck/material-handoff-paired-new.json
```

不带 `--live` 可离线核对数据摘要。配对模式只在同一任务的同一对运行内复用请求完全相同的准备声明，两边均由原宿主校验。未通过的准备也计入分母。对应的本地留证为 `material-handoff-sources-01.json` 与 `material-handoff-paired-01.json` 及其同名轨迹。三对准备失败均在覆盖审计连续两次返回 `assessment_schema_mismatch`。下一步可以用这些失败输入验证，模型能否从具体字段错误中修正自己的审计声明。
