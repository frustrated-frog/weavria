# ADR 0051：证据尝试归属与获取状态归约

## 背景

ADR 0050 建立了证据计划与范围匹配，但成功和失败没有使用同一适用性边界：

- 无关成功被记为 `unsupported / evidence_scope_mismatch`，完成评估据此提前放弃未查询的需求。
- 失败在参数匹配前按工具名归入需求，同一个多功能工具的其他操作失败也会污染当前需求。
- 一个生产者失败即可让整项需求变成不可用，未尝试的替代生产者没有参与判断。
- 完成评估按整个 Need 的失败总数耗尽重试，不同查询各失败一次也可能提前进入受限交付。

这些错误决定模型还能否继续取证，属于通用 Harness 的执行语义，而不是应用数据兜底。

## 决策

### 先判适用，再处理成功或失败

Resolver 在读取 Artifact、解释返回值和归属失败之前，先根据受信授权中的工具版本与规范化参数匹配
EvidenceMatchPlan。没有已允许授权、版本不符或参数不符的记录，只产生 `not_applicable` Probe，
不产生 Binding 或 NeedFailure，也不读取其 Artifact。

`not_applicable` 保留可审计的调用身份和原因，但不进入进度摘要、不可用性和契约缺口判断。
没有 Profile 的结构基线仍以 capability 名称归属；它不提供 Profile 路径的参数隔离保证。

### 归属失败与有界重试

NeedFailure 保存 `match_plan_id` 和 `attempt_identity_sha256`。规范化尝试身份由工具名、版本、
规范化参数和 Plan 身份计算，不包含 call_id 或响应内容。不同 Plan 各自保留失败；更换 call_id
不会变成新的查询范围。重试是否允许仍由 Tool Policy 决定，本机制只决定是否再次要求取证。

完成层原有的两次临时失败边界移入获取状态归约，并且只累计同一规范化查询的不同已接受调用。
两个不同查询各失败一次，不会合并耗尽重试。增量刷新中重复出现同一调用不增加次数。
永久失败只描述该次查询，不能被解释为目标数据不存在。

### 在现有 NeedState 中归约获取状态

新增 `acquisition_status`，由已归属 Probe 和 Failure 计算，不新建另一份事实账本：

| 状态 | 含义 |
| --- | --- |
| `open` | 尚有未尝试的声明路径，或已有可继续补充、处理时效问题的结果 |
| `retryable` | 存在尚未达到边界的适用临时失败 |
| `unavailable` | 各声明路径的已观察尝试均不可用或已达到同范围临时失败边界 |
| `contract_gap` | 各声明路径均已尝试并阻断，其中包含适用结果的契约不匹配 |

Profile 路径按 Match Plan 区分；结构基线路径按 capability 区分。未尝试的 Plan 保持 `open`。
同一 Plan 的参数允许列表是匹配谓词，不能视为必须穷举的工作清单；本机制不自动枚举参数组合。
某条路径已有匹配或部分结果时，不被其他失败覆盖。满足需求的权威 Binding 继续保留，成功后清除
状态中的未解决失败，原失败事实仍可在 Probe 和 ToolRecord 中审计。

`unavailable` 与 `contract_gap` 都是已声明路径及其已观察尝试的限制，不证明所有可能参数、动态
能力或未来来源均已穷尽。完整范围内查无数据仍由 Binding 的 `result_kind`、`scope_completeness`
和需求完成方式证明，不能从传输失败推导。

### 完成评估使用同一获取结论

TaskCompletionEvaluator 不再自行按 Probe 里的 `unsupported` 或 Need 的失败总数判断终止。
只有全部未满足的必需需求都处于 `unavailable / contract_gap`，才进入受限交付判断。
一个需求不可用，不能使另一个尚未查询的需求提前结束；可重试路径和未尝试路径继续请求修复。

评估结果的 `next_required_actions` 说明已尝试路径的限制，不得据此推断数据不存在。当前
`CompletionUnverifiable` 仅保留原因码，这段诊断不会自动成为另一轮模型指令；本次没有实现自然语言
限制说明的独立事实核验。应用发布检查、已有答案核验接口和不可降级的 Repair 门禁继续生效。

### 版本与持久化

NeedLedger 升级为 v4，Resolver 升级为 `evidence-resolver/5`，完成评估升级为 `task-obligations/7`。
新增字段受 Ledger v4 包络管理；嵌套的基础契约版本保持 v1。

v1/v2 继续先执行既有的 v3 上迁，再进入 v4。v3 到 v4 不修改已记录的状态、Probe 分类和失败事实，
缺失的 Plan、尝试身份与获取结论保持未知（`None / open`），不从工具名补造匹配证明。
无新归属信息的旧进度摘要保持兼容。新鲜投影时才用当前需求和可验证记录重新计算获取状态；旧事实
不被追溯改写为新结论。旧版 Profile 失败没有 Plan 归属时，不能关闭当前 Plan。

增量合并按 `(call_id, match_plan_id)` 去重，并让本次重新评估过的调用替换旧 Probe/失败投影，
防止旧版错误归属在刷新后继续被合并回来。已经移出当前需求的 Plan 不再提供失败或 Binding。

## 备选方案

- **只把失败分支移到范围匹配之后**：不能解决替代生产者未尝试和跨查询累计重试，因此不采用。
- **继续在完成评估中增加 reason_code 例外**：与 Resolver、进度和持久化状态继续分歧，因此不采用。
- **把参数允许值全部展开并要求穷举**：会让等价视图或格式选择变成多余工具调用，也不能证明未知参数
  空间已穷尽，因此不采用。独立可获取来源应由受信 Profile 显式声明不同 Plan。
- **新增获取调度器或自动执行回退**：超出本次范围。模型继续选择动作，Runtime 继续负责授权与总预算。

## 验证与当前边界

回归覆盖无关成功/失败、未尝试替代 Plan、不同查询的独立重试、同查询重试上限、适用契约缺口、
多个必需需求、成功回退、重复投影、序列化后继续归约、v1/v3 上迁和 Artifact 读取取消清理。
真实 AgentLoop 回归验证：来源 A 失败 → 提前 Finish 被要求修复 → 来源 B 成功 → 最终验收接受。

这些确定性测试证明归属与控制不变量，没有测量真实模型的回答质量、延迟或成本收益。
本次没有实现任务实例目标绑定、AND/OR 生产者表达式、任意参数空间穷尽证明、统一 Finalization、
Steering 拒绝竞态修复或应用长引用反馈修复。下一核心切片仍是让任务实例目标贯通 Match Plan，
再研究进度与收尾的组合。
