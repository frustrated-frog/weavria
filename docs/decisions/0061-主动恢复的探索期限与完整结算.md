# ADR 0061：主动恢复的探索期限与完整结算

- 状态：已采用
- 日期：2026-10-30
- 范围：Runtime 主动上下文恢复、准备期限、恢复结果结算
- 前置：[ADR 0032](0032-有预算的主动上下文恢复.md)、
  [ADR 0059](0059-完整准备时限与运行配置留证.md)、
  [ADR 0060](0060-语义提交与快照安装的取消一致性.md)

## 问题与复现

基线 `13da994` 已为普通准备和工具结算后的进度评估设置探索子期限，但接受 RecoverContext 后，
仍直接等待恢复规划与恢复视图预编译。轮数、字节、索引规模和工作量上限不能替代时间限制。
恢复依赖阻塞时，父期限可能先到，已经取得的证据无法在预留时间内形成答案。

旧代码上的回归先接受一个有效工具结果，再接受恢复动作，在规划端口阻塞。最终运行耗尽父预算，
事件中没有 RecoveryResolved，也没有收尾请求。同一缺口也存在于预编译阶段：即使原文范围和
请求候选已计算出来，等待仍可消耗全部父时间。

本次只修复这个通用执行边界，不改变恢复检索算法、领域证据规则或模型任务投影。

## 决策

### 规划与预编译共享固定探索期限

Runtime 将父 Run 截止时间传入 `_recover_context()`。开启收尾预留时，规划、原文读取和完整
请求预编译共同使用“父截止时间减实际收尾预留”的子期限；不是给每个阶段各分配一份新时间。
实际预留沿用既有 RunLimits 规则，最多占 Run 时长的一半。

进入恢复时如果探索时间已经用尽，不再启动规划。对于异步依赖，子期限取消会等待其清理；只有
本作用域的 `scope.expired()` 为真，才按探索预算耗尽处理。依赖自行抛出的 TimeoutError 仍按
原失败类别报告；外部取消仍传播，父期限仍保持原有终态语义。

规划返回后、预编译返回后都重新检查注入时钟。即使同步计算或不充分让出的代码越过了期限，
定时取消尚未获得调度机会，也不能接受迟到区间；规划已经迟到时不再启动预编译。这是结果
接受检查，不是抢占式中止能力。

关闭收尾预留时保留原有父期限路径。没有新增恢复专属模型次数、独立总时长或无限重试。

### 已接受的恢复动作必须结算

恢复仍沿用已有控制事实对：

```text
TurnDecided（RecoverContext）→ 准备候选与预编译 → RecoveryResolved
```

接受动作时已经消耗一次模型调用并推进恢复轮数。探索时间用尽时，先等准备取消清理，再将该动作
结算为现有 `budget` 状态，包含零区间、零恢复字节。该状态现在明确包括探索时间不足，不增加
Core、事件或数据库 Schema 版本。

结算绑定原请求摘要、已接受成果集合摘要、任务版本与轮数。在原有提交锁内再次检查任务版本：
如果 Steering 已发生，优先结算为 `stale`，不能把旧任务恢复结果安装到新任务中。

RecoveryResolved 必须成功持久化后，归约器才从 RECOVERY 进入 READY。预算结算不安装临时保留
范围，不增加恢复成功字节或已恢复范围集合；仍保留此次已消耗的模型调用与恢复轮数，以及同一
修订中的尝试记录。已有合法范围的去重语义继续沿用原机制。

恢复结果的接受事务位于准备子期限之外，沿用取消安全的 Journal 结算。不在一个可能取消的
“准备 + 提交”大 timeout 中一并处理，否则可能混淆已接受事实和未接受候选。存储失败继续
poison Journal 并终止执行，不能跳过结算直接请求 Finish。

### 收尾不绕过原验收

预算结算后回到原 Agent Loop。下轮根据剩余预算，从同任务版本已提交状态重新构建收尾视图，
继续执行 FinalizationPolicy、证据交付检查和完成验收。没有可用证据、任务版本不符或发布检查
不通过时，仍可以明确结束而不交付答案。

准时完成的恢复维持原行为：精确区间通过来源和完整请求预算检查后接受，实际模型请求必须包含
受保留的原文；后续响应接受后解除临时保留。探索超时不删除原 ToolRecord 或 Artifact，不重新
执行工具，也不将未提交的预编译报告当成模型已经看过的内容。

## 取舍

- 只限制 plan_recovery：预编译仍可能吃掉收尾时间，采用完整准备边界。
- 每个阶段重新分配一份时间：会延长探索总时间，采用同一个固定截止点。
- 超时后直接 Finish：会留下尚未结算的恢复动作，并可能绕过交付证明，保留控制事实闭环。
- 超时后接受已经算出的范围：无法保证预编译完整通过，也会接受迟到工作，统一丢弃候选。
- 新增 timeout 恢复状态：当前预算反馈已能表达零成功工作，先明确现有语义，保持协议兼容。
- 对所有异常统一降级：会掩盖依赖和持久化故障，只有拥有的探索期限触发预算结算。

## 验证与观察方式

使用领域无关的双工具任务：第一个需求已有证据，第二个需求尚未查询。真实 TaskAwareSessionPreparer、
NeedLedger、SessionContextCompiler、SQLite Journal 和完成策略参与执行，模型与工具使用确定性
替身。第一个结果不能满足第二个独立能力的需求，因此收尾只允许有限交付。

测试分别在恢复规划端口和已生成候选报告的预编译端口注入故障，验证：

- 阻塞到探索期限：完成清理，接受唯一 budget 结算，第三次模型调用形成 unverifiable 答案。
- 外部取消：传播 CancelledError，不发布答案；依赖主动超时仍是 failed/timeout。
- 预算结算持久化失败：JournalCommitError，中断 Run，不伪造恢复或请求收尾。
- Steering 竞争：旧动作结算 stale，不安装范围、不回答旧目标。
- 关闭预留：保持原父期限耗尽行为。
- 注入时钟模拟迟到返回，以及接受动作后探索预算已用尽：不接受迟到范围，不启动无预算规划。
- 准时恢复：正常计量、原文实际进入后续请求、临时保留随后解除。
- 事件回放：逐个结算后状态为 READY，范围、轮数和字节计量一致；未接受候选不出现在持久化
  SessionContextCompiled 中。工具始终只执行一次。

运行方式：

```bash
uv run pytest tests/sessions/test_recovery_deadline.py \
  tests/sessions/test_context_recovery.py tests/runtime/test_finalization.py
```

2026-10-30 验证记录：新增恢复期限测试 17 项通过；`uv sync --extra finscope`、Ruff 检查、
全仓格式检查、Pyright 均通过；全量 Pytest 共 1111 项通过。

## 当前边界与下一步

合作式取消不能强制终止阻塞线程或不返回的插件；清理和接受事务可能跨过预算边界，剩余父时间
不足时仍不保证有答案。budget 反馈本身不区分时间、Token 和字节维度，诊断需结合事件时序与
配置；后续确有消费需求时再独立演进类型。

本轮没有重新运行真实模型评测，不据此宣称任务成功率提升；没有增加 FinScope 专属规则、
Checkpoint/Resume 或另一套规划器。完成这轮执行正确性收口后，下一主线是梳理宿主完整状态与
实际模型输入的边界，设计确定性 TaskModelView，并分清必要证据投影与可选进度分析。
