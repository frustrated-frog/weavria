# 0067：失败尝试的局部语义与继续获取

状态：已采纳，2026-10-31。

## 本轮解决的问题

[0066](0066-模型工作视图的真实模型对照与适配器注入.md) 的真实轨迹暴露出一个跨模块矛盾：
NeedLedger 和进度评估将失败解释为已观察尝试的结果，收尾策略却将同一状态解释为提前结束获取的条件。
一批调用中，title 已获得、owner 的 primary 失败，宿主立即接受 limited / evidence_ready。
下一次非 Finish 决策被收尾守卫拒绝，尚有预算时也无法使用备用来源。

旧轨迹只保留了拒绝原因，没有完整保存被拒绝的候选参数，不能据此断言旧模型具体想调用哪个来源。
本轮以确定性回归复现这个入口错误，再用相同冻结任务进行真实模型复测。

本轮修改获取、收尾和完成验收之间的解释规则，不新增账本、来源枚举器或领域工作流。
FinScope 只是公开完成原因的接入方，不参与通用框架的规则设计。

## 必须区分的四种事实

| 事实 | 权威依据 | 能推出什么 |
| --- | --- | --- |
| 某次工具调用失败 | 已接受 ToolRecord，含参数、错误类别与 retryable | 描述这次尝试，不能证明目标事实不存在 |
| 相同动作不应继续重复 | 规范化动作身份、有效前沿、既有重试与停滞策略 | 限制重复执行，不能禁止所有新参数或来源 |
| 必需证据已满足 | NeedLedger 的满足状态与证明、范围、时效规则 | 可以进一步检查是否已实际交付给模型 |
| 宿主必须停止探索 | 父预算内的预留、工具额度或既有纠错停滞边界 | 有可信内容时可尝试有限收尾，不能升级证据状态 |

NeedState.acquisition_status 的 unavailable / contract_gap 仍只描述已观察路径。
即使所有已声明 producer 都有失败，也没有证明这些 producer 的全部参数空间不可获取。
MatchPlan 的允许值是匹配约束，不是宿主承诺搜索完毕的清单。

retryable=False 也不是“整个 Need 没有其他解法”。旧的逐动作重试、动作族有界探索和成功兄弟保留机制继续生效。
明确范围内的否定发现仍由既有 completion_mode、证明强度和完整范围证据判定，不与执行失败混用。

## 收尾入口的两次判断

NeedFinalizationPolicy 的 eligible 只表示“可以提前收尾”，采用既有 mandatory_satisfied，
不再把失败或证据契约缺口当成满足。

Runtime 在收尾指令下重新编译确切请求，再检查交付清单。正常提前进入 synthesis 必须同时满足：

1. 账本预检 eligible；
2. 确切请求的复检 eligible；
3. 复检 mode=complete，且 missing_need_ids 为空。

第二次检查防止自定义策略返回 eligible=True / limited 时提前关闭工具。
Artifact 身份、SHA、字段范围、Manifest 请求摘要、任务版本和账本摘要校验全部保留。

| 当前情况 | 行为 |
| --- | --- |
| 必需证据与交付完整 | 接受 complete / evidence_ready，进入只允许 Finish 的阶段 |
| 仍缺证据，且没有触及停止边界 | 普通 decision，允许模型选择其他获准动作 |
| 已触及预留或工具预算，且实际交付了部分可信证据 | 按原规则接受 limited，最终只能是 unverifiable |
| 同一前沿上完成纠错停滞 | 复用既有有界收尾路径，不增加无限重试 |
| 没有可交付内容、证据矛盾或独立必需动作未完成 | 不凭失败日志制造可交付证据，保留预算耗尽或修复语义 |

进入 synthesis 后的 Finish-only 守卫保持有效。本次修复入口，不允许收尾模型重新开启工具探索。

## 完成验收与有限回答

宿主强制进入 synthesis，与模型主动提交 Finish 是不同决策。
仍保留现有产品行为：当未满足项的已观察路径都受阻时，模型可以主动交付有限回答，
但结果必须是 unverifiable；这不是证明 Need 不可获取，也不是 required evidence 已满足。
仍有未尝试匹配路径或可重试路径时，按既有规则返回 repair。

旧分支使用 cannot_proceed，并跳过独立必需动作及 CandidateAnswerVerifier。
新实现将这种候选统一为 degraded_answer，且先检查独立必需动作，再检查应用答案验证器的 reject。
limited synthesis 与主动有限回答都不能绕过这些检查；外层 LayeredCompletionPolicy 的发布否决也继续生效。

完成原因明确限定为已尝试路径：

- mandatory_evidence_unavailable → attempted_paths_unavailable；
- evidence_contract_mismatch → attempted_paths_contract_gap；
- 已接受 limited synthesis 仍使用 finalization_incomplete_evidence。

本轮没有增加通用自然语言事实核验器。没有应用答案验证器时，框架不能证明有限回答的措辞真实；
unverifiable 不能被 UI 或外部评分器解释为“回答已经核实”。需要更严格继续获取策略的应用仍可追加完成策略。

## 一次请求在源码中如何流转

1. ToolExecutor 通过受控执行边界结算本批调用，成功兄弟成为 Artifact，失败保留完整 ToolRecord。
2. requirements.py 根据同一批事实更新 NeedLedger；progress.py 继续将局部失败作为 replan / repair 依据。
3. harness/finalization.py 判断必需证据是否全部满足。缺 owner 时 eligible=False，Runtime 继续编译 decision。
4. 模型自行选择新的工具参数。运行时沿用动作身份、准入、资源和取消边界，不替模型指定备用来源。
5. owner 获得后，Runtime 在新请求中检查 title 与 owner 的实际交付，再接受 complete / evidence_ready。
6. 模型返回 Finish，completion.py 检查义务、独立动作与应用验证器，输出真实核验等级。

建议断点顺序：requirements.py 的 _reduce_need → progress.py 的 _continuation →
NeedFinalizationPolicy.assess → Runtime 的 _finalization_context → TaskCompletionEvaluator.evaluate。

## 为什么采用这个方案

账本已经能够区分事实覆盖和尝试失败，问题出在消费者解释不一致。复用它比新建一个“是否穷尽”状态更可靠。
宿主不掌握工具参数空间，不能根据失败次数、工具名称或应用示例推断所有替代路径已经不可行。
同时，要求每个失败都无限探索也不成立，因此继续使用父预算、动作族停滞和显式有限收尾。

没有修改 NeedLedger / NeedState 的持久化 Schema，也没有修改 FinalizationStarted 事件格式或归约器。
既有事件保持原义回放，不重新解释历史 limited / evidence_ready。新运行通过策略版本区分：

- need-finalization/2；
- task-obligations/9；
- task-obligation-completion/5[task-obligations/9]。

FinalizationAssessment 是进程内评估值，不是持久化协议；本轮补充 eligible 的语义说明。
消费公开完成原因的接入方需要适配上述原因码，FinScope 的接入回归已同步。

## 确定性验证

新回归在修复前复现完整状态、新工作视图两条真实 Session 路径的提前收尾，修复后验证：

- 同批一项成功、一项或两项永久失败，保留成功结果并执行新的备用参数；
- 失败记录不被抹除，补齐后才进入 synthesis，所有预期字段都实际交付；
- 自定义策略返回 limited 不能凭 eligible 强制提前收尾；
- 工具额度和模型预留仍允许有限回答，不把它标为 verified；
- 失败后的主动有限候选不能绕过独立动作或应用答案否决；
- 失败及契约缺口可以产生无法核实的候选，但都不能成为提前就绪条件。

复用既有测试覆盖无证据、重复动作、纠错停滞、发布否决、取消清理、steering 与旧候选丢弃。

## 当前边界与下一步

本轮没有实现参数空间穷尽证明、自动来源枚举、全失败时凭日志生成答案、恢复协议、记忆或证据增量投影。
仍需要模型提出有价值的新动作；确定性动作准入和预算只约束执行，不能代替策略收益证明。

下一小步优先处理 v5 工作视图在历史紧窗口下的反馈增长预留，再单独处理已观察到的输出协议纠错问题。
两个问题都应保留冻结坏例，分别验证不变量、真实收益与成本，不通过扩大预算或削弱答案验收掩盖失败。
