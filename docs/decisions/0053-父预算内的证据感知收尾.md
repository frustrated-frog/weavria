# ADR 0053：父预算内的证据感知收尾

## 问题

模型次数和 Deadline 是执行上界，但仅有上界不能保证已经取到证据的 Run 留出生成与验收机会。
反过来，只凭 Need 满足强制结束取证，也可能在原文尚未进入模型请求时提前收尾。

本次使用现有 NeedLedger、已接受 Artifact 和确切请求的交付清单，建立显式、可回放的收尾阶段。
它不授权新工具，不重建证据账本，也不把未验证答案提升为 verified。

## 机制

### 父预算内的资源预留

RunLimits 增加 `finalization_model_calls` 和 `finalization_seconds`。模型次数预留必须小于总次数；
时间预留最多取本次有效 Run 时长的一半，始终位于 Session 的父请求期限内。

预留开启后，探索模型和工具使用扣除预留后的截止时间；排队工具超过探索期限则明确跳过并结算，
已开始工具仍通过既有超时和取消边界结束。探索模型在其期限超时时，可以在父期限内评估受限收尾。
收尾模型仍为完成验收留下有界时间，全部调用仍消耗原 Run 的总次数。

预留默认关闭（`finalization_model_calls=0`），保留旧策略作为对照；启用必须配置 FinalizationPolicy。
SessionEngine 自动采用 TaskAwareSessionPreparer 提供的 NeedFinalizationPolicy，也可显式替换。
策略版本和全部预留参数写入持久运行配置。

### 基于当前真实输入判断可交付范围

NeedFinalizationPolicy 的第一次判断产生可继续引用的来源与任务条件；Runtime 随后使用最终指令
重新编译请求，第二次判断只使用这一份确切请求：

- 对受信 Compiler 清单校验当前 ControlRequest 摘要、Artifact 身份及必要字段的完整范围。
- 对没有清单的普通 Builder，只接受与已接受 Artifact 值完全一致的标准 full 包络；单独引用回执
  不算交付。
- 已交付 Binding 复用 InformationRequirement.covered_by 的证明、范围和完成方式规则，不能仅因
  交付了同一 Need 的一个字段就宣称整个需求可回答。
- 持久 Ledger 必须与当前 Frame 的 revision、evidence_revision、进度摘要一致；矛盾证据和未完成
  的独立必需行动阻止收尾。持久 Binding 不在当前可读记录中时，也不会假称已交付。

任务事实和交付均充分时可提前进入完整收尾。模型次数、时间或工具额度达到预留边界时，可以基于
已经实际交付的可信内容进入受限收尾。没有可用内容时，以 `finalization_evidence_unavailable`
结束为预算耗尽，不从日志拼造答案。

若尚未到预留边界且关键原文未交付，继续普通执行；已有 EvidenceAccessProof 仍可证明合法的
有界读取。进入收尾后不再接纳普通工具或 RecoverContext，避免吃掉最后的生成机会。

### 显式事件与不可绕过的验收

`FinalizationStarted` 是新的版本化事件，保存任务修订、策略版本、原因、完整/受限模式、来源调用
和未完成需求。RunState 保存这个执行模式；Steering 清空旧模式，旧模型候选仍按原规则丢弃。
该事件可以追加到现有受控 Journal；旧事件的原始含义和包络版本不变，读新事件的消费者需要升级。

最终请求不再追加可用工具目录，明确只允许 Finish。Runtime 和纯归约器也分别拒绝收尾中的工具
提案；不是仅靠提示词阻止副作用。请求快照仍先落库后发送，未接受的阶段转换不生效。

候选仍执行完整分层完成策略。受限模式在必要信息不足时保留 unsatisfied 义务和 unverifiable
结果；独立答案核验器的 reject、必需行动未完成、应用发布 Repair 都不能被该模式绕过。重复 Repair
仍失败，不转换为可发布状态。当前并未增加自然语言限制说明的独立语义核验，不能因出现受限模式
就宣称答案每一句均已证实。

### 拒绝与 Steering 的序列化

预算拒绝的计数、拒绝事实提交及耗尽判断在同一提交锁内完成。锁内先核对任务版本，过期提案不
更新计数或触发终止。这样旧任务的拒绝不会在 Steering 已经胜出后结束新任务。

### 应用引用修复反馈的字节边界

同时修复原先 FinScope 把全部缺失来源标记拼入 guidance 导致 ValidationError 的路径。反馈使用固定
短指令，完整 source_id 继续保存在已接受 Artifact 中；完成检查记录的读取调用与候选文本允许重建
缺失集合。没有截断半个来源标记，也没有扩大 Core 控制反馈预算。六个长来源标记的回归验证该边界。
这项不改变现有应用要求哪些来源必须引用的策略，探索来源与实际采用来源的进一步区分仍是应用验收
后续工作。

## 使用与对照

通用宿主可配置：

```python
limits = RunLimits(finalization_model_calls=2, finalization_seconds=10)
# AgentLoop 显式传入 finalization=NeedFinalizationPolicy(...)
# TaskAwareSessionPreparer + SessionEngine 自动共享同一个 EvidenceResolver。
```

FinScope 提供显式环境变量：

```text
WEAVRIA_FINALIZATION_MODEL_CALLS=2
WEAVRIA_FINALIZATION_SECONDS=10
```

默认值分别为 0 和 10。关闭预留保留既有行为；开启后，仍应先确保应用证据面的匹配语义正确。
本机制不会替未采用 ADR 0052 的应用凭空验证目标身份。

冻结故障对照位于 `test_exploration_timeout_preserves_parent_budget_for_synthesis`：相同任务、工具、
模型脚本和 0.5 秒父期限，第二次探索调用一直等待。基线耗尽父期限且无答案；预留策略取消该次
探索，在同一父预算内生成受限结果。这个对照证明执行机会的保留，不证明真实模型任务收益或成本
最优，测试不调用网络或付费模型。

## 验证和边界

回归覆盖完整收尾、受限收尾、无证据拒绝、单纯引用回执、禁止工具、发布否决、重复修复、取消清理、
Steering 丢弃旧候选、Deadline 对照、事件回放及 FinScope SQLite/HTTP 两种预留配置。
旧拒绝竞态用真实 Journal 屏障固定事务顺序，验证新任务完成且旧耗尽拒绝没有入账。

输入字节与 Token、输出 Token 预留继续使用现有 Compiler/Provider 最终准入；收尾会释放此前因
工具拒绝抬高的反馈预留 floor，但没有重写 Compiler 的所有保守预留算法。证据太大、来源完全不可用、
供应商故障或验收无法修复仍可失败。预留不是必然回答保证，不是自动恢复执行，也不证明 Exactly-once。

备选的统一增加预算、工具被拒后立即强制 Finish、用未核验候选作为故障兜底，均无法同时维护当前
证据和发布不变量，故不采用。当前没有为此新增大型规划器、并行 Agent 或新的记忆系统。
