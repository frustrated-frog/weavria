# 0136 按候选声明验收有界事实

状态为已采用。本文承接 [ADR 0135](0135-历史结账修订与当前库存承诺的对照验收.md) 和[库存双向验收](../当前可承诺库存的双向验收.md)。

## 两个任务要求宿主判断什么

用户问“根据这次给的材料，结论是什么”。有时能从权威原文读出一个值，有时只能从完整目录确认所需记录没有提供。这两种回答都可能正确，需要的证据却不同。例如，发布归档里的 `failed` 表示目标测试有一次失败记录，`unreported` 只表示这份归档中找不到目标运行。误把前者写成后者会掩盖一次实际失败。

| 任务 | 存在匹配值 | 本次来源范围中缺少记录 |
| --- | --- | --- |
| 指定时点的 S4 可承诺库存 | 有效发布单给出东仓 0、西仓 31 | 完整来源清单只列历史结账材料。两仓数量均应为 null，仍需当前发布单 |
| W17 发布测试 | 对构建 c071、linux-x64、io-roundtrip 三项同时匹配，读到失败记录 R-41 | 完整归档里另有三个近似记录，目标组合没有记录。应报 unreported 和空编号 |

默认完成策略能判断是否获得所需材料。单纯放宽其时效约束，会让没有有效来源的库存数值也有机会通过。只在应用里运行离线评分器，又无法在交付错误时要求 Agent 当场修正。这里把可比较的事实、已接受的原文和现有任务义务接到同一次 Finish 检查。

## 一次 Finish 的执行过程

1. 宿主通过 `HarnessEvidence.bounded_fact` 安装一份 `BoundedFactContract`，绑定完整 `TaskInput`、只读来源工具和带版本的适配器。只有与绑定输入完全相等的任务使用这份契约。任务目标、约束或修订变化后，宿主需要重新判断适用性。契约身份参与完成策略版本，沿用已有的持久化版本检查。
2. 模型提交候选后，`TaskCompletionEvaluator` 核对任务锚点、Frame 修订和已提交的语义状态。适配器解析**整份交付**，返回 `FactValue`、`scope_empty` 或无法解析。示例拒绝多余字段、重复键和互相矛盾的状态组合。
3. `BoundedFactContract.check` 只扫描本 Run 已接受的调用。来源先按工具和回执身份筛选，再由 `CompletionContext.read_artifact` 重读实际字节并校验摘要。适配器检查目标、时间和覆盖范围，从原文提取零个或一个结论。未命中的搜索、失效的发布单和部分清单都不产生空范围证明。
4. 检查器比较所有适用读数。规范化的 JSON 保留类型，实际的 `0`、`false`、`null` 与范围为空可以区分。读数重复且一致时可通过，有冲突、无证据、超出读取上限或候选不符时返回修复原因。单次检查最多读取 64 份、总计 1 MiB 的来源，达到上限仍需检查下一份时拒绝采信局部结果。取消与截止时间沿用 Runtime 的完成检查。
5. 有值分支仍须满足原有证据获取要求。只有已证明范围为空，才可结束契约内尚未取到具体值的普通外部需求。该需求须只依赖声明的来源工具，没有单独的匹配计划、上游依赖或更高证明等级。必需动作要有实际成功回执，注册的成果验证器仍须给出当前有效的结果。账本继续保留缺项，完成回执单独记录答案的验证结果和实际读取的调用 ID。

适配器是宿主的信任边界。示例在安装时绑定归档内容摘要，验收只消费实际执行读取的匹配回执。库存的清单列有发布单时还必须读取发布单正文。发布适配器检查完整性、三项选择条件和唯一运行，既可返回通过也可返回失败。冻结的预期答案只供实验评分使用。真实接入需要由数据生产方定义范围、身份和有效期，才能主张来源完整。

## 固定证据与真实运行

确定性测试固定同一份工具回执，交换“有值”和“无记录”两份候选。两个领域的四种材料均只接受匹配候选。测试还覆盖了 CI 匹配到另一项真实结果、重复运行、部分归档、跨来源冲突、值的类型、额外必需动作、取消和读取上限。

真实模型对照使用 `deepseek-flash`、温度 0。每个组合各跑两个新会话，同一任务的两种策略交替先后执行。每次执行预算为 16 次模型调用、24 次工具调用、150 秒，含准备的请求期限为 210 秒。两组使用相同的输入、材料、评分器与预算。下表的分子是最终完成且通过答案和来源独立检查的会话数，分母包括准备失败。

| 冻结问题与材料 | 默认策略 | 启用有界事实验收 |
| --- | ---: | ---: |
| 库存，有有效发布单 | 2/2 | 2/2 |
| 库存，只有历史材料 | 0/2 | 2/2 |
| 发布，有目标失败记录 | 2/2 | 2/2 |
| 发布，归档缺少目标记录 | 2/2 | 2/2 |
| **正确交付总计** | **6/8** | **8/8** |
| 宿主回执为 verified 的交付 | 0/8 | 8/8 |
| 提供方实际调用数 / 总 token | 42 / 185,960 | 43 / 190,937 |

默认策略在发布场景的四次最终答案也全部正确。该场景观察到的收益是宿主可以分别证明有记录和无记录，交付率持平。库存默认策略一次在准备阶段因缺少选择条件停止，一次在读到清单后两次提交正确候选，均被要求继续取证。完成策略只参与已产生候选的检查。每格两次运行，成本总量也包含失败请求，不足以据此推断其他任务的成功率或平均成本。

离线重验按事件顺序恢复候选产生时的语义状态、可见回执和原文字节。最终实现对本批 8 次启用策略的交付重现了相同的判定和证据调用 ID。再检查上一批三个库存缺证会话，有一个在准备阶段没有候选，另外两个共五次提交格式与内容正确的候选。完整清单读入前的一次仍要求取证，清单读入后的四次均可验证。重验不会补发历史答案，也不会借用候选提交之后的回执。

## 复现与结束条件

```bash
uv run pytest -q tests/harness/test_bounded_fact.py tests/evaluation/test_fact_completion.py
uv run python -m examples.fact_completion
uv run python -m examples.fact_completion --live --repeats 2
uv run python -m examples.fact_completion --recheck .weavria/fact-completion/run-dw2_p9mt/2-inventory-absent-baseline.db --domain inventory --source absent
```

第二条命令输出冻结的输入与材料摘要。真实运行沿用库存实验的模型环境配置，每次生成独立目录；只要有一条运行未通过独立评分，命令就返回非零，完整分母保存在 `results.json`。最后一条使用本次实验的本地数据库路径，复现者可换成自己的运行目录。数据库和模型输出保留在本地。

这项机制的验收边界是两个独立领域共用一份完成策略，能拒绝交换后的错误候选，还能交代一次肯定或否定结论的证据。自由文本里的多个独立声明、开放网络中的不存在证明、准备阶段缺少选择条件，都超出本次验证范围。
