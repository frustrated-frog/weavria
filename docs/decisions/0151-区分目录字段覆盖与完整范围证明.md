# 0151 区分目录字段覆盖与完整范围证明

2026-11-25，已采用。

## 两个任务怎样暴露了同一个问题

软件升级任务要判断两个组件的版本、兼容性、测试回执与处置。安装迁移任务要从项目清单与锁文件计算直接依赖的变化。两个任务的第一次真实运行都自行提出了遍历目录的取证要求，都通过空查询取得了目录，又取得了所需原文。独立评分器认可了首版候选，完成检查仍各退回两次。账本对目录的判断都是 `partial`，缺少的字段列表却为空。

当时的执行行为有两个不同的原因。通用 JSON 提取器可以证明回执中存在 `/paths`，无法据此证明列表覆盖全集。证据归约在检查完所有字段后发现缺少范围证明，却返回了空的缺口列表。前者是来源适配器的职责，后者由 Harness 修复。

## 执行与边界

1. `EvidenceResolver` 先将满足证明强度与时效条件的绑定按适用范围分组。在单个范围内检查字段覆盖后，再按需求的完成条件判定。需要正值而只有空结果时记录 `$result`。需要列尽范围，或需要有完整范围支撑的空结果时记录 `$scope`。未声明字段且缺少支持关系时记录 `$proof`。已有完整证据的另一个范围仍可独立满足需求。
2. `TaskCompletionEvaluator` 将范围缺口连同修复建议交给 Runtime。只有适用范围内证据充分，当前缺口才会关闭。收尾仍检查其他需求、来源、工作状态和候选。账本沿用已有标记格式，Resolver 版本为 8，完成评估版本为 14。历史事件保留原判定。
3. 示例宿主通过已有的 `HarnessEvidence.extractors` 注册快照目录提取器，并交给它本轮授权的冻结文件集合。提取器只处理 `search_snapshot/1` 的成功回执，要求 Policy 已允许规范化的空查询，且该需求明确要求完整遍历 `/paths`。路径集合及数量都与宿主全集一致才证明目录完整。空目录也适用。过滤、截断、重复、缺项、错版工具或缺少授权记录均无法给出此证明。范围身份包含每个文件的路径与内容散列。
4. 完整清单只使目录资料达到 `acquired`。目录列全之后仍要取正文，领域事实、答案质量、真实时间有效性各有自己的验收条件。其他宿主继续使用自己的来源契约。

## 取舍与验证

直接把非空列表判为完整，会把第一页当成全集。把模型提议的遍历要求一律删掉，又会损害用户确实要求遍历的场景。采用宿主已知的有限集合，可以在工具回执边界独立核验完整性。首次构造对可见正文作散列，成本与总字节数成正比。一次列表核验的时间与返回路径数成正比。远程开放索引没有封闭成员清单，需要提供与该来源相符的分页或快照结束证明。

两份原始会话的同现场回放固定候选、任务帧、已接受回执和原件摘要。每个任务取原先两次退回的候选检查，通用提取器均记录一个待证明的目录范围，快照提取器均消除这个缺口。同一任务的两次检查使用同一个候选，不是两次独立任务成功。真实运行另外统计修订版的交付、正确保留的结论、重读和成本。[跨任务验收报告](../任务修订与整体验收复测.md)
