# ADR 0050：发布门禁与适用范围证据契约

## 背景

真实 FinScope 任务暴露出两类相互关联的问题。第一类发生在控制面：无法核验的候选可能绕过应用
验收，相同修复在相同前沿重复时可能被降级成可交付结果，反馈容量拒绝也可能在最后一条拒绝事实
写入前结束。第二类发生在证据面：Requirement 只保存工具名和 JSON Pointer，Resolver 可以把不同
对象、不同查询范围的字段拼成同一个已满足 Need。

这些问题不能通过 FinScope 专用工作流修补。模型输出、动作提案和工具结果都是不可信输入；是否
允许执行、哪些证据属于同一个需求，以及候选答案能否发布，必须由领域无关且可重放的受信契约
决定。

## 决策

### 不可绕过的发布门禁

1. 分层完成策略把 `unverifiable` 与 `accept` 分开。必需策略无法核验时，扩展策略仍必须执行；
   扩展策略的 `repair` 具有否决权。
2. 相同修复在相同语义前沿再次出现时，先持久化第二次完成检查，再以
   `completion_repair_stalled` 和 `COMPLETION_REJECTED` 失败，不再改写为可交付的
   `unverifiable`。
3. 完成失败、预算耗尽和协议错误保持不同终态原因，不能用统一的无答案文本掩盖真实边界。

### 可恢复拒绝与最终模型准入

1. 反馈、工具调用和能力视图拒绝先写入 `BatchRejected`，再判断等价拒绝是否耗尽。
2. 等价身份包含实际缺口或能力纪元；有效缩批、额度变化和能力变化会形成新的恢复前沿。每个任务
   仍受 `max_admission_replans` 总上限约束，避免无限换参数。
3. ModelProvider 与 SessionProvider 都在完整 HTTP JSON Body 构造后执行最终准入。Token 和字节
   维度独立生效，只配置字节上限时不能被 Token 配置缺失关闭。
4. SessionEngine 接受 per-run `ActionInterventionPolicyFactory`，为每次 Run 创建隔离实例并把版本
   写入运行配置。`AllowAllActionInterventionPolicy` 保留为只关闭软启发式阻断的可观测基线；授权、
   总预算、工具 Policy 和副作用边界不受影响。

### 从证据面编译可执行匹配计划

1. 任务覆盖审计选中的 `EvidenceSurface` 由受信主机编译为 `EvidenceMatchPlan`，保存 producer 名称
   与版本、Profile 版本、Surface 身份、参数选择约束、字段集合和最低证明强度。模型不能自行创造
   这些授权范围。
2. Resolver 使用成功 ToolRecord 中已接受的 `ToolAuthorization.normalized_arguments` 校验工具版本
   与参数约束。匹配失败只产生可审计 Probe，不产生 Binding。
3. Binding 记录 Match Plan、稳定 scope identity、证明强度、结果种类和范围完整性。默认结构提取
   只能给出 `structural` 或 `scoped_structural`；Profile 绑定的强制完成要求
   `scoped_semantic`。
4. 字段覆盖只在同一 scope identity 内归约。不同调用默认属于不同范围；只有应用 EvidenceExtractor
   明确给出相同稳定范围身份时，才允许跨调用合并。Need Ledger 升级为 v3，旧 v1/v2 数据显式上迁，
   不为旧记录虚构语义证明。
5. InformationRequirement 区分 `positive_value_required`、`report_findings` 和
   `exhaust_bounded_scope`。Binding 区分 `found`、`empty`、`not_found`、`partial` 及
   `complete`、`partial`、`unknown` 范围。空结果只有在完成方式允许且范围完整时才能完成需求。

### 活动任务状态是任务准备的必需输入

持久 Work 的后续输入会把已接受 TaskSpecification 作为独立的活动状态约束发送给解释器，并明确
当前用户输入具有优先级。它不再只能依赖可能被历史裁剪丢弃的旧 assistant 消息。任务原文、活动
状态和可选历史仍由上下文编译器统一计量与准入。

## 备选方案

### 在 FinScope 工具中硬编码公司、日期和资源联结

这会让通用 Runtime 理解金融对象，并且其他应用仍需重复实现同一种防串用规则，不采用。当前设计
只规定 producer、规范化参数、范围身份、版本和证明强度；具体 scope identity 仍由应用解释器提供。

### 继续允许结构字段跨任意调用合并

这种方案兼容性最好，但无法区分“字段存在”与“字段属于目标对象”，会把弱结构信号用于强制停机，
不采用。无 Profile 的旧工具仍可显式使用结构基线，但默认也不会跨不同动作范围拼接字段。

### 输出截断后自动增加预算或无限重试

这会改变已声明预算并掩盖供应商兼容问题，不采用。输出截断保持结构化失败；模型推理模式、输出
额度和任务准备策略必须通过显式配置与版本诊断调整。

## 后果与当前边界

- 已知冲突候选不能再借 `unverifiable` 发布，最后一次拒绝和完成检查均可在 Trace 中重放。
- Profile、实际规范化动作、应用语义提取和 Need 归约形成连续证明链，R1 的跨对象字段拼接反例被
  回归测试阻断。
- FinScope 的 Market Pulse 与精确资源读取提供语义范围身份；目录和搜索分页只声明部分范围，不能
  用单页空结果证明全局不存在。
- 活动 Work 状态不再与可裁剪闲聊历史处于同一保留等级。
- 本 ADR 不宣称已经实现统一 finalization mode、分页穷尽证明或阶段专用 Task Schema。它们需要在
  当前匹配与发布语义稳定后继续建设，并用真实复杂任务验证收益和误杀率。
