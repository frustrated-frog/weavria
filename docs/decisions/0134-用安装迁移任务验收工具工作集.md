# 用安装迁移任务验收工具工作集

2026-11-19，已采用。任务准备与覆盖审计 v1 的收口条件见 [ADR 0133](0133-覆盖审计的字段级纠错.md)。

## 先冻结交付，再运行框架

用户要把安装组合从 `local-memory + tokenization` 改为 `lexical-memory + tokenization`，需要一份精确到锁定版本的直接可选依赖变更清单。基础包、开发组和传递依赖不属于交付。这是一项新编的维护任务，使用仓库的真实历史数据，不是用户生产流量。

输入固定在提交 `d02a743`。项目清单使用完整原文；锁文件的 49 条记录均投影为包名和版本两列，去掉下载地址与 wheel 散列，不按问题筛选行。用户只指定交付结构，不提供文件名、正确包名、工具顺序或预填的任务解释。模型通过已有的归档搜索、读取和镜像工具访问这两份资料。未注册迁移专用工具，未新增领域提示，也没有禁用覆盖审计。

验收器在会话结束后独立检查：

1. 会话达到 `completed`。
2. 从持久化的成功工具记录找回 Artifact，核对两份资料的路径、内容和 SHA-256。只搜索到路径、只尝试读取或猜中答案都不够。
3. 交付是无重复键的 JSON，三个分组与运行前人工冻结的答案完全一致：新增 snowballstemmer 3.0.1；移除 numpy 2.5.4、onnxruntime 1.31.1、tokenizers 0.23.3；保留 tiktoken 0.14.0。数值版本、额外包、额外字段或错分组都不通过。包的顺序无关。

## 由轨迹定位的一个瓶颈

旧工作集三次都只展示 `search_snapshot`。三份已接受的解释均把搜索和读取列为必需能力；读取工具确实在注册表内，也没有被授权策略拒绝。原因在 [工作集的递减覆盖算法](0076-按需求覆盖选择动态工具工作集.md)：两个工具被关联到同一信息需求时，成本较低的工具一旦获得满额覆盖，另一个的边际收益就变成零。模型因此只能在路径列表及其 Artifact 上继续寻找正文。

`AdaptiveCapabilityPolicy` v6 保留原有按需求分配的第一轮，然后检查剩余名额和字节。对于仍未满足的必需外部需求，如果已有一个明确必需的只读工具可见，另一个同样明确必需的只读工具能够提供当前这些工具没有的顶层输出字段，则允许从余量中补入。扫描按需求优先级，同一需求内按成本和稳定名称排序；每加入一个工具就更新字段集合。例子中列表有 `paths`，阅读器有 `path / sha256 / text`，同形镜像不会仅凭名字再获一席。已经投入其他需求的名额不会被抢走。补选只改变展示，不执行工具、不提升权限、不计为证据，也不改变完成判据。

没有选择直接展示所有已声明工具：那会失去对替代能力的去重，也可能扩大副作用工具的可见范围。没有增加模型规划轮次：本次失败中模型已经选对了两个工具。字段差异只是低成本线索，不能证明工具之间存在数据依赖；只有一个名额、嵌套字段不同但顶层相同、或工具都返回同形文本时，这一改动不能保证可达性。满预算下跨轮换入工具是另一类问题，本次没有扩展。

## 结果与复跑

运行条件：deepseek-flash，温度 0，reasoning_effort=none，输出上限 4096 Token；执行限额 12 次模型调用、18 次工具调用、120 秒；准备限时 60 秒，整次请求限时 180 秒。每组预定三次，均使用独立空 SQLite 会话，从原始请求重新准备，未复用解释或首答。

| 同一任务，独立冷启动 | 原策略 v5 | 余量补选 v6 |
| --- | ---: | ---: |
| 读到两份正确资料 | 0/3 | 3/3 |
| 正确交付并完成 | 0/3 | 3/3 |
| 供应商调用总数（含准备） | 40 | 19 |
| 供应商报告的总 Token | 157,517 | 88,413 |

原策略两次预算耗尽，一次因无进展退出。新策略三次都先搜索再读文件，每次展示的业务菜单都包含读取和搜索。这是一个任务的重复运行，能定位并复现这个瓶颈，不能代表其他任务的成功率，也不能把全部成本差额归因于策略。真实运行没有使用相同的模型采样；确定性测试另行固定 Frame、Ledger 和描述符，覆盖同形候选、可选能力、单名额与字节边界。
