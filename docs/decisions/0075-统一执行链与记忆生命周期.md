# 0075 统一执行链与记忆生命周期

状态：已实现，2026-11-01。承接 ADR 0069，不修改研发宪章。

## 问题与机制选择

现有 SessionEngine 已有 ContextCompiler、动态工具视图、Task Frame、Need Ledger、完成检查与恢复读取。缺口在于阶段之间的接线：理解请求时还没有召回记忆；工具反馈后的语义刷新隐含在可选评估器内；记忆形成需要应用自己追赶会话事件。再建一个执行循环会分裂取消、版本和状态提交语义。

采用显式阶段和统一资源所有者：`AgentHarness` 组合 `SessionEngine` 与 Memory 存储，执行仍是原 AgentLoop。任务理解不是所有请求必须支付的前置模型调用；配置 `understanding` 才启用。上下文编译是统一入口的必选配置，模型与计量器必须配对。工具授权仍由 ToolPolicy 决定。

## 调用链与状态所有权

1. `AgentHarness.send` 在会话级别占用从运行到后处理的完整区间。它先有界续接已有记忆游标，再调用 SessionEngine。不同会话允许并发，同作用域的写冲突沿用 MemoryFormationEngine 的版本重审。
2. SessionEngine 接受用户输入，读取历史和待回答澄清。若配置任务理解，在请求总期限内召回 ContextSupply，作为 `SessionTaskContext.context_supply` 交给 TaskAwareSessionPreparer。记忆可以帮助解析指代和约定，不会改写原始 TaskInput 或直接满足需要工具验证的信息需求。
3. TaskUnderstandingInput v2 携带完整的来源供给。ModelTaskInterpreter 将其编码为明确标记的低信任任务数据，保留条件、争议、有效时间和来源。无来源保留 v1 序列化；v1 禁止携带供给。输入摘要覆盖 v2 供给。没有给 TaskFrame 添加一份长期缓存的记忆副本。
4. 每次决策继续使用现有 `prepare_turn → TurnPreparation → _apply_turn_preparation → build_control_request`。工具名称来自本轮接受的 capability epoch，Runtime 校验同 epoch 不允许换视图；工具调度继续使用该视图。TaskModelView、Need Ledger、上下文需求都由同一已提交工作状态投影。ContextCompiler 联合分配历史、工具记录、记忆的预算，保留工具调用和结果配对；一次编译内部不重新召回，下一次决策按新需求重新读取。
5. 工具结果持久化后，Runtime 显式调用可选的 `TurnSettler.settle_turn`，再调用 ProgressAssessor。Session 适配器先保存 before，再归约工具事实、刷新工作状态和能力，最后让可选评估器读取 before/after。没有评估器时也发生归约，且发生在 execution resolution 之前。此阶段仍受探索期限限制，不能侵占收尾预留。已提交事实不随超时撤销；下一次普通准备可补齐未完成归约，紧急收尾只能使用已提交的语义投影。
6. Run 的终态提交后，Harness 有界消费接受的会话事件。仅用户输入和 steering 能产生提取文档，工具与助手输出不自动成为记忆。提取、审阅、准入和写入仍由现有形成引擎负责；事件游标与结果原子提交。默认不启用竞争解释实验。

`TurnPreparation` 已承担当前决策视图的绑定，本轮不另造平行的 StepContext 状态系统。记忆查询与 Session 状态提交并非跨库事务，不宣称两者全局线性一致。

## 资源、失败与续接

Harness 拥有 Session 与 Memory 的 SQLite 存储生命周期，模型 HTTP 连接由宿主拥有。关闭时先取消并等待请求及形成调用退出，再关闭存储。没有无人跟踪的后台形成任务。`CancelledError` 始终传播；若取消发生在后处理，Runtime 终态可能已完成。使用同一 input_id 重试可以取得原报告并续接记忆，不会重新执行模型或工具。

以下为 v1/v2 行为；v3 的父请求期限见 [ADR 0077](0077-统一执行链的组合契约与请求期限.md)。

每次 `send` 的前置追赶和后置形成各有 `max_duration` 和 `max_events` 上限。固定消费到开始时的事件序号，不无限追赶新事件。总延迟上界由 Session 请求预算和两段记忆预算组成，并非把记忆耗时隐含算进已结束的 Run。`HarnessResult` 返回原始 SessionResult、`prior_memory` 和 `memory` 两份处理报告；它们是调用结果，不新增持久化 Schema。

报告状态为 disabled、read_only、completed、deferred 或 failed。预期依赖故障仅记录异常类型，不暴露正文或凭据，也不改写已提交的执行成功；程序缺陷仍抛出。游标是调用者确认的下界，取消或超时期间可能已提交，续接以数据库为准。`flush_memory` 可以独立追赶，无需创建一个新 Run。形成失败时下一请求的读取可能仍不完整，必须查看 prior_memory，不能把“回答成功”解释成“记忆已追平”。

单个 Harness 绑定一份宿主身份、精确作用域和陈述者。它不承担多租户身份认证。不能让不同用户共享同一实例再由模型选择授权。`sessions` 暴露原引擎供查看事件和高级控制，应用发送请求应走 Harness，绕过它会绕过形成和会话后处理串行约束。

## 替代方案与取舍

- 全部挂到通用 Middleware：让工作状态更新依赖可选 Hook 的配置顺序，拒绝。工具反馈结算是显式 Runtime 阶段。
- 每次把所有模块强制运行一遍：简单请求也支付理解、审阅和写入成本，拒绝。理解可选，记忆可禁用或只读，形成有准入策略。
- 持久后台 Worker：降低响应延迟，但需要额外所有权、调度和关闭语义。本轮选择父请求内有界形成，接受额外尾延迟。
- 自动修复所有记忆错误：当前竞争解释实验尚无稳定收益，继续显式 opt-in。
- 替换现有上下文算法：本轮重点是模块协作，保留已有预算选择、工具反馈、恢复与工作状态算法，避免借“统一”重写成熟路径。

## 验证范围

确定性集成覆盖自然输入事件到形成存储、跨会话召回到理解和决策、同 input_id 重试、形成失败后重开续接、超时、取消、关闭、同会话竞争、逐事件预算、只读/禁用配置，以及无进展评估器时的反馈归约时序。原有 Context/Runtime 回归继续验证配对、收尾、工具执行、恢复和 steering。

这些证明接线和生命周期，不证明自然语言提取更准确或任务成功率提高。本轮没有运行付费模型评测；后续应围绕真实长任务中的上下文选择与纠错收益深化，而非把接线完成当作所有子系统成熟。

本轮检查结果：全量 1342 项通过；最后补充理解输入序列化与真实适配器编码检查后，相关 56 项定向回归通过。Ruff、格式检查和 Pyright 全部通过。示例完成导入与命令行入口检查，未执行真实模型调用。
