# 0097 只读后台任务的可恢复等待

## 背景

外部系统已有一个运行中的任务，Agent 需要等待它完成，再用返回内容交付。例如，应用可以把文档解析任务的 ID 交给 Agent，由一个只读工具查询状态。通用的重复动作检查会阻止同参查询，工具内部睡眠又会把等待藏在尚未结算的调用中。进程退出后，后者无法复用 [0085 的结算边界](0085-只读任务结算边界恢复.md)。

## 决策

- 工具通过 `TypedTool(poll_interval_seconds=...)` 启用轮询。该参数要求工具为可安全重放的只读操作，无人工审批，并配置 `feedback_delivery="complete"` 与大小估算器。输出 Schema 使用顶层 `status`，取值为 `running`、`completed` 或 `failed`。任务 ID 应由入参提供。应用负责让同一组归一化入参始终查询同一个外部任务。
- 工具执行器先校验返回值，再按状态处理。`running` 留下完整的状态 Artifact 和版本化的 `ToolRecord.poll_after_seconds`。`completed` 按正常成功路径提供 Artifact。`failed` 提供已分类的工具失败。
- RunState 用已接受的 `ToolRecorded` 时间加间隔得出 UTC 查询下限。动作指纹来自该次准入已经绑定的工具名称、版本及归一化参数。等待发生在整轮结算后、下一轮上下文选择前。等待期间没有新执行事件，SQLite 的结算边界可用于显式 `resume(session_id, run_id)`。重放可以还原同一 Run、已接受的状态、查询时间和调用计数。进程离线时间计入原请求期限。
- 首版使用单调用查询轮次。只在等待中的同一查询获得新 `call_id` 且到达时间下限时，允许跳过语义重复检查。能力视图、反馈容量、动作干预、调用预算及工具授权照常生效。运行中换任务或提前提交 Finish 会被拒绝。宿主接受新的任务修订时会清除等待并唤醒循环。取消由原 Run 所有者处理，原请求期限和调用预算共同限制持续运行的任务。
- 查询返回完成后，下一轮仍按普通验收流程交付，验收器可以读取完成结果的 Artifact 并记录来源调用。轮询状态按控制元数据处理，等待期间暂停本轮语义进展判断和收尾；会话仍正常结算工具记录。

## 取舍

工具内部循环可以减少模型调用，但要求工具自行维护重试、期限和恢复位置。独立的调度服务可以在进程离线时继续查询，但需要跨进程领取、租约与调度恢复。此阶段复用已接受结果与原结算事务，由模型提出同一只读查询。恢复范围覆盖结算后的等待，下一轮已开始或调用在途时仍适用 0085 的原边界。

工具声明使用 ToolDescriptor v7，带等待信息的 ToolRecord 使用 v3，旧版本保持原序列化形状。每次查询消耗模型和工具预算。目前支持一条活动查询链，恢复需要调用方显式发起。

## 验证

`uv run pytest -q tests/sessions/test_polling.py` 使用本地确定性任务和真实 SQLite。用例在第二次接受 `running` 后退出进程，验证恢复前后 Run ID 一致，再与不中断路径比较查询时限、调用次数和最终 Artifact 来源。第三次查询仍返回 `running` 时，恢复路径按原预算结束。用例还覆盖提前收尾、替换任务 ID、取消和任务修订。
