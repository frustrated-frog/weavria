# ADR 0022：语义前沿与有界探索

- 状态：已采纳并实现
- 日期：2026-10-20
- 范围：AgentLoop v3、ProgressPolicy、批次准入、冻结机制实验
- 前置：[ADR 0013](0013-dynamic-capability-completion-progress.md)

## 背景

`semantic-progress/2` 只拒绝“相同状态下完全相同的规范化 ToolBatch”。这能阻止模型原样重复
调用，却把每个新 Artifact SHA256 都视为状态变化。工具若在结果中加入时间戳、请求标识或其他
波动字段，模型只需不断更换参数，就可以在没有减少任何必需 Need 缺口的情况下持续消耗工具和
模型预算。

问题不能改写成“调用次数太多”。同一工具可能需要用不同参数探索，任务也可能在获得部分字段、
新证据或新能力后继续使用它。需要区分：

- **语义前沿**：当前任务、Task Frame 有效语义、Need 状态和能力视图的组合；
- **规范化动作**：包含工具版本与参数的完整批次身份；
- **动作族**：保留批次中的工具及版本顺序、忽略参数的探索类别。

控制目标是在前沿不变时保留少量参数探索，同时阻止同一动作族无限制造表面不同的结果；Need
真正推进、任务修订或能力视图改变时必须重新开放探索。

## 决策

### 1. 以有效 Need 状态定义 Task-aware 前沿

当 `TaskObservation` 携带合法的 `need_state_sha256` 时，ProgressPolicy 使用以下内容构造前沿
指纹：任务修订号、去除投影版本字段后的 Frame 语义、Need 状态摘要和 Capability Epoch。

此时不再把原始 Artifact SHA256 纳入前沿。Artifact 只有经过 EvidenceResolver 归约，实际改变
Need 状态，才构成进展。这样时间戳变化、无关输出和重复的部分证据不能重置停滞计数。

Standalone AgentLoop 没有 Need Reducer 时，继续使用已接受 Artifact 与失败类别集合作为保守
降级；不能假装它拥有语义进度判断。

### 2. 同时维护精确动作和动作族

每次检查计算两个摘要：

- `canonical_tool_key_sha256`：有序工具名、版本和完整参数；
- `action_family_sha256`：有序工具名和版本，不含参数。

相同前沿中的精确动作再次出现时立即拒绝，原因是 `repeated_action`。同一动作族已经准入
`max_stagnant_batches_per_action_family` 个不同动作后，再提议新的参数变体也会拒绝，原因是
`stagnant_action_family`。默认上限为 3。

切换到另一工具族仍可探索；Need 摘要、任务语义或能力 epoch 发生变化，也会进入新的前沿。
这比全局“连续 N 次工具调用”更精确，不会因其他能力失败而封死独立来源。

### 3. 检查与提交采用两阶段协议

`ProgressPolicy.inspect()` 必须是纯检查，只返回 `ProgressCheck`。Runtime 成功接受
`BatchAdmitted` 后才调用 `record_admission()`。未提交的模型提议、任务修订竞争中失效的准入、
预算拒绝和能力视图拒绝都不能占用探索次数。

该顺序保证控制状态只依据已接受执行事实演进。`record_admission()` 会拒绝 blocked 检查、重复
提交和与检查时计数不一致的提交，防止调用方绕过两阶段约束。

### 4. 诊断与失败保持有界

`AdmissionNotice` 兼容增加 `progress_reason`、`action_family_sha256` 和
`prior_family_attempts`。新通知完整提供三个字段；旧 v3 日志缺省这些字段仍可解码。通知继续受
1024 字节控制通道上界约束，不复制参数和工具输出。

同一前沿上的无进展拒绝使用独立的 `max_no_progress_rejections`。超过上限后以
`ErrorCategory.NO_PROGRESS` 失败，不伪装成 Tool Budget 或 Deadline 耗尽。前沿改变会重新开始
拒绝计数。

## 执行不变量

1. 新 Artifact 本身不证明 Task-aware 语义进展；必须改变有效 Need 状态。
2. 没有被 `BatchAdmitted` 接受的提议不得进入尝试集合。
3. 工具版本参与精确动作和动作族身份；升级后的能力不会静默复用旧计数。
4. 参数不会进入诊断通知，Trace 只暴露稳定摘要与计数。
5. 新 Need 状态、任务语义、能力 epoch 或独立工具族都保留恢复路径。
6. ProgressPolicy 只限制准入，不能授权工具、替代 Tool Policy 或证明任务完成。

## 考虑过的替代方案

### 继续用 Artifact SHA256 代表进展

实现简单，但工具输出中的时间、排序或请求标识足以永久逃逸停滞检测；拒绝。

### 不区分工具族，前沿不变达到总次数后拒绝所有行动

能够减少调用，却会阻止 Agent 从失败来源切换到独立来源，也无法表达批次结构；拒绝。

### 每轮调用评判模型估计信息增益

可以覆盖更强的语义，但会引入不确定性、额外成本和新的失败面。目前没有真实失败轨迹证明其
必要性；保留为后续可替换策略，不进入默认 Runtime。

### 只依赖模型 Prompt 自觉停止

模型输出是不可信建议，无法形成可测试的预算与终止保证；拒绝。

## 验证与实验结果

运行：

```bash
uv run python examples/progress_control.py
uv run pytest tests/runtime/test_control_loop.py tests/evaluation/test_progress_control.py
```

冻结实验包含两个合成轨迹：

| 轨迹 | 语义前沿策略 | 仅精确重复基线 |
| --- | ---: | ---: |
| 参数持续变化、Need 不变 | 4 / 4 | 3 / 4 |
| Need 每轮真实变化 | 4 / 4 | 4 / 4 |
| 合计 | 8 / 8 | 7 / 8 |

Runtime 集成测试还验证：三个不同 Artifact SHA256 不会伪造 Need 进展；第四个同族参数变体在派发
前被拒绝；Need 摘要变化和替代工具族不会误拒绝；未提交的检查不计数；事件可重放且旧通知仍
可解码。

这些结果只证明冻结标签下的控制行为，不证明真实模型任务完成率提高。实验没有执行工具，也
没有评价某个新结果是否真的有信息价值。

## 影响、迁移与局限

- 自定义 `ProgressPolicy` 需要实现 `record_admission(check)`；这是为了保证检查与事实提交分离的
  有意协议变更。
- `RunLimits.max_stagnant_batches_per_action_family` 控制每个前沿/动作族允许的不同批次数；提高
  它会扩大探索，降低它会更早保护预算。
- 策略状态仍属于单次 Run 的内存控制状态。项目尚未支持未完成 Run 自动恢复，因此本 ADR 不
  宣称 Durable Progress Control；将来恢复时必须从已提交 `BatchAdmitted` 与 Task/Evidence
  事实重建，而不能序列化私有集合冒充权威日志。
- Need 摘要来自宿主配置的语义准备链。它能约束执行但不能提升权限；错误的 EvidenceExtractor
  可能导致误判，需要通过应用契约和真实任务评测校验。
- 当前机制衡量“状态是否变化”，尚不估计路径最终成功概率、证据独立性、信息增益大小或继续
  行动的期望价值。

## 下一步

在领域无关的文件、HTTP 与表单任务上冻结真实模型、Prompt、预算和策略，比较
`semantic-progress/2` 行为基线与当前策略的无效调用、误拒绝、任务完成、延迟和 Token。只有
真实失败表明状态变化不足以代表有效进展时，再研究可校准的信息增益或停止价值评估器。
