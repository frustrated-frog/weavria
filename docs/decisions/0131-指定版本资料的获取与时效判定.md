# 指定版本资料的获取与时效判定

2026-11-18。依据 ADR 0052 的双向目标匹配、ADR 0081 的 acquired 状态和 ADR 0130 的短材料失败轨迹。

同一个 current 可以指数据集命名的版本，也可以要求现实时间上的有效性。前者可以用请求中的目标、已授权调用参数和返回身份共同核实，后者需要提取器独立判断。任务解释应能表达二者同时存在。

适配器在 EvidenceSurface v3 上显式声明 material 获取模式并提供目标规则。宿主沿用目标绑定和覆盖审计，将该选择纳入计划身份及需求指纹。每个计划保留自己的证明门槛，匹配的结构字段可让材料进入 acquired。涉及事实判断的 satisfied 仍要求足以覆盖整个需求的语义证明。旧证据面的语义证明门槛继续生效。

对于明确要求现实时间有效性的需求，只有 freshness=valid 的证据能贡献覆盖。未证明时效的来源保留在账本，提示缺少的条件。解释器不根据调用发生时间、工具名、返回文本或名为 current 的版本自动授予现实时间证明。

验收使用同一请求和同一组已接受调用，分别替换版本、响应身份、证明强度和时效，再在统一 Harness 下运行原短材料。固定输入用于验证拒绝和接受条件，端到端运行观察解释器能否正确建立目标、执行模型能否完成任务。

## 模型声明与兼容

在包含材料证据面的目录上，任务解释与覆盖修复使用同一份模型输入词表。模型在目标中选择请求里的版本，再用 `time_requirement` 表达 `stable_or_named_edition` 或 `independent_wall_clock_recency`。前者编译为稳定资料，后者编译为要求时效。带目标的需求须给出时间条件。原有显式 `freshness` 声明仍按其原强度解析，同时提交两种条件会触发校正。原始任务、约束中的字符位置、授权入参、生产者版本与返回身份共同限定匹配。有限枚举可在用户目标里定位并提示最多 16 个原文位置，模型负责选择。

只在提示里解释 `current` 的两种含义曾在短材料的四次运行中全部失败。把两种含义拆成可选字段值后再做完整对照。直接把所有带版本的需求改为 stable 会丢失“确认 v1 至今有效”等真实要求，因此任何显式的现实时效条件都必须继续约束验收。

EvidenceSurface v3 和 EvidenceMatchPlan v3 表达带目标的材料获取，编译后的 InformationRequirement v2 保存 scoped_structural 门槛。旧版协议的默认值和线格式继续可读。计划身份包含证明模式，需求身份包含时间条件与计划。Resolver、任务理解与工作重验的策略版本已更新。回放既有事件时保留当时的判断，按新策略重新取证时采用新规则。数据库沿用已有事件和 Artifact 表。

## 执行示例

用户要求对照 original 和 current 两份配置。宿主从用户请求绑定两个目标。运行读取 original 时，该版本的 /text 记为 acquired，current 需求仍为 pending。即使两个版本的正文相同，只有随后读取 current 并核实返回版本，才能取得 current 对应的原文。工作记录可基于这些原文形成判断。若任务还要求证明“当前部署使用这个版本”，结构提取器保留 $freshness 缺口，只有能够独立判断时效的提取器才可补足。工作笔记即使通过模型重验，也须引用满足原需求时效和证明门槛的来源。

在一次需求归约中，每个计划按自己的门槛检查绑定，再按共同作用域检查字段覆盖。只有有效时间的来源能参与现实时效验收。缺口诊断仍能看到已找到的字段，避免引导模型反复读取同一原文。目标/字段校验在原工具与 Artifact 路径内完成，时效判断依赖已记录的提取器结论，归约过程中没有新增时钟读取或模型调用。

示例中的 `versioned_documents()` 返回统一入口的 `HarnessEvidence`，包含指定版本的工具、证据面、目标规则与覆盖审计。接入方将它传给 `AgentHarness.from_config(evidence=...)`。版本匹配依赖适配器正确报告身份；资料正文支撑哪些推论仍由任务分析或独立语义评价判定。使用滑动时间窗口的应用仍需提供有时间依据的提取器。

## 验证与复现

固定输入分别替换取证配置、请求版本、返回身份和时效证明。相同资料在旧语义配置下保持 partial，在材料配置下进入 acquired，错误版本不能建立绑定。联合计划保留各自门槛，已通过重验的笔记也不能借用其他来源的新鲜度。测试入口如下。

```sh
uv run pytest tests/harness/test_target_binding.py tests/harness/test_requirements.py tests/harness/test_work_recheck.py
```

真实对照保持 work_recheck 开启并使用局部补丁，基线使用原来的文档工具，配置组增加材料证据面及其所需的覆盖审计。两组的任务、文档、独立布尔答案和预算沿用同一运行器。模型自行拆分目标与形成工作笔记。短材料两项各重复两次，交换先后顺序。另对冻结源码和设计资料三项各运行一对。使用 deepseek-flash，temperature=0，reasoning_effort=none，窗口 64000，输出上限 4096，每任务执行模型最多 16 次，工具最多 24 次，限时 180 秒。供应商总调用还包括准备、覆盖和工作重验。

```sh
uv run python -m examples.work_recheck --live --compare-material --repeats 2 \
  --dataset examples/fixtures/work_evidence.json --output .weavria/work-recheck/edition-short-new.json
uv run python -m examples.work_recheck --live --compare-material \
  --output .weavria/work-recheck/edition-sources-new.json
```

短材料第一轮沿用原 freshness 词表，两组都为 0/4。第二轮基线为 0/4，配置组为 2/4。基线四次都留下时效缺口。配置组在一次容量变化和一次容量不变的任务中正确交付，先读 original 时 current 仍为 pending，读到对应版本后两组需求各自进入 acquired。一次记录了 revised 审查。其余两次在任务准备阶段失败，原始记录只保存了异常类型，无法据此归因到具体校验。两组总模型调用分别为 31 次和 25 次，消耗 216765 和 149742 Token，耗时 67.23 和 70.50 秒。准备阶段提前失败也会减少调用，成本应连同完成情况解读。

冻结源码和设计资料三项各运行一次，基线正确交付 0/3，配置组 2/3。配置组在三项中都绑定了两个版本，完成了设计修订和契约未变两项。源码修订在两组都以 `no_progress` 结束。两组总模型调用分别为 28 和 27 次，消耗 224975 和 222166 Token，耗时 68.02 和 82.05 秒。契约未变的配置组虽答对，终态仍有一条陈旧笔记，两个正确样本都没有证据失效触发的重验。这轮只说明指定版本的资料可以分别取齐，尚不足以证明依赖修复改善。后续实验应单独验证取得原文之后，工作笔记如何在容量和依赖顺序约束下完成更新。

最终实现将枚举和目标位置提示移入与能力目录相同的输入数据区。以相同配置重新跑两项短材料各一对，基线正确交付 0/2，配置组 1/2。容量变化一项在准备阶段收到 `invalid_model_response`，容量未变一项读齐两份原文，遇到一次工作笔记上限后仍正确交付。这个复核没有重复三项源码和设计资料，前述两批对照保留各自的实现摘要。

原始运行及轨迹保存在忽略目录 `.weavria/work-recheck/`，三轮短材料依次为 `edition-short-01.json`、`edition-short-02.json`、`edition-short-03.json`，源码与设计材料为 `edition-sources-01.json`。复现命令需注入模型环境变量，去掉 --live 可离线校验材料摘要。
