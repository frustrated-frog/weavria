# 条件依赖与预算内局部修复选择

状态：已实施，2026-11-06。

## 问题与决定

诊断前缀截断既不能识别未满足条件之间的前置关系，也可能被第一个大条目占据预算。本阶段将宿主独立验收的未满足条件组织为至多八个节点的有向无环图。边表示修复前置条件，不宣称通过统计推断发现因果关系；模型执行顺序仍不是固定 Workflow。

只有没有未满足前置条件的节点进入当前修复前沿。对最多八个前沿节点枚举所有子集，以反馈的实际 UTF-8 JSON 字节判断可行性，优先最大化可影响的不同条件数，再最大化独立修复入口数、最小化编码成本。共享下游只计一次。选择和输出稳定，不因诊断措辞变化制造执行进展。

新验收器显式选择 dependency_frontier；旧策略继续 prefix。CapabilityOutcome v3 保存完整紧凑拓扑、选中的根条件和省略计数；模型只接收当前可修复条目及延后数量，不把预算省略解释成通过。图只包含本轮未满足条件，已通过的前置节点及相关边由验收器重新检查后移除，不沿用旧图。

## 不变量与取舍

节点标识复用稳定条件码，在依赖模式中必须唯一。缺失前置节点、自环和多节点环都拒绝；截断后持久化拓扑仍完整，选中条目必须是根。依赖图不能赋予工具权限、额外重试次数或语义满足。初始槽位固定反馈预算，旧 v1/v2 线协议不变。

该机制处理正确验收条件之间的局部选择，不代替宿主验证条件本身。枚举至多 256 个子集，比为小问题引入通用调度器更直接，并能精确处理 JSON 编码的预算。此阶段不引入跨能力图、分布式任务或记忆学习。

验证图非法输入、汇合依赖、预算不足、超长首项、输入乱序、修复后的前沿推进、持久化回读、模型容量与实际容器纠错。基线与新策略共享验收谓词；真实小样本只提供任务观察，不据此宣称一般纠错收益。

## 验证结果与适用边界

完整机制、运行方式和对照数据见[条件依赖与局部修复选择](../条件依赖与局部修复选择.md)。真实 Docker 七种组合通过,新增故障链实际覆盖统计错误、修复统计、报告错误及最终验收。两组真实模型任务均完成,但任务理解及生成轨迹不同,没有建立一般能力提升的因果证据,所以保持显式启用。

当前目标函数计算可能影响的不同条件,不估计成功概率或修复成本。依赖语义由可信验收器负责,框架校验图结构、绑定证据并承担预算选择;不宣称从任意日志自动发现根因。增量重验与跨能力依赖不在此阶段范围。
