# 工作结论的版本依赖与增量失效

状态：已实现执行机制，真实模型收益待验证。

## 问题与边界

有界 `WorkingState` 已能记录带来源的阶段结论，并随 TaskFrame 需求修订退休不适用的笔记。但是，同一任务内修改上游结论时，后继仍可能作为有效结果参与上下文分配与收尾。全量清空会丢弃独立分支；只修改文字则隐藏了失效范围。

本阶段处理**显式提交的结论依赖**。模型负责提出关系与重验后的结论，归约器负责版本绑定、失效传播和使用约束。不自动推断自然语言蕴含关系，不把新 Artifact 当作旧 Artifact 的替代品，不将“重绑定成功”解释成“内容已被独立证明”。NeedLedger 仍是证据账本。

## 设计决定

`WorkNote.depends_on` 是 `{note_id, revision}` 的有界集合。`WorkingState.note_revisions` 由宿主维护：笔记内容、来源与依赖版本全部不变时保持旧值；新建或改变的笔记使用本次接受后的工作集修订号。用户可在一个提案中提交新父节点与后继，二者使用 `base_revision + 1`，但工具成功仍需等待 CAS 归约接受。

按拓扑顺序遍历最多六个节点，每条直接依赖归入以下一种原因：

- `missing`：父节点退出当前有界工作集；
- `blocked_by`：父节点自身尚待重验；
- `changed`：父节点有效，但当前版本与绑定版本不同。

受影响笔记保留原文、原始来源与绑定，不静默改成新版本。`recheck_note_ids` 只返回父节点存在且有效的失效笔记。模型先重验这些节点，再显式重绑定，下一次归约重新计算后继状态。重验上游不会自动确认下游；独立分支的笔记版本保持不变。

全量工作集替换语义保持不变。若退休父节点而保留后继，后继显示缺失依赖；模型可以恢复父节点、修改结论及其依据，或者明确退休不再使用的后继。任务需求修订沿用已有需求依赖闭包退休规则，跨需求的幸存后继再通过结论依赖图显示失效。

## 执行不变量与失败语义

1. 接受顺序、`task_revision`、`base_revision` 与 `processed_records` 沿用现有机制。同批竞争只接受匹配版本的提案，回放不重复应用。
2. 禁止重复、自引用、环和未来版本预订。对现存父节点绑定高于其当前接受版本的提案，以 `last_notice=invalid_dependency` 拒绝，不改写旧状态。否则未来某次更新可能使陈旧结论意外恢复。
3. 删除再加入或 A→B→A 都获得新版本；只按内容摘要判断身份不能满足这一不变量。
4. 状态读取重新校验版本覆盖、图和完整诊断。不能删除诊断字段把陈旧结论伪装为当前结论。
5. 工具在原有 8 KiB 状态预算内预留版本与最坏诊断开销；没有提高上下文、工具反馈或持久化上限。
6. 依赖边不能授权读取来源。来源仍经 `ToolContext.read_artifact`、JSON Pointer 与区间校验。取消继续向上传播；纯归约不产生后台任务，失败不发布部分状态。
7. 进度评估在结果失效时建议重规划，但不增加 `material_progress`，不改变证据摘要。反复修改工作笔记不能获得新的证据进展或逃避原有预算。

## 系统连接

- Task Model View 的完整视图及压缩视图均保留笔记版本、依赖边和诊断。
- 失效结果不能把 acquired 需求标为 `finding_recorded`，相关需求恢复探索权重；上下文优先取回可先重验的节点及父节点来源。
- `TaskCompletionEvaluator` 拒绝含失效 result 的活跃工作集，返回 `work_dependency_stale`；`NeedFinalizationPolicy` 不为它主动启动收尾。普通 plan/hypothesis 本身不增加最终交付义务。
- M1 的 `LongTaskDelivery` 同样检查当前已提交状态，不能以另一条独立结果掩盖仍失效的结果。
- 完整状态进入现有 Session 语义快照；重开读取与从事件重放得到相同图状态。压缩投影不作为恢复真相，历史接续包里的工作状态仍只是历史上下文。

## 版本与兼容性

`WorkNote`、`WorkDraftNote`、`WorkDraft`、`WorkUpdate`、`WorkProposal`、`WorkingState` 新写入使用 schema v2，保留 v1 无依赖记录的读取。v1 不允许混入依赖数据或版本诊断；新增空字段不会写入 v1 的旧线格式。旧工作头首次接受新提案时升级，未变笔记以旧工作集 revision 初始化版本，不追造不存在的单笔记历史。

工具版本为 `propose_work/5`。压缩模型投影为 schema v3、`stage-summary/2`；这不是持久化 WorkingState schema。Task Model View、进度评估、完成与准备策略均更新版本。读取旧数据不等于允许跨工具版本自动恢复已固定协议的活跃 Run，仍遵守已有配置兼容性约束。

## 替代方案与取舍

- **全部清空/重算**：规则简单，但独立分支也丢失；保留为实验基线。
- **只保存笔记**：成本低，无法识别已修订上游的后继；保留为不失效基线。
- **自动把依赖绑定到最新父节点**：省去显式版本，但把“还没重验”隐藏掉，拒绝采用。
- **内容哈希版本**：能发现文本变化，但无法区分删除后重新加入和 A→B→A。选择宿主接受序号。
- **自动语义冲突识别与结论核验**：需要独立的语义判据及真实任务证据，不在本切片中宣称支持。当前图仅约束模型显式声明的依赖，不能发现遗漏或故意删除的关系。

## 验证与下一步

契约和集成测试覆盖链式失效、缺失父节点、独立分支、ABA、环、未来版本、CAS、旧快照、诊断篡改、重放、取消、上下文投影、预算、最终拒绝与重验后交付，以及 SQLite 会话重开。

`examples/work_dependencies.py` 用冻结的六节点图和五个修订位置，对比不失效、其余节点全部重做、版本依赖三种策略。独立的反向边可达性作为范围判据，增量策略实际走提案工具和归约器。报告重验范围与轮数，不把合成图上的范围正确性称为真实 Agent 收益。

真实模型服务此前返回 `HTTP 402 insufficient_balance_error`，本阶段不重试付费调用。后续应验证模型是否能自行提出必要依赖、正确重验和恢复，以及误声明依赖带来的额外成本；只有这些实验才能支撑任务收益结论。
