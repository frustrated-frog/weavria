# 同源请求计量驱动的摘要选择

## 问题与结束条件

0102 的真实实验发现：摘要通过来源绑定和字节压缩检查，仍可能增加模型输入 Token。原文更长不等于编码更贵；摘要的地址、来源图和依赖引用也有成本。工具接收成功只能证明其来源与存储契约成立，不能自动证明适合放进下一次模型请求。

本阶段把**已生成摘要的表示成本**接入编译器选择，结束条件是：使用正式请求编码器比较同源表示；拒绝没有 Token 节省的正文而保留原文与恢复能力；保护完整反馈和恢复区间；兼容旧持久化记录；有反例、取消、容量和持久化恢复测试，以及保存的真实摘要回放。生成前收益预测、质量自动验收与自主任务收益不属于本阶段已证明的能力。

## 设计与数据流

新增 `ContextCompilerConfig.summary_selection`，默认 `coverage` 维持既有行为；`token_savings` 要求开启 `semantic_compaction`。它与效用分配策略、压力建议、阅读准备独立：成本通过只表示正文可以参与分配，不表示必须入选，也不把信息质量升级为事实。

一次编译的过程：

1. 按已接受记录加载来源，重建摘要 DAG，过滤失效/非法节点。原文和摘要仍共享现有依赖图与预算分配器。
2. 建立必选上下文，先验证其能够满足硬预算。完整工具反馈、受保护原文、最新对话、任务状态和控制预留不放松。
3. 对最近最多 32 个有效摘要，在相同必选背景下生成两个比较请求。摘要侧保留摘要正文，以及所有依赖的最低合法表示；原文侧只包含摘要覆盖的原文区间及这些原文自身的依赖。两边分别支付自己的引用闭包。非必选的摘要及父摘要引用不得强塞到原文侧，借此夸大节省。
4. 原文地址按 Artifact 分组，完整子树去重，连续/重叠字符区间取并集。已恢复区间及其结构上下文必须同时留在两边；原文必须完整交付时，摘要不能替代它。摘要只覆盖局部时不按整份大文件收费。额外计量全原文方案，若比带地址的摘录更便宜，则取较低成本作为基线。
5. 用宿主提供的 `SessionTokenCounter.count(SessionRequest)` 计量正式传输内容，包含协议、任务、元数据和依赖。只在摘要侧 Token 严格更少时开放正文，否则候选仅保留引用。大小预留并不是已发送 Token，因此不伪装成测量值；最终分配仍执行原来的 Token、JSON 字节、HTTP 字节、反馈下限和下一步容量检查。
6. 更新候选后重建分配器，避免旧计量缓存污染新选择。正常效用分配继续运行，恢复事实、已接受 Artifact、工具重试和授权都不被改写。

源码入口为 `context/compiler.py`；同源投影、区间并集和计量在 `context/summary_cost.py`；内容无关的报告在 `core/summary_cost.py`。前者使用已有 `complete_exchange`、`Passage` 与请求渲染，不增加模型供应商协议或另一条工具执行通道。

## 有界工作与失败语义

每个候选最多计量三个请求，总计最多 96 次计数；每个比较请求序列化后最多 256 KiB，来源地址总字节数先做保守上界检查。计量中按候选和请求让出事件循环。超出比较容量记为 `comparison_capacity`；超过候选数量记入 `deferred`。二者本轮只留引用，下一次重新评估，原文照常竞争预算。此上限约束额外工作，不是假定模型窗口只有 256 KiB。

原文方案可以超出本轮模型预算，只要在比较容量内仍可计量；否则会误拒绝最需要压缩的来源。摘要是否能实际发送，仍由后续正式分配确认。

计数器返回非法值属于框架错误，不能将其当作零成本；取消直接传播，不发布半份报告，不留后台任务，不执行额外模型调用或自动生成摘要。最低原文表示已经由编译器构造并有索引容量限制；比较请求的容量检查在序列化后进行，不宣称任意中间对象从未分配过超过 256 KiB。

## 持久化与兼容

`ContextCompilation` 增加 v17 和 `summary_selection`；v1–v16 序列化不出现新字段，也不允许携带此报告。新报告记录候选数量、推迟数量、实际计数次数、摘要 Artifact 身份、两种请求的 SHA-256、字节数、Token 数和决定。它不保存正文、模型推理或探针答案。

报告必须覆盖全部结构上有效的候选；实际选中的摘要必须有正收益比较。Session Store 同时校验落选候选的 Artifact 是否为本 Run 接受的摘要工具结果。`ConversationView.policy_version` 扩展 `context-compiler/17`，外层 `SessionRequest` 继续按功能采用 v8/v9/v10；摘要 Artifact、工具版本、恢复协议均不变。旧版本没有被重写，旧策略默认行为不变。

## 替代方案与选择理由

- 不将字节压缩比或平均 bytes/token 用作 Token 证明：0102 和本阶段反例均否定这种替代。
- 不在 `compact_context` 工具中拒绝无收益摘要：工具执行时缺少下一次请求的必选背景、恢复保护和完整计数器；同一摘要在不同边界可能具有不同收益。
- 不预测生成成本或未来复用次数：已有正文才能得到可靠表示成本；这一步不能追回已经支付的生成费用。
- 不用实验探针答案指导生产选择：它们只属于离线质量证据。压缩质量、信息完整性与成本是分别验证的条件。
- 不在分配器每个邻域搜索中再次测量所有原文替代组合：当前采用有界的候选准入，保留现有分配器的工作预算。复杂混合表示的最优搜索属于下一阶段研究，不把本次局部比较包装成全局最优。

## 验证与限制

[摘要选择的成本回放与边界](../摘要选择的成本回放与边界.md)记录命令和真实保存候选的结果。确定性验证包括：Token 与字节收益反向、局部来源不能借用无关正文的成本、必要依赖计费、共享范围去重、完整反馈与恢复保护、硬预算、容量降级、旧 Schema、计数器错误、取消，以及推荐 Harness 入口的 SQLite 写入/重开/重复输入去重。

**判断的含义是：在必选背景下，相对于选定同源原文基线，候选表示更便宜。** 它不是最后一次请求或整条任务一定节省 Token 的证明：效用分配还可能加入其他原文；两种原文基线也不是所有混合表示的最优解。`full` 策略专用于诊断时可能同时放入原文与摘要，不以其最终差值宣称自主压缩收益。

计量准确性取决于宿主计数器是否匹配目标模型；完整请求被正确编码不等于 `cl100k_base` 自动匹配所有供应商。此次提供可选择机制，**没有默认启用到 FinScope 或所有宿主**。下一步应校准实际请求 usage，并检验来源重叠、质量保留和最终分配联合优化的收益，再决定是否默认开启。
