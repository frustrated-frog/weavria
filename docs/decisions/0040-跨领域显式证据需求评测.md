# 0040 跨领域显式证据需求评测

## 状态与背景

已实现（2026-10-26）。

ADR 0038 与 ADR 0039 只在 FinScope 周度市场总结上验证了 Evidence Profile、
`broad_or_explicit` / `explicit_only` demand policy 和独立覆盖审计。单一金融任务不能说明
这些机制真正属于通用 Harness：相同结果也可能来自 Prompt 对市场字段的偶然拟合、工具输出
形状相似，或评测器只奖励既有案例。

本决策增加一个完全独立的软件发布就绪任务。它不复用 FinScope HTTP DTO、`/data/*` 输出树、
页面上下文、市场时间语义或答案模板，而是使用嵌套对象与数组组成的发布档案，要求模型判断
是否发布、说明阻塞项和回滚准备。用户可见变更与客户通知只有在用户明确提出时才进入任务，
用来同时检验 `explicit_only` 的负例与正例。

## 决策

### 第二领域仍只通过公开 Harness 契约接入

`apps/release_readiness` 是评测专用应用适配器。它注册一个
`read_release_dossier@1` 只读工具，并声明五个证据面：

- `release.decision`：发布建议与风险等级；
- `release.blockers`：关键失败与阻塞缺陷；
- `release.rollback`：回滚验证、窗口和运行手册；
- `release.user_changes`：用户可见变更，`explicit_only`；
- `release.customer_notice`：通知受众、负责人和模板状态，`explicit_only`。

前三个证据面为 `broad_or_explicit`。所有 JSON Pointer、facet 参数约束和领域名称都留在应用
目录；Core、Runtime 和 Harness 不导入发布概念。

发布档案标为 `private`。默认的公开能力发现策略因此不会暴露它。适配器必须分别提供：

1. 精确允许 `read_release_dossier@1` 进入语义发现的私有发现策略；
2. 对每次规范化参数调用重新授权的私有只读执行策略。

发现许可不是执行授权，工具描述也不是授权依据。确定性基线首先因为缺少显式私有发现策略
而被宿主拒绝；最终实现保留了这次失败所证明的边界，没有把工具改成公开数据来绕过校验。

### 小型权威结果使用有界完整反馈

每个 facet 的强类型输出不足 1 KiB，但通用自适应摘录会按任务词面排序 passage。最初的
确定性闭环只把 `release_id`、版本和来源引用交给下一轮模型，没有保证 `hold`、`PAY-417`
和回滚窗口可见。字段已经进入 Artifact 并不等于模型已经得到这些字段。

适配器因此为每个规范化输入同步构造实际输出，计算精确 JSON 字节上界，并以
`release-dossier-output/1` 声明 `feedback_delivery=complete`。Runtime 在派发前预留完整反馈空间；
实际输出若超过承诺仍会失败关闭。这里选择完整交付是因为结果小且上界可证明，不把相同策略
推广到大型任意工具输出。

### 冻结正负两例与三档协议

`tests/fixtures/release_readiness_v1.json` 以 SHA-256 固定一个脱敏档案和两个任务：

- `core-go-no-go` 只要求发布判断、阻塞项和回滚准备；必须排除两个 `explicit_only` 面；
- `explicit-release-communication` 在相同核心任务上明确增加用户可见变更与客户通知；必须包含
  两个 `explicit_only` 面。

答案评分检查档案中的规范值和禁止泄漏项。发布建议使用权威枚举 `hold`，而不是要求模型必须
说某个中文近义词；这修复了首轮真实运行中“明确写出 hold 和不建议发布却因缺少‘暂缓’而
判错”的词面假阴性。

真实模型探针沿用 ADR 0038 的三档协议：

- `off`：不给规划器 Evidence Profile，不运行覆盖审计；
- `profile`：只提供版本化证据面与 demand policy；
- `model`：再增加独立义务审计、主机引用校验和最多一次完整规格修复。

报告同时记录计划证据面召回/精确率、required fields 召回/精确率、完整需求契约是否精确、
`explicit_only` 泄漏、覆盖报告、主机 adjustment、repair、Need 状态、答案、工具轨迹、Token
与时延。完整需求契约除了字段与生产能力，还比较 `source` 和 `freshness`，避免字段命中掩盖
时间语义错误。

## 执行与验证结果

### 确定性跨层基线

`tests/release_readiness_app/test_cross_domain_baseline.py` 在正式 `SessionEngine` 路径运行两例。
冻结解释器与独立覆盖声明不是 Agent 能力证据，而是机制上界：两例覆盖报告均充分、无修复和
主机 adjustment；负例只执行 `decision`、`quality`、`operations`，正例再执行 `changes` 与
`communications`；所有 Need 满足，完整反馈中的关键事实到达最终模型请求。

### 2026-10-26 真实模型单次跨域消融

使用 `deepseek-flash`、温度 0、JSON mode、32,768 Token 窗口、4,096 执行输出上限、8,192
理解输出上限和 `reasoning_effort=none`。每档各运行两个新会话，每个正负案例一次。下表是
两例合计，不是成功率估计：

| 模式 | Runtime 完成 | 字段精确 | 完整需求契约精确 | 显式面泄漏 | 答案规范值通过 | Provider 调用 | Provider Token | 端到端耗时 | 工具调用 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| off | 2 / 2 | 0 / 2 | 0 / 2 | 0 | 1 / 2 | 10 | 58,186 | 35.14 秒 | 11 |
| profile | 2 / 2 | 2 / 2 | 0 / 2 | 0 | 1 / 2 | 8 | 45,665 | 24.30 秒 | 8 |
| model | 2 / 2 | 2 / 2 | 0 / 2 | 0 | 2 / 2 | 10 | 62,244 | 34.27 秒 | 8 |

`off` 的核心负例漏掉 `/quality/critical_failures` 并增加 `/readiness/rationale`，显式正例又增加
测试通过率和 rationale；两例都不是冻结字段契约。它还在核心负例重复读取三个 facet，最终
产生 6 条工具记录。`profile` 和 `model` 的四个自然样本都精确选择对应证据面：负例没有把
变更或通知提升成义务，正例完整选择五个面。`model` 两例的独立审计均为 `sufficient`、
repair count 为 0、证据面召回与精确率均为 100%，最终报告没有主机 adjustment。

这组单次样本复现了 FinScope 中的结构结论：适配器提供的语义证据地图是本轮字段精确改善的
主要观测差异；自然样本中的审计器没有触发修复，其额外价值是独立分解、主机校验、拒绝门禁
和可持久化证明。`model` 的答案与 `profile` 的答案差异可能来自模型非确定性，不能据两例把
答案收益归因给审计。

### 有界修复诊断

另对显式正例运行一次 `forced-broad + model`，不计入上表。宿主先注入一项合法但无字段的
宽泛 `stable` 需求，再让真实模型审计、修复和复审。一次修复后：

- 五个证据面和 11 个 required fields 全部精确，repair count 为 1；
- 完整需求契约精确，五个 Need 全部 `satisfied`；
- 五个 facet 各读取一次，完成决策为 `accept`，答案规范值通过；
- 3 次理解调用加 3 次执行调用，共 39,591 Provider Token，端到端约 19.46 秒。

它证明当前模型可以沿正式修复路径闭合第二领域任务，但初始弱规格是人为注入的，不能计入
自然规划成功率。最终充分报告没有 adjustment；现有持久 Frame 只保留最终报告，因此本次数据
不声称初始不足究竟由模型直接识别还是由某个中间主机降级单独造成。

### freshness 是独立失败维度

三档自然规划的六个规格都把冻结档案需求声明为 `freshness=current`。结构解析器可以证明字段
存在，却不能仅凭 `generated_at` 证明这份 Fixture 是调用时最新的权威版本，因此所有自然运行
的 Need 都停留在 `partial`，完成策略在有界校验后返回 `unverifiable`。这不是应当抹平的测试
噪声：字段覆盖充分和覆盖审计充分都不能证明时效性。

有界修复诊断保留了初始 `stable` 语义，Need 因而全部满足。这说明下一步若要让真实发布源支持
`current`，必须由拥有源语义的适配器定义可验证的快照版本、获取时间或最大陈旧窗口，再由
应用 Evidence Extractor 判定；不能因为输出里有时间字符串就无条件标记 freshness 有效。

## 备选方案与取舍

- **继续扩写 FinScope Prompt**：不能提供跨领域证据，故停止对单一任务调参。
- **把发布字段写入 Harness**：会破坏领域无关性，也无法推广到第三种工具形状，故所有语义留在
  适配器 Profile。
- **把私有 Fixture 工具改为 public**：能让默认发现策略通过，却混淆数据敏感性和开发便利，故
  使用应用显式发现策略与独立执行策略。
- **始终完整注入整个档案**：会让负例无法观察最小证据范围，也绕过工具和 Need 演进，故按 facet
  获取；仅对单次小结果作有界完整反馈。
- **把 `generated_at` 自动视为 current**：时间字段只能证明一个声明值存在，不能证明来源最新，
  故保持失败关闭。
- **用嵌入相似度评价答案**：会引入另一非确定模型并模糊权威值错误；当前使用明确规范值，同时
  记录其词面局限。

## 关键不变量

- `explicit_only` 不能由能力目录或候选规格自我授权；原始任务必须提出对应语义需求。
- 负例和正例共享同一工具、Fixture、预算和执行指令，只改变用户明确范围。
- 私有能力的发现与具体调用授权相互独立，均失败关闭。
- 完整反馈必须在派发前有版本化字节上界，不能以“小概率超预算”替代证明。
- 字段精确、覆盖充分、Need 满足、完成验收和自然语言答案是不同层次，报告不得互相冒充。
- 实验报告不保存请求正文、供应商原始响应或凭据；密钥只从进程环境读取。

## 当前局限与下一步

本轮每档只有两个任务、每例一次，不能估计成功率、方差或 Provider 成本分布。正负例虽然跨越
金融与软件发布，仍只有两个应用；`explicit_only` 的自然语言需求判定仍来自低信任模型。工具
参数约束尚未传播成派发时独立 Policy，最终答案评分也只验证冻结规范值，不验证所有推理质量。

下一小步不应继续为这两个 Prompt 调参。应先设计领域无关的 temporal evidence contract：明确
“稳定事实”“截至某时点的快照”和“调用时最新”分别需要什么来源元数据、适配器证明与失败语义，
再用一个真实可版本查询的来源验证。只有适配器能证明当前性时，才新增 Release Evidence
Extractor；否则保持 `unverifiable` 是正确结果。
