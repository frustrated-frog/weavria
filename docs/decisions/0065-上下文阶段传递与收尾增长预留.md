# ADR 0065：上下文阶段传递与收尾增长预留

- 状态：已采纳并实现
- 日期：2026-10-31
- 源码基线：`cdfdf1b`
- 范围：Runtime 构建端口、Session 适配器、模型视图增长证明、编译报告及发送留证
- 前置：[ADR 0053](0053-父预算内的证据感知收尾.md)、
  [ADR 0064](0064-模型工作视图的生产接入与增长预算.md)

## 问题与本次能力

模型工作视图接入后，预算触及预留和证据提前就绪两条收尾入口的行为不一致。
前者先执行 `prepare_finalization()`，后者先执行 `prepare_turn()`，再由 Runtime
判断需要收尾。适配器却用上一次准备留下的 `_finalizing` 决定投影、历史检索和下一轮预留。
于是可能发送带 FINALIZATION 指令、但 `phase=decision` 的请求。

另一个问题独立存在：即使视图正确标为 synthesis，编译器仍预留完整工具目录、需求进度和
来源版本的探索增长。删除收尾指令中的工具目录反而增大了“最大说明减当前说明”的差额，
省下的空间又被预留。必需证据可能因此无法交付。

本次让阶段成为每次构建的显式宿主输入，并按该阶段允许的后续变化计算增长。
修复领域无关，不改变应用规则，也不扩大模型窗口、工具权限或完成验收范围。

## 一次请求如何流转

1. Runtime 沿现有最终化策略判断当前任务是否可以收尾。证据就绪、资源预留、工具预算和
   纠错停滞仍共用原来的状态机；没有新增另一套阶段状态。
2. `_build_context()` 将 `phase=decision/synthesis` 传给 `build_control_request()`。
   这既覆盖普通准备后的提前收尾，也覆盖从已提交快照准备的预算收尾。
3. Session 适配器用这个调用局部值生成视图、选择是否检索历史，以及是否预留下一轮工具
   反馈。不再缓存 `_finalizing`，不解析指令字符串。Projector 返回的阶段必须与宿主输入一致。
4. Compiler 根据视图阶段生成 v2 收据，联合计算实际请求、增长预留和控制反馈预留。
   编译后再检查实际交付；提前收尾预检失败时，Runtime 以 decision 重新构建。
5. 只有通过实际交付检查后，Runtime 才接受 `FinalizationStarted`。请求留证事务同时
   核对视图来源、收据和 Runtime 的实际最终化状态，再允许 Provider 发送。
6. 收尾候选仍经过完成与发布检查。收到 `CompletionRepair` 时继续用同一语义头和
   synthesis 视图重建请求，使用独立控制反馈空间。取消会等待清理，steering 使旧任务版本失效。

预编译 synthesis 不等于已经接受收尾。适配器不能把一次尝试安装成跨调用阶段，
否则预检失败后会漏掉普通决策需要的检索和预留。

## 容量上界与阶段预留

以下容量声明保持不变：

- 同一任务修订下的稳定定义、工作标识、投影器版本；
- `max_progress_bytes`、`max_instruction_bytes`；
- `maximum_bytes` 对完整进度、64 位来源计数和阶段长度的上界。

记当前视图编码为 V，当前指令的 JSON 编码为 I，完整容量分别为 Vmax、Imax：

| 阶段 | 本次视图增长预留 G | 下一轮工具反馈预留 | 控制反馈 |
| --- | --- | --- | --- |
| decision | `(Vmax - V) + (Imax - I)` | 按已有配置保留 | 保留 |
| synthesis | `0` | `0` | 保留 |

收尾中的 `G=0` 有严格前提：同一任务版本已进入 Finish-only，不能继续调用工具、扩展目录、
恢复新证据或更新语义快照。它不表示任务视图容量为零，也不缩小公开容量声明。
完成纠错只改变有界 control 通道；现有 `CONTROL_FEEDBACK_BYTES` 继续覆盖其增长。
Session 包络的来源计数余量也继续保留。任务修订重新构建视图，不让旧收尾预付任意新任务。

Compiler 继续分别证明：

- 规范请求字节 + 控制余量 + 下一轮预留 + G 不超过规范字节预算；
- 实际 BPE 输入 Token + 同样的保守余量不超过输入窗口；
- 实际 HTTP 字节 + 两倍未知字节余量不超过传输预算。

工具派发前的 `reserve_feedback()` 仍使用完整探索增长证明；Runtime 本身禁止收尾派发工具。
本次没有放宽这一边界。v5 未知反馈的整包字节到 Token 上界也保持原来的保守策略。

## 契约版本与兼容

- ControlRequest v3/v4/v5、TaskModelView v1 和外层 SessionRequest v5 的字段与序列化不变。
- 新编译输出使用 **ContextCompilation v10 / context-compiler/10**。
- 新的 **TaskModelViewReceipt v2** 显式记录 phase；保留完整容量字段，增长字段记录本阶段
  预留。synthesis 收据不能宣称探索增长。发送事务重新计算收据，并核对实际 Runtime 阶段。
- v9 只接受 v1 收据，v10 只接受 v2 收据。旧收据不输出新增 phase 字段，仍按原来的
  完整增长公式读取和核验。两种版本不能混用，不自动重写已保存报告。
- SQLite 表结构不变，无需数据迁移；旧代码不能读取 v10，不能把新报告伪装成 v9。
- `BaseControlContextBuilder.build_control_request()` 公开签名新增必需关键字
  `phase: Literal["decision", "synthesis"]`。自定义该端口的实现需要接收并使用宿主阶段，
  不能从 base 指令或前次准备推断。旧 `ControlContextBuilder.build_control()` 和恢复端口
  的签名保持不变；Session 的兼容入口显式转交 decision。

## 为什么选择这个设计

阶段已经存在于 Runtime 最终化判断中，再加一个可变适配器阶段会产生两个状态来源。
显式逐次传递能够自然处理提前收尾、预算收尾及预检回退，成本只增加一个调用参数。

不能把 synthesis 的最大容量字段直接改小：这些字段承担同一任务修订下的稳定布局约束，
在回退决策时仍然有效。也不能直接取消所有预算余量：控制反馈仍会在纠错时增长。
因此保留容量声明，只改变可审计、有版本的阶段预留策略。

没有采用临时提高上限、解析 FINALIZATION 文本、额外模型调用或第二套阶段状态机。

## 回归与可复现验证

```bash
uv run pytest tests/harness/test_task_model_view.py tests/context/test_phase_budget.py
uv run pytest tests/runtime/test_finalization.py tests/harness/test_session_preparation.py
```

新增验证包括：

- 在修复前复现：总模型调用上限 5、收尾预留 1，读一次后提前就绪，第二轮错误地仍为
  decision；修复后与总上限 2 的调用预留入口一致，保持全部需求、跳过历史检索、释放下一轮预留。
- 在真实编译后注入一次交付不足，验证预检回退后恢复 decision、历史检索及完整增长证明。
- 一次收尾候选被要求纠正，下一轮实际携带最大长度 guidance；语义视图保持不变，控制余量
  仍存在，随后能够完成。投影器不能自行覆盖宿主阶段。
- 在 synthesis 模型调用期间取消或 steering，验证清理完成、旧候选不发布、新视图绑定新修订。
- 用 1/12 个真实 TypedTool 描述构造目录容量，在 12K/64K 窗口及紧/宽字节限制下检查分配。
  普通决策继续预留增长，紧预算的大目录不能因此被错误准入；收尾保持必需原文完整交付。
- 分别将 Token、规范字节、HTTP 字节收紧到实际收尾请求加控制余量附近；新策略可以编译，
  原完整增长公式会超限。替换为最大 guidance 和八项 issue_codes 后，实际三种计量仍符合预算。
- 使用真实 SessionEngine、SQLite、工具与 `policy=full` 保留一个超过 16K 的必需值，
  先测宽预算，再按实际报告求窄界。两次均执行同一读操作和两轮固定模型动作；窄界能完整
  交付，而旧增长公式会越界。该回归明确选择 full 分配策略，不能推断默认覆盖策略总会选择完整大字段。
- v9/v1 报告和收据往返序列化不变，v9/v2、v10/v1 混用被拒绝。

这些测试证明阶段接线、可行性和执行不变量，不能证明真实模型回答质量、规划效率或事实正确率。
完整 Session 回归使用固定 FakeSessionProvider；其 completed/unverified 也不意味着答案经过独立事实核验。

## 当前局限与下一小步

本次没有默认启用模型工作视图，没有增加记忆召回、增量证据投影、写操作或 Resume。
大目录检索和 v5 反馈充分界的保守性仍是已有边界。

下一小步先使用冻结工具数据、相同模型配置与预算进行有限真实任务 A/B，观察无效调用、
反馈拒绝、实际交付和任务结果；随后建设必要证据增量更新，将其与可选进度分析分离。
未配置真实模型时不把确定性回归当成 A/B 已完成。
