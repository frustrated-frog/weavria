## 问题与本轮交付

后续 [ADR 0064](0064-模型工作视图的生产接入与增长预算.md) 已完成显式启用的生产接线。
本文保留当时的原型、测量和接入设想；实际增长证明、摘要损失边界及限制以 ADR 0064 为准。

TaskFrame 保存任务解释、编译后需求、目标、覆盖审计与版本。当前整个 TaskObservation 会进入
模型请求，存储必须保留的内容由此变成每轮模型都要消费的内容。扩大包络不能解决信息是否必要。

本轮完成源码级设计、候选投影与冻结输入的结构测量。原型位于 labs/task_model_view_design.py，
不被生产包导入。Core、Runtime、Provider、请求及持久化 Schema 均未改变，不能据此宣称
TaskModelView 已上线或真实任务效果已经改善。

## 源码路径与关键耦合

| 位置 | 当前行为 | 接入必须维持的承诺 |
| --- | --- | --- |
| core/model_io.py::TaskObservation | v1/v2 承载 task-frame/1–6 | 完整观察继续供宿主检查 |
| sessions/engine.py::_refresh_semantics | 提交 Frame/Ledger 后安装缓存 | 只投影同一份已提交状态，保留取消一致性 |
| runtime/agent.py::_build_context | 完整观察进入上下文构建 | 投影发生在编译前，不在 Provider 发送前裁字段 |
| context/compiler.py::compile | 联合选择历史和原文 | 选择、计量和报告针对同一实际请求 |
| runtime/agent.py::_admit_batch | 观察参与反馈预算和进度判断 | 宿主判断用完整状态，模型预算用模型表示 |
| runtime/agent.py::_verify_completion | CompletionContext 读取完整观察与账本 | 不把精简视图当完整 Frame 解析 |
| sessions/store.py::prepare_request | 核对摘要并保存实际 SessionRequest | 留证请求与 Provider 输入一致 |
| models/openai_compatible.py | Counter 与 Provider 共用请求体构造 | Token、字节和发送内容继续一致 |

另外两个接入陷阱已经从源码确认：

1. ControlRequest 当前是 v3/v4，SessionRequest 外层是 v5。Provider 和 Compiler 中仍有
   `schema_version == 4` 的恢复能力判断。增加请求版本时，不能粗暴改成 `>= 4`，否则可能
   把未开启恢复的新格式请求当成允许 RecoverContext。
2. request_byte_ceiling() 把观察当作稳定前缀，只允许 history/feedback/control 改变。新的
   需求进度会随工具结果增长，不能直接套用该假设，否则当前请求较小也无法证明下一轮能交付。

## 一份宿主状态，两种消费路径

```text
已提交的 TaskFrame + NeedLedger + SemanticVersion
    ├─ 宿主：版本、权限、进度、完成验收、追溯
    └─ 确定性 TaskModelView
          → 上下文编译与证据原文选择
          → 统一计量、准入、留证、发送
```

Core 只定义领域无关的视图信封、来源版本和收据，不解释金融、发布检查或 NeedStatus。
Harness 投影自己的结构状态。投影同步、无 I/O、不调用模型，不再建一套任务状态机。
完整 Frame 与简版不得同时全量发送；模型视图不能反过来授权工具、满足需求或接受完成。

### 信息保留与省略

| 信息 | 第一版处理 |
| --- | --- |
| 原始目标和约束 | 仍由独立 TaskInput 携带，权威性不变 |
| 模型解释的目标、路由、已接受结果 | 保留 model_inference 标记 |
| 请求目标与已解析身份 | 保留关系与来源，不猜别名，不增加领域映射 |
| 必需需求、依赖、完成模式、字段、新鲜度 | 全部保留，不做 top-k 或静默截断 |
| 需求状态、缺失字段、获取状态 | 来自同一账本，区分未查、失败、空结果与不足 |
| 冲突和过期 | 必须呈现，不因“只保留未完成项”而丢失 |
| 澄清 | 保留已选问题、剩余歧义和结果，不复制整棵候选与权重历史 |
| 完成义务 | 保留交付要求，原义务仍由宿主验收 |
| 覆盖审计、匹配计划实现、旧判断历史 | 保留在宿主，不默认反复发送 |
| 页面信息 | 保留必要导航信息及 trust，不提升成证据 |
| 事实正文 | 仍由 Compiler 从原始 Artifact/历史交付，不能由账本状态杜撰 |
| 工具范围 | 仅呈现当前宿主范围，可见性仍不是授权 |

原型暂时保留完整 bindings，先验证损失边界。生产版应把稳定定义与动态进度拆开，避免把整个
binding/probe 列表变成另一个膨胀的 Frame。

普通决策和收尾由明确阶段参数区分，不从 instructions 字符串猜测。收尾保留所有必需需求和
限制，不呈现探索动作；真正的 Finish-only 约束仍由 Runtime 与 FinalizationStarted 执行。

### 已取得不等于已交付

Ledger 中有 binding，不证明正文进入本次请求；SATISFIED 也不是事实核验等级。模型工作
上下文由任务视图、控制反馈和实际原文共同组成。Compiler 选择内容后继续生成
EvidenceDeliveryManifest，由原 FinalizationPolicy 检查实际交付。

不能把含最终请求摘要的 Manifest 塞回同一请求，形成摘要自引用；也不能先宣称已交付再裁正文。
第一版不在任务视图中复制最终 Manifest 摘要或自行生成 delivered 标记。更细的模型可见交付
提示需要独立的编译后固定点设计和验证，不混入第一版投影。

## 首个生产切片的接入方案

1. 建议增加独立 TaskModelView 信封和 ControlRequest v5；新版本中模型视图与完整观察互斥。
   旧 v3/v4 保持原序列化，不增加空字段、不重写旧请求。
2. v5 显式表达恢复是否启用；旧版本通过兼容属性保持原语义。统一修改 Provider、Compiler
   等请求版本判断，不让格式版本自动成为能力授权。
3. 现有 build_control 散参接口会重建请求，可能遗漏新字段。采用接收完整 base 请求的版本化
   构建端口，保留旧端口兼容路径，不在 Provider 做补丁式替换。
4. Runtime 保留完整观察和 semantic_state，向投影器显式传递当前任务、阶段和范围；模型
   请求使用投影。Completion、Progress、Intervention 继续读宿主状态。
5. ContextCompilation 使用新内层版本记录投影版本、源状态版本和摘要、视图与请求摘要。
   Session 留证时核对已提交语义头；旧版本视图不得发送。外层 SessionRequest 结构不必仅因
   内层升级而改变，但旧读者会拒绝新内层，必须明确升级。
6. SessionEngine 默认关闭投影，通过公开组合启用。无 TaskFrame 的普通工具路径仍依靠
   TaskInput 工作，不要求业务证据画像，也不强制同时启用理解、覆盖、恢复和记忆。

协议、投影、编译、发送留证和宿主验收需要作为一个完整切片接通，不能只发布无人消费的类型。
应用中把模型输入的 task_observation 当 Frame 解析的 Fake Provider、说明和测试也需同步迁移。

### 下一轮增长的准入证明

目标、需求定义和依赖组成稳定部分；状态、版本和证据联系组成动态部分。后者采用有限结构：
枚举状态、已知缺失字段集合、有界失败摘要与来源联系，不复制任意异常文本、完整审计或事实正文。

已知定义按实际 BPE 计量；未知反馈和动态进度按声明的编码上界计量。布局版本、定义摘要与增长
上界必须绑定到准入证明，不能把当前进度当固定前缀。控制字符、Unicode、转义与多工具结果共同
增长都要进入验证。

Steering、任务定义或能力代际变化使旧布局证明失效，需要重新构建准入。如果普通工具反馈会
触发新的必需定义或工具目录增长，还必须处理其与“下一轮最低反馈可交付”的关系，不能等执行后
才用超预算掩盖证明失效。生产切片必须落实这一边界；当前初始状态探针没有解决它。

## 离线结构探针与结果

```bash
uv run python -m labs.task_model_view_design
uv run pytest tests/test_task_model_view_design.py
uv run pyright labs/task_model_view_design.py
```

使用既有冻结数据：四个普通工具任务、两个软件发布就绪任务。真实 TaskAwareSessionPreparer
准备状态，解释器读取固定规格；不调用模型、不执行工具、不提交实际 Work。软件场景沿用已有
私有目录发现策略，没有增加 FinScope 规则。报告记录数据集摘要、分词器名称和 tiktoken 版本。

cl100k_base（tiktoken 0.14.0）测量如下，**只比较任务组件**，不是完整 SessionRequest、HTTP 请求体、usage、
费用或任务正确率：

| 冻结样例 | 原任务组件 Token | 候选 Token |
| --- | ---: | ---: |
| direct_identity | 437 | 243 |
| document_lookup | 632 | 484 |
| ambiguous_action | 1307 | 275 |
| core-go-no-go | 1153 | 969 |
| explicit-release-communication | 1562 | 1389 |
| 合计 | 5091 | 3360 |

五个成功准备样例的任务组件 Token 减少约 34.0%，UTF-8 字节由 17570 降至 11905。收益不均：
澄清候选历史较多的样例变化最大；发布就绪样例仅约 11%–16%。不能推出完整请求降低 34%，
也不能证明长任务、积累多条证据或真实模型已经获益。

第六个 current_time 在投影前准备失败：默认 CapabilityResolver 返回空目录，冻结规格需要
read_clock。失败保留在 preparation_failures，不计入投影分母，也不靠预标记工具、扩大权限或
删除样例制造成功。这是普通接入能力的独立观察，不属于投影收益或投影回归。

后续 [ADR 0063](0063-任务准备的有界能力目录与执行隔离.md) 已修复小目录中词法预筛选与
执行范围的耦合；当前探针六例均能准备。本节保留当时五例的原始测量，不能将新分母套用到
旧结果，也不因此宣称模型工作视图已经接入生产。

原型验证确定性、输入不变、需求身份完整保留、动作呈现不扩张、混合任务/证据/进度版本拒绝。
尚未验证已积累证据时的大小、目标别名、矛盾、恢复、反馈增长和完整交付链路。

本轮原型测试 5 项通过；全仓 Ruff、格式、Pyright 和 Pytest 通过，共 1116 项测试。

## 生产切片的完成标准

- Fake Provider 确认模型只收到投影，宿主仍拿完整 Frame；旧请求与回放兼容。
- Compiler、Counter、Mock Transport 和 SQLite 快照证明计量、发送、摘要一致。
- 同一模型脚本与工具事实下，目标约束、覆盖验收、缺失说明、发布拒绝与权限不被削弱。
- 普通工具、无任务准备、部分证据、收尾、恢复、动态能力和可选组合均有明确行为。
- 取消、版本变化和持久化失败不发送旧视图，延续 ADR 0060/0061 的接受边界。
- 准入证明覆盖下一轮动态视图增长，不只证明当前请求较小。
- 冻结任务与配置后记录完整请求成本，再显式启用真实模型比较无效调用和交付质量，保留无收益
  情况，不以本轮组件测量代替能力评测。

第一版不引入 LLM 摘要、业务规则、新规划 Agent 或平行的简化 AgentLoop。接通并验证后，再
分离必要证据投影与可选进度分析，随后适配已有记忆召回。
