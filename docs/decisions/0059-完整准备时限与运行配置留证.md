# ADR 0059：完整准备时限与运行配置留证

## 背景与问题

对 main `141cd0e` 的源码复核确认两个遗漏：

1. ADR 0057 的探索子期限位于 `await TurnPreparer.prepare_turn()` 之后，只约束上下文构建。
   Session 的语义刷新、历史读取仍可能消耗全部父时间；工具结算后的进度评估也会刷新语义，存在
   相同问题。仅限制模型和工具请求不足以保住已声明的收尾资源。
2. 服务曾显式使用收尾预留 2 次 / 30 秒，但 `.env.example` 仍是 0 次 / 10 秒。仅记录一次
   请求成功，无法判断后续服务是否使用同一组运行设置。

## 决策一：准备链路共享探索截止时间

启用收尾预留时，Runtime 在调用普通 `TurnPreparer` 之前建立子期限，覆盖本轮语义刷新、历史
读取、视图安装与上下文编译。工具反馈结算后的可选进度评估也使用同一探索截止时间。

- 子期限到达时，取消并等待当前操作清理；只处理本作用域产生的超时。
- 依赖自己抛出的 `TimeoutError` 保留依赖失败分类；外部取消继续传播。
- 超时的进度评估不发布部分结果，成功结算的工具记录继续保留。
- 任务版本已改变时，不安装或使用旧准备结果，重新进入当前版本的决策边界。
- 父期限、调用次数上限、完成检查与应用发布规则保持生效。

`TurnPreparer` 的接口不变，增加可选伴随协议 `FinalizationPreparer`。其同步方法
`prepare_finalization(task)` 只允许从已提交状态投影视图，不进行 I/O、语义刷新或新的授权，
没有安全快照时返回 `None`。Runtime 重新校验预算、任务版本、能力上限与 epoch。普通准备器
没有此协议时，只允许复用同一任务版本已安装的准备；首次准备尚未完成或 Steering 后只有旧版本
状态时，明确终止，不能以“必须收尾”为由拼接答案。

Session 适配器缓存最后成功准备的历史视图和版本。收尾投影使用当前版本已提交的语义快照，跳过
可选历史检索并释放下一次工具反馈预留。语义更新只有在存储提交完成后才替换本地缓存，包括澄清
计划；取消尚未提交的刷新不能改变完成依据。上下文仍可按需读取权威 Artifact，Trace 和成果仍
必须持久化，因此本决策不承诺收尾完全无 I/O。

一次请求的关键流程如下：

1. 普通回合在探索期限内刷新状态、读取历史并编译请求。
2. 工具反馈先按原协议结算；剩余探索时间允许时再做进度评估。
3. 后续准备到达子期限，取消并等待清理，检查当前任务版本。
4. 从已提交快照投影收尾上下文，由原 FinalizationPolicy 判断能否交付。
5. 重新请求 Finish 候选并经过全部完成检查；不能交付时保留明确失败终态。

## 决策二：推荐配置与逐次运行记录一致

FinScope 的启动示例与 `.env.example` 明确推荐收尾 2 次 / 30 秒，理解和执行的推理参数都为
`none`。这些设置只属于宿主策略。通用 Runtime 和无环境变量的 FinScopeSettings 保留关闭预留
的兼容默认值，显式设置调用预留为 0 可运行原基线。环境文件需要启动脚本加载，不自动生效。

应用工厂将实际传给 SessionEngine 的 RunLimits、ContextCompilerConfig、历史和恢复配置，
连同允许记录的模型设置、Provider 类型与策略版本构造成运行摘要。摘要使用明确字段名单，排除
密钥、URL、文件路径、任务内容和模型响应。规范化 JSON 的 SHA-256 形成配置指纹，启动日志与
新 Run 保存同一份摘要。

SessionEngine 新增可选 `configuration_metadata`，在构造时校验并深拷贝为有限 JSON。它只用于
诊断，既不进入 Prompt，也不参与授权和完成决策。调用方负责剔除私密信息；通用框架不理解
FinScope 的字段。设置该参数的新 `runs.config` 使用版本 5，增加同名字段；未设置时继续使用
原版本 1–4。旧记录不重写，数据库表和事件 Schema 不变；重复输入沿用原 Run 的原始配置。

指纹只证明被记录的宿主设置相同。它不记录服务 URL，也不证明模型版本、后端数据、代码或注入
Provider 的内部参数相同，更不能证明回答事实正确。

## 备选方案与取舍

- 增加总时长：会掩盖预算边界遗漏，无法保证准备不会继续耗尽父期限。
- 超时后重新执行完整准备：可能再次阻塞，且会让收尾依赖未提交的新语义结果。
- 无条件使用旧缓存：Steering 后可能回答过时任务；当前方案要求同一任务版本并保留原验收。
- 将所有准备器升级为新的强制接口：会破坏现有扩展；可选伴随协议保留兼容且将安全边界写明。
- 将整个 Settings 序列化或仅散列：会泄露凭据或把秘密变成指纹材料；应用显式名单更容易核查。
- 只打印启动参数：无法关联单次请求，重启后也无法定位该 Run 的实际设置。

## 验证与证据强度

领域无关回归先在旧实现上复现：工具完成后，第二次 TurnPreparer 永久等待，原结果为
`budget_exhausted`；修复后同一父预算内取消准备并交付 `unverifiable`，工具没有重复执行。

确定性测试进一步覆盖：

- 首次准备超时无快照、Steering 使缓存版本失效，均不请求旧任务答案。
- 外部取消发生在准备中时，资源清理完成且不触发收尾。
- 依赖主动抛出的超时仍归类为依赖失败，不误认为探索预算已到期而发布答案。
- SQLite 历史 head 变慢时，可以使用已提交且包含新工具证据的语义快照收尾。
- 语义刷新算出候选但尚未提交时取消，不将其作为成果依据，不伪造进度。
- 启动日志与真实保存的 Run 配置一致，外部修改元数据不会改变快照，重复输入不会重写配置。
- 密钥、带凭据的 URL 和本地路径不进入摘要或指纹材料；两阶段推理、预留或策略改变会改变指纹。

运行方式：

```bash
uv run pytest tests/runtime/test_finalization.py tests/harness/test_session_preparation.py \
  tests/sessions/test_engine.py tests/finscope_app/test_runtime_profile.py \
  tests/finscope_app/test_server.py
```

本轮验证的是执行不变量与配置可比性，没有重新运行付费真实模型实验，不能据此宣称真实任务
成功率提高。异步取消要求依赖合作；同步阻塞或吞掉取消的第三方代码仍可能延迟清理，父期限不
构成抢占式隔离。Artifact、Trace 或数据库故障仍可能阻止交付。

## 后续边界

本次没有引入 TaskModelView、记忆注入、逐句事实核验或 Checkpoint/Resume。下一步应独立设计
确定性的模型任务投影，避免把完整内部状态直接暴露给模型，再以固定任务集比较表现和成本。
