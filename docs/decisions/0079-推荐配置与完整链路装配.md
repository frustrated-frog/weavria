# 0079 推荐配置与完整链路装配

状态：已实现，2026-11-01。承接 ADR 0075、0077、0078。

## 问题与范围

统一生命周期已经存在，但普通应用仍需手工构造任务理解器、理解请求编译器、模型工作视图、历史检索、原文恢复以及记忆提取和审阅。调用 `AgentHarness` 并不意味着这些可选组件已经配套。接入代码容易漏装，局部测试也不能证明所有组件同时开启时能够协作。

本轮目标是把现有成熟度不同的组件接入同一条真实执行链，明确普通接入方负责什么、框架负责什么。没有新增算法、第二个调度器或应用专用流程；也不以一套配置的存在宣称模块已经达到成熟框架水平。

## 决策

### 推荐配置解析到原有对象

新增不可变 `HarnessConfig` 和 `AgentHarness.from_config`。配置只声明能力选择及原有额度，不创建另一份运行状态。工厂生成原有组件后调用 `AgentHarness` 构造函数，所有请求仍执行现有 `send → SessionEngine → AgentLoop`。

- 默认接通任务理解、TaskModelView、动态能力选择、历史选择和当前 Run 原文恢复。
- `working_records=True` 接通工作记录工具、归约、上下文聚焦和工具选择；依赖任务理解，非法组合在启动前拒绝。
- `memory_write` 为 `off / basic / fact_sets / conditions`，复用 `HarnessMemory.from_model` 成套选择提取、审阅和准入。默认不写长期记忆。提供 Memory 存储和作用域而保持 `off`，表示只读召回；不提供则禁用记忆。
- 完成验收、工具 Policy 与调度仍通过公开扩展点注入，不复制其实现。

启用表示组件可以在所属阶段参与，不要求每条消息都执行所有组件。直接回答不必调用工具，也不必记录工作笔记；记忆形成可能产生零候选或拒绝全部候选。

### 宿主提供资源和授权

模型连接、认证、业务工具、存储路径、MemoryAccess 与 MemoryScope 继续由宿主提供。执行使用 `SessionModelProvider`，任务理解使用 `ModelProvider`；宿主可以让二者共享 HTTP 连接，但框架不推断供应商或读取应用的环境配置。

任务理解需要 `reasoning_model` 和匹配的 `reasoning_counter`。输出预算使用该计量器自己的输出上限；输入窗口采用配置中声明的共同允许窗口。如果执行与理解用不同模型，宿主应选择二者都支持的窗口。记忆可使用独立 `memory_model`，未提供时使用 reasoning_model。不开启任务理解时，单独提供 memory_model 即可形成记忆，无需构造理解组件。

这没有新增跨角色的总 Token / 调用次数预算。既有父请求期限继续覆盖前置追赶、Session 和后置形成；记忆仍受自己的阶段策略和请求限制。配置 ID 用于追踪配置身份，不代替具体模型版本、请求收据或可复现实验清单。

### 保留高级构造入口

直接 `AgentHarness(...)` 仍允许替换理解、选择、投影等策略。`from_config` 中的 HarnessMemory 只接收存储与作用域，若已塞入形成组件则拒绝，避免显式开关与已注入组件相互覆盖。需要自定义形成组件时使用底层入口。

没有选择通用依赖注入容器或动态插件总线：当前依赖图固定，显式构造更容易看清生命周期和调用顺序。也没有强制所有调用迁移到工厂；研究和对照仍需要低层策略端口。

## 记忆处理结果

`MemoryUpdateReport` 增加 `extracted_candidates / admitted_candidates / rejected_candidates / deferred_candidates`。这些数值来自本次成功返回的形成 Job 与准入计划，不增加模型调用，也不重新扫描数据库。

`completed` 表示游标追平，不等于形成了新记忆；候选数与准入数可帮助接入方区分零提取、拒绝与准入。准入候选可能对应更新或已有事实，不是新增数据库行数。发生提交与取消竞争时，报告仅表示调用方确认的下界；重试按数据库游标继续，可能计数为零。前置与后置计数分别保留，不冒充累计统计。

未改变持久化 Schema。配置元数据版本为 `unified-harness/5`，增加 `configuration_id`；结果报告是运行期返回值的兼容扩展。

## 一次组合执行

`tests/memory/test_configured_harness.py` 使用推荐工厂、真实 SQLite、真实任务理解与记忆模型适配器，仅替换模型端口的非确定性输出：

1. 接受用户约定；提取器基于真实事件来源生成候选，审阅和准入产生持久记忆。
2. 新会话召回该约定，理解请求以低信任数据携带它，执行模型也获得相应 ContextBundle。
3. 来源工具失败后，Need Ledger 与动态选择提供备用工具；备用返回约 90 KB 结果，成果卸载后仍可读取。
4. 模型提出有来源的工作记录；归约后的状态进入 TaskModelView，需求和引用进入后续上下文选择。
5. RecoverContext 精确回取尾部；read_artifact 按现有首页/续页协议读取成果。两者共用权威 Artifact，没有重新执行来源工具。
6. Run 完成，后置形成消费新的用户事件但产生零候选。同 input_id 重试不会重跑理解、执行模型或工具。

另覆盖禁用理解/历史选择/恢复、只读记忆、模型形成失败、外部取消、准入拒绝及缺失依赖。形成失败保留执行结果；取消传播并等待模型清理；重试只续接形成。

这些是确定性集成测试，不是自然语言规划、记忆质量或成本收益实验。模型响应脚本预设了决策，不能用它证明自主换工具或长任务表现。此次未改变底层策略，基线仍是相同组件的手工装配；主要结果是框架拥有装配责任和可观察的完整链路。

验证结果：新增组合用例 7 项通过；全量 `uv run pytest -q` 为 1379 项通过（79.16 秒）。Ruff、全仓格式检查、Pyright 与 CLI `--help` 均通过。未调用真实模型，未变更 FinScope。

## 限制与后续

工厂不会增加未实现的能力：没有自动恢复未完成的 Session Run、后台形成 Worker、新 Skills 引擎、多 Agent 编排或新的摘要算法。关闭 history_retrieval 仅关闭相关历史选择策略，不删除持久会话或基础历史读取工具。关闭 context_recovery 仅关闭当前 Run 的 RecoverContext 控制操作，不删除已有 Artifact 读取能力。

后续继续检查同一入口在多轮延续、澄清和目标修订中的组合行为，再把发现的实际断点补入原链路。真实模型任务评测应复用此入口，不能另搭一条手工装配的演示链路来替代默认框架行为。
