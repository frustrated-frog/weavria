# ADR 0025：结算后进度信号与可解释控制

- 状态：已采纳并实现
- 日期：2026-10-21
- 范围：Task-aware Session、Need/Evidence、AgentLoop v3、控制事件与回合决议
- 前置：[ADR 0024](0024-规范化动作身份与观察后停滞门控.md)

## 背景

`semantic-progress/5` 能在派发前拒绝精确重复和同族参数逃逸，但它只回答“这个动作是否还允许
尝试”。`need_state_sha256` 也只回答有效 Need 投影是否改变，不能解释改变来自字段覆盖、义务完成、
独立来源、矛盾还是失败。仅凭摘要变化继续执行会把无关状态波动当成进展；仅凭摘要不变停止又会
忽略一次失败后出现的新能力或仍可修复的路径。

本轮要解决的不是学习一个成功概率，而是在 `TurnSettled` 之后建立一组可重放、可审计的进度
信号，并让 Harness 的下一步决议绑定这些信号。完成真实性仍由 Completion Policy 判断；工具
准入仍由 Tool/Progress Policy 判断。

## 决策

### 1. 准入控制与结果评估是两个阶段

保留 `ProgressPolicy.inspect()` 作为派发前的纯准入检查。新增 `ProgressAssessor` 端口，在完整
工具批次结算后运行。Task-aware Session 的实现先用已接受的 ToolRecord 刷新并 CAS 提交新的
`SemanticSnapshot`，再比较前后 `NeedLedger`，生成版本化 `ProgressAssessment`。

没有 Task Frame 或宿主未配置 Assessor 时，AgentLoop 保持原有行为，不根据原始 Artifact 数量
伪造语义评估。Assessor 异常会使 Run 以 Runtime 失败关闭，但已经结算的工具事实不会回滚或丢失；
取消仍沿用 Run 的取消传播。

### 2. 五类信号分别计算，不压成一个不可解释分数

`need-progress-assessment/1` 生成：

1. **义务变化**：只计算当前回合可观察的必需 `need_satisfied` 与 `capability_result` 义务，记录
   open before/after、newly satisfied、reopened 与 unchanged open。`answer` 和 `clarification`
   属于交付阶段，不会被工具结果提前判定完成。
2. **证据覆盖增量**：把必需 InformationRequirement 的 JSON Pointer 变成稳定覆盖单元，记录
   covered before/after、newly covered 与 lost coverage。覆盖表示声明字段已有可用 Evidence
   Address，不等于事实为真或来源足够。
3. **独立信息收益**：只接受 EvidenceExtractor 给出的 `source_identity_sha256`。新 Artifact、
   producer call 或不同参数不自动代表独立来源。缺少来源身份的新增 Binding 进入
   `unattributed_new_bindings`；同一稳定来源的重复 Binding 单独计数；新增矛盾单独计数。
4. **行动成本**：记录本批 proposed/succeeded/failed/skipped、Artifact 字节、已用模型回合以及
   剩余模型/工具额度。当前没有 Provider token 与分阶段延迟的权威事实，因此 Schema 明确只标记
   `runtime_counters/1`，不使用字节数冒充 Token。
5. **继续可行性**：使用确定性、版本化规则产生 `ready / viable / constrained / blocked` 和
   `verify / continue / repair / replan / stop` 建议，并附稳定 reason code。它是下一步控制依据，
   不是完成许可或统计概率。

`quality` 由可验证的正向增量和回归组合归约为 positive、neutral、regressed 或 mixed；
`material_progress` 只有在义务完成、覆盖增加或新增已归因独立来源时为真。单纯 Ledger 版本变化不算
实质进展。

### 3. 来源独立性由提取器声明，默认保持未知

`EvidenceEvaluation` 与 `EvidenceAddress` 新增可选 `source_identity_sha256`。它应表示应用能够稳定
识别的独立治理来源，例如发布机构、数据库或权威文档集合的脱敏身份。StructuralEvidenceExtractor
不知道领域来源，默认留空。

框架不从 `artifact_sha256`、`call_id`、工具名或 URL 字符串猜测独立性。这样会少报某些收益，但
不会把同一接口的重复响应误报为多源交叉验证。提取器错误声明独立来源属于插件语义错误；当前框架
只能校验摘要格式，不能独立证明现实来源关系。

`NeedLedger.progress_sha256()` 同时纳入去重后的稳定来源身份：同一来源的重复调用不会推进语义
前沿，新增明确归因来源会推进前沿。EvidenceResolver 因此升级为 `/2`；Task-aware Session 的组合
版本会记录这一变化。`SemanticProgressPolicy` 本身仍是 `/5`，因为它继续只消费宿主提供的不透明
Need 摘要，来源归约属于 EvidenceResolver 而不是 Runtime 准入策略。

### 4. 完整评估成为事件，摘要进入受限控制通道

AgentLoop 接受 `ProgressAssessed` 前验证：Run 处于最新 `TurnSettled` 后的 READY 阶段、Task
Revision 未变、评估绑定的 call IDs 与完整 TurnFeedback 顺序完全一致，且同一结算边界尚未接受
另一份评估。完整 `ProgressAssessment` 写入 v3 Journal；`ProgressNotice` 只投影评估摘要并继续受
`CONTROL_FEEDBACK_BYTES` 的 1KB 上限约束。

Reducer 额外投影 `pending_progress_sequence`：只有紧邻当前状态、尚未消费的
`TurnSettled` 序号才能接受一次 `ProgressAssessed`。`TaskRevised`、下一次
`ContextSelected` / `TurnDecided` 或 `BatchRejected` 都会使旧结算边界失效，避免旧反馈被重复
评估并覆盖更新的控制观察。这是可重放的状态机不变量，不依赖主循环恰好按正常顺序
调用。

下一轮 ControlRequest 会同时看到原 Tool Feedback 和 ProgressNotice。`TurnResolution` 升级到
`progress-aware-resolution/2`，绑定评估 SHA256，并把建议映射成 continue、repair 或 replan。
`verify` 只要求模型提出 Finish Candidate；`stop` 只表示已观察路径不可继续并要求重规划或如实
收束，Runtime 不会绕过 Completion Policy 自动成功或制造新的终态。
如果 `ProgressAssessed` 已接受后 Task Revision 在决议提交前发生变化，控制提交锁内重新读取的
当前 Revision 优先：旧评估不再绑定决议，系统生成 `revision/1 + replan/task_changed`，
而不会将过期的 Progress reason 带入新任务。

## 控制规则

当前确定性基线按以下优先级处理：

1. 下一次模型回合已无额度，或仍有开放义务但工具额度为零：`blocked / stop`；
2. 可观察义务全部满足：`ready / verify`；
3. 必需来源全部不可用且不可重试：`blocked / stop`；
4. 义务重开、覆盖丢失或新增矛盾：`constrained / repair`；
5. 失败仍可重试：`viable / repair`；
6. 出现实质进展：`viable / continue`；
7. 能力视图扩展：`viable / replan`；
8. 其余无实质进展：`constrained / replan`。

这不是声称上述顺序普遍最优。它是可替换策略研究前的可解释基线，后续应在冻结任务、预算和模型
配置下比较不同控制策略。

## 执行不变量

1. ProgressAssessment 只能引用完整结算回合，不能遗漏失败或跳过的兄弟调用。
2. Task Revision 改变后，旧回合评估不能进入新任务的控制通道。
3. 义务、覆盖、来源、成本和可行性保持分量化；单一摘要不能替代完整评估。
4. 未归因来源永远不计作独立信息收益；不同 Artifact 也不自动独立。
5. ProgressNotice 是低权限观察，不授权工具、不验收答案、不写长期记忆。
6. `verify` 不等于完成；只有当前 Revision 上的 CompletionAssessment 可以接受 Finish Candidate。
7. Assessor 失败不能抹掉已接受 ToolRecord；持久评估事件失败时 Run 按 Journal 失败规则关闭。
8. Token、延迟、事实真值和来源现实独立性没有权威测量时必须保持未知。
9. 每个当前 `TurnSettled` 最多被一个紧邻的 `ProgressAssessed` 消费；新的控制事实不得重开旧边界。
10. Task Revision 比旧评估优先；`task_changed` 决议不得绑定过期 Progress Assessment。

## 考虑过的替代方案

### 只比较 Need Ledger 摘要是否变化

无法区分有用字段覆盖、重复来源、矛盾和版本噪声，也无法解释控制决定；拒绝。

### 把不同 Artifact 或 Tool Call 计作独立来源

同一 API 的重复响应会被错误放大，而且模型可以通过改参数制造“信息增益”；拒绝。

### 将五类信号加权成一个 Progress Score

早期没有经过校准的数据与任务分布，固定权重会隐藏不同失败模式，也不利于 Completion 与
Progress 的职责分离；本阶段保留向量和可解释规则。

### Assessment 直接终止 Run

“没有继续价值”与“可以向用户交付什么”不是同一命题。自动成功会绕过验收，自动失败也可能阻止
模型如实报告限制；本阶段仅影响下一步决议。

## 验证与证据强度

确定性测试覆盖：

- 部分字段覆盖带来 coverage delta，但不会提前满足义务；
- 同一稳定来源补充第二字段会完成义务，但 independent source delta 保持为零；
- 同一来源的重复调用不改变 Need 进度摘要，新增明确归因来源才推进语义前沿；
- 无来源身份的 Binding 不被计作独立来源；
- 工具额度耗尽且义务未完成时给出 blocked/stop；
- ProgressAssessed 持久化、1KB 摘要投影、下一轮 ControlRequest 和 TurnResolution 摘要绑定；
- 伪造 call ID 的评估在事件归约处被拒绝；
- ProgressAssessed 接受后立即发生 Task Revision 时，旧评估被丢弃且正常重规划；
- 新提议被拒绝后，旧 TurnSettled 的反馈不能被再次评估或覆盖拒绝通知；
- Assessor 故障保留已经结算的工具事实并失败关闭；
- Task-aware Session 的真实语义刷新产生 verify 建议，随后仍经过 Completion Policy。

冻结控制面实验 `evaluate_progress_signals` 用五种已校验 Assessment（continue、verify、repair、
replan、stop）比较当前解释性建议与“状态摘要变化就 continue，否则 replan”的朴素基线；当前结果
为 5/5 对 2/5。该实验只验证控制面能区分摘要变化无法表达的动作，不验证上游 Extractor 判断或
真实模型任务收益。

这些测试和冻结实验证明计算、控制区分与执行不变量，不证明策略改善开放任务成功率。现有 DeepSeek 对照属于
`semantic-progress/4` 的准入策略，不能作为本评估器的收益证据；本轮没有调用付费模型。

## 当前局限与下一步

- `source_identity_sha256` 依赖可信 Extractor 协作，尚无通用 Provenance Registry 或来源关系图。
- Coverage 基线只理解声明的 JSON Pointer；语义蕴含、交叉字段约束和事实真值仍由领域 Evaluator
  负责。
- Cost 尚未包含真实 Token、延迟、货币成本和副作用风险；Control 也未做剩余价值/成本比估计。
- 当前策略是确定性基线，没有学习式价值函数、置信区间或历史任务校准。
- Session Semantic commit 与 Runtime ProgressAssessed 是相邻的两个持久边界，不是跨存储事务；
  失败后保留已提交的语义事实，但当前系统尚未实现崩溃恢复后补算评估。

下一步应冻结一组领域无关的多来源研究、文件修复和 API 故障任务，比较“仅摘要变化”、当前规则与
不同成本敏感策略；同时把 Provider usage、端到端延迟和来源身份覆盖率加入报告。只有真实任务结果
支持时，才研究基于历史轨迹校准继续价值或引入学习式 Critic。
