# ADR 0008：运行中任务干预与回合 Harness 控制

- 状态：接受
- 日期：2026-10-15
- 前置：[ADR 0007](0007-persistent-conversations.md)
- 范围：单用户持续会话，运行中追加要求，逐轮上下文准备，显式下一步控制

## 能力问题

持久化历史解决了请求之间的接续，但此前执行中的 Agent 仍沿用旧目标工作。用户改变要求时，只能等待旧工作完成，再提交下一条请求。正在生成的模型提议、排队工具和正在验收的结束候选都可能已经过时；仅保存新消息无法改善这些行为。

本阶段建设一条完整机制：接受用户补充要求 → 更新当前工作目标 → 停止旧决策继续派发 → 保留已启动工作的结果 → 为新方向重建上下文 → 重新决策和验收。它不需要额外调用一个控制 LLM。

## Preparation、Model Decision、Execution Outcome 与 Resolution

Runtime 保留模型决策和实际工具结果的原有 v3 契约，新增独立 TurnResolution。它绑定当前任务版本、提议版本、所观察的运行事件位置、模型提议摘要和验收摘要，明确下一步：

| 阶段与事实 | Harness 下一步 |
| --- | --- |
| 提议或结果属于旧任务版本 | replan |
| 当前版本的工具批次提议 | dispatch，再进行原有预算准入 |
| 当前版本的结束候选 | verify |
| 当前批次结果已汇合 | continue |
| 验收发现缺口 | repair |
| 当前验收已经解决 | complete；验收无法验证时仍保留 unverifiable |

控制事实与运行事实分开存储；Run 的状态仍由 ControlEvent v3 归约。Resolution 是基于命名快照作出的控制决定，不能凭它绕过工具准入、任务版本校验或完成事务。例如 complete 决定形成后又接受了用户要求，最终提交仍必须重新比较版本；旧的 complete 不能使新任务结束。

当前控制策略为 revision/1，是具体的确定性规则，不宣称已经实现通用策略自适应、复杂规划或可任意修改执行流的 Hook 系统。CompletionPolicy 继续承担可替换的任务验收。

TurnPreparer 是有限的异步准备端口：为当前 TaskInput 重建模型外层上下文，并返回剩余当前 Run 字节预算。它不能修改执行事实、任务身份、工具集合和总预算。本阶段的 Session 实现每轮根据最新目标及补充要求，重新选择历史交互；不再复用进入 Run 时冻结的相关性视图。

准备期间到达新要求时，旧准备结果被丢弃；即使旧准备报告预算不足，也先检查是否已经过时。ContextSelected、ModelStarted 和完整模型请求快照在同一 Runtime 准备锁内形成，不能被任务更新插入中间。实际运输发生在锁外；运输中的旧结果返回后再判定过期。

## 用户输入怎样成为当前工作目标

SessionEngine.steer(session_id, text, input_id=...) 返回 TaskUpdate。原始目标保留，用户补充以有序约束进入新的 TaskInput，revision 恰好增加一次；后来的要求优先于冲突的较早任务要求。TaskUpdate 同时保留原文与输入身份，不让模型或宿主预先解析出下一组工具。

这一规则表达用户指令的顺序，不宣称已经进行了通用自然语言冲突消解。模型负责理解要求和选择行动；Harness 负责使当前要求成为后续输入、调度和验收的共同依据。新要求不会重置原 Run 的计数器与 Deadline。

成功确认表示输入与对应 TaskRevised 已在同一 SQLite 事务接受，并已发布到 Runtime 内存状态；没有“已接受但忘记应用”的内存队列。相同输入 ID 和原文重试返回原 TaskUpdate；不同内容或跨 send / steer 模式复用同一身份会冲突。调用开始时绑定当前 Run；存储查询或等待锁期间旧 Run 结束，输入不会静默改投下一 Run。调用方也可用 expected_run_id 显式绑定。Run 已结束或尚未进入可干预执行时，新 steering 明确拒绝，不自动排队。

## 派发与完成的仲裁

任务更新、模型准备、工具启动及最终提交使用同一 Runtime 接受锁：

- 更新先于 ToolStarted：旧调用被跳过，不发生实际工具执行。
- ToolStarted 先被接受：调用属于已启动工作，允许其实际结果收敛；其兄弟队列在启动前再次检查版本。
- 整批提议已接受但尚未准入：更新可以使全部调用过时；全部跳过后产生反馈，无需为不会执行的调用伪造准入。这是对 v3 旧状态机缺失路径的补充，并未放宽实际执行前的反馈保证。
- 更新发生在模型运输期间：旧提议丢弃，下一轮重新准备。
- 更新发生在验收期间：旧验收被丢弃。
- 验收已接受，更新赢得最终提交前的锁：结束候选失效，重新规划。
- RunEnded 已提交：新更新拒绝；不会把输入确认给已结束的 Run。

不持有锁等待模型或工具完成，因而用户可以在这些阶段实际进入。当前不主动中断正在运输的模型请求；它返回后再丢弃。已经启动的外部效果不被撤回或假装取消。

提交任务由 settle_mutation 持有到结果明确。取消输入等待者不会丢失已经提交的版本；原输入身份可取回结果。输入提交失败会封住日志，并取消、加入活动模型或工具，最后记录存储中断（存储仍可用时）。引擎关闭同时加入 send 和 steer 的所有权任务。

## 历史与版本演进

ConversationTurn / ConversationItem / ConversationView 升为 v2，分别保留完整 TaskUpdate、带原文摘要的更新视图及选择策略 conversation/2。原始 user 字段仍是最初输入，不将它悄悄改写成拼接后的任务。相关性选择同时考虑用户补充文本；过长更新可以用 read_session_history 的 field=update / update_id 按字符范围补读。该工具版本升为 2。

SessionRequest 升为 v5，外层包含 ConversationView v2，内层仍为 ControlRequest v3。SessionModelProvider 与 FakeSessionProvider 使用 v5；调用方适配器需要显式升级。SessionResult v1 与 RunReport v3 不变。

SQLite Schema 1 → 2 增加 directives 和 control_decisions；迁移与交互投影升级在一个事务完成。原始 Run 事件、会话事件和 v4 模型请求快照保留原始字节。新 SessionEvent 使用 v2；读取仍支持 v1 旧事实，但 v1 不允许承载新增的 task_updated / control_decided。旧 v4 请求作为审计原文保留，不用新模型伪装反序列化成 v5。

模型请求快照仍是准备后真正运输的内容。每轮视图按完整外层序列化重新计费，剩余预算再交给当前 Run 的反馈准入；没有将历史补充文本免费塞进指令。

## 替代方案与取舍

- 等待结束后再发送：实现容易，但继续执行过时工作；作为冻结实验的基线。
- 取消整个 Run 再创建新 Run：丢失当前 Run 的工作连续性，且不能判断取消的工具效果；本阶段不采用。
- 写持久输入队列、稍后消费：有利于 follow-up，但需要额外的接受/应用状态、消费恢复与终态仲裁。本阶段将接受和应用放进同一事务，先完整交付实时 steering；不借队列表宣称支持 follow-up。
- 每次更新都让 LLM 重写计划或需求：增加成本，可能丢失原文；当前保留有序要求，由正常决策轮次理解，不额外调用控制模型。
- 通用 Hook 随意改状态、工具与模型：无法说明哪些变更保持执行语义；当前仅开放有限准备端口，未来按实际能力需求增加类型化操作。

## 验证与结果

确定性测试覆盖：模型运输中的过时提议、已接受但未派发的批次、在途工作保留、排队工作跳过、验收与完成提交竞态、取消输入确认、并发版本链、存储失败、逐轮历史重选、长补充原文回读和 Schema 迁移。真实子进程分别在更新事务之前、事务完成但确认之前退出；重新打开后输入与版本要么同时存在，要么同时不存在。

冻结的 examples/steering_experiment.py 从本地目录发现资料。目录只暴露名称和主题，答案必须通过实际读取内容计算；模型替身按一个有限 JSON 任务语言决策，验收器读取已接受成果验证选择和数值。新目标在第一个读取已经启动时到达：

| 策略 | 文件读取 | 到达新目标后的过时读取 | 模型决策 | 跳过调用 | 最终验收 |
| --- | --- | --- | --- | --- | --- |
| deferred：旧工作结束后发送 | 7 | 4 | 6 | 0 | verified |
| steering：修订当前工作 | 3 | 0 | 4 | 4 | verified |

两组得到相同最终结果。相同 28,000 字节请求上限下，总输入观察值分别为 47,668 和 26,300 字节。报告记录数据版本、求解器、验收器、任务文件摘要、实现摘要、源码树摘要与配置。它证明该固定改目标任务中的调度、工作复用与成本差异；不能证明真实 LLM 的理解、规划、冲突消解或长期任务成功率。
