# ADR 0060：语义提交与快照安装的取消一致性

- 状态：已采用
- 日期：2026-10-30
- 范围：Session 语义刷新、SQLite 提交、探索超时后的收尾
- 前置：[ADR 0014](0014-semantic-acceptance-and-safe-association.md)、
  [ADR 0059](0059-完整准备时限与运行配置留证.md)

## 问题与复现

Session 的语义刷新先计算候选快照，再用版本 CAS 提交 SQLite。只有提交成功，候选才能成为
已接受状态。但 SQLite 工作线程不能由协程取消直接中止：`SQLiteSessionStore._submit()` 会先
等待线程结算，再向调用方传播取消。于是存在下面的时序：

1. 工具结果已被接受，语义刷新提交进入 SQLite 事务。
2. 探索子期限到达，刷新协程收到取消；工作线程继续完成事务。
3. 存储层提交成功后传播取消，没有将返回值交给适配器。
4. 适配器仍保留旧 SemanticSnapshot、NeedLedger、能力视图和澄清计划。
5. 收尾按旧账本运行；Session 随后拿旧版本提交 Work 终态，触发 `semantic head changed`。

这不是只读金融场景的问题，而是任何“异步持久提交后更新内存投影”的使用者都可能遇到的问题。
网页评审提供线索后，本次在旧代码上以真实 SQLite 事务和工作线程复现了第 5 步：
`SessionEngine.send()` 在终态提交时抛出 `SessionConflictError`。HTTP Host 会将它映射成 409，
因此已持久化的 Run 终态并不保证此次 HTTP 请求成功交付。

## 决策

在 `_SessionAdapter._refresh_semantics()` 中，沿用 Runtime 已有的 `settle_mutation()`，将
`commit_semantic()` 的整个异步操作交给当前调用方持有并等待结算。该操作获得独立的受跟踪任务，
调用方的取消不再提前截断提交返回值的交接。

成功取得存储层返回的已提交快照后，在无 `await` 的区间中一起安装：

- 模型可见工具名称与 capability epoch；
- TaskObservation 与完整 SemanticSnapshot（包含 NeedLedger）；
- 对应的工具记录计数与 clarification plan。

安装完成后，如果等待期间收到过取消，立即重新抛出 `CancelledError`。不把取消变成成功，也不
吞掉外部取消。Runtime 的探索超时作用域仍负责判断是否转入收尾；只有其自身到期才执行该路径。

事务失败时不会返回已提交快照，安装区间也不会执行。无取消时保留原存储异常；取消与失败同时
发生时，沿用 `settle_mutation()` 的既有行为：取消优先传播，并通过异常链保留失败原因。

Session 的后续终态提交继续使用 `adapter.semantic`，没有降低 CAS 要求或在冲突后无条件重试。
已经提交的证据版本正确安装后，终态才能基于该版本继续推进。

## 一次请求如何流转

`SessionEngine.send()` 创建任务与初始语义头；Runtime 接受工具反馈后，适配器刷新语义。
如果探索期限恰好在 SQLite 提交中到达，调用方先等待事务成功或回滚。成功则安装完整投影，随后
传播取消。探索超时边界接管后，`prepare_finalization()` 从这个同任务版本的已提交状态构造视图，
完成原有证据与发布检查，再请求 Finish。最后 Session 使用新语义版本提交 Work 终态。

外部取消走原取消路径，不生成降级回答。事务回滚则保留旧状态，无法建立可交付证据时明确结束。
工具原始结果和已接受执行记录均保留，不重复执行工具。

## 备选方案与取舍

- 修改 `_submit()`，提交成功时一律忽略取消：会改变所有存储调用的契约，并丢失取消信号。
- 只给提交加 `asyncio.shield()`：调用方仍可能先收到取消并退出，提交任务还在后台，缓存安装的
  所有权没有解决。当前方案等待操作结算，不留无人跟踪的任务。
- 取消后重新读数据库：多一次 I/O，读操作仍会被取消，也可能读到另一个语义版本，不能代替
  取得本次提交的确定结果。
- 提前安装候选，或只更新版本号：回滚时会发布未接受状态，或者让版本与实际账本、能力视图分叉。
- CAS 冲突后直接覆盖或重试：会掩盖状态交接缺陷，可能覆盖合法的新版本。

选择现有结算机制使修复保持在 Session 的状态投影边界。没有增加公开接口、持久化 Schema、
依赖、模型调用或应用业务规则，也没有更改 Core、工具权限和完成检查。

## 验证

领域无关测试通过 SQLiteSessionStore 的测试子类注入提交屏障：SQL 修改已经完成，事务仍未
COMMIT；此时触发真实探索期限或外部取消，再释放工作线程。这与“候选尚未交给存储”的既有测试
是不同的取消时点。断言面向公开事件、请求、持久语义头、执行结果及重复输入行为。

覆盖情况：

- 探索超时后事务成功：新证据进入收尾请求，Run 完成，Work 终态 CAS 成功。
- 探索超时后回滚：无虚假证据刷新，保留工具记录并明确预算耗尽。
- 外部重复取消与提交成功或回滚竞争：线程先结算，取消继续传播，不再请求模型回答。
- 无取消的提交失败：旧语义状态保留，Run 明确失败。
- 关闭后重新打开引擎：已接受的语义头不变，重复输入返回原 Run 报告，不重执行工具。
- FinScope 正式 ASGI 接口与真实 SQLite：保持证据事务跨过探索期限，随后提交，HTTP 返回 200
  和原有 `unverified` 完成结果，而不是 409；模型与外部数据均使用确定性测试替身。

## 当前边界与下一步

结算必须等待存储操作给出确定结果，可能包括排队与事务结束。如果 SQLite 或文件系统永久阻塞，
协作式取消不能强制终止它，父期限也不能作为抢占式存储隔离保证。成功安装已提交状态不保证
剩余时间足够交付；原有父期限、任务版本和证据验收仍然生效。

本次没有实现进程崩溃恢复、跨进程共享内存缓存、持久续跑、增量证据算法，也没有重新运行真实
模型评测。确定性测试证明的是提交和投影的一致性，不证明普遍任务成功率提升。

下一小步是核实主动上下文恢复的探索期限与恢复决策结算。完成这一正确性收口后，再推进确定性
TaskModelView 和必要证据投影，保持 FinScope 仅作为测试场景。
