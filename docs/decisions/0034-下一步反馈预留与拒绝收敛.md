# 0034 下一步反馈预留与拒绝收敛

## 背景与状态

已实现（2026-10-24）。本决策修正联合上下文编译与工具准入之间的一个通用失配，不改变任何 FinScope 领域契约。

真实运行中，当前模型请求虽然满足输入 Token 与 32KB 序列化上限，但分配器把几乎全部剩余字节交给了可选历史。模型随后提出一个普通只读工具调用，`reserve_feedback` 计算下一轮最低回执需要 14,118 字节，而编译报告只留下 9,232 字节，因此调用在派发前被拒绝。后续模型反复提出同一动作，直到模型调用预算耗尽。工具、模型供应商和完成验收都没有实际失败。

根因由两个独立问题叠加：

1. OpenAI-compatible 传输会把可信 `instructions` 从用户 JSON 提升到系统消息。旧的字节上限仍把这段已知文本按“每个未知字节最多消耗一个 Token”计价，重复消耗了不必要的保守余量。
2. Context Compiler 只为当前请求和控制通知保留空间，没有在暴露工具时为下一步工具动作与最低反馈保留空间。当前视图可发送，不代表执行一步后仍可继续。

## 最终决策

### 对稳定传输内容进行精确计量

`SessionTokenCounter.request_byte_ceiling` 接受可选的当前 `SessionRequest`。提供请求时，OpenAI-compatible 计数器执行以下计算：

1. 对固定协议、可信 instructions 和 framing 使用真实 tokenizer 计数；
2. 对未来可能变化的用户 JSON 继续使用“一字节最多一 Token”的充分上界；
3. 将 transport 中被移出用户 JSON 的 instructions 字段差额加回，返回与 `SessionRequest.model_dump_json()` 相同的字节量纲。

设输入额度为 `I`，固定系统内容 Token 为 `S`，framing 为 `F`，序列化请求与 transport 用户 JSON 的固定差额为 `L`：

```text
未知用户载荷上限 = max(0, I - S - F)
序列化请求上限 = 未知用户载荷上限 + L
```

未提供请求时保留旧的全载荷保守计算，供没有稳定请求快照的调用方使用。计数器版本升级为 `openai-compatible-session/2`，使持久编译报告可以区分计量语义。

### 编译当前上下文时保留下一步空间

`ContextCompilerConfig.next_step_reserve_bytes` 默认上限是 4,096 字节。Session Runtime 只有在当前存在任务可用的主工具时才启用该预留；实际值取配置上限与请求字节预算八分之一中的较小值。纯直接回答以及只有外围历史读取能力、没有主工具的任务仍可使用完整当前请求预算。按比例封顶避免小窗口被固定 4KB 预留挤掉关键历史。

分配器把该预留同时加入字节成本和 Token 成本。未知未来内容仍按一字节一 Token 计费，因此历史、证据正文和恢复片段不能抢占这段空间。预留不是工具执行许可，也不保证任意大参数批次都能执行；模型提出动作后，`reserve_feedback` 仍以实际调用、可读证据闭包和 `FeedbackBounds` 做精确准入。

`ContextCompilation` 增加 v5 字段 `next_step_reserve_bytes`，并验证：

- `request_bytes + control_reserve_bytes + next_step_reserve_bytes <= budget_bytes`；
- `input_tokens + control_reserve_bytes + next_step_reserve_bytes <= input_budget_tokens`。

旧 v1-v4 报告维持原有验证和序列化，不补写新字段。

### 重复硬拒绝必须有界收敛

反馈预算、工具次数或能力视图拒绝后，Runtime 使用任务修订、拒绝原因和规范化行动价值键构造拒绝前沿。调用 ID 即使因请求摘要变化而改变，只要工具与规范化参数没有改变，仍视为同一前沿。

模型可以在配置的 `max_no_progress_rejections` 次数内读取控制通知并改写动作。超过次数后，Run 以 `failed / no_progress` 结束，不继续空耗模型调用预算。成功准入或真正改变行动前沿会清零计数。Runtime 不伪造工具结果，也不替模型合成答案。

### 根据真实拒绝自适应扩大反馈余量

固定的 4,096 字节只能保护普通小动作，不能保证带较长基础指令、页面观测或多工具的真实批次。因此 Runtime 在首次 `feedback_budget` 拒绝后，记录该批次由 `reserve_feedback` 证明的 `required_bytes`，并把它作为下一轮编译的反馈容量下限。

编译器对每个候选上下文同时验证字节上限和 Token 充分上界；不能容纳下限的候选被视为不可行，分配器会删除低效用可选历史后重试。若删除全部可选内容仍无法达到下限，则回退到原有结构化拒绝路径，让模型缩小批次或改变行动，不把“该提议太大”误报为整个 Run 的上下文耗尽。

`ContextCompilation` 增加 v6 字段 `feedback_reserve_floor_bytes`，并强制 `feedback_budget_bytes >= feedback_reserve_floor_bytes`。成功准入后 Runtime 清除该临时下限，避免上一个批次的大小永久挤占后续上下文。

## 关键不变量

- 当前请求可发送和下一步可继续是两个不同约束，必须分别计量。
- 稳定内容可以精确计量；未知反馈仍使用充分上界，不使用平均字节/Token 比。
- 下一步预留只能影响上下文选择，不能绕过工具预算、Policy、证据访问闭包或真实反馈准入。
- 可选历史不得挤占显式预留；必要上下文加预留本身超限时必须明确报告上下文预算耗尽。
- 已知的真实批次不得因固定预留过小而在不变上下文中重复拒绝；必须先尝试为它释放可选历史。
- 相同的不可执行提议不能无限消耗模型预算。

## 替代方案与取舍

- **提高 FinScope 的模型次数或请求字节上限**：无法修正预算被可选历史吃满的问题，也会掩盖通用 Runtime 缺陷，拒绝。
- **缩短 FinScope Prompt 或硬编码单工具调用**：属于场景定制，不能保证其他长指令 Agent，拒绝。
- **工具执行后再裁剪反馈**：破坏执行前最低反馈承诺，拒绝。
- **为所有可能批次预留最坏空间**：任意工具参数没有有限通用上界，会严重压缩有效上下文。当前保留一个可配置的生产性步进空间，再由实际动作准入精确判断。
- **重复拒绝时自动 Finish**：Runtime 没有可交付答案，自动完成会伪造任务结果。当前选择明确失败并保存诊断事实。

## 验证与限制

确定性回归覆盖：长可信指令的请求感知计量、长历史下仍能执行一次普通工具调用、拒绝后把真实需求传给下一轮编译、自适应删除可选历史、超大调用继续在副作用前拒绝、同一硬拒绝在模型总预算前收敛，以及 ContextCompilation v1-v6 兼容。

4,096 字节与八分之一窗口封顶仍是首轮的通用默认策略；后续轮次已可根据真实拒绝自适应。该机制不保证超过整体请求上限或必要上下文本身无法容纳的批次可执行。后续应在冻结任务集上比较上下文保留、工具准入率、完成率和 Token 成本。
