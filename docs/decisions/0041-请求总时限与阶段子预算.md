# ADR 0041：请求总时限与阶段子预算

- 状态：已采纳并实现
- 日期：2026-10-26
- 范围：Session、任务理解、Agent Runtime、Deadline
- 修订：[ADR 0013](0013-dynamic-capability-completion-progress.md) 第 6 项的预算组织方式

## 背景

Session 过去直接用 `RunLimits.max_duration` 创建 `RootBudget`。任务理解与 AgentLoop 虽然共享
一个不可增长的 Deadline，但 `max_duration` 同时被解释成“完整请求总时限”和“Agent 执行
上限”。当任务理解需要多阶段规划、覆盖审计和修复时，它会消耗 AgentLoop 的执行份额。

真实 FinScope 轨迹暴露了该耦合：任务理解约消耗 92 秒，Agent 执行在已取得全部必要证据后
只剩约 88 秒；一次可修复的空模型响应后，运行在答案生成前以 `deadline` 结束。应用明明分别
配置了 180 秒理解上限与 180 秒执行上限，实际却只能共享 180 秒，配置语义和运行行为不一致。

## 决策

1. `SessionEngine` 新增可选 `max_request_duration`。它是从输入被接受到终态提交的父级硬
   Deadline；未配置时等于 `RunLimits.max_duration`，保持既有调用方行为。
2. 任务准备继续受父 Deadline 监督，也继续遵守准备机制自己的阶段上限。阶段内部的规划、
   审计、修复仍共享同一准备 Deadline，不能逐步重置。
3. AgentLoop 获得 `min(RunLimits.max_duration, 父 Deadline 剩余时间)`。准备阶段未使用的时间
   不会把 Agent 执行扩张到其声明上限之外；准备超时也不会绕过父 Deadline。
4. FinScope 将父时限配置为“任务理解上限 + Agent 执行上限”。默认形成 360 秒请求硬上限，
   同时保留两个阶段各自 180 秒的限制。
5. 生效的父时限写入持久 Run 配置，便于失败轨迹解释与实验复现。

## 不变量

- 所有阶段仍受一个从 Session 入口开始、不可增长的单调父 Deadline 约束。
- 子阶段只能缩小可用时间，不能重置或超过父 Deadline。
- AgentLoop 的运行上限始终不超过 `RunLimits.max_duration`。
- Deadline 到期继续归一化为 `budget_exhausted / deadline`；取消仍原样传播。

## 取舍与限制

该修复解决阶段预算耦合，不保证慢模型一定完成，也不把提高时限当作上下文质量修复。反馈
空间拒绝、证据片段选择和空供应商响应仍由各自机制控制。FinScope 的父时限由两个阶段上限
相加得到，因此最坏墙钟时间提高；这是显式、有界且可观测的成本。

## 验证

确定性测试使用注入时钟让任务准备消耗 70 秒、模型执行消耗 50 秒：兼容默认配置在 100 秒
共享父时限下终止；配置 200 秒父时限后，AgentLoop 仍只获得 100 秒自身上限并完成。真实模型
回归使用同一 FinScope 比较问题，检查最终答案、工具轨迹、终态和总耗时。
