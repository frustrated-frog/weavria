# 0145 恢复尚未派发的只读批次尾部

2026-11-22，已采纳。同步扩展 ADR 0085 的显式恢复入口。

## 问题与选择

一个只读模型批次依次提交 A、B、C。A 和 B 的工具回执及原件已经提交，C 尚未启动，进程此时退出。原恢复接口要求整轮已有执行结算，因而无法利用更细的工具级提交。拆成多个模型轮次能留下检查点，但会在正常或普通故障路径增加模型调用。

恢复者直接使用当前 Run 的接受事实。复用已经提交的前缀，再经普通工具执行器派发原批次中从未启动的尾部。每次读取的身份、结果和最终反馈顺序都沿用原提案。

## 如何取得执行权

应用重开 SQLite 后，通过原有的显式入口恢复：

```python
result = await harness.resume(session_id, run_id)
```

SQLite 在同一事务中核对会话、最新 Run、恢复配置、期限、历史索引水位及独占执行权。通过事件归约得到的部分批次必须满足这些条件：

- 原批次已接受逐调用反馈信封，模型决策属于当前任务修订。
- 一个非空前缀已有 ToolRecorded，剩余调用尚无 ToolStarted。进行中的调用、被跳过的调用及等待状态轮询都不符合。
- 持久 proposal resolution 与原提案摘要一致。原模型请求的控制视图摘要必须与原 ContextSelected 一致；启用工作视图时同时核对语义头、账本和能力视图版本。
- 已提交原件重新检查当前 Policy 与内容摘要；失败反馈作为已发生的结果保留。待派发调用须继续符合只读、可安全重放、无需审批和当前能力可见性。重新计算的规范化动作及反馈信封必须与原准入证明完全一致。

恢复领取沿用 SessionResumeClaimed 与原有游标。Run ID、模型调用数、工具调用数、总期限和既有事件继续生效。当前数据表及事件格式即可表达这些事实。

## 派发、结算与失败

SessionEngine 将已接受的原模型请求交给 AgentLoop。恢复分支在下一次模型决策前调用普通批次派发器。它只派发尾部，沿用原 call ID、原任务模型视图、存储的反馈信封和原准入的 Artifact 读取集合。刚刚提交的 A、B 仍属于同一批次，尾部工具没有新增读取它们的权限。工具派发仍先保存 ToolStarted，再由执行器调用当前 Policy。

尾部执行完毕后，原批次整体结算一次。TurnSettled 按原提案顺序汇合新旧回执，然后更新工作状态并生成执行决议。即使进程退出前已经保存了工作提案，更新工作状态仍发生在整个批次结算之后。

如果恢复者在领取执行权之后、派发之前再次退出，可以再次领取。如果已经有 ToolStarted 且缺少 ToolRecorded，显式恢复仍拒绝执行。完成状态、取消状态、过期任务修订及仍有未知调用的批次各有原来的处理语义。这一切片要求至少还有一个待派发调用；全部回执已落盘但尚未来得及结算的独立断点留待后续验证。

## 验证与适用范围

同一真实进程退出现场中，C 未启动时，原 Run 的三条 ToolStarted 各出现一次，恢复只读 C，只调用一次模型用于汇总。旧实现拒绝该现场，按基线整题重跑要读三次并作两次模型决策。C 已启动且结果未知时仍拒绝恢复。已结算前两条的既有恢复方式仍只读 C，但需要先让模型提出 C。

覆盖初次与二次进程退出、旧原文权限撤回、尾部当前权限拒绝、跨兄弟读取隔离、反馈上界变化、原始请求篡改、期限耗尽、外部取消和工作状态结算。确定性模型用于隔离并检验执行语义。此前真实模型对照已报告两种分批方式的差异，本轮的恢复结果用于衡量原文重读和模型重新决策的开销。[三分支验证](../只读取证分支的失败修订与恢复验证.md)
