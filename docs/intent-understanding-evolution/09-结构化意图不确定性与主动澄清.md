# 第九阶段：结构化意图不确定性与主动澄清

## 本阶段解决的问题

到 P1 修复结束，Weavria 已能安全创建、等待和显式恢复一个澄清任务，但澄清内容仍只有
`ambiguities: tuple[str, ...]`。框架知道“有问题要问”，不知道“有哪些可行理解”“问题会排除
哪些理解”“错误理解会导致什么动作”，所以无法解释为什么先问某一个问题。

本阶段把澄清从字符串生成升级为一个小型决策过程，同时保持三个既有边界：原始 TaskInput
不被改写、模型推断不构成授权、FinScope 不进入通用契约。

## 代码改动索引

### `src/weavria/harness/intent.py`

新增完整算法切片：

- `IntentHypothesis` 表示候选解释与动作签名；
- `ClarificationAnswerOption` 表示一个答案留下哪些候选；
- `ClarificationQuestionCandidate` 表示一个有限问题分区；
- `IntentUncertainty` 校验候选唯一性、完整分区和动作分歧；
- `ClarificationQuestionValue` 与 `ClarificationDecision` 保存定点分数；
- `ConsequenceAwareQuestionSelector` 计算方向性错误代价、当前最优动作后悔值、问题回答后的
  剩余后悔值与交互成本，再进行确定性排序。

这里最重要的信任拆分是：候选解释和相对支持来自模型；能力风险、副作用与审批要求来自宿主
ToolDescriptor。算法只决定问什么，不决定工具是否可执行。

### `src/weavria/harness/understanding.py`

`TaskSpecification` 增加可选 `uncertainty`。模型提示词要求所有新 `clarify` 输出提供结构化候选，
并明确相对权重不是概率。两层校验共同保护边界：

1. Pydantic 校验字段、路由、问题分区和歧义引用；
2. `ModelTaskInterpreter` 与 `TaskUnderstandingEngine` 校验候选能力没有越过本轮目录。

TaskUnderstandingEngine v3 默认调用问题选择器，将结果编译为 `TaskFrame.clarification_decision`。
Task Frame 和 TaskFramePatch 升到 v3；`load_task_frame`、`load_task_frame_patch` 负责显式上转旧
v2 数据。

解释澄清回答时，输入中新增旧 Task Specification 与被回答的问题。它们被标记为数据，不覆盖
当前 TaskInput，但可以让“alpha”之类的短回答保留其语义来源。

### `src/weavria/harness/clarification.py`

`BlockingAmbiguityPolicy` 升级到 v2。对于 v3 Frame，它只投影已经接受的选择结果；对于从 v2
上转且没有选择结果的历史 Frame，仍保留旧式阻塞问题作为兼容路径。`ClarificationPlan` 额外
暴露被选问题标识和价值分解，方便测试与观察。

### `src/weavria/harness/session.py`

会话准备器将问题标识加入 Clarification ID 的稳定种子，把被选问题写入
`PendingClarification.question_text`。显式回答时从当前 SemanticSnapshot 读取旧问题，并传给任务
理解引擎。新 Observation 使用 `weavria.task-frame/3`。

### `src/weavria/harness/completion.py`

TaskCompletionEvaluator v3 同时读取 Frame v2 和 v3。若 v3 澄清候选输出不等于策略选中的问题，
返回 `clarification_question_mismatch` Repair；只有一致输出才进入等待用户输入的不可验证终态。

### `src/weavria/sessions/engine.py` 与 `src/weavria/harness/agent.py`

两个执行入口都把已选问题作为低信任数据加入指令，并禁止在该轮执行工具。独立
`TaskAwareAgent` 在没有外部 Completion Policy 时，会为结构化澄清启用任务义务验收，避免绕过
问题一致性检查。

### `src/weavria/evaluation/intent_clarification.py`

新增可复现实验契约，把当前策略与 `first-candidate/1` 比较。实验只接收冻结候选和 Registry，
不调用模型、不执行工具，因此可稳定验证算法变化，但不能证明候选生成质量。

## 可复现实验结果

运行：

```bash
uv run python examples/intent_clarification.py
```

冻结三个场景分别检查高风险动作边界、非均匀候选权重和用户交互成本。结果为：

- 当前策略命中预期问题 3/3，固定首问基线 0/3；
- 当前策略总净价值 2,400,000，基线 1,470,000；
- 所有数值都是算法内部的定点效用单位，不是任务成功率或概率。

## 本阶段证据能说明什么

确定性测试证明：非法候选会被拒绝，可信风险会影响问题排序，排序可重放，问题展示不会偏离
计划，回答会通过显式 Patch 继续旧 Work，旧 Frame 有迁移入口。

它不能证明真实模型总能生成完整候选，不能证明相对权重可靠，也不能证明三个合成场景上的
净价值提升会转化为真实任务完成率提升。详细论文边界、算法和后续实验方案见
[意图不确定性与主动澄清实现指南](../意图不确定性与主动澄清.md)与
[ADR 0015](../decisions/0015-后悔值驱动的主动澄清.md)。

## 下一阶段进入条件

只有冻结真实任务集、模型、温度、预算、用户模拟器和评测器版本后，才进入多轮信念更新或
clarify-or-commit。若真实模型主要失败在候选生成，应先改善结构化生成与修复；若主要失败在
相对权重，应研究校准或排名学习；若主要失败在重复问题，再增加提问历史和冗余成本。不能在
没有失败证据时同时引入这三类复杂度。
