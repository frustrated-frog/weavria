# 工作结论的证据重验与实验

本机制处理当前 Run 中已有显式依赖的工作结论：上游变化后，不能仅修改依赖版本就把旧结果恢复为可交付状态。它在工作提案工具内组织原文并审查候选更新，确定性归约器只核对已经接受的收据。它是显式实验能力，语义判断仍可能误拒或误接纳。

## 接入与源码入口

```python
config = HarnessConfig(
    configuration_id="my-agent-recheck-v1",
    context=ContextCompilerConfig(window_tokens=64000, output_tokens=4096),
    working_records=True,
    work_recheck=True,
)
# AgentHarness.from_config 复用 reasoning_model 与 reasoning_counter 组装审查器。
```

已有 CLI 可使用 `uv run python -m examples.harness_session --session demo --message '你的任务' --work-recheck`。该选项同时启用任务理解与工作记录，会增加真实模型调用；模型连接依旧由宿主管理。高级接入可注入 `WorkRechecker`，默认实现为 `ModelWorkRechecker`，可以使用不同的模型与匹配的请求计量器。

源码阅读顺序：

1. `harness/configuration.py`、`assembly.py`：声明实验开关并装配模型、计量器、工具和会话策略。
2. `harness/work.py` 的 `recheck_targets`：用旧依赖边和候选父版本找出受影响且试图改变的结论，包括降级和删除；同时修改父子也会被识别。普通计划和假设的调整不增加完成义务，但将失效假设提升为结果需要重验。
3. `harness/work_recheck.py`：从宿主绑定的工作视图读取旧状态，组织直接上游、候选结果与授权原文，完成准入和一次批量模型审查。
4. `harness/work_recheck_contracts.py`：收据绑定任务、工作集、旧结论版本、完整更新摘要、策略和材料附件。
5. `work.py` 的 `reduce_work`：核对收据后原子接受提案，继续计算后继失效。失败保留旧状态、推进记录游标；回放不请求模型。
6. 原有 `context.py`、`completion.py`：继续回取待重验来源并拒绝使用失效结果收尾。

## 一次请求的过程

假设 A 是原始统计，B 依赖 A，C 依赖 B，D 是独立发现。模型修正 A 后，B、C 失效。下一次 `propose_work` 只修改 B，并保留其他节点。

工具取出 B 的旧结论、当前 A 的说明和原文，以及候选 B。完整请求满足 Token 和字节预算后，模型返回以下一种结果：

| 判断 | 含义与后续行为 |
| --- | --- |
| `supported` | 原结论文字不变，当前证据仍支持；核对来源与版本后允许换绑 |
| `revised` | 候选结论已修正并受当前证据支持；接受后让后继继续重验 |
| `withdrawn` | 原结论应撤回，提案必须删除它或标为 rejected；后继不会自动成立 |
| `insufficient` | 结论错误、条件不明或证据不足；保留旧状态并反馈缺口 |
| `blocked` | 上游仍失效、缺失或同批改变；先提交上游再重验 |
| `unverified` | 协议、引文、模型或容量不满足核验要求；不能冒充正确拒答 |

正向判断需要引用每个当前上游的原文证据组。引用必须在对应片段中唯一、精确定位；它证明引用存在，不能证明语义蕴含。允许增加已经接受且有效的新上游，不能悄悄移除旧依赖；新增上游与下游重验需分次提交。经重验可以将假设提升为有来源的结果。

每段证据有显式的 `evidence_index`，每个目标同时给出 `parent_evidence_groups`。同一文档的不同区间仍是不同证据项；模型无需猜测数组下标，也不能用文档编号替代区间编号。

接受 B 后，C 绑定的 B 版本仍然过时；模型随后重验 C。D 的内容和版本保持不变。若一个提案包含多个目标，其中任何一个失败，整个工作提案不更新；其他业务工具已经成功的结果仍然保留。

## 预算与执行承诺

- 仍使用至多六个工作节点和 8 KiB 工作状态；完整材料放在由提案引用的 Artifact 附件内。
- 每个提案至多一次批量审查，最多六个目标。材料包上限 64 KiB，模型结构化输出上限 16 KiB；完整请求（包含 Schema）还要经过真实计量器准入。不能通过截掉必要原文来获得正向接纳。
- 工具最长 60 秒，内部模型调用最长 45 秒，并受 Runtime 剩余期限约束。取消向上传播，不重试、不创建后台任务。
- 审查调用属于工具内模型调用，不计入主 Agent 的 `max_model_calls`。它受工具次数和父期限约束；这不是跨阶段总 Token 强制预算。实验记录额外调用与供应商 Token，不能只报告主循环成本。
- 原文只能通过 `ToolContext.read_artifact` 读取。材料附件的写入不代表提案已接受；孤立附件不能成为完成事实。
- 新状态和带收据提案采用 v3。默认关闭时继续使用原 v2 行为；读取 v1/v2 不自动开启新策略。由于输出 Schema 新增可选收据，关闭策略时的工具描述也从 v5 升为 v6；启用时版本还绑定审查策略。旧运行不会静默跨版本恢复，继续遵守现有配置兼容规则。

## 如何验证

```bash
uv run pytest tests/harness/test_work_recheck.py tests/harness/test_work_dependencies.py
uv run python -m examples.work_recheck

# 显式真实模型对照，需 WEAVRIA_MODEL_BASE_URL / NAME / API_KEY。
uv run python -m examples.work_recheck --live --output .weavria/work-recheck/results.json

# 固定真实轨迹中的失效起点；仅测候选接纳，不测规划或最终任务收益。
uv run python -m examples.work_recheck_replay \
  --trace .weavria/work-recheck/results-code_revision-0-False.trace.json \
  --case code_revision
```

确定性测试走真实工具、Artifact 和状态归约，覆盖逐层重验、独立分支、证据不足、引文错误、多个上游的引用覆盖、假设提升、计划调整、权限、容量、超时、取消清理、收据错绑/重复、旧工具绕过、旧格式兼容，以及推荐入口上的完成拦截、SQLite 重开和输入去重。Fake 判断仅验证执行机制。

真实实验材料冻结于 `tests/fixtures/work_recheck/tasks.json`，包含仓库源码前后片段、原设计与新设计、未变化的设计材料三项任务，保留原文摘要和来源提交。宿主不预填答案、工作笔记或依赖图；模型按分阶段资料复核的用户任务形成记录。最终两个布尔结论独立评分，是否声明依赖、出现失效、触发重验和成功交付分别记录。任务字段与评分答案不传给工具。

两组使用相同模型、任务和预算，但初始模型轨迹可能不同；因此端到端结果不能单独归因为审查机制。固定起点回放另从真实轨迹提取状态和候选，并加入明确错误的反例；它不把未核验或结构性拒绝算作语义上正确识别了反例。

## 实验记录与当前边界

2026-11-13 的开发版首个源码任务：原策略正确完成（8 次模型调用），重验策略在形成工作记录前无进展失败（6 次）。随后三任务完整开发对照：原策略 3/3 正确，重验策略 1/3 正确。重验组的源码题没有触发重验；文档题产生一次未核验收据；未变化材料题在形成依赖前失败。不能将这些结果包装成策略收益。

固定起点开发回放揭示了两类边界：源码轨迹的中间计划没有原文来源，无法提供上游证据；文档轨迹把新增上游和下游换绑放在同一提案中。当前实现已将同批新上游提前阻断并给出修复提示，也修复了假设提升为结果的误拒。普通非结果计划不再受到语义重验约束。原文引句的转述或拼接仍会成为未核验结果。

另一次完整复测仍是原策略 2/3、重验策略 1/3，重验组没有实际生成审查收据。随后固定该轮文档任务的真实起点，显式把原有假设作为结果使用，暴露了区间编号歧义：模型引用的句子确实存在，却指向同一文档的另一区间。v3 增加显式编号，保持原文匹配规则不变。相同候选回放中，原候选获 `revised` 并接受；错误候选得到 `unverified` 并保留旧状态，不能把后者算作语义拒答成功。每个候选额外调用模型一次。假设提升是受控探针，不能算作自然任务规划收益。

### v3 最后一组完整对照

模型为 `deepseek-flash`，temperature=0，reasoning_effort=none，输出上限 4096，输入窗口 64000；每项任务至多 16 次主模型调用、24 次工具调用、180 秒。每组完整运行三项任务各一次，不挑选不同轮次中的最佳结果。

| 任务 | 原策略 | 显式重验 |
| --- | --- | --- |
| 源码前后版本 | 无进展失败 | 无进展失败；产生 blocked 收据 |
| 设计文档补充 | 正确完成 | 正确完成；未实际触发模型重验 |
| 未变化的材料 | 正确完成 | 无进展失败 |

结果为原策略 **2/3**、重验策略 **1/3**。两组轨迹存在差异，不能把所有失败归因于审查器，也没有依据宣称其提高任务成功率。`final_stale` 包括计划和假设；它不等于仍有失效结果被放行。此次完整对照没有一次正向模型重验接纳，因此只能与固定起点探针分别解释。

原策略总计 25 次模型调用、217195 个供应商 Token、68.03 秒；重验策略为 28 次、264463 Token、79.78 秒。两组 Token 报告均覆盖全部调用，时间为三项任务累计墙钟时间。该小样本同时包含主循环与准备成本，不能将差值全部解释为审查模型的直接成本。

本地完整记录位于 `.weavria/work-recheck/`：`development.json`、`validation.json`、`final.json`、`release.json` 分别保存各轮完整结果；`replay*.json` 保存所有固定起点探针，`.trace.json` 保存标准化执行事件。原始输出不进入 Git。实验在保留任务开始时已有修改的当前工作区执行，实验两组共享同一实现；记录模型配置、材料摘要及实现摘要。收口时另修正了类型标注和关闭模式的工具描述版本；这些不改变重验算法，未为版本标签重跑昂贵模型实验，记录中的实现摘要仍以实际运行时为准。

工程验证：全量 pytest **1899 通过、24 跳过**，跳过项均为需要显式 Docker 镜像的原有集成测试。最后的区间编号修复后，重跑本机制及既有依赖回归 **33 项通过**；全仓 Ruff、格式检查和 Pyright 通过。上述工程证据不替代真实收益验收。

本能力不会因契约测试通过而默认开启。尚未实现自动发现漏声明依赖、任意新资料的冲突检测、删除父节点后的自动语义协调，或模型审查的真值保证。下一步应根据完整失败轨迹研究模型工作记录的来源和依赖质量，以及精确引文协议的交付成本，不能继续无条件叠加审查轮次。
