## 能力变化和问题

此前一个 `/text` 字段可以同时把四个不同问题标成 satisfied。现在结构字段齐备进入 acquired，
语义证据自身覆盖完整需求才进入 satisfied。工具与上下文保留继续分析资料的机会；工作记录
中的带来源结论降低相应探索权重，未决问题提高权重并参与检索查询。模型主动 Finish 仍可交付
未经独立核验的综合回答，简单任务不必写笔记。

这不是自然语言答案验证器，也没有增加一个规划 Agent。模型必须承担原文理解、比较和形成
结论的工作，Harness 负责让这些进展能够持续影响执行。详细取舍、算法和兼容规则见
[ADR 0081](decisions/0081-区分资料获取与问题分析进展.md)。

## 一次请求如何流转

1. TaskUnderstandingEngine 保留用户提出的具体问题，而不是把目标改写成“读取文件”。
2. Runtime 接受读取结果后，EvidenceResolver 检查字段、作用范围与时间条件，形成 acquired
   或其他资料状态；读取成功不会直接证明问题已解决。
3. 模型可以继续读取、回取 Artifact 或提出工作笔记。propose_work 仍只生成提议 Artifact，
   TaskAwareSessionPreparer.refresh 中的 reduce_work 按接受顺序归约，沿用版本与取消语义。
4. work_analysis_status 把笔记与需求的来源地址关联。只有来源适用的 result 能降权，issue
   优先于 result；删除笔记后重新分配，不维护另一套不可见的完成标记。
5. AdaptiveCapabilityPolicy 与 project_context_focus 使用同一份权重。下一次模型请求看到
   当前问题、资料状态、工作摘要及按需选择的原文，继续自行决定行动。

组合测试中，两个问题都已取得资料、工具预算只有一个位置：为 alpha 写入带来源结论后，
工具选择转向 beta；给 alpha 增加未决问题后又转回 alpha。上下文需求权重同步改变，原始来源
锚点仍保留。错误来源不能降权，笔记不能改写 NeedLedger。这是机制验证，不是模型能力收益。

## 诊断结论

- **修复已在真实路径出现。** 候选一 documents coverage-1 的最后请求中，四个实际问题均为
  acquired/analysis_pending，read_document 仍可用，ProgressNotice 要求 continue；宿主不再
  用原文字段覆盖触发需求完成或提前 synthesis。
- **检索语境仍不足。** 该请求的 `/text` 片段包含配置示例中的 `memory_write="basic"`，
  模型把示例值当成推荐默认值；输出只引用聚合文件，没有保留所需原文件路径。候选二有一次
  文档回答四个字段都正确，仍缺必要来源和长任务行为，按冻结规则继续记失败。
- **回取还不能稳定转成结论。** 候选一 repository coverage-1 已主动提出 read_artifact，
  但连续分页请求超出反馈预算，缩短到 3000 字节后仍差 54 字节。精简说明后，候选二两组
  各有两次实际回取，但仍出现 admission_replan_exhausted、finalization_evidence_unavailable
  或错误答案。没有放宽反馈或上下文检查来绕过问题。
- **模型协议与工作记录采用仍有缺口。** 候选二文档有三次 model_output_repair_exhausted，
  两个候选都没有提出工作记录。不能将所有失败都归因于模型，也不能断言改一条提示就会解决。
