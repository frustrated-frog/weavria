# 统一框架独立接入与源码流程

本文提供同一个公开入口上的两个自由提问示例：项目文档研究、代码仓库只读分析。不依赖 FinScope，
不加载 M1 的题目或评分答案。两者使用维护在仓库中的原文 JSON 归档，工具只能读取已加载的原文，
不能访问任意宿主文件。示例中的模型真实决策，不预填 TaskFrame、工具顺序、工作笔记或记忆。

当前 M1 未达成。命令用于独立接入和观察实际失败，不能当作稳定完成任务的承诺；已知问题见
[验收问题清单](统一框架验收问题清单.md)。CLI 保留原有 64000 窗口、128000 请求字节上限和
120 秒 Run 期限，不与冻结的 M1 32K 实验混算；真实模型必须支持调用方声明的窗口。

## 运行两个示例

在仓库根目录执行 `uv sync`。在本地环境设置 `WEAVRIA_MODEL_BASE_URL`、
`WEAVRIA_MODEL_NAME`、`WEAVRIA_MODEL_API_KEY`；使用当前模型时前两项分别为
`https://api.deepseek.com` 和 `deepseek-flash`。API Key 由本地环境注入，不写进脚本或仓库。

文档研究：

```bash
uv run python -m examples.harness_session \
  --snapshot examples/data/m1_harness/corpus.json --scene documents \
  --state .weavria/independent-documents --session research --input-id question-1 \
  --working-records --memory \
  --message '结合原文说明记忆形成失败会怎样影响已经完成的回答，并引用实际读取的文件路径。'
```

代码仓库分析：

```bash
uv run python -m examples.harness_session \
  --snapshot examples/data/m1_harness/corpus.json --scene repository \
  --state .weavria/independent-repository --session analysis --input-id question-1 \
  --working-records --memory \
  --message '追踪 AgentHarness.send 到关闭清理的源码流程，说明请求与存储的生命周期，引用文件路径和符号。'
```

两项通过不同 `--state` 隔离存储。同一项目的后续会话保留 `--state`，改用新的 `--session`；
同一会话追加问题时保留 session，使用新的 input-id。重试完全相同的输入时保留原 input-id，
框架复用已完成结果并可续接记忆形成；不要将同一个 input-id 用于不同消息。

若输出 `pending_clarifications`，保留相同 state/session，用新的 input-id 发送补充信息，
并传入输出中的 `--clarification-id`。这样补充会续接原 Work，而非另开一个无关工作。

输出分别包含 `status`、`output`、`prior_memory` 和 `memory`。先看执行状态，再看结果是否正确；
记忆报告中的 admitted 数量仅指准入，不证明之后一定召回、正确修订或被模型使用。
原始会话和来源位于 state 下的 `session.db`，记忆和形成计划位于 `memory.db`。

若要使用未声明生效起点的项目约定，在 `--memory` 后加 `--include-unknown-time`。
Python 接入对应 `HarnessMemory(..., include_unknown_time=True)`。它让模型看到标记为时间未知
的完整事实组，不推断其当前一定有效；默认 False 保留严格时间查询。明确的“从现在起改为新值”
可以替代 unknown 旧约定，旧知识仍可按 head 查询，详见 ADR 0080。未来变更仍会延后。

## 宿主实际提供什么

`examples/harness_session.py` 只构建模型适配器、计量器、工具注册表、存储路径和项目授权。
`snapshot_tools` 根据应用选择加载文档或源码，复用 `examples/m1_corpus.py` 的只读工具；不导入
`examples/m1_harness.py`，也不读取 `cases.json`。用户可以把 `--message` 改为其他自由问题。

应用通过 `HarnessConfig` 开启工作记录和 basic 形成，通过 `HarnessMemory` 绑定同一项目的
读写作用域，再调用 `AgentHarness.from_config`。这些场景名称只在示例应用中出现，框架核心
不识别文档研究、代码分析或具体问题。真实多用户服务应从身份认证结果构建授权，不能复用示例的
固定单用户身份。

## 沿一次请求阅读源码

| 阶段 | 入口与关键数据 | 如何连接下一阶段 |
| --- | --- | --- |
| 配置装配 | `harness/assembly.py`：`AgentHarness.from_config` | 建立理解、上下文来源、工作记录与记忆形成组件；SessionEngine 仍是唯一会话执行引擎 |
| 接受输入 | `AgentHarness.send` → `sessions/engine.py`：`SessionEngine.send` | 父期限包含前置记忆追赶、执行与后置形成；input_id 幂等判断先于新的模型执行 |
| 任务解释 | `harness/session.py`：`TaskAwareSessionPreparer`；`harness/understanding.py` | 由原始 TaskInput 和上下文形成 TaskFrame、信息需求及完成条件；澄清通过持久 Work 续接 |
| 选择行动能力 | `harness/working_set.py`：`AdaptiveCapabilityPolicy` | 根据未完成需求和已有状态选取当前业务工具；工作记录和来源恢复由框架支持工具提供 |
| 构建模型输入 | `harness/task_view.py`；`harness/memory_context.py`；`context/compiler.py` | 将 Frame、NeedLedger、WorkingState 投影成模型视图；召回授权记忆组，与历史和工具材料共同分配预算 |
| 执行与更新 | `runtime/agent.py`；`harness/requirements.py`；`harness/work.py` | 校验模型动作、管理工具与反馈；已接受结果更新需求，工作提案经版本和来源校验后归约 |
| 原文恢复 | Context 的回取机制与 Runtime 的 `read_artifact` | 模型根据缺口取回已接受的原文；恢复本身不表示任务已完成 |
| 完成与形成 | Completion 检查 → Session 提交 → `harness/memory_session.py`、`memory_formation.py` | Run 结果先稳定提交；仅从符合策略的已接受用户输入形成记忆，形成故障不会抹掉成功回答 |
| 下一会话 | 同一存储和项目授权上的 MemoryContextSource | 对下一任务重新查询，而不是把整个历史自动塞进 Prompt；时间和相关性筛选仍可能排除记录 |

需求账本回答“还缺什么、哪些工具结果已被接受”；工作记录保存有来源的简短计划、结果、失败尝试
和下一检索需求；上下文编译器决定本轮实际展示哪些内容。三个状态有不同职责，不能用一份自然
语言摘要替代全部状态。记忆跨会话保存可复用事实，但不会自动满足当前任务中必须通过工具取得的
外部证据义务。

采用这条链路的原因是复用已有模块职责与执行语义，让宿主只声明配置。它也暴露出当前组合限制：
基础容量预留较高；工作工具暴露不保证模型主动使用；unknown 时间记忆和后续明确变更尚未形成
可用闭环；完成检查不能证明全部自然语言结论正确。这些限制已经列入问题清单，不由演示掩盖。

## 观察与验证

```bash
# CLI 参数检查与两种工具装配不需要模型；实际命令会访问已配置模型。
uv run python -m examples.harness_session --help

# 推荐入口的确定性组合回归。
uv run pytest tests/harness/test_m1_session_chain.py tests/memory/test_configured_harness.py -q

# 真实任务的冻结配置、原文散列与规模检查，不调用模型。
uv run python -m examples.m1_harness
```

本次已验证 CLI 帮助、两个原文工具注册表及类型/格式检查；自由提问命令未作为额外成功样本运行。
真实能力以完整 M1 实验结果为准。下一步先处理已记录的组合断点，不添加新的框架模块。
