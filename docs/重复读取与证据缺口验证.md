# 重复读取与证据缺口验证

日期：2026-11-13。范围：继续核查 ADR 0123 实验中的重复读取和 `missing_evidence`。本轮交付诊断程序、受控反例和验证记录；Runtime、证据策略、预算和完成门禁均保持原行为。

## 结论与证据强度

1. **已确认时效性缺口的具体来源。** 文档失败轨迹把名为 `current` 的固定版本解释成 `freshness=current`。`/text` 已存在，缺的是 `$freshness`。默认结构提取器不能证明实时性，重复读取相同资料不会补齐它。
2. **已确认工具接入缺少版本范围。** 实验的 `read_source` 没有配置带参数匹配的证据范围。默认结构提取器按工具名和字段存在性匹配，因此只有 original 的记录也会计入 current 的需求。这是当前实验接入和需求绑定的限制；结构覆盖不能证明版本或语义正确。
3. **全文替换未消除重复读取。** 固定实际请求，仅把已有 original 的片段展示换为完整原文，每组重复三次，模型都再次提议读取 original 和 current。不能把重复读取完全归因于原文被截断；任务进展表达、工作记录意图与模型行动选择的因果关系仍未查清。

以上三项分别来自确定性回放和真实模型干预，不等于端到端能力改善，也没有理由开启默认语义重验。

## 一、缺的是时效性，不是正文字段

历史输入为 `.weavria/work-recheck/binding-final-document_revision-0-True.trace.json`。通过冻结任务集重建三个已接受的资料 Artifact，逐一核对完整 ArtifactRef（包括内容摘要），再让现有 `EvidenceResolver` 计算投影。

current 文档需求在真实轨迹中为 `partial`，`missing_fields=["$freshness"]`，但绑定都包含 `/text`。源码路径：`harness/requirements.py` 的 `StructuralEvidenceExtractor.evaluate` 对 `freshness=current` 返回 `freshness=unknown`；`harness/completion.py` 将尚未取得完整证据的需求汇总成 `missing_evidence`。模型侧需求视图保留 `$freshness`，但最终完成反馈只有通用的“获取缺失字段或说明限制”，没有解释当前工具为什么不能提供时效性证明。

在**离线探针**中仅把该固定材料的时效性要求改成 stable，原有记录就得到 acquired。这个变更仅用于定位因果，不应用到旧运行或正式策略。需要实时行情、最新状态等任务仍必须有真实时效证据，不能全局删除 freshness 校验。

本轮另做两次完整源码任务以采集实际请求。关闭重验组再次在 `freshness=current` 的需求上留下 `$freshness` 并被完成门禁拒绝（7 次模型调用，54157 个供应商 Token）；开启组因重复读取失败（6 次，34890 Token）。两次都没有触发模型重验，保留于 `diagnosis-context.json`，不作为新旧策略效果比较。

## 二、版本范围与语义证明必须分开验证

对上述历史文档轨迹做以下确定性干预：

| 需求与输入 | current 需求状态 | 绑定的资料版本 |
| --- | --- | --- |
| 原需求、全部记录 | partial，缺 `$freshness` | original 与 current |
| 仅改为 stable、全部记录 | acquired | original 与 current |
| stable、只保留 original 记录 | acquired | 只有 original |
| 显式约束 `/version=current`、只保留 original | pending | 无 |
| 同一约束、全部记录 | partial | 只有 current |

范围干预使用已有 `EvidenceMatchPlan` 和 `EvidenceParameterMatch`，由分析者明确指定目标 need ID，**不是模型自动识别的成绩**。最后一行仍是 partial，因为 profile-bound 需求要求 scoped_semantic，结构字段覆盖不能冒充语义证明。这个反例同时说明：不能仅给需求补版本约束就宣称完整解决，也不能通过降低 proof 要求使测试“通过”。

复现程序为 `examples/work_recheck_diagnosis.py`，本地结果 `diagnosis-binding.json` 记录输入、实现摘要、分析者指定的范围及各变体。它只读取标准事件和冻结材料；材料不匹配时明确失败。

```bash
uv run python -m examples.work_recheck_diagnosis \
  --trace .weavria/work-recheck/binding-final-document_revision-0-True.trace.json \
  --case document_revision \
  --version-need need-a61a6a06eb8df1244dd0ce8c=current \
  --output .weavria/work-recheck/diagnosis-binding.json
```

## 三、固定模型请求的展示方式干预

在 `examples/work_recheck.py` 增加显式 `--capture-requests`，只为本地冻结语料诊断保存规范 SessionRequest，不记录认证头、原始供应商响应或私有推理。默认不开启；原始请求留在被忽略的 `.weavria/`，不提交 Git。

所选请求为 `diagnosis-context-code_revision-0-True.requests.json` 的第二次调用：模型已读过 original，工作图为空，四项需求都显示 acquired / analysis_pending，其中两项实际要求 current。请求中确实有源码；六个 `/text` 片段累计 5076 字符，合并后只有 `[0,2182)` 的 2182 个字符，原文总长 2502。片段重叠与 320 字符未交付均可确认。

探针只把已接受的 original 展示还原为完整原文，保留 Artifact 身份、任务、需求、反馈、工具目录和模型配置；不会补尚未读取的 current。重建前检查冻结文档摘要。模型给出的新行动只记录，不执行工具，所以没有更新状态或改变证据。

| 变体 | 输入计量 Token | 传输字节 | 三次下一步决策 |
| --- | --- | --- | --- |
| 实际捕获的片段请求 | 5430 | 23387 | 均再次读取 original，同时读取 current |
| 仅将 original 换为完整原文 | 4708 | 20047 | 同上 |

完整原文减少了重叠文本，输入 Token 少约 13.3%，但这个固定起点上的重复读取没有消失。两组各三次供应商总 Token 分别为 17193、14883。模型为 deepseek-flash，temperature=0，reasoning_effort=none，输出 4096，上下文窗口 64000，字节预算 128000；交替组顺序，每个请求只问一次下一步行动。温度为零不构成确定性保证，回放行动也不要求逐字等于自然运行。

```bash
# 有显式模型环境配置时才运行；默认 probe 不调用模型。
uv run python -m examples.work_recheck --live --capture-requests \
  --case code_revision --output .weavria/work-recheck/diagnosis-context.json
uv run python -m examples.work_context_probe \
  --requests .weavria/work-recheck/diagnosis-context-code_revision-0-True.requests.json \
  --call 2 --live --repeats 3 --output .weavria/work-recheck/context-probe.json
```

`--capture-requests` 的再运行可能产生不同轨迹，默认第 2 次调用不保证又是同样的失效起点。重现上表需使用本轮保存的捕获文件及其报告摘要，新的轨迹须重新检查。探针的摘要绑定原始捕获文件和两个实际请求，禁止把另一次任务的较好表现替换进本次结果。

## 工程验证与下一步

新增 `tests/evaluation/test_work_diagnosis.py`，验证时效性和版本范围可独立操纵、错误版本被范围约束排除、正确版本不自动提升证明强度，以及全文干预保留所有非材料字段、拒绝篡改语料。它们是归因探针的执行承诺，不是 Agent 能力测试。

相关测试 73 项通过，全量 pytest **1921 通过、24 跳过**；跳过项均需要显式配置 Docker 测试镜像。全仓 Pyright、Ruff、格式检查通过。全部实验在保留任务开始时八处已有修改的工作区运行，报告扩大了实现摘要范围，纳入需求、覆盖、视图、模型适配与 outcome 契约；不能把工作区结果等同于只含本轮提交的干净 checkout。

后续应先设计并验证**需求到具体资料版本的绑定**，区分命名版本和实时性要求，并让失败反馈明确是字段、版本、时效性还是证明强度不足。这一步需要真实输入约束和来源身份，不能靠 original/current 关键词特判、关闭无进展保护或放宽完成门禁解决。重复读取的其他原因仍需进一步隔离。
