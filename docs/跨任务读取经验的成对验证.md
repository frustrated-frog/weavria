# 跨任务读取经验的成对验证

2026-11-21。在 Weavria 的公开发送入口验证一件事：一个 Run 的读取拿到了完整原文，后续 Run 换了问题和来源，沿用上次的选源经验还能省掉哪一次读取，又会把模型引向哪里？

## 实验边界

每次实验都新建会话和数据库。先实际执行一次只读任务，得到一条已结算的经验。正例是读取 httpx 的发行元数据并收到完整文档。负例是读取 httpcore 的命令入口文件，工具报告该文件缺失。目标任务只能读自己的两项候选，模型能看到两项路径和同一条历史对话。八个跨任务案例各自改变目标措辞，两条候选路径也都与前一任务不同。另外两个对照分别只调换候选顺序、只改写目标并调换顺序。

原文来自基准提交 `1983fa4` 的锁定环境中十个 Python 安装包的公开 wheel 元数据。虚拟路径省略版本目录，避免从路径猜中发行号。`METADATA` 快照选取名称、发行版本、元数据版本和 Python 约束四个头字段，`WHEEL` 和已发布的 `entry_points.txt` 保存文件内容。两处预期缺失已在安装包中核对。实验所称“完整交付”指工具返回了对应快照全文。冻结语料 SHA-256 为 `f1c3b0cd94da4c82f223cd9275c5a041d6d8b47190408733c30f62cfe3d7a373`。[冻结语料](../examples/data/read_retry_transfer/wheel_headers.json)

每组都先固定两项读取，实际触发反馈预算拒绝。分组只影响首次提案中候选的排列，拒绝通知、权限检查、执行和持久化均走正式链路。

- **现行精确匹配**沿用原始候选顺序，由 Runtime 按 ADR 0144 对当前目标和候选集合查询经验。
- **按同名文件迁移**是实验策略。回放器用新 Run 的身份读取同会话旧现场已核验的结果。上次完整交付则前移唯一同名文件，上次工具失败则后移。两个候选都同名、都不同名，或收据只有节选或引用时，维持原顺序。决策只读取旧动作路径、交付类别和新候选路径。核对答案和指定证据源只用于评分。

这个设计给迁移组提供了正确的历史现场键，是对“已找到相关经验之后如何使用”的验证。实验没有测试从长历史中自主找出相关任务的能力。两组拥有相同对话历史，因此模型也可以从聊天记录自行推断。

## 如何评分

真实模型使用 `gpt-6-luna` 和 `medium` 思考强度。每个案例每种策略运行两次，两轮交换先后次序。固定的首个提案之后，模型可接受建议、直接选择另一份文件或继续读第二份。每个目标 Run 的上限为五个模型决策轮次、四次工具调用。逐组比对候选集合、拒绝所需字节和当时的反馈预算。

1. **建议命中**看宿主是否推荐包含所问字段的文件。**首读命中**看第一条真正执行的读取，模型可以忽略建议。
2. **原文到达**逐条核对目标 Run 的模型请求。工具名、来源参数、完整交付标志和正文都须匹配冻结原件。
3. **有据答对**同时要求原文到达、最终答案去除两端空白后与独立标准值完全相等。猜中一个常见版本号不算有据答对。只运行本地确定性回放时，仅记录动作与交付，回答质量保持未评。

## 观测结果

下表只统计八个跨任务案例，每格为两次运行的合计。指定证据源是能够直接回答当前问题的文件。精确匹配组的历史命中为 0/16，两组的目标原文最终均到达模型 16/16 次。

| 当前任务 | 指定证据源 | 现行组首读命中 | 迁移组首读命中 | 实际读取次数（现行 / 迁移） | 有据答对（现行 / 迁移） |
| --- | --- | ---: | ---: | ---: | ---: |
| pluggy 发行版本 | METADATA | 0/2 | 2/2 | 4 / 2 | 2 / 2 |
| starlette 的 Python 版本约束 | METADATA | 1/2 | 2/2 | 3 / 2 | 2 / 1 |
| httpcore 的 wheel 格式版本 | WHEEL | 2/2 | 0/2 | 2 / 4 | 2 / 2 |
| fastapi 命令的入口函数 | entry_points.txt | 2/2 | 2/2 | 2 / 2 | 2 / 2 |
| h11 发行版本 | METADATA | 1/2 | 2/2 | 3 / 2 | 2 / 2 |
| uvicorn 命令的入口函数 | entry_points.txt | 2/2 | 0/2 | 2 / 4 | 2 / 2 |
| 两份元数据中选择 click 的版本 | click/METADATA | 2/2 | 2/2 | 2 / 2 | 2 / 2 |
| 构建 pytest wheel 的生成器 | WHEEL | 0/2 | 0/2 | 4 / 4 | 2 / 2 |

**复用有收益的条件。** 从 httpx 转到 pluggy 后，发行版本依然由发行元数据记录；两次都省掉了先读 wheel 描述文件的步骤。starlette 的 Python 约束也在元数据里，迁移组两次直接读到原文，其中一次最终回答没有通过逐字评分。现存指标只能定位到原文交付之后，无法还原当次具体输出差异。负经验在 h11 上也节省了一次读取，前提是它和 httpcore 确实都缺少命令入口文件。

**误导出现在哪里。** 从“发行版本”转到“wheel 格式版本”，两个问题都有“版本”，直接依据却从 METADATA 变成 WHEEL。迁移组两次都先读了完整但答非所问的原文，再补读 WHEEL。把 httpcore 缺少入口文件的经验套给 uvicorn 也有相同代价；uvicorn 自己的入口文件实际存在。fastapi 任务中，宿主两次都建议先读 METADATA，模型两次都直接选择了命令入口文件，因此建议虽错，首读仍然正确。

**缺乏区分力的经验。** click 案例有两份同名元数据，依据文件名无法识别任务实体；pytest 的两个候选中没有和旧成功来源同名的文件。迁移策略两次都维持了各自的原顺序。click 任务中模型能利用包名选择正确文件，pytest 任务中两组均先读入口文件再补读 WHEEL。

| 八个跨任务案例，两轮合计 | 现行精确匹配 | 按同名文件迁移 |
| --- | ---: | ---: |
| 宿主建议命中指定证据源 | 6/16 | 6/16 |
| 模型实际首读命中 | 10/16 | 10/16 |
| 有据答对 | 16/16 | 15/16 |
| 实际读取次数 | 22 | 22 |
| 真实模型调用次数 | 38 | 38 |
| 供应商报告的总 Token | 72,527 | 72,549 |

两个额外对照单独看。目标和候选相同、仅换顺序时，现行策略两轮都命中旧经验。仅改写目标时，现行策略两轮都没有命中，实验策略两轮都推荐了正确文件。这四组配对中出现两次“答案正确、目标 Run 没有实际读取”的情况，均按缺少本轮证据处理。包括对照共 40 个目标 Run，94 次真实模型调用均返回 HTTP 200；每个 Run 的真实调用数都等于记录的决策轮数减去固定首轮。

## 判断与复现

就这批案例，继续使用现行精确匹配。按文件名放宽后，三类任务的建议从错变对，另外三类从对变错，整体读取成本没有下降。更值得验证的下一种经验是“哪个来源负责哪个字段，以及这条观察适用于哪个实体”。一次完整交付能证明该次可读，一次工具失败只能证明当次未能读取。八个跨任务案例全部来自安装包领域，每种策略每个问题重复两次，结果只用于识别机制边界。

以下命令分别复现确定性现场、契约测试和两轮真实模型对照。`--out` 接受新的 JSONL 路径，逐次记录预算、宿主建议、实际读取、原文交付、评分和成本。`--case` 可单独选择表中案例，案例标识见[实验入口](../examples/read_retry_transfer.py)。

```bash
uv run python -m examples.read_retry_transfer
uv run pytest -q tests/test_read_retry_transfer.py
uv run python -m examples.read_retry_transfer --live --env-file .env.m1-openai --round 1
uv run python -m examples.read_retry_transfer --live --env-file .env.m1-openai --round 2
```

后续将带字段证据和实体绑定的条件判断接入了 Runtime。启用方式与同一语料上的对照见 [ADR 0147](decisions/0147-按实体与字段条件复用单读经验.md)。
