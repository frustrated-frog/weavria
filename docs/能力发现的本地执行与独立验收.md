# 能力发现的本地执行与独立验收

这一轮把能力发现接入真正的工具执行与结果验收：模型自行选择工具、参数和调用顺序，运行结束后，再由模型看不到的答案和执行证据判定。设计见 [ADR 0127](decisions/0127-能力发现的本地执行与独立验收.md)。没有新增 Runtime 依赖或修改核心持久化协议。

## 本次解决的问题

此前实验停在 `TaskUnderstandingEngine.prepare`，能回答“选中了哪些工具”，不能回答“是否完成任务”。新的入口 `examples/live_capability_execution.py` 完整调用 `AgentHarness.send`，经历发现、解释、动态工具视图、Runtime 调用、Artifact 归档、完成检查及 Session 关闭。

固定任务包含文件指纹、文件大小和修改时间、归档版本差异、先查位置再求指纹、带重叠区间的日历空闲窗口，以及删除能力缺失、本地正文读取能力缺失、无需工具的概念判断。7 个具体工具和 84 个模板干扰工具均有真实本地读取实现。干扰工具读取自己的领域/视图元数据快照；它们的任务难度仍远小于真实业务系统，不能据此宣称已经覆盖复杂企业目录。

环境数据和任务判定分为两个文件：`capability_execution_environment.json` 只含数据，`capability_execution.json` 含原始问题、标准答案和证据路径。模型只收到问题和当前阶段可见的协议/结果，工具闭包不接收任务 ID 或答案。任务文件绑定环境字节摘要，修改环境而不更新任务清单会在调用模型前失败。

## 一次请求如何流转

以 `locate_fingerprint` 为例，用户只给 `release-17`，不提供对象路径。

1. `run_case` 建立独立临时目录，将二进制文件、资产目录、归档和日历数据写入本地文件；构造 91 项 `ToolRegistry`。
2. 混合发现召回卡片，模型提名能力；启用 fit 时展开完整协议并判断是否还需补搜。任务解释器生成执行规格。
3. 模型通过 `locate_asset` 获得当前路径，随后自行生成 `compute_file_checksum` 的参数。两个操作都由 Runtime 校验、授权和执行。
4. 工具结果形成 Artifact，Need 状态与工具视图按既有机制推进。模型提交最终 JSON，正常 Completion Policy 决定是否允许交付。
5. 运行结束后读取持久化 `ToolStarted`、`ToolRecorded`，检查答案、实际路径和调用依赖。前一步记录必须早于后一步的开始；同批调用中预猜路径不能通过依赖验收。
6. 提取诊断后关闭 Session 并删除临时目录。取消继续向上传播，已接受调用保留到实验输出。

日历工具使用排序加游标扫描：裁剪请求窗口，合并重叠/相接的忙碌区间，输出满足最小时长的最大空闲窗口。测试另用逐分钟占用格进行独立计算；任务标准答案为事先冻结的两个窗口。模型也可以只读忙碌区间后自行推导，判定器接受这条证据路径。

## 独立验收与证据强度

`answer_correct` 比较交付 JSON 与冻结答案，字典键顺序无关，类型、数组顺序和内容严格匹配；重复 JSON 键、用 0/1 冒充布尔值都被拒绝。

`evidence_satisfied` 检查成功的真实调用、对应参数和 Artifact 摘要，不能由模型自报调用成功替代。`task_success` 同时要求 Run 完成、正确交付和证据满足。无需工具/缺失能力任务要求零工具调用。对于缺失能力，成功交付的是明确的 unavailable 答复，不代表用户原本要求的删除或读取已经完成。

`safe_stop` 单独记录无工具调用的明确能力不足停止，或者正确交付 unavailable。发现返回 NO_PROGRESS 可以是合理停止，但没有交付答案时不算 `task_success`。模型异常、超时和普通准备失败不算安全停止。`expected_behavior` 是正确交付或明确安全停止的并集，不能当作实际任务完成率。

`unrelated_calls` 是调用的工具名不在任一冻结证据路径、也不是框架读取辅助工具的次数。它只是路径外调用指标：例如同时读取归档正文和包含正文的完整历史，正文调用会被记为路径外，未必真的与用户目标无关。错对象/错窗口由参数证据验收拒绝，不依赖这个计数。这个指标不参与任务成功判定。

工具路径只允许规范虚拟绝对路径和清单内对象。逐级 `openat` 配合 `O_NOFOLLOW`，拒绝文件/祖先符号链接、FIFO、超限文件、路径穿越和内部源文件的直接读取。每次读取最多 64 KiB，不创建脱离请求的后台线程。这是本地实验隔离，不能用来宣称实现了通用生产文件沙箱。

## 首次执行暴露的接入缺口

最初使用默认 `StructuralEvidenceExtractor`。真实模型为文件指纹等任务声明 `freshness="current"`，工具已经成功返回正确字段，但通用提取器无法证明时效性，Need 留在 partial，缺口为 `$freshness`。模型重复提交正确指纹仍被 Completion Policy 拒绝。这证明“工具选对并调用成功”不能代替完整链路验收。

修正属于本地适配器：`LocalSnapshotEvidence` 明确声明本次 Run 内无缓存读取当前本地快照的语义，只支持所绑定工具目录和版本的已授权成功结果，并核对 Artifact 身份。通用字段检查仍然生效；缺失字段、未知版本和不对应的 Artifact 都不能通过。原 Task/Need 的 current 要求没有改变，证据强度仍为 structural，通常只能推进到 ACQUIRED，不能证明答案或对象选择在语义上正确。

默认使用该适配器。`--evidence-mode structural` 可重现不接入时效性证明的组合；这不是放宽通用 freshness 规则，也不为其他工具提供默认“成功就新鲜”的推断。缺少参数作用域证明、模型声明错误字段等问题仍可能导致失败，后续应从具体记录分析。

## 运行与验证

默认命令只校验冻结清单，不调用真实模型：

```bash
uv sync --extra local-memory
uv run --no-sync python -m examples.live_capability_execution
uv run --no-sync pytest tests/test_live_capability_execution.py -q
```

真实运行需要通过环境变量配置 `WEAVRIA_MODEL_NAME`、`WEAVRIA_MODEL_BASE_URL` 和可选 API Key、reasoning effort。准备好本地 E5 权重和分词器后运行：

```bash
uv run --no-sync python -m examples.live_capability_execution \
  --live --repeats 2 \
  --model /path/to/multilingual-e5-small/model.onnx \
  --tokenizer /path/to/multilingual-e5-small/tokenizer.json \
  --output .weavria/capability-discovery/execution-new.json
```

输出路径必须不存在。实验逐行保存终态、参数、证据摘要、发现过程、完成检查原因码、最终 Need 缺口和供应商 usage；不保存凭据或私有推理。输出 Schema v2 增加证据模式和完成诊断；最初没有适配器的结果为 v1。

四组比较：混合发现、只检查、检查加两轮补搜，以及每次直接向执行模型暴露全部工具的基线。前三组执行配置一致，只改变发现配置；完整目录基线没有任务理解，因此不是只替换检索算法的严格消融。逐题轮换顺序，每题重复两次。模型温度 0、输出上限 4096、窗口 64000、请求字节 256000；准备最多 60 秒，父请求 180 秒，执行模型与工具各最多 12 次。准备内部另有共享调用/Token 账本，未把两阶段预算混称为一个总调用上限。

## 冻结实验结果

2026-11-14，模型为 deepseek-flash，reasoning_effort=none，其他参数如上。两次完整对照分别包含 8 任务 × 4 策略 × 2 次重复，共 128 次运行；另有一次单题诊断用于定位 freshness。数据与目录在两次对照之间保持一致：

```text
任务清单 SHA-256: 8dab70fd2f481c10a52d54ef4cad8f76fbe0a31b3afe2478ddccb24043f3b9c5
环境数据 SHA-256: a9d51fe86ea613baeb92fb8b62befe2719802348a5cb2b82a380bbf0e5c62960
工具目录 SHA-256: 7ca57b5e4be69265a60484dc857d43b0044e48d70e20239ca755d1a6df18ba61
```

初始组合未提供本地时效性证明：

| 策略 | 正确交付 | 正确交付或明确停止 | 模型调用 | 总 Token | 累计耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 混合发现 | 6/16 | 6/16 | 70 | 247,949 | 83.828 s |
| 只检查 | 3/16 | 7/16 | 61 | 203,818 | 71.680 s |
| 检查加补搜 | 2/16 | 6/16 | 86 | 286,347 | 95.421 s |
| 完整目录直接执行 | 16/16 | 16/16 | 28 | 200,503 | 25.323 s |

混合发现的 10 个需工具任务均已调用工具，却在完成阶段失败。单题诊断保留了正确 SHA-256 候选、有效 Artifact、Need 的 `$freshness` 缺口和 `missing_evidence` 完成拒绝；确定性回归测试复现同一因果链。完整目录基线没有任务理解和 Need 时效性门控，因此没有这个接入缺口，但独立答案/证据验收仍生效。

接通 LocalSnapshotEvidence 后重新完整运行：

| 策略 | 正确交付 | 正确交付或明确停止 | 模型调用 | 总 Token | 累计耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 混合发现 | 16/16 | 16/16 | 61 | 224,288 | 72.969 s |
| 只检查 | 9/16 | 13/16 | 59 | 199,567 | 74.785 s |
| 检查加补搜 | 9/16 | 13/16 | 83 | 280,267 | 97.821 s |
| 完整目录直接执行 | 16/16 | 16/16 | 28 | 200,552 | 26.529 s |

16 次中包含 4 次目录缺失任务，因此“正确交付”包含按用户要求返回 unavailable，不代表 16 次外部操作成功。检查两组均有 4 次 NO_PROGRESS，保护了执行边界，却没有交付用户要求的 unavailable JSON；另外各有 3 次真实失败：

- 归档版本比较两次都停止。检查已经支持正文和历史工具，但仍报告缺口；加补搜后累计扫描 72 张卡片也没改变判断。完整历史足够让执行模型比较两版，混合/完整目录组均成功。这里反映的是组合可行性判断不足，不能记成目录缺失。
- 日历题每组各有一次 `fit_support_pointer`。模型引用没有定位到真实协议字段，宿主按原规则拒绝；没有放宽引用校验或人工替换指针。每组另一轮成功，说明温度为 0 也不能视为完全确定。
- 补搜相对只检查多 24 次模型调用和 80,700 Token，没有增加本任务集的正确交付或明确停止数。部分额外成本用于真正无能力的请求，部分用于没有必要新增工具的比较任务。

本组任务和预算下，混合发现虽能正确交付，但 Token 比完整目录多约 11.8%，模型调用 61 对 28；不能声称大目录发现天然省成本。完整目录有足够窗口、任务短、输出小，因此是有竞争力的基线。耗时是本机端到端累计观察，同机还运行过工程检查，未做隔离性能基准；Token 和调用数来自逐次白名单 usage，所有调用都有用量记录。

结果保存在忽略目录 `execution-frozen-02.json` 和 `execution-frozen-03.json`，单题诊断为 `execution-diagnostic-01.json`，均位于 `.weavria/capability-discovery/`。第一次启动在配置序列化阶段失败，尚无模型调用；失败文件 `execution-frozen-01.json` 保留，修正使用嵌套配置的 JSON 序列化并补回归测试。第二次完整运行期间仅补充深层非法 JSON 的评测器异常保护和测试；发现提示词、检索、任务、工具协议和答案规则未改。最终判定器已重新离线验算两次全部 128 行，结果一致。

工程验证覆盖真实文件变化、独立日历算法、错对象和顺序、字段缺失、时效性来源、参数/路径隔离、FIFO/符号链接、取消/超时和临时环境回收。专项 31 项测试通过；全量 2017 passed、24 skipped（未配置显式 Docker 测试镜像），Ruff 检查、格式检查和 Pyright 均通过。Fake 测试只证明链路和执行不变量。

## 当前限制与下一步

这些是可执行的合成任务，包含有意义的参数依赖、二进制处理、区间计算与能力缺失，但还不是外部真实工作负载。重复两次不足以证明统计显著性，也不能证明长任务、动态目录或多轮上下文的收益。完整目录在这个规模与足够窗口下仍是必须认真对待的基线。

本步未新增执行中主动搜索、通用语义成果判定或从失败自动学习。下一小步应优先深化适用性检查的组合可行性：区分必须由外部工具完成的获取/副作用，与取得证据后可由模型完成的比较和综合；保留本轮失败任务，再设计相应表示和停止规则。协议引用错误的有界恢复也需要独立验证，不能用降低引用校验来解决。
