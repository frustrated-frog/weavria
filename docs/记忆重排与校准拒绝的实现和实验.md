# 记忆重排与校准拒绝的实现和实验

## 本次解决的问题

原有混合检索给候选排名，再按需求覆盖和字节成本选择。它无法表达“最高排名仍不相关”，因此无答案请求也会被塞入一条记忆。本轮加入完整事实组的交叉编码重排、独立无答案样本的秩校准，以及可追踪的拒绝和无法评估状态。

新路径显式启用。默认保持原行为。这里的接受只表示值得供给为参考材料，不证明记忆为真、条件已满足或足够完成回答。

## 调用链与数据结构

```text
HarnessMemory.retrieval / MemoryContextSource
  → SQLiteMemoryStore.retrieval_snapshot：授权和双时间筛选
  → TaskMemoryRetriever：逐需求 BM25 / Dense 与组级融合
  → MemoryReranker.assess：完整组配对、打分、拒绝或扣留
  → TaskMemoryRetriever：按剩余关联的名次做覆盖和预算选择
  → Harness：转换并验证 ContextSupplyReport v3
  → ContextCompiler：整组进入模型请求或因预算整体省略
  → Session 事件：持久化供给、校准身份和省略诊断
```

`MemoryPairScorer` 接收 `(需求, 完整事实组)`，返回原始标量或 `None`。`None` 明确表示整对输入无法在容量内评估，不能按低分或已拒绝处理。

完整组表示包含主体、属性、所有成员正文和值、限定条件、有效时间及争议状态。不仅向模型发送最高分成员，也不删除没有词法匹配的例外。组正文只序列化一次，在多个需求间共享。

`MemoryRerankPolicy` 默认每需求最多评估 32 个候选、总共 512 对。按候选名次轮转分配额度，避免第一个需求耗尽总预算。未被评估的关联没有供给资格。某组对任一需求被接受时，仍整体保留；其他需求上的拒绝不能删除这个有效关联。

Memory 保持独立子系统：内部使用不可变的 `MemoryDemandAssessment`、`MemoryRerankAssessment` 值对象。Harness 在边界转成带 Schema 版本、严格计数校验的 Core 协议，Memory 不反向依赖 Core/Context。瞬时结果与持久化协议的区别是本次边界转换存在的理由。

## 为什么排名之外还要校准

交叉编码器联合阅读需求和事实，输出 logit。它比独立 embedding 更能比较词语间关系，但原始分数没有“高于某值就一定相关”的统一含义，也不是正确概率。

`NullScoreCalibration` 保存固定流水线下 n 条无答案查询的最高候选分数。候选分数 s 的经验上尾值为：

```text
p(s) = (1 + 无答案查询最高分中大于或等于 s 的数量) / (n + 1)
```

只有 `p(s) <= alpha` 的关联才进入后续覆盖选择。相等分数计入尾部，避免在并列分数上过度接受。8 个校准样本时最小 p 为 1/9，无法通过 alpha=0.1；不会用 0 次已知误报制造 100% 信心。实现用排序元组和二分查找，单个查询的尾概率计算为 O(log n)。

采用每条无答案查询的**最高候选分数**，是因为一个查询会尝试多个候选。不能把这些高度相关的候选当成多个独立校准样本。完全没有候选可用的查询以 `None` 记录，相当于排序上的负无穷；未完成推理不能作为这种空候选样本。

在校准查询与未来无答案查询可交换、评分过程固定的前提下，可以用有限样本秩校准解释这种拒绝规则。但本次人工样本不证明线上满足前提。alpha=0.1 是每个需求的名义参数，不是“每条记忆有 90% 正确率”，也不是多个需求整轮的误接受保证。有答案请求中的错误候选同样没有因此获得精度保证。

替代方案包括固定分数阈值、仅按第一第二名分差拒绝、生成模型自报置信度、用相关性标签训练判别器。本阶段选择无答案秩校准，使样本来源、有限样本分辨率和语料变化更容易审计；代价是校准依赖明确的数据分布，且不会弥补模型错误排序。

## 校准绑定与恢复

流水线摘要绑定：第一阶段策略及实际回退状态、编码模型身份、交叉评分模型身份、完整组表示版本、配对额度，以及可见记忆集合摘要。

`population_digest` 覆盖作用域、可见版本和完整来源，不包含仅仅变化但未影响可见集合的查询时钟。因此重复读取不会无故失效；新增、修改、撤回、过期或跨作用域都会使旧校准失效。重新打开 SQLite 后，相同可见语料保持相同身份。

发现不匹配时显式失败，不静默套用旧门槛。这意味着当前更适合固定或稳定的记忆快照。持续增长的记忆集合需要宿主显式重校准，低成本增量校准尚未实现；因此没有将这个路径改成在线默认。

`ContextSupplyReport v3` 新增重排报告。v1/v2 的序列化结构保持原样。每需求记录候选数、评估数、接受数、最高分及对应 null p 值；组级分别记录可供给、已拒绝和无法评估。原始候选总数必须等于最终供给、预算/数量省略、拒绝和无法评估之和。完整报告也计入字节预算。

这是记忆供给的拒绝，**不是最终答案拒答**。当前生成模型可能凭自身知识继续回答；本轮没有证明它对缺失个人事实一定正确拒答。

## 本地推理、失败和资源

`OnnxMemoryPairScorer` 使用原生 tokenizer 的文本对输入，而非给两个字符串随意拼分隔符；支持 pad ID 为 1、单 logit 输出的 XLM-R 类 ONNX 分类模型。它与既有 E5 编码器共用 `_local_onnx` 中的文件校验、可选依赖加载和有界线程生命周期，两个公开适配器仍各自解释输出协议。

- 单批最多 32 对，检索编排实际以 8 对为批次；每个模型实例一个推理 worker。
- 输入先检查字节容量，再检查真实 pair Token 数，默认最多 512 Token。超限整个关联进入无法评估状态，不截断条件或例外。
- 校验输出数量、单标量形状和有限性；原始 logit 不经过伪装成置信度的 sigmoid。
- 故障策略可选择 `raise` 或 `withhold`。后者整轮扣留评估结果，不释放已成功的部分批次，也不回退到未经评估的候选。
- 取消不转换成拒绝或成功；当前有界同步推理批次被等待结束后再传播取消。关闭操作也等待已拥有的工作。这不是硬抢占。
- 模型和 tokenizer 使用读取字节的 SHA-256 标识，可提供预期摘要校验。默认包不下载模型，权重和向量不进入 Git。

## 冻结实验

2026-11-07，使用 `examples/fixtures/memory_reranking.json` 的 24 条事实、22 个事实组。32 条独立无答案查询用于校准；另有 20 个评估请求，其中 12 个有答案、8 个无答案，共 15 个正向需求、17 个预期事实。旧的 16 个请求单独作为回归集。

数据在首次运行前冻结，alpha 固定为 0.1；没有使用评估标签选择门槛、调整模型或编写逐案例规则。每套语料分别执行同一组 32 条校准查询。结果是人工定向检索证据，不是开放任务成功率或自然流量上的统计认证。

使用相同第一阶段 Hybrid、每案例组数上限和 16000 字节供给预算。每案例向量缓存为空，共享已加载模型；耗时不含模型加载。单次本地探针同时有开发检查运行，时间只用于说明数量级，不作为稳定延迟基准。

| 新评估集 | 事实召回 | 完整需求覆盖 | 无关事实 | 无答案时不供给 | 平均耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Hybrid | 70.6% | 66.7% | 16 | 0/8 | 272 ms |
| Hybrid + 交叉重排 | 94.1% | 93.3% | 12 | 0/8 | 1065 ms |
| Hybrid + 重排 + 校准拒绝 | 94.1% | 93.3% | 3 | 6/8 | 1014 ms |

| 旧回归集 | 事实召回 | 完整需求覆盖 | 无关事实 | 无答案时不供给 | 平均耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Hybrid | 60% | 61.1% | 10 | 0/2 | 204 ms |
| Hybrid + 交叉重排 | 85% | 83.3% | 5 | 0/2 | 848 ms |
| Hybrid + 重排 + 同语料校准 | 85% | 83.3% | 1 | 2/2 | 855 ms |

不能省略的失败分析：

1. 新集的日志脱敏需求仍选错。22 个组全部参与评分，正确的脱敏规则得分 -4.226，错误的取消规则得分 -1.713。这次不是来源丢失或预算遗漏，而是交叉模型排错，校准也没有识别这种有答案查询中的错误候选。
2. 新集仍对数据库具体版本、最近报告完成日期两个无答案请求误供给；分别返回了缓存规则、归档偏好。主题相关不等于足以回答具体问题。
3. 旧集仍遗漏视觉需求和通用框架边界，长工具输出案例仍选错参数校验规则。不能把平均召回提升解释成每种任务都改善。
4. 首轮把新语料的校准直接用于旧语料时，旧集召回只有 60%，低于仅重排的 85%。据此补上可见语料绑定，并分别校准；这一工程修正没有修改评估标签或 alpha。旧集本身是已知回归集，不是额外盲测。
5. 增加了约 0.6–0.8 秒的本地推理成本。相同命中结果下，带拒绝的一次计时略快于仅重排属于测量波动，不能宣称拒绝让推理更快。

## 如何使用和复现

```bash
uv sync --extra local-memory
uv run --extra local-memory python -m examples.memory_reranking \
  --encoder /absolute/path/multilingual-e5-small \
  --scorer /absolute/path/mmarco-mMiniLMv2-L12-H384-v1
uv run pytest tests/memory/test_reranking.py tests/memory/test_onnx_encoder.py tests/test_architecture.py
```

两个模型目录各包含 `model.onnx` 和 `tokenizer.json`。先通过 `MemoryReranker(scorer)` 运行独立无答案查询，检查每个需求均完整评估，收集报告最高分和同一个流水线摘要，再构造 `NullScoreCalibration`。不得将存在相关事实、评分失败或未完整评估的请求当作无答案校准样本。

将校准传给 `MemoryReranker(scorer, calibration=calibration)`，再传入 `TaskMemoryRetriever(..., reranker=...)`，由 `HarnessMemory.retrieval` 或 `MemoryContextSource.retriever` 接入。宿主在两个本地模型的 `async with` 内运行 Harness，并先关闭 Harness。API 允许仅重排而不拒绝，报告明确标记 `rank_only`；没有校准时不会声称已验证绝对适用性。

## 下一小步

重点是“相关材料是否足够支持当前问题”的验证：区分具体事实值、主题规则和推断，结合问题需求与记忆中的条件、时间和缺失字段判断可用程度。日志脱敏的错误排序和日期问题的高分假阳性是不同失败原因，不能只靠再调一个阈值解决。

另一个明确限制是动态记忆更新后的校准维护，需要研究可控的增量校准和漂移检测。目前采取严格失效策略，没有宣称已解决在线自适应。设计取舍与第一方依据见 [ADR 0114](decisions/0114-记忆候选重排与无答案校准拒绝.md)。
