# 有界工具反馈完整交付

## 1. 本次新增了什么能力

Weavria 新增通用的工具反馈交付契约。工具可以选择默认的自适应交付，也可以声明：当本次结果属于当前反馈时，下一次模型调用必须看到完整结果。

内置 `read_artifact` 采用完整交付，因为它输出的已经是模型主动请求、由长度限制控制的精确范围。对应架构决策见 [0036 有界工具反馈的完整交付保证](decisions/0036-有界工具反馈的完整交付保证.md)。

## 2. 它在 Agent 系统中解决什么问题

Artifact 卸载与上下文选择存在两个不同目标：前者防止大型原始结果直接占满窗口，后者决定当前任务真正消费哪些信息。旧实现把二者混在同一套叶子摘录策略中，即使模型已经使用读取工具把范围缩小，读取结果仍会再次被拆成 Passage 并丢弃部分字段。

这会制造危险的假象：Trace 显示工具成功、Artifact 也包含所需数据，但模型实际没有看到它。模型只能得出“数据不可用”，或者继续浪费工具预算重复读取。

完整交付契约把“结果存在”与“结果已经交给模型”重新区分，并为后者建立可测试的不变量。

## 3. 一次请求在代码中如何流转

1. `TypedTool` 把可信的 `feedback_delivery` 固化进版本化 `ToolDescriptor`。
2. 工具执行成功后，`ToolExecutor` 将同一策略写入 `ToolRecord`；模型不能通过参数修改它。
3. Artifact 仍然只在存储中保存一次，普通工具反馈首先携带引用。
4. 上下文构建器识别当前必须反馈的调用。
5. 若策略为 `adaptive`，继续按任务相关性选择引用、摘录或完整结果。
6. 若策略为 `complete`，该调用只生成完整表示，分配器不能选择更便宜的摘录。
7. 编译器同时保留派生结果的因果来源引用。
8. 如果完整表示不能同时满足字节和 Token 预算，编译失败并保留明确的预算原因。
9. 下一轮不再要求该反馈时，记录重新参与普通自适应分配。

## 4. 为什么采用当前设计

交付策略属于工具的语义契约，而不属于某次模型动作。只有工具实现知道其输出是否已经有界、部分结果是否仍有意义。因此策略在注册时由可信宿主声明，在执行记录中持久化，在上下文编译时执行。

选择“当前反馈完整、后续自适应”，兼顾了正确性和长任务成本。永久固定完整结果会使每一次有界读取都累积在 Prompt 中；只在当前反馈边界锁定，则保证模型至少有一次机会消费它，同时保留后续压缩空间。

## 5. 如何运行测试或观察结果

```bash
uv run pytest tests/tools/test_execution.py -q
uv run pytest tests/context/test_evidence.py tests/context/test_compiler.py -q
uv run pytest tests/sessions/test_engine.py -q
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
```

运行证据中可以观察：

- 普通工具仍生成 `ToolRecord` v1，策略按 `adaptive` 解释；
- 完整交付工具生成 `ToolRecord` v2，并记录 `feedback_delivery=complete`；
- 对应 `ContextChoice` 的 `required=true` 且 `representation=raw`；
- 模型请求中的工具输出带有 `representation=full` 和完整 `data`；
- 紧预算下抛出上下文预算错误，而不是变成 `representation=excerpts`。

冻结信息交付实验额外保留了相同任务的“预算不足”和“预算足够”两组样本，用来同时验证明确失败语义与可完成性，而不是通过放大原有样本的预算隐藏成本。

## 6. 当前刻意没有实现什么

- 没有识别任何应用、领域、字段或日期；
- 没有根据工具名称写分支；
- 没有让所有工具结果默认完整进入上下文；
- 没有放宽字节、Token、权限或因果依赖限制；
- 没有声称信息完整可见就等于模型推理一定正确；
- 没有用自然语言关键词判断答案是否与证据冲突。

## 7. 下一小步建议

在冻结的领域无关任务集中比较自适应交付与有界完整交付，统计关键事实保留率、额外工具调用、模型调用、Token 与完成率。如果多个工具需要完整交付，再设计可验证的输入相关输出上界，使 Runtime 能在工具派发前证明下一步完整反馈可容纳，而不是引入静态且过度保守的全局上界。
