# 上下文编译修复与资源边界

## 新增能力与解决的问题

本轮修正 Context Compiler V1 的四个相互关联的问题：按工具顺序抢占正文预算、模型可见来源与工具可读来源不一致、候选容量不足被误判为内部缺陷，以及索引和分配缺少足够的工作边界。完整决策见 [ADR 0030](decisions/0030-上下文预算交换与证据访问闭包.md)，基础概念见 [上下文编译与信息恢复](上下文编译与信息恢复.md)。

现在编译器可以撤回低价值表示，用释放的预算保留更有用的来源；同时将该次模型决策的当前 Run 可读证据固定下来，使工具执行产生的依赖和准入预留一致。原文、事件和成果不会因视图变化被删除。只有显式启用联合编译的路径使用这一受限访问语义。

## 一次请求在代码中如何流转

1. `context/compiler.py` 检查来源容量，`compiler_sources.py` 从原文构建或复用索引。工具成果必须匹配已接受的精确引用；历史索引按完整交互摘要缓存。steering 后原文可复用，需求特征和选择重新计算。
2. `ContextUnit` 记录来源身份、表示候选和依赖。最新反馈的最低回执必须保留，正文不再按出现顺序抢先占位。每个必要调用的非引用表示独立增加 0.25 的可用性收益，与语义收益共同竞争。
3. `ContextAllocator` 执行密度和绝对收益贪心，随后尝试删除、降级或交换。每个候选重建闭包并计量完整请求。搜索额度耗尽时保留已验证的可行解；最后再验证准确请求。
4. Session 将请求和 `ContextCompilation` v2 报告事务提交。Runtime 接受当前选择后，构建 `EvidenceAccessView`，绑定 `ControlRequest` 摘要、任务修订和权威工具记录闭包。编译报告中的请求摘要绑定外层 `SessionRequest`，两者作用层级不同。
5. 模型提议一批调用后，`reserve_feedback` 只为这个视图中可能读取的全部依赖与新调用最坏回执预留空间。`BatchAdmitted` v2 保存相同视图；归约器独立重建并校验它。
6. `ToolExecutor` 从该准入事实取得精确引用，传给 `ToolContext`。读取不在集合中的成果会在访问存储前失败；回执不能声称读取了准入外的依赖。新结果结算后再进入下一次编译。

例如已有 40 个工具成果，但此次选择只包含 `c0`。过去模型只看到 `c0`，工具却能读取任意 40 个成果，所以必须为全部回执预留。现在本批次只能读取 `c0`，因此预留与只有一个历史成果时相同。若模型仍请求完全省略的 `c17`，调用返回策略拒绝；不能先执行再发现下一轮放不下其依赖。

取消与任务修订保持既有所有权：索引构建取消不留下半成品，已启动工具使用其原准入视图，排队的过时调用停止派发。新的任务修订重新选择来源、重新计量和准入。

## 为什么采用这种设计

“必须报告发生了什么”和“必须展示所有正文”具有不同代价。前者属于执行正确性，后者需要在信息价值与预算之间选择。将正文改为软收益，才能撤回无关大结果；为每个必要调用分配独立特征，又能避免一个不透明结果的展示吞掉所有其他结果的可用性收益。

成本不是来源字节数的简单加和：请求结构、共享依赖、JSON 编码和 BPE 都会改变完整成本。分配器使用精确请求计量，并通过有限邻域控制组合搜索。两条贪心各使用约三分之一搜索额度，余量最多进行四轮单供给项/单接收项修正，供给项和接收项各最多 16 个。

这里没有全局最优保证；多个来源联合撤回后才能获得的收益仍可能漏掉。表示序号不表示严格成本顺序，因此降级候选也必须实测。搜索截断和结果预算不足分开处理：前者交付已验证计划，后者终止运行。

访问视图是预算承诺的执行前提。缩小预留必须同时缩小读取集合，否则模型可以用历史 ID 绕过本次选择，使后续依赖闭包超过预算。这是 ToolContext API 内的来源读取约束，不能替代外部工具 Policy 或执行沙箱。

## 资源配置与失败语义

| 参数 | 默认值 | 约束 |
| --- | ---: | --- |
| `max_units` | 256 | 历史交互与当前工具记录总数，最多可配置 1024 |
| `max_passages` | 8 | 单来源片段候选的最大展开数量，最多可配置 32 |
| `max_source_bytes` | 16,777,216 | 已接受记录、历史和成果声明大小的编码字节总量 |
| `max_index_bytes` | 67,108,864 | 活动索引的 Pointer 与值编码总量，以及缓存估算字节额度 |
| `max_index_passages` | 65,536 | 活动索引片段总数 |
| `max_scoring_work` | 2,000,000 | 原始片段数乘以需求词项和锚点总数的估算门限 |
| `max_allocation_steps` | 4096 | 分配搜索的候选访问次数上限 |

评分门限不是精确 CPU 指令计数，未单独计入小型候选重评分、失败回执特征等开销。索引与缓存的字节估计也不等于 RSS；Python 对象、词项、候选载荷与临时请求另有内存成本。缓存最多容纳 `max_units` 条来源，按各类插入顺序淘汰，当前优先淘汰工具缓存，再淘汰历史缓存；不是一个统一的全局 LRU。

索引按树节点/片段定期让出事件循环，片段评分与排序同样协作式让出，分配每 16 次候选访问、每 32 次新组合计量让出。单次 JSON 解析、散列、请求序列化和 BPE 计量仍不能被硬抢占；不能将协作式取消描述为实时截止保证。

`ContextCapacityError` 带资源名、请求量和容量，Runtime 对应 `budget_exhausted / context_capacity`。数量超限进一步区分 `mandatory_units` 与 `candidate_units`；前者是必要闭包本身装不下，后者是总候选超过处理容量。本轮没有超大候选集的预检索策略，二者都显式终止，不静默丢弃来源。最低模型请求超限继续报告 `context_tokens` / `context_bytes`。终态事件保存容量分类；具体数值可从编译异常获得，尚未新增持久化容量诊断载荷。

搜索阶段被额度截断时，报告的 `allocation_exhausted` 为真；即使总步数未满，某一贪心阶段也可能已经用尽其分配份额。`evaluations` 是未命中缓存的完整组合计量数，与搜索访问数不同。

## 兼容与当前限制

`ContextCompilation` v2 增加搜索诊断；`BatchAdmitted` v2 增加版本化访问视图。旧 v1 JSON 原样序列化，历史数据库不改写。新事件中的嵌套版本要求升级读者。编译器策略标记为 `context-compiler/2`，默认未启用编译器的 Run 仍保留全历史读取和预留规则。

当前模型只能完整回读其所选当前 Run 来源，不能凭完全省略的成果 ID 扩大本批次权限。历史 Session 工具仍能按已接受的会话地址恢复过去 Run 原文，但其原有 Run 顺序约束阻止借道读取当前 Run 成果。没有实现主动范围扩展或全库检索。

本轮没有加入摘要模型、向量召回、长期 Memory 或自动恢复执行；没有真实模型任务成功率、长任务纠错或自主恢复收益证据。有限交换解决了可复现分配反例，执行访问闭包修正了预算承诺，资源门限约束了准备规模；这三项都不能单独证明成熟 Harness 水准。

下一小步应将“完全省略来源如何重新进入可读视图”设计为显式的信息需求与重新准入流程，并在冻结的领域无关长任务上比较：选择质量、恢复调用、最终正确性、引用、总 Token 与编译成本。先验证需求，再决定是否需要多区间检索或更强的语义特征。
