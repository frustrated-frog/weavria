## 待处理的问题

### M1-03：模拟用户修订错误地重入了执行任务

- **归属：验收脚本缺陷，已确认。** `ObservedModel.generate_session` 同步等待回调，回调在
  当前 send 所属任务里直接调用 `agent.steer`。SessionEngine 明确要求独立的用户输入任务。
- **证据：** `batch-1/documents_steering-coverage-1.json` 终态 `model_failure`，会话中的错误
  原因为 `RuntimeError`；对照 `examples/m1_harness.py` 的回调与
  `SessionEngine.steer` 的任务所有权检查即可确定违规调用链。
- **影响：** 触发该路径的失败不能归因于模型不能跟随修订。未读取来源、从而未触发修订的失败
  则是另一种情况，不能一起抹掉。
- **修复判据：** 在受跟踪、可取消并会等待清理的独立用户输入任务中注入原定修订；不改触发条件、
  目标文本或成功判据。回归验证任务隔离、修订生效、取消后没有遗留任务，再独立保存复测结果。

### M1-04：自然形成的未知起始时间记忆被默认召回排除

- **归属：形成与消费的组合缺口，已定位机制。** 抽取器要求未明确起始时间时保留 unknown。
  `HarnessMemory` 的装配没有暴露时间选择，`MemoryContextSource` 默认
  `include_unknown_time=False`，这类记录因时间筛选而无法进入模型上下文。
- **证据：** `batch-1/documents_memory-coverage-1/memory.db` 和
  `repository_memory-coverage-1/memory.db` 都有一条已准入的用户长期约定，
  `valid_from=None`、`valid_to=None`；随后新会话不能正确回答。原文与查询都是中文，当前证据
  不支持将此失败归因于跨语言检索。
  对后者数据库的临时副本作无网络验证：相同中文查询，`include_unknown_time=False` 命中 0 组，
  `True` 命中并交付 1 组。原始数据库未被修改；此诊断不改变本轮冻结配置或任务得分。
- **影响：** “写入成功”与“下一会话可用”脱节。返回零组也不能被解释为用户没有约定。
- **修复判据：** 明确当前知识查询与严格有效时间查询的区别；让宿主可以选择是否携带未知时间
  事实，并保持未知标识、来源、作用域和完整冲突组。不能把 unknown 静默改成当前有效，不能
  为验收预写事实。需要自然形成→新会话→实际模型可见 bundle 的回归和真实复测。

### M1-05：未知开始时间的旧约定不能接受明确从现在生效的变更

- **归属：记忆时间修订能力缺口，已定位机制。** 首条约定未声明开始时间；后续用户明确表示
  “从现在起采用新值，替代旧值”。审阅已识别 change 并绑定旧事实，准入仍返回
  `deferred / unsafe_relation`，因为当前 change 路径要求旧事实具有已知 `valid_from`。
- **证据：** `batch-1/repository_memory-coverage-1/memory.db` 的 correction 形成计划：
  `supported=true`、`time_supported=true`、`relation=change`，但未产生修订 mutation。
  用户新约定“文件路径升序”没有替换当前库中的“严重程度降序”。文档语言任务有相同形态。
- **影响：** 即使解决召回筛选，仍不能保证修订后使用新值；两个问题不能合并成“打开召回即可”。
- **修复判据：** 为未知起点的旧规则定义明确的退役/修订语义，保留知识时间历史、不编造旧规则
  的生效时间，并验证按当前时间和历史快照查询的行为。涉及持久语义时须先补设计与迁移分析。

### M1-06：长上下文任务发生读取和恢复，但没有形成有效工作记录

- **归属：实际能力缺口；根因尚未完全确认。** 模块存在与模型会使用它是两回事。
- **证据：** `batch-1/documents_long_context-coverage-1.json` 调用了 15 次执行模型，读取完整
  `research_bundle.txt` 并执行 `read_artifact`，但 `work_updates=0`，默认记忆配置事实未找到。
  对应首个 `request_views` 的 instructions 中确实包含 `propose_work` 及完整 Schema，不能
  直接归因于工作工具没有接入。`repository_long_context-coverage-1` 已发生上下文恢复，最终
  因 `finalization_evidence_unavailable` 耗尽预算，也没有工作记录更新。
- **影响：** 原文回取已参与，但尚未形成“识别缺口→定位资料→保存中间成果→继续完成”的可靠闭环。
- **修复判据：** 分清未选择工作工具、提案非法、归约未接受以及记录未影响后续选择的各类原因；
  核查每次调用实际输入与反馈。不能由宿主补正确笔记或指定工具序列来替模型完成任务。

### M1-07：澄清续接仍会失败，或在没有读取资料时给出错误入口

- **归属：混合问题，须继续定位。** 首个澄清问题已经能交付；失败发生在回答澄清之后，不能
  自动归为 M1-02 的重复。
- **证据：** `batch-1/documents_clarification-coverage-1.json` 已完成提问，第二次 send 抛出
  `TaskUnderstandingError`；会话只记录 `task_preparation_failure` 中断，没有更细的 attempts。
  `repository_clarification-coverage-1` 续接同一工作，但没有读取源码，最终错误地把
  `AgentHarness.from_config` 当作自定义内部策略入口。
- **影响：** 接线与版本续接通过，并不意味着理解结果和行动正确；当前报告只保存异常类型也不足
  以精确归因。不得通过放宽已接受意图的一致性检查掩盖失败。
- **修复判据：** 补充内容无关的阶段/错误分类诊断，复现确切失败条件，再判断是生成问题、候选
  意图约束过紧还是解释后校验缺口；分别验证成功续接和合法拒绝。

### M1-08：任务完成声明、来源事实与输出协议仍有差距

- **归属：实际行为失败与验收表达限制并存。** 不将所有错误混成一个成功率原因。
- **证据：** `documents_multistep-coverage-1` 找到其他 ADR，却没有读到任务要求的使用说明，
  将入口与形成失败状态答错；`repository_multistep-coverage-1` 在模型输出纠错耗尽后失败。
  部分输出中，字段含有正确标识符加解释，例如 `flush_memory（…）`，仍会被冻结的精确字符串
  评分拒绝；这属于字段表达上的潜在假阴性，但不能消除同一任务的错误事实或缺失来源。
- **影响：** Runtime `completed` 不能代替结果正确。当前严格 JSON/字符串指标也不等同于一般
  自然语言语义正确率，不应据此推断模型所有回答都错。
- **修复判据：** 先按事实错误、缺少读取、协议失败与仅表达差异分开复核。评分不在看到结果后
  静默放宽；如确认评分器需要修订，应单列新版本和理由，保留原分数并完整重跑比较组。
