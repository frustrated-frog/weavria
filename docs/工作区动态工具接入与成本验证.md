# 工作区动态工具接入与成本验证

后续阶段已接入独立成果验收驱动的计算能力退出，见[成果验收与计算能力生命周期](成果验收与计算能力生命周期.md)。下文保留 ADR 0107 阶段的行为与测量口径。

## 这一阶段解决什么

工作区清单已将正文留在 Artifact，但此前示例关闭了任务理解，并把整个注册表再次写入固定提示词。Runtime 本来就会生成当轮菜单，因此这份重复目录既增加输入成本，也会误导模型调用已退出视图的工具。

本阶段删除重复目录，将工作区工具接入现有 TaskUnderstanding → AdaptiveCapabilityPolicy → Runtime 链路，提供显式 `--capabilities adaptive` 模式；默认仍为静态模式。同时修正选择器计费和多步计算能力的生命周期：按实际展示条目计算字节，任务声明的隔离计算不会因一次调用返回而提前退出候选。

这不是根据轮数排列“读源码 → 执行 → 合并”的专用流程。真实运行的任务规格仍由模型提出，需求账本与工具记录参与下一轮选择，任务产物由独立宿主验收。

## 入口到终态的调用链

1. `examples/sandbox_execution.run_task` 装配相同的四个业务工具：读取冻结源码、工作区计算、文件读取、版本合并。静态模式展示全部；动态模式先调用真实任务解释器。
2. 示例宿主的 `RegisteredDiscovery` 只允许披露本次注册的精确名称和版本，供解释器考虑私有计算工具。它只授予发现能力；工具调用仍受 SandboxToolPolicy、版本绑定、输入校验及接受视图约束。
3. `TaskAwareSessionPreparer` 将解释归为 TaskFrame 与 NeedLedger。`AdaptiveCapabilityPolicy.select` 复用原有需求覆盖矩阵、失败折扣、数量/字节约束、贪心密度与最佳单例比较。
4. 可见工具名称提交到原有 SemanticSnapshot。Runtime 使用同一个 `model_tool_view` 生成菜单，编译完整请求并检查真实字节及 Token 预算，之后才调用模型。
5. 工具结果通过原来的接受链进入状态归约，工作集重新选择；视图变化推进 epoch。隔离计算仍可进行后续阶段或修正，但不能绕过进展干预、调用预算或最终成果验收。
6. `VerifyWorkspace` 读取附件原文，独立计算 AST 统计，核验报告内容、父 revision 和保留文件。仅有一次计算成功不会使这个验收器接受不完整成果。

源码阅读顺序：[统一展示及字节计量](../src/weavria/tools/catalogue_view.py) → [工作集选择](../src/weavria/harness/working_set.py) → [Runtime 菜单生成](../src/weavria/runtime/agent.py) → [示例装配与验收](../examples/sandbox_execution.py) → [请求成本观察](../examples/capability_cost.py)。设计见 [ADR 0107](decisions/0107-工作区动态能力选择与展示成本.md)。

## 两个通用机制变化

### 展示成本与发送表示一致

旧选择器按完整 `ToolDescriptor` JSON 收费，其中包括输出 Schema、策略和执行元数据。Runtime 的执行菜单只发送名称、描述和输入 Schema。因此一个宿主输出契约很大的工具可能被拒绝展示，尽管实际模型菜单很小。

`model_tool_view` 现在同时供 Runtime 与 `model_tool_bytes` 使用，保持输入验证关键字和参数说明，返回独立副本；旧 Journal 的 version 字段和原始输入 Schema 表示保持兼容。选择器使用紧凑条目的 UTF-8 字节数，策略版本升级为 `adaptive-capabilities/4`。新增测试验证：完整宿主契约超过 16 KB，而实际菜单小于 512 字节的工具仍可在 512 字节描述预算内入选。

这里仍不是 Token 计量。每项字节之和不包括外层数组分隔符、框架回取工具和任务/历史；ContextCompiler 和 Provider 继续按完整请求准入。原注册 Schema 与执行校验不会随模型视图压缩而变弱。

### 多步计算不以单次回执结束

先前独立 `capability_result` 目标看到一次 ToolSucceeded 后就不再产生选择收益。隔离计算的一次返回可能仅是中间文件，甚至是包在成功工具结果中的代码错误诊断，不能据此判定整个计算目的完成。

当前 Frame 明确声明的 `isolated_compute` 能力获得 `compute:<name>` 覆盖目标，必需权重为 2、可选权重为 0.5。它仍参加同一覆盖算法和硬预算，不强制常驻；任务改写后重算，不保留跨任务授权。没有声明的计算工具不能由旧视图或只读发现自动激活，普通 side_effect 没有获得这项待遇。只读需求及一次性动作的既有规则保持不变。

代价是计算工具可能保留到任务结束。更精确的退出需要把“中间版本已生成”和“最终成果已验收”绑定到可验证的成果义务，当前没有假装具备这项语义。

## 真实失败与回归边界

新 Docker 集成用例通过正式 Harness、SQLite 和真实容器运行：读取源码 → 生成清单 → 按需读取文件 → 注入 NameError → 模型提出修正。进展策略因浅层调用义务均完成，先建议验收；独立验收返回 `workspace_incomplete` 后，模型再提交修正并成功。这条链保持原来的干预和验收规则，没有调大预算或关闭校验来放行。

测试断言实际模型请求只有一份目录，未声明的合并工具不出现；计算工具在中间结果与代码错误之后仍可见，已完成的一次性读取退出。随后检查原文不变、父版本一致及 SQLite 重开后的容器恢复。这里的解释和动作是测试替身，只证明组合契约，不证明自然语言规划质量。

最终检查：Ruff Lint、格式和 Pyright 全部通过；默认测试 1635 项通过、16 项 Docker 测试默认跳过；显式启用 Docker 后沙箱套件 85 项通过。调用预算、进展干预和成果验收没有为测试放宽。

一次真实静态运行失败于绝对路径参数：模型把 `/workspace/inputs/sources.json` 当成 `inputs[].path`，多次收到笼统参数错误后触发无进展保护。现已把相对虚拟路径说明写入 `ArtifactFile.path` 和文件读取参数的公开 Schema，而非只写在 Python 类型注释里；完整的路径遍历和挂载校验仍然保留。后续两种模式完成了任务，但各一次复测不足以证明已经消除所有路径误解。

## 运行与可复现对照

```bash
uv run pytest tests/harness/test_working_set.py tests/harness/test_capability_cost.py \
  tests/tools/test_schema_view.py -q
uv run python -m examples.capability_working_set
WEAVRIA_TEST_DOCKER_IMAGE="$SANDBOX_IMAGE" uv run pytest tests/sandbox -q
```

固定需求轨迹的选择实验沿用原有五阶段、四个需求、两个工具额度；按新的展示口径重算，永久并集/固定菜单/动态选择累计描述字节分别为 5960/1490/1043，未覆盖需求阶段数分别为 0/9/3。永久并集五阶段均超过数量预算。这是计费口径与有界选择的确定性验证，不是新一轮智能能力成绩。

真实运行需显式提供本机已有固定镜像和模型配置，输出文件须尚不存在：

```bash
uv run python -m examples.sandbox_execution --workspace --capabilities static --run \
  --image "$SANDBOX_IMAGE" --env-file .env.finscope-debug --output /tmp/workspace-static.json
uv run python -m examples.sandbox_execution --workspace --capabilities adaptive --run \
  --image "$SANDBOX_IMAGE" --env-file .env.finscope-debug --output /tmp/workspace-adaptive.json
```

示例报告升为 v3：增加模式、已提交能力视图和实际执行请求的菜单成本。模型原始输出留在本地报告，不提交仓库。`CatalogueCostProvider` 只观察请求，将相同请求的菜单补成全部业务工具做本地计量，任务、历史、语义视图、框架回取工具及提示词后缀不变；补全请求不实际发送，也不代表模型在该反事实下会采取相同行动。真实供应商用量另由 RecordingHTTPTransport 记录，不能把本地 TokenCounter 估计混同为账单。

## 2026-11-05 的结果与证据强度

冻结输入 SHA-256 为 `2995899e2cb6e36606109c145dcf8eff8d003be8ba41099a790f08dc7f6fe362`，镜像为 `sha256:57cd7c3a7a273101a6485ba99423ee568157882804b1124b4dd04266317710de`。真实模型为 `deepseek-flash`，temperature=0、reasoning_effort=none、最大输出 4096 Token，窗口 131072 Token；两边均为清单工具集、2 KiB 工作区、最多 10 次执行模型调用/8 次工具调用、262144 字节请求、150 秒 Run、160 秒完整请求。动态模式另有受父期限约束的任务准备，计入总用量。Tokenizer 为 tiktoken 0.14.0 / cl100k_base。

用量覆盖率均为 100%。两边都发生过重复声明基线输入的参数错误并恢复；静态模式还曾尝试访问未被接受的 Artifact，被拒绝后继续。延迟只是此次采样，两次运行并发发起，不能作为吞吐或延迟优势证明。

动态模式未声明 `merge_workspace`，六次执行请求均只展示计算、源码读取和文件读取三个业务工具，epoch 未变化。**真实任务并没有表现出按阶段持续收缩菜单。** 其信息需求停留在取得资料但未完成语义验证的状态，原有策略仍保留来源工具。

对这六条相同请求，仅补回合并工具，每条增加 1094 个 instructions 字节、244 个本地估算 Token；累计增加 1464 Token。这个配对计量支持“减少一个无关工具确实缩小输入”，不受不同生成代码和轮数的混淆。它不证明整体更省：真实动态总 Token 比静态高约 **22.45%**，任务理解与工作状态成本未被菜单节省抵消。

也保留两次早期结果：路径说明完善前，静态模式失败，9 次调用、56,821 Token，未生成工作区；动态模式完成，含准备共 7 次调用、54,219 Token。复测包含参数说明变化，不能把前后结果全部归因于选择策略。默认保持静态示例入口，动态模式显式启用；不拿上阶段重复目录的旧结果作为唯一成本基线。

## 当前边界与下一小步

本次没有新建执行引擎、学习型路由器、自动授权或模型主动扩展工具目录协议。选择权重仍为启发式；初始解释漏掉计算能力、描述预算不足、需要多轮读取却只有浅层调用义务等情况仍有局限。计算能力的保守保留提高可继续执行性，但不能代替成果验收或证明最终任务收益。

下一步应深化**可验证成果义务与能力生命周期**：用原文件、阶段结果和最终验收区分继续计算、继续阅读与释放工具，避免仅靠调用成功退出，也避免已经取得资料的来源长期占用菜单。这个机制需在真正要求正文回取、分支合并和失败纠正的任务上继续验证；不能为节省一次准备成本，提前把自然语言任务固化为应用工作流。
