# 只读取证分支的失败修订与恢复验证

后续实现保留这张基线结果表。当前代码中，C 尚未启动的现场已能原地恢复并只读 C。最新语义和复验见 [ADR 0145](decisions/0145-恢复尚未派发的只读批次尾部.md)。

2026-11-22，在主分支 f3db902 的执行语义上完成。问题是三项独立取证中，一项失败、被用户替换或随进程中断时，已经取得的两项证据能否直接复用，何时能安全汇总。

## 同一任务，两种派发方式

每题都从三份安装包资料分别读取发行版本、Python 版本约束和命令入口。两套题使用不同安装包。原文沿用跨任务读取实验的冻结 wheel 快照，SHA-256 为 f1c3b0cd94da4c82f223cd9275c5a041d6d8b47190408733c30f62cfe3d7a373。工具返回指定快照的完整内容，评分核对三字段 JSON，并逐项检查提交答案时的模型请求是否包含对应原文。

- **整批**在初次提案中提交 A、B、C，最多两个工具同时执行。
- **分阶段**先提交 A、B，等两份回执进入当前会话，再由模型决定第三条如何推进。

两种方式都从正式 AgentHarness.send() 进入，使用相同保护边界、模型、资料和预算。回放器只固定了初次提案，便于控制故障发生的位置。重试、选择修订后的来源和汇总由真实模型决定。额外的自主提案组把首轮也交给真实模型。这一组观察模型如何分批，任务中的待查字段和候选路径始终明确给出。

## 在线回合中的失败与修订

真实模型为 gpt-6-luna，推理档位 medium。两题各做两轮配对，交换策略的先后顺序。故障条件分别是 C 首次读取遇到临时失败，以及 A、B 占用两个并发槽时用户将 C 换成 C′。每次为独立会话，最多七个决策轮次、九个工具调用，Run 期限为 90 秒。

| 场景与策略 | 有据答对 | 实际读取 | A / B 重读 | 真实模型调用 | 总 Token |
| --- | ---: | ---: | ---: | ---: | ---: |
| C 临时失败 · 整批 | 4/4 | 16 | 0 | 8 | 16,659 |
| C 临时失败 · 分阶段 | 4/4 | 16 | 0 | 12 | 24,280 |
| C 等待派发时修订 · 整批 | 4/4 | 12 | 0 | 9 | 18,296 |
| C 等待派发时修订 · 分阶段 | 4/4 | 12 | 0 | 8 | 15,972 |

固定首轮占用 Run 的决策预算，表中“真实模型调用”只计算供应商实际调用。这 16 个目标 Run 的 37 次供应商调用均返回 HTTP 200。失败场景里，两个方案都只重试 C；额外阶段增加了一次读取前的模型决策。修订场景里，整批的四次 C 提案均产生 CallSkipped，分阶段当时还没有提议 C。两种方式都读取了 C′ 并复用了 A、B。

同日再做一轮确认，含八个固定首轮对照和两个自主提案诊断 Run，共 10/10 有据答对，供应商调用 24 次且均返回 HTTP 200。自主组的两个任务都在首个有效提案提交 A、B、C，遇到 C 的首次失败后只重试 C，各三次模型调用、四次工具读取。任务已明确字段、来源和单次重试要求，这两次只能说明在该条件下模型会分批并局部修复。

另外用确定性回放把并发槽增至三个，让旧 C 在修订前已经启动。事件顺序为“接受任务修订 → 提交旧 C 的工具结果 → 启动新修订的模型决策”。Runtime 会等旧批次收齐反馈，才启动新一轮决策。此时已过期的读取占用真实资源，下一轮仍需读取 C′。

提前汇总也有可复现边界。只拿到 A、B 时，脚本模型提交 Finish，默认完成策略返回执行状态 completed、任务状态 unverifiable。外部评分判定失败。默认执行终态本身无法表达“三条指定证据都已到齐”。项目已有可插拔完成策略；本例用默认设置验证工具批次与任务义务之间的边界。

## 进程退出后的恢复

本部分使用真实子进程退出和 SQLite 重开，模型使用确定性回放。三个现场都有 A、B 的已持久化回执，C 在三个现场处于不同状态。先尝试原 Run 恢复；被拒时，另外测量显式在新会话完整重跑的成本。

| 退出时刻 | 已启动未记录的工具数 | 原 Run 恢复 | 恢复或整题重跑时实际读取 |
| --- | ---: | --- | --- |
| 整批，C 已启动，A、B 已提交 | 1 | resume_unsafe_boundary | A、B、C |
| 整批，串行槽位中的 C 还未启动，A、B 已提交 | 0 | resume_unsafe_boundary | A、B、C |
| A、B 单独成批且完成执行结算，尚未提出 C | 0 | 成功，原 Run ID 不变 | C |

中间一行控制了“调用已经启动但结果未知”这个因素。即使 C 从未启动，当前恢复仍要求最后接受的位置与整轮结算游标一致。工具结果已经逐条落盘，恢复规则还没有使用它们推进未完成的批次。前两行的重读是所测完整重跑方案的成本。新 Run 专门从历史成果重建任务的方案另需评测。

## 研发优先级

优先验证**在原 Run 中继续已准入批次里尚未派发的读取**。A、B 的结果可核对，C 的 ToolStarted 尚未出现。下一切片需要绑定原任务修订、准入回执、工具版本、读权限和剩余预算，再只派发尚未执行的 C。已派发却缺少结果的情况有不同的失败语义，需要单独处理。随着任务节点能独立结算，再将明确的证据义务接入成果验收，才能让汇总等到当前任务的材料满足条件。

两题属于同一文档类型，两种策略的故障位置是实验控制变量。实测支持具体执行边界和成本判断，开放式任务拆解、不同领域的计划质量和吞吐量仍缺少证据。本次交付为可复现评测，对照沿用当前 Runtime 的执行与恢复语义。
