# 反馈准入空转修复

## 1. 本次新增了什么能力

本次增加了三项相互配合的通用能力：

1. 模型适配器能够区分稳定系统内容与未知未来反馈，避免把可信 instructions 重复按最坏字节成本计量；
2. Context Compiler 在暴露工具时预留下一步反馈空间，并在真实拒绝后按批次需求自适应释放可选历史；
3. Runtime 对重复的反馈预算、工具预算和能力视图拒绝实施有界收敛，避免一直重试到模型预算耗尽。

对应架构决策见 [0034 下一步反馈预留与拒绝收敛](decisions/0034-下一步反馈预留与拒绝收敛.md)。

后续真实运行仍暴露了固定任务上下文被过度预留、内部 JSON 与 HTTP 请求体混用字节上限的问题。
[0054 统一请求计量与反馈前缀预算](decisions/0054-统一请求计量与反馈前缀预算.md)进一步修正这两点：
固定会话、任务和 TaskObservation 使用稳定 BPE 前缀计量，只有可变反馈后缀保留最坏上界；
最终 HTTP 请求体单独计量，并在发送前重选可选上下文。

## 2. 它在 Agent 系统中解决什么问题

旧实现分别保证“当前上下文可发送”和“工具执行前预留最低反馈”，但两个局部正确机制没有共享下一步预算。长会话中，当前编译器可以选择大量有价值历史并恰好压到请求上限；模型随后即使只调用一个普通工具，最低动作、回执和控制通知也无法进入下一轮。

失败 Trace 的关键事实是：

| 指标 | 观测值 |
| --- | ---: |
| 当前 ControlRequest | 约 12.6KB |
| 旧反馈预算 | 9,232B |
| 单次普通工具最低预留 | 14,118B |
| 工具实际派发 | 0 次 |
| 模型调用 | 10 次后耗尽 |

所以界面显示 `budget_exhausted`，但真正的问题不是工具结果过大，而是工具从未获得执行机会。

## 3. 一次请求在代码中如何流转

1. Session 根据当前任务解析可见能力。如果存在任务可用的主工具，把 `ContextCompilerConfig.next_step_reserve_bytes` 与请求字节预算八分之一中的较小值交给编译器；没有主工具时传入零。
2. 编译器构造历史、当前证据和恢复片段候选。每个候选的计量成本除了当前请求，还包含控制通道与下一步预留。
3. 分配器只能在扣除预留后的预算中选择可选历史。必要来源仍不可删除；必要请求本身超限时明确终止。
4. OpenAI-compatible Token Counter 对系统协议和可信 instructions 精确分词，对未来未知用户 JSON 保留一字节一 Token 的上界。
5. 模型提出工具批次后，Runtime 仍用实际工具参数、最低成功/失败回执、可读证据闭包和剩余工具次数做准入。
6. 准入成功后预留空间被真实反馈使用；准入拒绝则通过结构化通知交给模型重新规划。
7. 首次反馈预算拒绝后，Runtime 把实际 `required_bytes` 传给下一轮编译；编译器先缩减可选历史，仍不可行时才保留拒绝并让模型改写行动。
8. 如果模型在同一任务修订上反复提出语义相同且不可执行的动作，超过限制后以 `no_progress` 结束，不再空转。

## 4. 为什么采用当前设计

当前设计把三个不同问题分开：

- Context Compiler 决定可选信息能占多少空间；
- Token Counter 负责供应商传输的准确计量与未知内容上界；
- Runtime Admission 根据实际动作决定能否派发。

预留不是把工具调用写死到工作流，也不是让编译器猜测模型下一步的完整参数。它只保护一个通用的执行机会。真正动作仍由模型选择，并接受现有 Policy、工具预算、进度控制和证据访问校验。

```bash
uv run pyright
uv run pytest
```

运行 Trace 中可以观察 `feedback_reserve_floor_bytes`、`feedback_budget_bytes`、`BatchAdmitted` 或 `BatchRejected`。
早期报告使用 ContextCompilation v6；当前 OpenAI-compatible 计数器生成 v8，额外记录
`transport_request_bytes` 和 `transport_budget_bytes`。可容纳的批次应出现 `ToolStarted` 与
`ToolRecorded`，而不是在未改变的上下文中连续只有 `BatchRejected`。

## 6. 当前刻意没有实现什么

- 没有根据 FinScope 页面、金融术语或 `read_market_pulse` 名称添加特殊逻辑；
- 没有保证任意大参数、多工具批次都能装入下一轮；
- 没有在 Runtime 中自动缩小模型提议或执行批次前缀；
- 没有在无答案时自动生成降级答案；
- 没有保证超过整体请求上限或必要上下文本身无法容纳的批次可执行。

## 7. 下一小步建议

将下一步预留纳入领域无关真实任务评测，记录不同预留策略下的任务完成率、历史保留率、工具拒绝次数、模型调用次数和总 Token。只有当固定预留在多类任务中出现明确不足，才进一步研究按工具 Schema、任务义务和行动价值自适应分配，不提前加入 FinScope 专用规则。
