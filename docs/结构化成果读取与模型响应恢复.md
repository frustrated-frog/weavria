# 结构化成果读取与模型响应恢复

## 1. 本次新增了什么能力

本次完成两个相互配合的通用能力：

1. `read_artifact` 可以按直属子节点分页读取大型数组和对象，并给出确定性的下一页游标及更窄指针；
2. Runtime 可以识别、记录并有限恢复非法模型响应，修复调用完整计入预算与事件链。

对应架构决策见 [0035 结构化成果分页与模型协议恢复](decisions/0035-结构化成果分页与模型协议恢复.md)。

## 2. 它在 Agent 系统中解决什么问题

Artifact 卸载只能解决“大结果不应整体进入 Prompt”，不能自动解决“模型如何找到并读取所需片段”。旧版对字符串有范围读取，却把数组或对象视为不可切分整体。节点过大时，错误只要求选择更窄指针，但模型还没有看到子节点结构，形成先知道路径才能读取、先读取才能知道路径的循环依赖。

另一个问题是模型协议具有非确定性。JSON Mode 会降低格式错误概率，却不能保证响应一定有内容、一定未截断、一定符合 Weavria 的判别联合类型。旧实现把所有这类错误统一成 `ModelOutputError` 并立即结束，既没有恢复机会，也无法从 Trace 判断失败阶段。

## 3. 一次请求在代码中如何流转

### 结构化成果读取

1. 模型使用已经授权的 `artifact_id` 和 RFC 6901 `pointer` 调用 `read_artifact`。
2. Tool Context 校验 Artifact 属于当前 Run 和已接受证据视图，并记录对生产调用的依赖。
3. 字符串按字符区间返回；数组按索引顺序、对象按排序后的键分页。
4. 分页器尝试在 `length` 字节内内联每个直属子值。
5. 如果某个子值过大，页项目仍返回它的类型、编码大小和精确指针，但以 `included=false` 明确表示内容未被伪造或截断。
6. `end` 是下一次调用的 `start`；`has_more=false` 表示当前节点已遍历完。
7. 工具输出作为新的 Artifact 保存，其完整分页元数据通过 `context_paths=("",)` 进入后续证据选择。

### 模型响应恢复

1. Provider 收到供应商响应后，先验证响应信封、结束原因和文本内容。
2. JSON 解码与 `ModelTurn` Schema 校验分阶段执行，失败被映射为有限错误码。
3. 原始文本不会写入事件；只计算长度和 SHA-256。
4. Runtime 在当前模型阶段接受 `ModelOutputRejected`，从而让拒绝本身成为可回放事实。
5. 若诊断允许修复，且专用次数、模型调用次数和总期限都尚未耗尽，状态回到决策边界。
6. 下一轮 `ControlRequest.control` 携带 `ModelOutputRepairNotice`，其中固定动作码要求重新返回简洁、完整的 JSON 对象；既有可信协议仍负责约束唯一合法输出形态。
7. 新调用成功后连续失败计数清零；再次失败则继续消耗修复预算，达到上限时明确结束。

## 4. 为什么采用当前设计

分页选择“直属子节点页面”，而不是对任意 JSON 文本做盲目字节切片，因为字节切片可能产生无效 JSON，也会丢失路径和类型。直属子节点同时提供三种能力：发现结构、读取小值、导航大值。

模型修复放在 Runtime 而不是 Provider 内，是为了保持成本和状态真实。一次供应商重试就是一次新的模型调用，必须在 `ModelStarted`、请求快照、Deadline 和持久事件中可见。严格 Schema 仍然是安全边界，恢复机制只允许模型重新生成，不能把非法输出宽松解释成动作。

## 5. 如何运行测试或观察结果

```bash
uv run pytest tests/tools/test_execution.py -q
uv run pytest tests/models/test_openai_compatible.py tests/models/test_calls.py -q
uv run pytest tests/runtime/test_control_loop.py -q
uv run pytest tests/sessions/test_engine.py -q
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
```

在 Trace 中可以观察：

- Artifact 读取成功时，`ToolRecorded` 的工具版本为 2，对应结果包含 `start/end/total/has_more`；
- 非法响应后出现 `model_output_rejected`；
- 可恢复时下一次请求的 `current.control.kind` 为 `model_output_repair`；
- 每次修复前都有新的 `model_started`，`model_calls` 会真实增加；
- 达到上限时终态原因是 `model_output_repair_exhausted`，不可恢复错误则是 `model_output_rejected`。

## 6. 当前刻意没有实现什么

- 没有识别任何 FinScope 字段、市场术语或工具名称；
- 没有自动替模型选择某个业务 JSON Pointer；
- 没有放宽 `ModelTurn` Schema，也没有从自由文本中猜测最终答案；
- 没有把原始非法模型响应写入日志或数据库；
- 没有为旧 v1/v2 Runtime 静默改变历史失败语义；
- 没有宣称有限修复一定能挽救供应商持续异常。

## 7. 下一小步建议

用冻结的领域无关长结果任务集比较旧版“整节点失败”和新版“结构分页”，关注任务完成率、额外工具调用、读取字节数和指针错误率。同时统计真实 Provider 的诊断分布与一次、两次修复成功率；只有数据证明默认次数或页预算不合适时，再调整策略，不依据单个应用硬编码。
