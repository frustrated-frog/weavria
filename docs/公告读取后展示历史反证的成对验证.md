# 公告读取后展示历史反证的成对验证

## 问题和验收条件

[上一轮实验](decisions/0149-用当前需求与来源版本约束单读反证.md) 已经观察到首读排序的改善。本轮固定公告已进入模型请求的时刻，两组都可结束、读表或采用其他可行动作。唯一的实验干预是在这一次请求中展示旧表的历史反证。后续决策继续使用普通请求。

正式批次使用三个场景，各做四组成对重复，偶数轮交换先后顺序。当前时刻场景中，至少两对减少无效的实际读表，并且没有一对增加，才视为可复现的节省。同时检查三种场景的逐项时刻、来源引用及当轮实际送达的原文，展示组不能让任何基线已成功的配对变为失败。双时刻任务必须能够取得必要的旧表，更新任务必须不展示旧反证。检查目标决策阶段的 HTTP 调用、输入成本及预算拒绝。只有这些条件同时成立，才考虑改变主链路的请求内容。

## 实验构造

- 资料、种子动作与初始提案固定。种子在真实 SessionEngine 中完整读到旧表、提交可定位引句并改读公告。这里用脚本提交判断，隔离已有反证的使用效果。目标模型自行决定公告到手后是否继续读。
- 两组从独立数据库和固定 Run ID 构造相同的决策现场。逐对比较原始 SessionRequest 的 SHA-256。展示组在已有的低信任 ContextBundle 中放入原任务、旧来源的名称及内容摘要、原判断和核验过的短句，旧表的历史班次不在短句中。绑定当时的权限与版本记录，在目标 Run 用旧调用的归一化参数重新授权。只有仍能确认同版原件时才展示。
- 当前任务只问现行时间；双时刻任务同时要求旧时刻和现行时间；更新任务明确告知用户所问的同名表已重新发布，旧公告仍可读。两组对每项答案使用相同的时刻、引用路径及当轮完整交付检查。历史会话中的答案不能单独获得正确分数。
- 预跑时工具反馈上界为 7500 字节。定向 Trace 显示，重读一份文档需要预留 14422 字节，预算为 14337 字节。短调用 ID 的测试替身可通过，真实 Provider 的调用被拒。正式组统一改为 6000 字节；首个双读仍被拒，单读可以完成。预跑数据不计入结果。

## 复现

```bash
uv run python -m examples.read_counterevidence_feedback --env-file .env.m1-openai --rounds 4
```

## 冻结现场的结果

2026-11-23 使用 `gpt-6-luna`，推理力度为 `medium`。每一格都是四轮合计，箭头左侧只交付公告，右侧按实验条件补充反证。成本从公告已送达到最后一次模型决策累计。正确要求每个时刻与引用都匹配，并且模型在目标 Run 中实际收到了相应的完整原文。

| 场景 | 公告后的实际工具读取 | 模型 HTTP 调用 | 输入 Token | 后续预算拒绝 | 有当轮原文且答对 |
| --- | --- | --- | --- | --- | --- |
| 仅查当前时刻 | 4 → 0 | 8 → 4 | 17531 → 8768 | 0 → 0 | 4/4 → 4/4 |
| 同时查新旧时刻 | 8 → 8 | 16 → 16 | 37078 → 38012 | 4 → 4 | 4/4 → 4/4 |
| 同名时刻表重新发布 | 4 → 4 | 12 → 11 | 26568 → 24338 | 4 → 3 | 4/4 → 4/4 |

只问当前时刻时，基线各轮的后续读取为 1、2、1、0 次，其中三轮读了旧表，一轮还复读了公告。展示后均为 0 次。双时刻组特意展示同一条旧判断，四轮仍然都取得必要的旧表。两种展示场景的首个请求各增加 165 个估算输入 Token。更新场景四对都省略了反证，组间的小幅差异来自相同输入下的后续生成。

## 接入会话后的独立复测

复测重新建立两组数据库，分别打开和关闭 `read_retry_feedback`。模型通过同一个正式 Provider 获取 SessionEngine 编译并持久化的请求。首次读取使用原提案里固定版本的公告，使 Runtime 可以验证模型实际采纳了推荐的动作。模型接下来可以自主结束或继续读。每对请求去掉 `previous_read` 并恢复旧反馈版本后，序列化摘要必须完全相同。

| 场景 | 实际展示轮数 | 公告后的实际工具读取 | 模型 HTTP 调用 | 输入 Token | 后续预算拒绝 | 有当轮原文且答对 |
| --- | --- | --- | --- | --- | --- | --- |
| 仅查当前时刻 | 4/4 | 4 → 0 | 8 → 4 | 17801 → 8892 | 0 → 0 | 4/4 → 4/4 |
| 同时查新旧时刻 | 0/4 | 4 → 4 | 8 → 8 | 17780 → 17780 | 0 → 0 | 4/4 → 4/4 |
| 同名时刻表重新发布 | 0/4 | 7 → 8 | 15 → 17 | 33530 → 38032 | 4 → 5 | 4/4 → 4/4 |

仅问当前时刻时，基线逐轮读取 2、1、0、1 次，包含三次重读旧表和一次重读公告。接入后四轮均直接用公告作答，首个请求的编码估算各增加 161 个输入 Token。双时刻任务改变了需求，旧反证没有改变当前排序，因此只交付普通反馈。重新发布的场景也没有展示，两组都取得新版原文。后一场景启用组实际多用了两次模型调用，无法将这个差异归因于反证。

实验隔离了反证的**消费**。种子判断、初始提案和目标首读固定，资料来自一个合成场景。结果支持在相同需求、相同来源版本且确实改变排序时启用一次展示。自然任务中形成反证的频率，以及在多个领域分摊新增 Token 后的净收益，仍需另测。

uv run pytest -q tests/test_read_counterevidence_feedback.py tests/test_read_counterevidence.py
uv run python -m examples.read_counterevidence_feedback --env-file .env.m1-openai --production --rounds 4

在线复测使用配置文件中的模型凭据、临时数据库和公开合成资料。每行 JSON 包含配对轮次、输入摘要、实际后续读取、交付判定、HTTP 状态与成本，供独立复算。实现的准入与恢复语义见 [ADR 0150](decisions/0150-在单读反馈中展示改变排序的反证.md)。
