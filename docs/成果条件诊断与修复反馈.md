# 成果条件诊断与修复反馈

## 本阶段解决的问题

2026-11-06，成果验收从一个 `workspace_incomplete` 原因码，扩展为可定位的条件诊断。模型能够看到哪个条件失败、期待什么、实际观察到什么、对应哪份成果，以及宿主建议检查的方向。计算能力的保留/退出仍由上一阶段的验收状态控制，诊断不生成自动工具调用。

例如，第一阶段统计正确但没有第二阶段报告时，反馈是 `report_stage`，绑定已接受的统计工作区根 Artifact，提醒使用其 revision 作为 base，并说明 base 文件已经挂载。代码运行成功但报告数值错误时，则反馈 `report_content`，要求检查统计列求和及三行报告格式。这两个问题以前都会变成同一个总原因码。

## 数据结构与调用链

`OutcomeRepairIssue` 包含稳定条件码、条件说明、预期、观察、建议、可选根 artifact_id 与位置标签。位置是诊断信息，不是可执行的文件地址。验收器返回至多八项，必须自行排序优先级，且只有 repair 可以携带未解决条件。

详细验收器通过可选的 `OutcomeRepairFeedbackProvider` 协议声明 `repair_feedback_bytes`，范围为 256–8192。比如示例的 `VerifyWorkspaceRepair` 声明 2048 字节；旧 `VerifyWorkspaceOutcome` 不声明容量，仍保留总原因码基线。宿主通过 `HarnessEvidence(outcome_verifiers=(verifier,))` 装配，两者复用同一注册入口。

一次工具反馈沿以下流程执行：

1. 验收器使用已有 `CapabilityOutcomeContext` 读取已接受结果及受控附件，独立检查内容。
2. Resolver 验证诊断的 artifact_id 确实被这个验收器读取过。仅仅在接受记录里存在，仍不满足绑定条件。未绑定时整份结论退为 unverifiable，诊断不交给模型。
3. 按验收器的优先顺序保留能放入字节预算的完整前缀，记录 `omitted_issues`。不切断 JSON 条目，不把省略的问题标成通过。声明容量过小可能一项都放不下，此时省略计数明确说明仍有问题。
4. `CapabilityOutcome` v2 把容量、诊断及省略计数持久化到现有 NeedLedger v7。v1 保持原线协议，旧验收器无额外预留。
5. `TaskModelViewProjector` 在初始验收槽位建立时就固定容量。反馈原样进入 `capability_outcomes.feedback`；新反馈到达只改变内容，不扩张同一任务的容量承诺。范围不匹配时不展示旧诊断。
6. 模型主动提交 Finish 而验收仍 repair 时，`TaskObligationCompletionPolicy` 从同一诊断中提取首项条件码与修复建议。短反馈仍遵循原来的 258 字节 JSON 字符串预算，完整信息保留在 Task Model View。

核心代码分别在 `src/weavria/harness/outcome_contracts.py`、`outcomes.py`、`task_view.py`、`completion.py`。示例内容检查在 `examples/sandbox_execution.py` 的 `VerifyWorkspace.diagnose`：先检查执行与统计，再检查父版本、统计保留和报告内容；任何一个不可变工作区已满足完整任务仍可通过，没有引入“最后版本覆盖所有成果”的隐式语义。

## 为什么这样设计

自由文本长日志难以限定成本，也容易把噪声带入后续决策；直接生成工具调用则把验收与规划、授权混在一起。本阶段使用有界条件诊断，框架负责引用归属、生命周期和容量，宿主负责条件的正确性，模型负责选择后续行动。

诊断文本和省略计数不参与账本的进度摘要。改变错误措辞不会得到新的进度奖励，不会清空动作指纹、重复调用记录、工具重试次数或 Policy。新的事实或实际验收状态变化仍按原机制计入进度。建议中出现工具名或成果 ID 也不授予调用/读取权限。

修复后 verified 必须清空未解决条件；任务修订建立新的未验收槽位，不继承旧问题。验收器的超时、取消、受控读取、上下文关闭行为复用上一阶段机制。宿主应输出可展示、经过脱敏的诊断，框架不把原始 stderr 或文件正文自动升级成指导文本。

## 测试与真实执行

确定性回归覆盖详细反馈前后的固定容量、v1 原线协议、v2 回读、Unicode 字节计量、完整前缀截断、问题数量上限、未检查成果引用拒绝、verified 禁止残留问题、诊断文字变化不构成进展，以及完成拒绝中的具体条件码。原有取消、超时、恢复与工具退休测试继续通过。

最终默认测试 1654 项通过、19 项 Docker 用例默认跳过；显式工作区 Docker 六种组合通过。Ruff 检查、格式检查、Pyright 均通过。

## 如何运行

```bash
uv run pytest tests/harness/test_capability_outcomes.py tests/harness/test_completion.py -q
WEAVRIA_TEST_DOCKER_IMAGE="$SANDBOX_IMAGE" uv run pytest tests/sandbox/test_workspace_docker.py -q
uv run python -m examples.sandbox_execution --workspace --capabilities verified --run \
  --image "$SANDBOX_IMAGE" --env-file .env.finscope-debug --output /tmp/feedback-summary.json
uv run python -m examples.sandbox_execution --workspace --capabilities repair --run \
  --image "$SANDBOX_IMAGE" --env-file .env.finscope-debug --output /tmp/feedback-detailed.json
```

输出路径需尚不存在。只有显式启用的验收器支付反馈预留成本；容量不足仍由既有 Context/Runtime 拒绝，不自动扩大预算。

## 当前边界与下一步

后续阶段已实现可选的[条件依赖与局部修复选择](条件依赖与局部修复选择.md)。本文记录前缀反馈切片及其当时实验，依赖策略和 v3 契约以新文档为准。

框架尚不自动发现任意领域的正确验收条件，也不保证修复建议本身必然有效。诊断没有自动形成长期记忆，不会绕过权限、替模型修改成果或解除合理的重复调用限制。每轮仍重新验证当前事实，未增加增量验收缓存。

下一步值得深入的是条件之间的依赖与局部修复选择：区分“先修上游数据”与“只改最终格式”，并用多个领域、多个错误位置的任务验证是否减少无效重试。当前切片先保证条件诊断能够准确、安全、经济地到达模型。
