# 自然记忆形成与跨会话消费验证

本轮验证 2026-10-31 已打通的消费链能否承受自然形成误差，不增加新的生产 Runtime 机制。此前固定规范化准入后的消费成绩为完整组 20/20；该结果排除了提取、语义复核和键名漂移，不能外推为完整记忆闭环成绩。

## 问题、基线与冻结条件

数据 `examples/data/memory_lifecycle/cases.json`，版本 `memory-lifecycle/1`：四组连续输入、12 个检查点，每组独立项目作用域，两次重复。

| 情景 | 连续变化 | 检查目标 |
| --- | --- | --- |
| 条件例外 | 一般中文 → README 英文例外 → 纠正例外为中文 | 一般规则与例外共存、纠正后的消费 |
| 到期失效 | 有效至 1 月 10 日的中文 → 1 月 10–20 日的英文 | 查询不同现实时间，到期后回答 unknown |
| 冲突纠正 | 中文 → 矛盾英文记录 → 明确纠正全部矛盾说法 | 保留争议与后续解除争议的边界 |
| 写入隔离 | 一次翻译任务 → 正式中文规则 → 英文假设讨论 | 临时指令和假设不污染长期记忆 |

每个检查点对照无记忆、逐条 top-1、完整组 top-1 三臂，轮换顺序。它们共享同一份真实模型形成的持久化事实；未向形成器提供标准谓词、关系、mutation、预期答案或正确组标签。评分器中的答案只在调用结束后使用。

`deepseek-flash`、temperature=0、enabled/high 思考、输出上限 8192；形成每步总时限 90 秒，消费单次 90 秒、一次模型调用、关闭输出修复、16,000 请求字节；Context window=32,768、安全余量 256。使用 cl100k_base 估计，服务端 usage 独立记录；供应商别名与思考模式不保证权重或输出完全固定。形成器沿用独立提取/复核和 conservative-memory-admission/2，没有调整 Prompt 以迎合本数据集。

## 执行链与职责

1. 用户原文通过真实 `SessionEngine.send` 接受。Fake 只返回确认回答，不生成任何候选或预先规范化事实；事件时间注入为 2026 年 1 月的各输入日，期限仍使用真实 monotonic 时间。
2. `SessionMemoryIngestor` 顺序消费 SessionEvent，只把用户输入作为候选证据。真实模型分别提取、复核，宿主检查引用、作用域、条件和修订安全性；拒绝/待定也属于已完成准入决定。
3. 每个成功的焦点作业立即显式重放，检查作业内容相等且没有增加模型调用。形成失败不会被跳过，后续阶段标记 blocked，不伪造形成完成。
4. 关闭形成阶段的 Memory owner，再重新打开同一记忆库。每次消费使用独立的新 Session 文件，没有 prior 历史。记忆来源按查询日期召回，与 Context 联合选择，然后模型作答。
5. 保存候选、计划、当前事实投影、已交付组、编译报告、输出、实际用量和错误类型。失败后还应保存未完成作业阶段与安全原因链；不保存原始响应、认证头或隐藏思考。

输入、形成和消费属于明确的宿主顺序组合，不是自动后台学习；本轮没有启用 TaskModelView 或工具，不能据此证明它们与自然记忆的联合任务收益。

## 评分与诊断边界

答案接受有限的中英文语言别名。已知答案必须引用实际交付的 active 断言的 source_id，且该断言具有相同语言值；unknown 必须无引用。虚构、未交付、重复来源或只在库中存在的来源不算依据。

这是有限结构评分，不是通用语义蕴含或适用条件判定器。它无法仅凭值和来源证明“新纠正已写入”：旧一般规则可能碰巧与答案一致。因此必须同时公布形成完成情况、准入决定、实际事实和交付内容；形成失败后的答案正确不能记为完整流水线成功。运行器 v2 单独记录 `pipeline_passed`，它也只表示形成无执行错误且本次结构评分通过，不表示所有语义解释正确。

完整组只保证精确 `(scope, kind, subject, predicate)` 内的完整性。自然提取若把一般规则和例外写成不同谓词，完整组无法跨键发现它们；通过提高 k 回避此问题不等于解决形成阶段的语义归一化。冲突解除还涉及完整冲突集合、权威依据和原子修订，不能简单取消 contested 保护来提高成绩。

## 复现与确定性验证

```bash
uv run --env-file .env.finscope-debug python -m examples.live_memory_lifecycle \
  --live --repeats 2 --output .weavria/memory-lifecycle-new-run.json
uv run pytest tests/test_live_memory_lifecycle.py -q
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest -q
```

`--live` 为必需，运行器拒绝覆盖旧 JSON/JSONL。逐条结果同步追加，最终报告绑定数据、源码、模型配置与计量器摘要。四项 HTTP 替身测试验证真实 Session 输入→形成→关闭重开→新 Session 消费、过期过滤、完成作业不再调模型、预期答案隔离、形成失败标记、取消清理及秘密不进入报告；它们不证明真实模型的语义能力。

## 实测结果：2026-10-31

主实验北京时间 19:42:22–19:50:56，计划并完成 72 次消费调用；22 个输入阶段中，12 个形成阶段正常完成，6 个直接失败，4 个因先前失败而阻塞。每臂 24 个检查点中，13 个此前的形成链没有执行失败。

| 方案 | 消费执行完成 | 答案与来源结构评分通过 / 全部计划 | 形成未失败且评分通过 / 全部计划 |
| --- | --- | --- | --- |
| 无记忆 | 24/24 | 6/24 | 不适用 |
| 逐条 top-1 | 24/24 | 15/24 | 11/24 |
| 完整组 top-1 | 24/24 | 15/24 | 11/24 |

本轮完整组没有超过逐条 top-1。15/24 不能当成完整流水线成功：其中四次发生在形成已经失败之后，例如 README 纠正为中文时旧一般规则恰好也为中文，或者形成失败的空库在过期查询中恰好回答 unknown。两个记忆臂在形成未失败的 13 个检查点中各通过 11 个；这也不证明全部形成解释都正确，仍须看事实和适用关系。

### 从实际轨迹定位到的缺口

1. **事实族键漂移已造成漏召回。** 首次重复的例外情景，一般规则成为 `predicate=默认语言, document=技术文档`；README 例外成为 `predicate=document_language, document=README`，还夹带 `exception_to` 条件。两者都通过准入但处于不同精确组。逐条与完整组均只交付中文一般规则，README 任务均回答错误。组闭包正确执行，形成的语义组织没有支撑它。
2. **争议被写成普通摘要事实，未与竞争断言关联。** 冲突情景第一次提取出“技术文档语言规则记录=两项冲突的长期规则记录”，第二次提取出“冲突状态=未裁定”和“处理方式=保留两项说法”等新 active 事实。既有中文事实未进入 contested 状态。第二次消费只命中旧中文，错误忽略了尚未裁定的争议；第一次虽回答 unknown，也不能算结构化冲突机制正确工作。
3. **形成失败与消费成功是不同维度。** 六次直接失败中，三次响应以 length 结束、completion_tokens=8192：两次在复核阶段，一次在提取阶段。另三次在仅一次提取调用后失败、响应为 stop；原始运行器只记录 MemoryFormationError，不能进一步断言是协议、候选 Schema 或引用落地中的哪一种。本轮之后补了安全原因链和未完成作业留证，没有事后编造原始失败原因。
4. **条件成立时，时间与隔离机制能工作。** 第一次重复中，失效情景的三个日期和临时指令隔离的三个检查点均通过；第二次重复在早期形成失败后被阻塞，必须计入全部计划，不能只汇报成功那次。
5. **尚不能声称冲突解除已验证。** 两次最终纠正均在形成阶段失败，没有形成新的可靠消费状态。代码本身仍限制直接修改 contested 目标；本实验还暴露了更早的竞争关系形成缺失，下一步不能只放开保护条件。

## 失败作业的补充重放

在主实验结束前，对四个已经失败、后续不再写入的数据库做只读 SQLite backup，在副本上调用原 `MemoryFormationEngine.process(access, job.input)`，配置和流水线版本相同。原主实验的计划、事实和评分保持不变，不把补充重放混入主表。

- 两个提取尚未保存的作业分别重新提取、复核，共各两次调用，完成并准入；这是有成本的补充重放，不是首次运行成功。
- 两个已保存提取的作业各只调用一次 reviewer，证明它们复用了原提取；两次仍达到 8192 上限而截断，均未完成。恢复机制不会自动解决重复的预算耗尽。
- 补充共 6 次调用，输入 15,700、输出 30,642、总 Token 46,342。这里验证阶段复用与失败语义，没有再测重放后的新会话作答，不能宣称任务已经恢复成功。

主运行器 v1 对失败阶段留证不充分，补充读取了四个未完成作业。最终运行器 v2 增加 `failure_audit` 和 `pipeline_passed`；只增加诊断与评分元数据，没有修改形成提示词、消费提示词、召回或数据集。本页主表使用 v1 原始输出和已记录的 formation_complete 计算，未重新调用模型以覆盖失败。
