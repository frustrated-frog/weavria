# 能力适用性检查与补搜的实现和验证

本轮补上了“找到了相关工具，但它并不能做用户要求的动作”这一环节。机制默认关闭：在原有语义提名之后，检查完整协议是否适用；存在缺口才改写查询并补搜。相关决策见 [ADR 0126](decisions/0126-能力适用性检查与有界补搜.md)。

## 从文件指纹失败看执行过程

旧实验要求计算本地文件的内容指纹，首轮 24 张卡没有包含 `read_file_digest`。卡片模型提名了 `find_archived_document` 和 `read_sensor_archive`，原解释器进一步错误选择归档读取。

开启新机制后，一次请求依次经过：

1. `TaskAwareSessionPreparer` 和 `CapabilityResolver` 仍先确定策略允许且可用的目录。`TaskUnderstandingEngine.prepare` 建立总期限并固定原始请求。
2. `ModelCapabilityDiscovery.scan` 复用原有卡片扫描、提名和合并。这一步只得到可能相关的名称，不是最终适用结论。
3. `capability_fit.fit_request` 展开提名工具的完整描述符，包含输入输出 Schema。模型逐一判断动作、输入对象/命名空间、输出承诺是否支持当前请求。
4. `validate_fit` 验证判断必须恰好覆盖此次提供的每个身份。判断引用当前目标或显式约束的原文；supported 项还须通过 JSON Pointer 引用说明或 Schema 字符串叶子。错误身份、虚构原文、错误指针和不存在的引文均拒绝，不能直接进入补搜。
5. 本题检查返回 search，并拒绝两个不匹配项。缺口查询进入同一 `HybridCapabilityIndex`，排除已经看过的 24 项；下一组新卡包含 `read_file_digest`。新提名展开后再次检查，通过才交给原任务解释器。
6. 解释器继续生成 TaskSpecification，并沿原有需求、Schema、Policy 和 Runtime 路径准入。适用性检查不执行工具、不填执行参数、不满足任务完成义务。

真实开发集记录的轨迹是 `scan → inspect → scan → inspect → interpret`，只增加一轮补搜。补搜并非拿到标准答案后手写查询，运行时查询由检查模型根据原文缺口生成；标准答案只在模型调用结束后用于统计。

## 状态怎样推进

新增的 `CapabilityFitConfig` 定义补搜上限：默认两轮、每轮最多两个查询、单次最多展开 24 个完整协议。原有发现器持有所有阶段的调用和输入 Token 账本，scan、merge、inspect 共享 max_calls、max_input_tokens 和父准备期限；补搜不会重开一份预算。

每次 discover 局部保存已检查卡片、保留的支持项、检查报告、补搜检索报告和模型请求步骤，不把会话状态写进全局对象。search 后保留已支持的操作，与新提名联合复查，避免寻找第二个工具时丢掉第一个；下一轮仍能撤销此前的错误判断。

索引的 `exclude_names` 在两路排名截断之前生效。如果旧第一名已看过，新查询可以拿到第二名，不能先截断再过滤成空集。排除项只改变当前查询资格，完整目录摘要、BM25 文档频率与向量缓存不变。同轮多个查询也排除彼此已取得的候选，避免重复消耗窗口。

没有将召回相似度解释为置信度，也没有根据“分数低”触发规则式重试。触发条件是对实际请求和完整协议的语义检查，宿主负责可验证的状态推进与边界。

## 三种结果与失败边界

- `ready`：至少一个支持项，模型未报告必需操作缺口；只发布这些支持项。
- `no_tools`：当前任务无需工具；支持项与缺口都必须为空。它不能用来表示“需要工具但目录里没找到”。这一语义仍需真实模型评测，类型约束本身无法证明模型判断正确。
- `search`：至少一个带原文锚点的缺口与查询，进入有界补搜。

补搜次数耗尽或目录已经检查完仍有缺口，返回 `NO_PROGRESS`，报告 `repairs_exhausted` 或 `catalogue_examined` 等原因，不把已支持的部分工具发布为完整候选。这里的“目录已检查”也只代表卡片已经进入模型，不代表证明了全世界不存在所需能力。

上下文任务保留上一阶段的全扫描策略，然后检查提名的完整协议；此时若仍有缺口就停止，不把最后一句脱离上下文后重新检索。缺少具体参数值原则上留给后续澄清；输入对象类型、命名空间或输出能力不匹配才是此处的问题。

非法模型输出不会自动重试或悄悄退回旧路径。容量、模型故障、超时、取消和报告接收失败保留原错误分类。取消传播并清理已有调用；本地 ONNX 仍需等待当前有界推理批次结束。目录在发现中变化时，原 TaskUnderstandingEngine 的身份检查继续拒绝准备结果。

## 引用检查能证明什么

`RequestQuote` 只证明引文属于当前目标或某条显式约束，不生成字符区间，所以不要求重复引文具有唯一出现位置。`ProtocolQuote` 使用 JSON Pointer 定位实际字符串叶子，处理 `~0`、`~1` 和数组索引，不接受伪造字段或整个对象冒充引文。

两种检查都不能证明语义蕴含：模型仍可能引用真实但无关的句子，或遗漏一个请求动作。本机制也没有把所有输入输出关系变成形式化规划。必要的不确定性检查、任务覆盖审计和实际执行结果验收继续独立存在。

## 报告与兼容

不配置 fit 时，旧配置序列化省略新增空字段，原发现请求和版本摘要保持不变。没有排除项的检索报告仍是 v1；有排除项使用 v2，并记录被排除身份。

开启 fit 使用发现报告 v3，保存完整目录规模、累计检查卡片数、追加检索报告、检查步骤和 stop_reason。检查列按实际 offered_names 排序，模型返回顺序不能错配判断。报告校验补搜查询来自已接受缺口、候选集合持续新增、检查身份来自此前提名、最终选择对应最后一次适用性验收。

理解记录对应 v4，旧 v1/v2/v3 继续可读；Session 和 Runtime 的持久化 Schema 不变。详细报告仍由 reporter 显式导出，失败异常携带未完成过程。正文、协议引文和补搜查询只在调用中短暂使用，报告保留摘要与判断码，不存私有推理。

## 实验设置

开发集原封不动复用上一阶段 96 工具/8 任务。另行冻结 `examples/fixtures/capability_fit.json`：9 个具体能力和 84 个干扰项，共 93 个工具、12 个任务。它增加了路径与归档 ID 的区别、正文与属性的区别、校验和、日历占用/空闲、TLS 到期、多个动作、无需工具，以及删除文件、发送邀请、读取未归档本地正文这三类目录缺失。

这些仍是人工构造的领域无关任务与只用于准备的工具，尚未执行真实业务操作。日历空闲题预先允许“直接查询空闲工具”或“读取占用区间后推导”的替代选择，避免把合理组合误计为错误；其余按冻结的工具集合验收。目录缺失题只评估是否避免执行替代工具，安全停止不等于完成用户任务。

四个对照：原混合扫描、只做适用性检查（max_repairs=0）、检查并补搜（max_repairs=2）、完整协议目录。逐题轮换顺序，共用 deepseek-flash、temperature=0、reasoning_effort=none、32,000 Token 窗口、4,096 输出额度、256,000 请求字节和 60 秒任务期限。E5 权重和分词器与 ADR 0125 相同，没有为本次结果更换模型、调 top-k 或修改提示词。

## 开发集结果

| 策略 | 正确工具集合 | 明确未解决而停止 | 模型调用 | 总 Token | 总耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原混合 | 7/8 | 0 | 16 | 74,024 | 22.160 s |
| 只检查 | 7/8 | 1 | 23 | 85,812 | 26.718 s |
| 检查加补搜 | 8/8 | 0 | 26 | 97,036 | 31.716 s |
| 完整目录 | 8/8 | 0 | 8 | 229,381 | 13.456 s |

只检查把文件指纹题的错误接受变成了明确停止；加入补搜才找回正确能力。相对原混合增加了约 31% Token 和 10 次调用，不能只报告准确率改善而隐去开销。完整目录在该规模与预算下仍更快，只是 Token 更多。单次开发集结果不证明普遍提升。

## 新任务集结果

| 策略 | 符合预期的准备行为 | 明确未解决而停止 | 模型调用 | 总 Token | 总耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原混合 | 10/12 | 0 | 27 | 130,144 | 44.148 s |
| 只检查 | 12/12 | 3 | 33 | 124,205 | 46.372 s |
| 检查加补搜 | 12/12 | 3 | 45 | 163,617 | 56.166 s |
| 完整目录 | 10/12 | 0 | 13 | 365,376 | 33.668 s |

8 个需工具任务与 1 个无需工具任务在检查两臂都准备成功；另外 3 个目录缺失任务均以 NO_PROGRESS 明确停止。12/12 是包括安全停止在内的预期准备行为，不是 12 个任务全部完成。

原混合在发送邀请、读取未归档本地正文两题发生其他准备失败；它们没有执行错误工具，但也未给出机制内明确的缺口停止，表中未将普通失败计为正确。完整目录在发送邀请题准备失败，在本地正文题则接受了 `read_archived_text`；完整 Schema 中的归档 ID 不能替代本地路径，这一不匹配被检查路径拒绝。不得将普通异常、适用性拒绝和错误接受混为一个失败指标。

新任务集上无需补搜的 9 题，原混合与完整目录也全部正确。补搜在 3 个目录缺失题各消耗两轮后停止，没有增加有效能力；相对只检查多 12 次模型调用和 39,412 Token。这说明当前收益包含“错误替代被拒绝”和“某些召回遗漏被恢复”两个不同方面，尚未解决如何更早判断继续补搜的价值。所有调用均保留供应商用量，没有按成功样本删掉失败开销。

所有运行输出保存在忽略目录 `.weavria/capability-discovery/fit-development-01.json` 与 `fit-holdout-01.json`。模型调用失败不会被删除或续填为成功。开发集启动后仅补充报告交叉引用校验和测试，未改变检查提示词、排名或补搜规则；新任务集在首次真实运行前冻结。

## 接入与观察

沿用已打开的编码器和 HybridCapabilityIndex，在配置中显式启用：

```python
CapabilityDiscoveryConfig(fit=CapabilityFitConfig(max_repairs=2))
```

该配置可传给 `ModelCapabilityDiscovery(config=...)`，或设为 `HarnessConfig.semantic_discovery`，并通过 `AgentHarness.from_config(capability_index=index, ...)` 装配。无需索引也可做全扫描后的检查；全目录已经检查仍有缺口时停止。

```bash
uv sync --extra local-memory
uv run --no-sync python -m examples.hybrid_capabilities --live --fit --repeats 1 \
  --model /absolute/path/model.onnx --tokenizer /absolute/path/tokenizer.json \
  --dataset examples/fixtures/capability_fit.json \
  --output .weavria/capability-discovery/new-fit-run.json
uv run pytest tests/harness/test_capability_fit.py \
  tests/harness/test_capability_index.py tests/harness/test_semantic_discovery.py
```

验证结果：全量 pytest **1,986 通过、24 跳过**（跳过项需要显式 Docker 镜像），发现/索引/适用性定向测试 **65 通过**。Ruff、全仓格式检查和 Pyright 通过。测试覆盖原文与 Schema 伪造、判断顺序、补搜去重、共享调用/Token 预算、部分支持保留、取消/超时、报告兼容与正式 Harness/Session 装配。

模型连接仍通过 WEAVRIA_MODEL_* 环境变量配置，输出路径必须不存在。去掉 `--fit` 保留原四路索引实验，去掉 `--live` 只运行本地编码检索，不会调用付费模型。

## 当前限制与下一步

本阶段尚无执行中交互搜索、Skill 组合、对话查询重写、自动扩充目录或基于完成结果的学习。已检查但未提名的卡片不会重复查看，因此卡片层的假阴性仍可能留下；补搜次数有限，也可能因模型错写查询、错误判为 ready/no_tools 或协议格式不合法而失败。

下一步应让真实执行任务检验这些判断：候选能否接受真实参数、返回足够且匹配的结果，何时将工具反馈转换成新的能力缺口。先用本地可执行任务与独立结果判定补上这条证据链，避免长期把“选对了工具名称”当成 Agent 完成任务。
