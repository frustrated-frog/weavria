> **FinScope 是首个真实应用场景，不是框架的宿主、产品边界或抽象来源。**

## 0. 如何使用本文：它是长期宪章，不是待完成的功能清单

本文的主要读者是未来每一次进入仓库工作的 Codex、开发者、技术评审者与研究协作者。其作用是让任何一次开发都能追溯到项目真正追求的技术方向，防止项目在长期迭代中逐渐退化为“把能看到的功能逐一补全”。

本文**不是**一次性的 PRD、固定开发排期、某个岗位 JD 的改写，也不是要求立刻创建全部目录和接口。文中的技术主题是持续研究的能力地图：只在依赖条件、真实问题和工程价值成立时引入，并始终遵守已接受协议的演进语义。

每次较大的模块设计或架构变更，应当先核对本文相应章节及当前代码、测试与 ADR，再决定本轮真正解决哪个问题。长期目标保持稳定，具体技术方案可以根据新论文、新实践、新失败轨迹以及用户新决策调整。**不能因为某一项功能尚未实现，就用空接口或示例代码冒充完成；也不能因为短期工期压力，悄悄降低本宪章定义的技术标准。**

本文的修改必须有明确理由、变更记录与项目所有者的明确同意。Codex 可以提议修改，但不得为了方便当前实现而擅自放宽标准、删除长期目标或降低验收定义。

## 1. 为什么开发 Weavria

### 1.1 我们不缺另一个简单 Agent 封装

直接使用一个现有框架、注册几个工具、放上聊天窗口并输出流式答案，可以较快交付 Agent 应用，但不是 Weavria 的根本目标。Weavria 要掌握 **Agent 系统的核心运行机制与工程能力的设计权**，而不只具备调用这些机制的能力。

Weavria 必须自己回答：模型的一次决策如何成为一个合法的动作？多工具执行的事实如何汇合并进入下一轮？长任务如何保有可追溯的工作状态？上下文不足时怎样选择、压缩和恢复信息？过去的经验如何形成可纠错的记忆？工具发生副作用且进程崩溃时如何确认结果？不同策略的改进如何被可靠验证？运行与治理如何从单进程自然升级为可管理的基础设施？

这些问题具有各自独立的算法、数据结构、时序、事务、权限、成本与信息损失难点。它们构成项目的长期研发内容，而不仅是产品特性名称。

### 1.2 为什么观察大厂 Agent Infra 岗位

招聘 JD、云厂商产品、开源社区架构和工程案例，是用来观察 **现实生产问题与产业技术需求** 的窗口。它们说明团队实际在处理 Harness Kernel、Managed Runtime、Control Plane、Agent Identity、Tool/MCP Security、Context & Memory、Evaluation 等能力。

**我们不会按照一份 JD 的顺序逐项仿制功能。** 岗位并不规定 Weavria 的目录、接口、技术路线或发布时间。我们用这些信息反问：哪些能力解决了真正的问题？哪些是框架的通用基础？哪些属于公司级部署平台？哪些应该在有需要时引入？

未来 Weavria 成熟后可以成为 Agent Infra / Runtime / Harness 岗位面试和技术交流的重要项目证据，但**面试匹配度是高质量研发的结果，不是架构的唯一优化目标**。不能为了简历关键词而引入不必要的微服务、控制台、Swarm 或训练流水线。

### 1.3 质量参照系，不是模仿对象

PaiSmart / 知枢是已有的实际 Agentic RAG 项目，可用于确认我们已经解决过哪些业务 Agent 问题；DeerFlow、LangGraph、Deep Agents、DeepSeek Harness、OpenHands 等可以用于考察成熟工程如何处理不同难题。论文提供研究假设、算法和实验方法。

过去讨论使用过“PaiSmart 约 5 分、DeerFlow 约 9 分、Weavria 目标至少 7.5 分”的非正式比喻。它的**唯一含义**是要求 Weavria 的核心工程能力明显超越普通个人 Agent 应用，在选定方向达到成熟开源系统的技术深度。它不是通用 Benchmark、不能直接从 Star 数或功能覆盖率推导，也不能被用来武断宣称项目已达到某一分数。

对标的是 **难题解决的程度、设计的内在一致性、机制的原创组合与可验证性**，不是源代码、功能清单、类名和 UI。

## 2. 两条主线必须同时成立：Agent 智能能力与 Agent 工程基础设施

Weavria 不能只做一个严谨的状态机，也不能只做一个“很聪明但无法安全运行”的 Agent。必须长期维持两条相互支撑的研发主线。

**Agent 能力主线（Capability / Intelligence）：** 研究任务理解、信息需求、规划与行动选择、Tool/Skill 组合、上下文决策、记忆写入与召回、反思纠错、完成判定、复杂任务拆分与协作。核心问题是：**这些机制如何改变 Agent 能做的事情，以及对信息与行动的使用方式？**

**系统工程主线（Reliability / Infra）：** 研究执行所有权、状态一致性、预算与截止时间、异步调度、持久执行、故障恢复、幂等与审批、身份授权、隔离、版本、部署和观测。核心问题是：**Agent 做出决策之后，系统如何在真实失败条件下可靠、安全、可审计地完成它？**

二者相互依赖：Agent 需要可靠地保存事实和执行成果以支撑长时推理；Infra 又必须容纳动态决策、任务修订、上下文变化和不确定模型行为。不能把所有“技术深度”收缩成持久化与故障恢复，也不能把生产可靠性视为可选附属功能。

**Evaluation & Research 是第三条贯穿两条主线的证据链**，负责揭示效果与失败边界，而不是凌驾于技术研究之上的形式化工作。

## 3. 什么才算“有技术深度”

任何被选定为核心研发主题的子系统，都应尽量达到以下四种深度。四者不是简单相加，缺失关键一项会限制整体成熟度。

### 3.1 机制深度（Mechanism Depth）

解决实质性难题；给出具体的算法、状态模型、数据结构、权责分配、决策规则与计算代价。能够解释输入如何经过处理变成输出、内部有哪些竞争策略、失败边界在哪里、为什么没有采用更简单或更复杂的方案。

不能以 `Protocol`、抽象基类、Pydantic Schema、几个配置枚举或包装第三方 SDK，代替机制本身。接口可能是必要的，但不自动具有算法深度。

### 3.2 工程深度（Engineering Depth）

当输入非法、依赖失败、任务超时、模型取消、工具产生部分结果、并发顺序变化、状态被修订、进程崩溃或旧版本数据恢复时，有明确且能验证的执行语义。关键不变量由代码约束，而非仅由 Prompt 宣称。

需要分清 **代码明确保证什么、仅在可信插件协作时保证什么、外部系统不支持时无法保证什么**。不要把“SQLite 存过状态”描述为完整 Durable Execution，不要把异步超时误称为能强制杀死阻塞代码，不要把生成幂等键误称为外部 Exactly-once。

### 3.3 研究深度（Research Depth）

同一问题可以选择不同策略，并能够通过真实任务、模拟失败与冻结配置比较其质量、成本与适用边界。研究不仅要记录成功案例，也要记录性能退化、失败样本、复杂度和反直觉结果。

**研究应当服务于技术探索，而不是替代技术探索。** 不能为了尽快展示对照实验而刻意采用浅层实现。设计时应清楚知道将来如何判断好坏；随后先实现足够真实的机制，再以匹配该机制的测试和实验验证。不是每个小改动都要求昂贵的 LLM A/B 实验，确定性不变量可由契约与故障注入证明，任务收益才应由真实模型与任务集证明。

### 3.4 系统协同深度（Compositional Depth）

一个强模块不能只在自己的孤立单元测试中表现优秀，还要能与其他模块保持语义一致：Task Frame 改变后如何重新选取 Context；Memory 如何提供有来源的历史事实而不是覆盖权威数据；Tool Result 如何形成 Artifact、Event 与模型反馈；Checkpoint 如何保存恢复所需的版本和控制状态；Policy 如何约束动态能力暴露。

真正优秀的 Harness 应该通过合理组合产生能力，而不是有几十个互不协作的高级组件。

> **共同验收原则：这个模块“完成了”不等于这个模块“做深了”。**

## 4. 项目不做什么

Weavria 明确不以以下路径作为主要研发方向：

1. 复制 DeerFlow、LangGraph、Codex、Claude Code 等框架的目录与执行架构，替换命名后发布。
2. 直接让这些框架接管 Weavria 的主要执行控制链路，再称之为“自主研发”。
3. 为了显示技术复杂而预先创建全部微服务、Manager、抽象层、分布式组件和空目录。
4. 为 FinScope 的特定股票接口倒推 Runtime 类型，将金融术语写入通用 Core。
5. 仅用固定 Workflow 或硬编码关键词代替复杂 Agent 的真实理解与决策，再用演示任务证明它聪明。
6. 用各种工具包装、Prompt 微调或模型能力，掩盖 Memory、Context、Recovery 等机制的缺失。
7. 以测试通过率、文件数量、论文引用数、功能数量或主观评分充当技术成熟度的充分证据。
8. 将尚未实现或只在可信单机场景成立的保证，包装为生产级安全性、分布式可靠性或通用最优算法。
9. 把论文实验直接塞进稳定 Runtime，导致正式行为随实验配置失控。
10. 为了对齐招聘 JD，把独立研究项目提前变成复杂的企业管理 SaaS。

这不是否定已有优秀框架和工程基础设施。可以采用标准协议、成熟算法、数据库、HTTP、Pydantic、OpenTelemetry 等公共技术；关键是**核心 Agent 执行语义和关键研究机制始终由 Weavria 自身决定和掌握**。

## 5. 长期目标架构：职责分离而非强制微服务

```text
Applications / Integrations              FinScope、未来第二独立场景、SDK/CLI/API
              │
              ▼
Agent Harness / Capability Layer          Task Understanding / Planning / Skills
                                           Context / Memory / Completion / Coordination
              │
              ▼
Agent Runtime Kernel                      Model Turn / Tool Dispatch / Run State
                                           Event Reducer / Budget / Cancel / Control
              │
              ▼
Durable Execution Foundation              Event Log / Artifact / Checkpoint / Effect Ledger
              │
              ▼
Managed Runtime                           Admission / Worker / Lease / Recovery / Scheduling
              │
              ▼
Infrastructure Adapters                   Storage / Queue / Sandbox / External Tools

Control Plane      管理 AgentDefinition / Version / Deployment / Policy Binding
Security Plane     横向约束身份、授权、凭据、网络、文件和执行隔离
Evaluation Plane   横向建设 Trace、Benchmark、回放、故障注入、发布门禁
```

图是逻辑能力关系，不表示一律单向运行调用，也不代表必须分为多个进程。早期的 Managed Runtime 可以与 Kernel 处于同一个 Python 包或进程；安全和评测是跨层约束而不是晚期才安装的插件。

### 5.1 权威依赖方向

- `core` 只表达领域无关的基本事实、协议和不变量，不依赖业务、存储实现或模型供应商。
- `runtime` 管理执行与状态；不能为了访问业务资料反向导入 `apps`。
- `harness` 使用 Runtime 的公开能力组织 Agent 行为；任务理解结果不自动提升为用户事实或执行权限。
- `sessions` / 持久化 / Worker 等可作为组合或适配层演进；避免把 SQLite 特性写死到 Kernel 接口。
- `control` 记录配置与生命周期；具体 Run 锁定生效配置版本，不依赖在线可变配置隐式改写任务。
- `labs` 是实验场；正式运行链路不导入实验包。
- `apps/finscope` 属于应用域；可使用 Weavria 公开接口，Weavria 不能反向依赖它。

设计新增层级时必须回答：它拥有哪一种以前无处承载的决策或不变量？若只是转发方法、改名或包装另一层，应优先取消这个抽象。

## 6. Runtime Kernel：自主、明确、可解释的执行语义

**研究命题：** 把不可信、非确定性的模型行动提议转化为有界、可审计、可重放状态的执行过程，并能够接受真实环境反馈持续推进。

重点技术：

- 区分 `Session`、`Run`、`Turn`、`Step`、`Attempt`、`Event`、`State`、`Artifact`、`Checkpoint`，明确身份与生命周期。
- 决策层的 `ModelTurn`、完整 Tool Batch、Finish Candidate、任务修订与执行阶段；模型意图不构成执行许可。
- 可验证的 Event Acceptance 与纯 State Reducer；Event 是已经发生或已经接受的权威事实，而不是供 UI 观看的状态日志。
- 有界并发、独占执行屏障、兄弟调用成功/失败隔离、批次反馈完整汇合、稳定投影顺序。
- 截止时间、模型轮次、工具次数、输入和输出预算的统一消耗与明确的终止原因；取消传播必须覆盖子任务。
- Prompt 或模型不得绕过 Runtime 的权限、预算、终止、恢复与状态一致性规则。
- 任务修订、旧模型响应失效、进行中工具结果保留、尚未派发调用跳过，以及修订后重新验收。
- 确定性执行轨迹、失败注入、属性与状态机测试，并说明行为在异步插件不合作时的边界。

**最低不变量：** 未接受的行动不得派发；结果必须关联正确调用身份；整轮反馈不能悄悄遗失兄弟失败；不能在旧 Task Revision 下完成新任务；终态不能偷偷恢复为 RUNNING；不能把一轮模型的 Finish 直接等同于任务质量验收。

**纵深方向：** 自定义调度策略、任务连续性控制、异步执行所有权、增量状态归约、可替换的 Completion Policy、精确预算核算。需要根据实际失败与性能问题逐步引入，不以所有抽象同时存在为目标。

**验证：** Fake Provider/Fake Clock 支持纯机制断言；真实模型用于验证纠错与规划收益；实际输出的错误、部分完成和引用必须从运行事实独立核查。

## 7. Durable & Managed Runtime：从持久会话到可替换执行者

**研究命题：** 即使服务重启、Worker 被杀、调用超时、租约过期，任务身份、已经确认的事实和可恢复进度仍然保持一致；替换执行者不会错误重放外部副作用。

要严格区分：

- **Durable State**：任务、会话、事件和成果有持久记录。
- **Durable Execution**：恢复者能根据权威记录恢复执行位置，决定什么可以安全复用或继续。
- **Managed Runtime**：执行权可由调度器授予不同 Worker，具备队列、租约、Fencing 和资源治理。

研究范围包括：事件事务提交、Checkpoint 游标、Task/Model/Tool Attempt 的可恢复边界、恢复状态机、Worker Lease、单调递增 Fencing Token、持久调度与任务抢占、原始事件重放与外部动作重试的区别，以及长期任务中的定时等待和人工审批。

**特别重要的语义约束：**

- `ToolStarted` 已提交不代表外部工具已经完成；`ToolRecorded` 已提交才代表结果正式接受。
- Artifact 的存储成功与 ToolRecorded 的提交要建立可恢复的一致性关系；孤立快照不能自动成为已完成事实。
- 工具效果可能已在外部成功、但内部 Ledger 尚未记录成功，此时属于 `UNKNOWN`，不能简单重新执行。
- 幂等键应传至真实外部系统并有适用范围及过期契约；不支持幂等或结果查询时，安全策略必须允许停止、协调或人工确认。
- 租约和 Fencing 保证的是受控持久化边界的所有权，不能撤销已经发送至外部的副作用。
- `Cancel` 是请求执行停止的控制意图，不自动证明外部执行已被停止。
- 恢复必须明确对模型调用、工具副作用和会话结果分别采用何种政策；不能承诺跨系统 Exactly-once。

**研究与工程验收：** 在 Event 持久化前后、工具提交前后、Checkpoint 写入前后主动 Kill 进程；另一执行者重建 State 和执行游标，完成可安全继续的工作，对结果未知的副作用保持保守。增加 stale worker、重复队列消息、租约到期、Checkpoint 损坏、版本不兼容等测试。仅恢复聊天历史不算本模块验收。

**演进纪律：** 先做单机可恢复执行，再根据真实需要扩展单机多进程和 Worker Replacement，最后才考虑跨机器集群。数据库从 SQLite 升级至 PostgreSQL 等应由所需的并发、锁与可靠性证明其必要性，而不是出于架构装饰。

## 8. Tool、MCP 与执行安全：工具不是函数表

**研究命题：** 在模型不可信、工具能力各异、调用具有副作用且运行环境可能失败时，如何完成安全、有限、可追溯的能力执行。

工具必须拥有稳定身份与版本、严格输入输出类型、明确的效果类别和幂等承诺、权限与风险分类、超时和资源限制、审计来源、失败归类以及可选择的回放策略。**工具描述与模型可见性不是执行授权**；`ToolRegistry` 发现能力，`Policy` 根据身份及具体参数决定执行，`Executor` 负责尝试，`Effect Ledger` 记录和协调外部效果。

深入研究：

- 工具参数与内容校验、JSON Schema / Typed Contract 演进、Provider 原生 Tool Call 归一化。
- 并发工具的实际安全性、顺序和依赖，不能仅凭 read-only 名称假定线程安全。
- `READ` / `WRITE` / `GENERATE` / `EXTERNAL_EFFECT` 及其恢复语义；`REPLAY_SAFE`、`AT_MOST_ONCE`、`REQUIRES_RECONCILIATION` 等策略的适用条件。
- 同一 Run 内和跨 Attempt 的工具身份、动作指纹、外部幂等键和结果复用。
- 审批应绑定实际调用主体、工具版本、规范化参数、Policy 版本和批准范围，过时审批不可泛化复用。
- Tool Output、MCP 元数据、检索资料均为低信任内容，不得借模型上下文提升为系统指令。
- Agent Identity、User Identity、Credential Handle、最小权限、Network/File Policy、敏感参数与日志脱敏。
- 不可信代码执行和阻塞插件必须具备隔离途径；协作式异步取消不能冒充进程/容器级硬终止。

MCP 属于扩展能力与互操作协议，不能成为绕过 Weavria Registry、Policy、Ledger 和审计的捷径。研究 MCP 时分别考虑工具发现、授权、长任务、服务侧变更和故障语义，而非仅能调用服务器就算完成。

**验收：** 有明确的工具超时—继续运行问题测试、跨租户权限拒绝测试、重复写入测试、审批过期测试、工具崩溃时 UNKNOWN 状态测试，能够解释系统在不支持外部幂等的情况下究竟保证什么。

## 9. Context Engineering：不是截断，而是可恢复的信息分配

**研究命题：** 在有限 Token、成本和注意力预算下，把当前任务真正需要的事实交给模型，减少无关内容，同时尽量保护后续可恢复、可核实的信息。

严格区分：

- **Execution History**：事件、工具事实与来源的完整权威记录。
- **Artifact**：原始成果和数据，可通过身份与范围访问。
- **Context View**：一次模型调用实际消费的、按预算构造的信息投影。
- **Compaction**：对部分历史构建更短表示的过程，它通常有损，不能改写权威事实。

持续研究：Tokenizer-aware 成本核算，消息原子组与工具调用—结果配对，任务相关性与语义检索，依赖闭包，重要性/新颖度/时效性排序，多级信息表示（完整、片段、摘要、引用）、大型 Tool Output 卸载、Artifact 按需回取、压缩游标和摘要版本、恢复时的 Context Rehydration。

**最低不变量：** 不让一条 Tool Result 脱离其对应调用而被模型误用；不悄悄删掉刚发生的关键失败反馈；不能让压缩摘要替代原始状态或来源；历史回取必须遵守运行身份和访问权限；超过硬预算时要明确失败或采用声明的降级策略。

**技术问题不能偷换：** `len(text)` 或 UTF-8 字节可以作为早期可验证的近似，但不等于实际 Token 数；简单窗口裁剪、规则摘要、向量召回也不天然等于 Context Engineering 的终态。

**研究路径：** 使用完整上下文、固定窗口、纯摘要、按相关性选择、依赖闭包选择、分层压缩与按需恢复等策略构成可替换实现；根据任务完成率、引用正确性、关键事实保留率、Token/延迟成本和恢复质量比较。不能只追求 Compression Ratio 更高。

## 10. Memory Engine：不是向量存储，而是有生命周期的事实系统

**研究命题：** 哪些信息值得记住，如何形成、组织、更新、纠错、遗忘和检索，使记忆可靠改善未来任务，而不是把错误累积进 Prompt。

概念上区分 Working、Conversation、Episodic、Semantic 和 Procedural Memory；并明确它们与 Session State、外部知识库 Evidence、Context View 的界限。可以共享存储，但不能混同语义或生命周期。

深入研究：

- 记忆候选提取、事件来源、信息归一化、实体对齐、作用域归属与写入许可。
- 重复消除、冲突检测、事实修订、版本谱系、失效与撤销、用户明确纠错优先规则。
- `valid_time`（现实有效时间）与 `recorded_time`（系统获知时间）的双时间语义；面向历史任务的 As-of Retrieval。
- BM25、Dense、RRF、关系扩展、时间与来源重排序，以及索引重建、过期处理和性能退化方案。
- 记忆置信度与权威性区分，可信用户陈述、工具结果、模型推断不得无条件互相覆盖。
- 程序性记忆的适用条件、任务类型、执行效果和反馈；一次成功经验不能直接晋升为全局指令。
- 遗忘策略、噪声控制、更新成本、敏感信息保护和用户/项目/Agent/租户隔离。

**最低不变量：** 未经确认的推断不会自动变成永久用户事实；新事实不抹掉可审计历史；长期记忆不能突破当前用户或 Agent 的权限；同一事实在不同时间的有效版本可解释；检索返回来源而不只是文本和相似度分数。

**研究验收：** 记忆更新、跨会话时间推理、冲突纠错、应当拒答、长期污染与召回成本；与无记忆、简单历史窗口、BM25、Dense 等朴素策略对比。不能把“成功写入并召回一段文本”当成 Memory Engine 成熟。

## 11. Harness 智能组织：Task Understanding、Planning、Skills、Completion、Orchestration

**研究命题：** 在不把用户请求预先翻译为固定 Workflow、不把所有能力同时暴露给模型的前提下，帮助 Agent 正确理解工作目标、选择信息来源、规划行动、管理中间状态、持续纠错并判断何时真正完成。

### 11.1 任务理解不是固定分类器

`TaskInput` 是用户与宿主的权威原始意图记录；`TaskFrame`、规范化目标、信息需求、歧义分析、能力需求和完成条件属于模型推导出的有版本、低信任语义投影。**推导结果不得悄悄改写原文、提升权限或变成终态真相。**

研究意图与信息需求联合建模、工具必要性、任务拆分、澄清价值、指代与会话状态、需求变化后的计划修订、开放世界能力搜索。若简单问题无需工具，系统应能直接回答；若事实依赖外部最新信息，应能正确暴露必需工具；若歧义阻塞安全动作，应能有依据地请求澄清。不能靠枚举若干固定关键词永久解决此问题。

### 11.2 规划与执行的边界

计划是可变工作假设，不是强制全部按节点执行的事实。应区别动态 Agent Loop、确定性 Workflow、任务依赖 DAG 和多 Agent 协作的语义；它们可以组合，不能为了使用某个技术名词而全部揉成一个图调度器。

值得研究的是真实任务中的可中断计划、完成证据、依赖屏障、任务状态、无进展识别、局部重规划、分层目标与成本感知行动。模型产生计划不代表计划可执行，计划完成也不代表用户目标已完成。

### 11.3 Skill / Tool 动态能力

Skill 可以携带操作知识与工具约定，但不能因为加载 Skill 就赋予超出现有 Agent/用户身份的权限。大型能力目录应研究语义发现、分级披露、按需激活及能力版本；最终工具执行仍经过独立授权。

### 11.4 完成验证与纠错

Finish 是候选结果，Completion Policy 应在适用场景检查权威成果、引用和完成义务。无法核验时允许明确 `unverifiable`，不能把“模型说完成”转换成高置信成功。完成检查应受 Deadline 和版本约束，旧 Task Revision 的成功不能替代新需求的验收。

### 11.5 多 Agent 与并行协作

真正需要多角色专业分工、不同权限空间、并行信息收集和任务分歧处理时，再引入 SubAgent。重要难点是子任务身份、预算继承、上下文隔离、权限收窄、结果冲突、证据合并与失败传播。Swarm 数量不是成熟度指标。

**验收：** 在多阶段、长上下文、动态变化任务中，证明正确行动、修订、局部恢复、完成真实性与成本改善，而不是用写死的解释器完成已知答案。

## 12. Model Adapter：模型可替换，但模型差异不可假装不存在

模型供应商只是执行不可信决策的外部系统。其 API、Message Format、Tool Call 语法、结构化输出、流式协议、模型能力与错误行为均需要被规范化，但不能通过归一化掩盖实际能力差异。

具体研究：模型能力协商、Token 估算与真实 usage、结构化输出的严格校验、流式增量 Tool Call 组装、部分输出失败时的结算与回退、参数模式、Timeout/Cancel、模型失败分类、上下文窗口不匹配和供应商特定约束。任何协议修复必须有边界、版本和可观测记录，不得偷偷修改用户语义或绕过预算自动重试。

默认 Fake Provider 负责证明内核正确性；真实模型实验负责证明 Agent 行为。不能由 Scripted Fake 的固定任务成功推断通用决策能力。

---

## 13. Control Plane：面向未来的 Agent 资产治理，而不是先做后台

**研究命题：** 当同一套 Runtime 被多个应用和团队复用时，如何明确管理“运行的是哪一个 Agent 定义、哪一套工具与策略，以及为什么允许发布”。

长期资产模型可以覆盖 `AgentDefinition`、不可变 `AgentVersion`、`HarnessProfile`、`RuntimeProfile`、`ModelProfile`、`Tool/Skill Binding`、`Policy Bundle`、`Deployment`、`Release`、`Evaluation Gate` 与 `Owner/Tenant`。

**重要不变量：** Run 创建时绑定有效的配置版本及兼容性信息；执行中不能因管理员修改在线定义而静默改变 Tool、Prompt、Policy 或 Memory Scope；旧版本恢复前必须检查协议、工具和数据兼容；回滚是启动新运行或切换部署指向，而不是改写已经存在的执行事实。

首先研究不可变 Agent Artifact、版本快照、策略引用与发布门禁。当多 Agent、多部署需求真实出现，再建设完整控制面、配额与成本管理、灰度发布、审批流程及更复杂组织治理。

**不能把写 CRUD、做漂亮管理后台当成 Agent Infra 的技术深度终点。** 核心仍是版本对执行行为的约束、稳定生命周期与可靠升级/回滚语义。

## 14. Evaluation、Observability 与演进闭环

### 14.1 权威事实不等于 Trace

Event Journal 是恢复与状态判定的权威事实；Trace 是可查询、可聚合、可采样的诊断投影。可以使用 OpenTelemetry 进行跨服务导出，但不能因为一个 Span 成功而认为副作用已持久确认。日志、Trace、Event、Checkpoint 的保留策略和安全级别应明确区分。

### 14.2 测试分层，不以测试替代研究

- **契约/确定性测试**：验证事件顺序、类型与身份、策略授权、状态归约、取消和时间行为。
- **故障注入**：验证崩溃、网络失效、乱序、Lease 竞争、重复投递、UNKNOWN 副作用、恢复协议。
- **Agent 行为评测**：验证真实模型的规划、工具选择、纠错、完成、检索和记忆质量。
- **系统实验**：验证时间、内存、Token、吞吐、延迟、并发度、索引与策略的成本收益。
- **回归/发布门禁**：将已发生的 Bad Case 冻结为任务、策略与数据版本，防止能力退化。

遵守科学比较原则：明确问题与假设、控制关键变量、完整记录配置、报告样本规模与不确定性、保留失败结果；不要把三五个玩具样例的成功称为达到工业级效果。

### 14.3 技术设计与验证的正确次序

Codex 不应再机械地把“如何证明有效”放在一切讨论的最前面，从而忽略机制和算法深度。更合适的过程是：**理解真实问题 → 深读技术方案与替代机制 → 设计具有深度的可行方案 → 明确不变量与预期收益 → 实现 → 验证正确性 → 评测效果 → 分析失败并演进。**

设计前必须知道怎样识别失败，却不要求先完成大规模实验才准许进行技术探索。实验是技术深度的证据，不是项目追求的唯一内容。

### 14.4 在线持续改进

未来形成 `Build → Evaluate → Gate → Release → Run → Observe → Evolve` 闭环。线上失败轨迹经去敏和授权后进入候选测试集；新版本必须与旧版本进行可追溯比较，证明改进效果与成本，并对退化设置门禁。此时才讨论自动产生候选策略或 Harness 自我改进，不能让未经审查的实验代码直接更改生产内核。

---

## 15. 开源研究与论文复现：海纳百川而不依附任何一方

开源项目是经验来源，论文是技术假设和算法思想来源。阅读它们时不以“接入了多少项目”为成就，而是研究自己面对的具体技术问题。

每项有必要的深度调研应说明：问题定义、源项目固定版本、关键调用路径/核心算法、该设计在源项目环境下的依赖条件、优势与缺陷、与 Weavria 的语义差异、可复用思想、拟采用的独立实现方式，以及可能新增的约束。

可以研究并吸收 LangGraph 的状态与检查点设计、DeerFlow 的上下文和 Harness 实践、DeepSeek Harness 的插件生命周期、OpenHands 的运行事实、Mem0/Graphiti 的记忆治理、Temporal 的持久执行思想、Inspect AI 的评测组织等，但**不把任何项目作为必须效仿的整体架构**。

论文复现应在 `labs/` 中保持相对隔离，区分三个层级：

1. **思想借鉴**：采纳某个机制启发，不能称完整复现。
2. **核心机制复现**：实现论文中界定的算法、约束及对应消融/对照，说明与原论文的环境差异。
3. **结果复现**：数据、基线、训练/推理过程及指标具备可对比条件，才能讨论结果是否接近论文结论。

可持续跟踪的新研究包括 Tool-aware Reasoning、Agent RL、Search / ReTool 类多步行动学习、Context Optimization、Memory Evolution、Agent Runtime Improvement 等方向，不固定为某八篇论文。论文更新不应迫使 Runtime 重写，而应通过可替换策略、标准轨迹、模型接口与实验基础设施纳入。

实验晋升生产的条件是：机制本身完整、接口不破坏工程不变量、相关任务收益有证据、失败和资源成本在可接受范围内，并通过版本化回归。研究无收益同样要留存结论，不要硬把实验包装为成功。

## 16. FinScope 与未来第二真实场景：验证独立性而不是绑死领域

FinScope 是 Weavria 第一个真实业务应用，可以提供多源金融资料、实时/历史数据、复杂问答、研究链路、页面上下文与用户观察等具有挑战性的问题。它应通过稳定的适配器和受权限控制的 HTTP 接口接入。

金融语义、股票代码、行情时效、新闻证据、领域 Prompt、UI 与完成规则属于 `apps/finscope`，不进入 Weavria 的 Core/Runtime。应用可以暴露“事实来源 + 发布时间 + 获取时间 + 允许使用的操作”，而通用 Harness 只理解领域无关的 Provenance、Timestamp、Tool Schema、Access Policy 和 Evidence Identity。

FinScope 的特殊挑战不能只在 FinScope 内用临时规则补丁掩盖。若发现通用的任务理解、上下文回取、工具取消或恢复问题，先将其改写为领域无关的问题，用独立测试复现，再决定是否应上升为框架机制。

当 Weavria 接入第二个语义显著不同的场景（如文档研究、客服、浏览器任务或代码资料分析）且无需改动 Core 领域契约时，才能更有说服力地证明可嵌入性和通用性。

任何实际金融任务中的回测或历史分析都应保持 As-of 信息边界，不把后知事实作为当时可用证据；此项是 FinScope 的强业务约束，但其通用时间与来源基础可以成为框架能力。

## 17. 成熟度与研发优先级：7.5+ 是目标，不是口号

“7.5 分以上”是技术水平的长期标尺，不是阶段评分任务。每个模块的成熟度应使用**实际证据**，而不只使用类、目录、Demo 数量。

| 状态 | 允许宣称的能力 | 不允许宣称的能力 |
| --- | --- | --- |
| Contract | 协议清楚、输入输出和状态受验证 | 已具备完整执行或生产可靠性 |
| Mechanism | 有真实算法和闭环执行，能解释内部决策 | 普遍改进 Agent 任务质量 |
| Engineering | 失败/并发/取消/版本等不变量有系统测试 | 超出测试前提的分布式或安全保证 |
| Validated | 使用匹配任务与真实模型取得可复现结果 | 在未覆盖领域全面优于成熟项目 |
| Operational | 有恢复、管理、权限、观测与现实服务指标 | 无边界的 Exactly-once、绝对安全或通用最优 |

技术选择优先考虑四个问题：当前最实质的阻塞是什么？哪项改进能形成可持续复用的底层能力？它对其他模块的依赖是否已建立？实现后有没有办法观察它的真实行为？

不要依据岗位清单给所有模块平均分配开发时间；也不要只选最容易测出正向指标的题目。技术纵深应围绕有价值、难解决且与现有架构连贯的主题集中建设。

## 18. 研发路线：阶段性焦点，而非不可改变的固定时间表

现有 Weavria 已具备部分 AgentLoop v3、Task Frame、Artifact/Context、SQLite 多轮会话与运行中 Steering 的实现基础。未来开发应以当前主分支事实和失败轨迹为准，而不是重新从零照抄以下路线。

**主题 A：可信的真实任务闭环。** 稳固模型协议与工具历史，建立真实模型、真实资料、多步纠错、完成验收基线；不能长期把固定 Fake 模型成功当成 Agent 智能能力。

**主题 B：Durable Execution 的技术纵深。** 建立可恢复运行位置、Checkpoint 与 Event 的提交关系、Effect Ledger、UNKNOWN 状态恢复、Crash 注入与 Worker Replacement；这是进入生产 Infra 的关键台阶。

**主题 C：Context 和 Memory 纵向研发。** Context 研究 Token-aware 选择、摘要、卸载与回取；Memory 研究提取、时效、纠错、版本、混合检索与遗忘。优先形成具有独立价值的机制，而不是架构空层。

**主题 D：工具安全与复杂任务组织。** 按需推进 Capability、Agent Identity、MCP、审批、Sandbox、Skills、可分解任务和 SubAgent 的执行关系；先解决需求和语义，再决定使用什么架构。

**主题 E：Managed Runtime 与 Control Plane。** 当多 Worker 和多版本使用需求成立时，深化 Run Admission、Lease/Fencing、Worker 生命周期、AgentVersion 与发布回滚。

**主题 F：生产评测与研究进化。** 建设真实任务基线、标准 Trace、故障注入、Experiment 和发布门禁，支持论文复现、策略择优与必要的自动改进。

各主题在每个开发周期可能交替推进。基础安全检查、测试、Trace、错误处理、版本记录不能被解释为“未来阶段才做”；真正昂贵的多租户管理、分布式协调、Swarm 和训练集群则应推迟到需求与证据充分时。

## 19. 可作为最终面试与技术展示的系统能力演示

理想的综合演示并不是一个满屏组件的 Dashboard，而是一个真实、可观察、可被故障打断的 Agent 任务：

- 真实模型接收复杂目标，理解信息需求，按权限发现能力，拆分必要工作。
- 多工具读取真实资料，产生来源明确的 Artifact；任务执行中重组 Context，保留关键失败反馈并按需回取完整结果。
- 任务持续较长时间，在工具调用与 Event 提交边界受到人工故障注入；Worker 退出，新执行者根据权威历史和幂等规则安全恢复。
- 对危险工具，授权或审批不足时拒绝执行；结果未知的外部效果进入协调而非盲目重放。
- 用户可以修订目标，旧提议作废，已经确认的事实保持有效，下一轮完成验证使用新版本任务。
- 所有关键行为能通过 Event、Trace 和 Tool Ledger 解释；改变 Context/Memory/Tool/Runtime 策略后，可重复运行同一任务集并发现质量与成本变化。
- AgentVersion 更新前通过质量门禁；需要回滚时不会改写旧任务事实。

这是一幅**长期综合能力图**，不是下一次迭代必须全部做完的验收脚本。每完成一个真实纵向切片，就可以独立展示其机制与失败边界；绝不把预设脚本演示说成真实自主 Agent。

未来面试应能深入讲解真实源码调用链、算法与协议选择、数据库与时序、不变量、竞争方案、实验与失效场景。只会描述“支持 Agent Memory / MCP / 多 Agent”不能证明达到目标。

## 20. Codex 的强制工作协议（每次重要研发任务遵循）

### 20.1 开始前：先定位真实问题

Codex 开始重大功能、重构或架构评审前，应阅读根 `AGENTS.md`、本宪章相关章节、对应 ADR 和当前实际源码/测试；用简短语言确认：当前能力与缺口、本轮解决的真实问题、该问题为什么具有价值、拟采用机制的关键设计与本轮明确不做的部分。

不要只因为用户提出了某个模块名称，就自动生成同名目录、Interface 和空 Provider。必要时先提出两三个具有可操作差异的设计方案，对关键不确定性进行针对性源码或论文研究，而不是机械地每次搜索一长串项目。

### 20.2 实现时：保护执行语义与模块边界

新代码必须让目标机制真实承担对应决策与责任：不能把困难环节预先硬编码在应用、Fake Model、Fixture 答案或高优先级 Prompt 中，之后宣称 Harness 已解决该问题。不得突破安全、权限、状态、取消、持久化的现有不变量来追求功能演示成功。

优先实现一个有完整边界的纵向切片。基线实现可以简单，但必须明确这是 Baseline 而非最终完成；若需求包含深度算法或工程语义，不能以“接口后续可扩展”为借口长期回避。

### 20.3 完成后：四类证据和七个回答

按影响范围给出：测试/契约结果、故障边界、任务/质量表现、成本/性能变化；如某一项不适用或未执行，明确标注。交付说明应回答：

1. 本轮实际解决了哪个 Agent/Infra 技术问题？
2. 从入口到终态的核心调用链、关键数据结构和算法是什么？
3. 为什么选择这个机制，与哪些替代方案存在实质取舍？
4. 有哪些必须维持的工程不变量，它们如何被代码保证？
5. 它怎样与 Task、Tool、Context、Memory、Runtime 或 Evaluation 协作？
6. 哪些测试或实验能证明当前声明，哪些能力还没有证据？
7. 当前最重要的未解决问题是什么，下一步最值得深入哪个机制？

### 20.4 冲突、提议与宪章维护

- 如果当前用户明确请求与本文方向不同的探索，先说明边界和影响，再按用户当次明确要求处理，不得擅自声称“宪章不允许用户改变方向”。
- 如发现本宪章过时、互相矛盾或阻碍有根据的新研究，应提出修订建议与 ADR，并请求项目所有者同意；Codex 不得自行降低长期目标。
- 仓库当前实现与本文目标出现差距时，以诚实差距报告为准，不能修改 README、测试或本文来掩盖缺陷。
- 任何“已达到某成熟度或已超越某框架”的表述必须给出明确、可比较、可复现的事实依据。

## 21. 面向未来的新需求，怎样进行架构取舍

遇到新工具、Skills、Memory 论文、RL 方案、生产平台需求或热门 Agent 概念，应当用同一套问题过滤：

**真实价值：** 它解决了当前或可合理预见的什么困难问题？如果没有它，现有机制会在哪些场景失效？

**技术归属：** 属于 Runtime 的执行事实、Harness 的推理/编排策略、Infra 的管理与隔离，还是特定应用能力？是否破坏低层依赖边界？

**机制本身：** 需要什么状态、算法、事务或协议？是否只是包装已存在的组件？是否能实现为策略而非改写内核？

**执行代价：** 新增多少复杂度、调用、Token、延迟、数据维护和安全风险？在并发与故障条件下是否仍成立？

**证据计划：** 哪些确定性测试用于验证不变量，哪些真实任务用于验证收益？失败后如何回滚？

如果目前证据不足、机制尚未想清楚，允许暂停编码并继续研究。**及时承认尚不知道，比快速堆出错误的基础设施更符合 Weavria 的长期目标。**

## 22. 明确保留的底线（不得为快速交付牺牲）

- **独立性：** 不让完整外部 Agent Runtime 接管主执行链路；不让 FinScope 业务侵入通用内核。
- **深度：** 不用接口齐全、简单规则和漂亮演示代替底层机制。
- **正确性：** 对取消、并发、预算、身份、事务和恢复作出真实承诺，不能无依据扩大保证范围。
- **智能性：** 不把 Agent 长任务、任务理解、上下文和记忆简化为只有固定状态或 Prompt 的应用逻辑。
- **研究性：** 有针对性地研读源代码和论文，形成自己的设计；实验用于验证，不挤占对机制本身的深入研究。
- **安全性：** 外部资料和模型输出保持低信任；执行权限、凭据、租户、写副作用始终受独立控制。
- **可持续性：** 已接受契约与数据迁移有版本，真实失败能够反馈到研发，任何技术更新都不破坏长期演进路径。
- **诚实性：** 未实现、未运行、未验证和仅在限定前提下成立的能力，必须明确标记。

## 结语：Weavria 希望成为怎样的工程作品

Weavria 不是一个为了凑齐功能点的课程项目，不是某个开源框架的 Python 重写，也不是一套固定论文复现的集合。它应当是一个可以长期研究、独立使用、接受真实故障、不断检验新技术的 Agent Harness 与 Infrastructure。

**我们最终追求的不是“实现了 Agent Loop、Memory、Context、Tool、Control Plane、Evaluation”，而是让选择建设的每一部分都真正解决深刻的 Agent 工程问题，并且能够从原理、算法、状态、故障、取舍和真实结果把它讲清楚。**

**长期目标：达到成熟优秀 Agent 框架的技术水准，核心能力达到先前约定的 7.5+ 质量标尺，并持续向更高水平演进。** 这个水平只靠真实源码、稳定契约、工程表现和可复现的证据来证明，而不是由宣言自动赋予。

> **一句话准则：先理解困难问题，再做有技术纵深的机制；用工程不变量守住可靠性，用真实任务与实验促进进化。**
