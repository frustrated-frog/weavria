# 能力混合索引的实现与验证

本轮在语义发现前增加了可复用的混合候选索引。它减少每个任务交给发现模型的能力卡数量，保持完整协议展开、任务理解和 Runtime 授权边界。索引默认不启用，设计依据见 [ADR 0125](decisions/0125-能力混合索引与候选扫描.md)。

## 一次请求怎样流转

1. `TaskAwareSessionPreparer` 仍先通过 `CapabilityResolver.discovery_catalogue` 得到本次策略允许且可用的目录。私有或不可发现项不会先进入编码器再被过滤。
2. `TaskUnderstandingEngine.prepare` 建立父期限，将任务原文和适用上下文交给 `ModelCapabilityDiscovery`。如果请求有历史、澄清、应用上下文或 ContextSupply，本版显式全扫描，并记录 `context_requires_full_scan`。
3. 对独立任务，目标与显式约束共同组成查询，`HybridCapabilityIndex.retrieve` 在同一期限内等待锁，防御复制目录，并查询或构建索引。相同目录复用完整快照；目录变化时仅复用当前目录中仍然出现的同内容片段向量。
4. BM25 访问命中词项的倒排表；Dense 对全部单位向量计算余弦相似度，并按工具聚合片段最大值。两路默认各保留 24 个身份，再通过 RRF 取 24 个候选。两路分数不能直接比较，RRF 名次也不是置信度。
5. 发现模型检查这 24 张卡，提名后仅展开对应工具的完整 Schema。解释器再次选择，才形成任务和执行视图。检索本身既不执行工具，也不证明某个工具足以完成任务。

例如冻结题中的西班牙语存储容量问题，词法通道未找到 `read_storage_usage`，真实 E5 把它排到 Dense 第 1 名。它进入候选扫描，语义模型提名后再展开原始输入输出协议。另一题“文件内容指纹”则在两个检索通道都未进入前 24 名，后续模型看不到正确工具；本轮把这个失败完整保留。

## 关键结构与更新语义

核心实现为 `src/weavria/harness/capability_index.py`：

- `CapabilityEncoder` 只约束版本和 query/passage 编码；宿主拥有模型连接与关闭责任。现有公开 `OnnxE5MemoryEncoder` 结构上满足该协议，无需复制 ONNX 实现或让索引理解 Memory 存储。
- `_Snapshot` 保存工具身份、词项计数/长度、倒排表、工具到片段的映射和单位向量。只保留最后一个快照，不保存查询正文。MappingProxyType 和 tuple 防止内部容器被意外改写。
- 表示含名称、版本、完整说明和各至多 32 个输入/输出字段名；完整说明按默认 384 字节分块，不静默丢弃尾部，实际编码器仍检查 Token 容量。片段仅服务召回，不替代正式 Schema。
- 新构建和查询均成功后才发布快照。中途失败或取消时旧快照仍可服务相同旧目录，但不能作为新目录的结果返回。移除或撤权的身份不会从历史向量缓存补回。
- 完整目录摘要绑定所有描述符；即使 Schema 修改没有改变召回概览，也会改变索引身份。编码器版本漂移直接拒绝，需要宿主新建实例；同版本输出维度变化也拒绝。
- 默认最多 2,048 工具、8 MB 目录、2 MB 召回文本、8,192 个片段位置、400 万向量元素、3,200 万次查询乘加。发现器另有目录和模型预算，取实际调用路径上更严格的约束。精确 Dense 仍为线性扫描，当前并未实现 ANN。

锁覆盖构建和查询，避免相同实例重复冷构建，也限制并发资源使用。代价是同实例查询串行，多权限目录交替可能反复重建。没有后台刷新、持久向量数据库或多租户缓存淘汰策略。本地 ONNX 的取消需要等待当前有界 CPU 批次结束，不能硬抢占。

## 报告和兼容性

`CapabilityRetrievalReport` 记录目录/编码器/索引/查询摘要、两路排名、候选集合、片段数、维度以及本次编码/复用数量，不保存正文或向量。

未配置索引时仍返回发现报告 v1，序列化保持原字段与顺序。配置索引后返回 v2，新增 `scan_scope`、`retrieval` 和 `fallback_reason`。`catalogue_size` 始终是完整可见目录规模；`scanned_count` 是真正完成模型检查的卡数。候选扫描完成只表示检查了全部候选，不代表全目录覆盖。

理解记录相应使用 v3；原 v1（无发现）和 v2（全扫描报告 v1）继续可读。Session 的持久化 Schema 与授权未改。详细报告仍通过 `discovery_reporter` 导出，失败报告由 `CapabilityDiscoveryError.report` 携带；取消不追加归档 I/O。

## 冻结实验与结果

仍使用上轮 96 个工具、8 个任务的原始语料，没有修改题目、工具描述或答案。7 个任务需要工具，共 8 个应召回身份；1 个任务应直接回答。84 个干扰工具由模板生成，输入输出协议也有意简化，因此只验证发现与准备阶段的选择，不能视为真实工具执行或开放任务收益。

冻结身份：

```text
dataset SHA-256: 2bffd5546b4272db07aed80fffc555a489d8f31461ccfed685c38c3d4dbf0c9a
catalogue SHA-256: b5bb2aa86b55a7c9bc4406895e2be83c7013d549be4a254e80b564c52c6e5aa6
encoder: intfloat/multilingual-e5-small, 384 dimensions
model SHA-256: dd476dd0c2514e9b9be83aeb3853fac0763e0bdf4a71645407587d77c48a2d88
tokenizer SHA-256: 0b44a9d7b51c3c62626640cda0e2c2f70fdacdc25bbbd68038369d14ebdf4c39
ONNX Runtime 1.31.1 / tokenizers 0.23.3 / NumPy 2.5.4
CPUExecutionProvider, inference threads=1, max_tokens=512
LLM: deepseek-flash, temperature=0, reasoning_effort=none
window=32000, output=4096, request_bytes=256000, task deadline=60s
```

本地编码检索连续两遍：首次冷构建加查询 0.723 秒（不含模型文件加载），编码 96 个片段；随后 15 次查询均不再编码目录，耗时中位数 8.9 ms、最大 22.3 ms。每次候选为 24 项。Dense 和 Hybrid 均完整覆盖 6/7 个需工具任务、召回 7/8 个目标身份；文件指纹工具漏掉。无工具题的“空目标集合已覆盖”不代表正确拒绝，拒绝由后续模型检验。

四路真实准备对照按题轮换调用顺序。Token 是供应商报告的输入与输出之和；耗时是各题耗时总和，失败也计入。原词法臂沿用既有 Resolver 的 12 候选策略；因此它与新的 24 候选 Hybrid 比较不是固定候选数的消融实验。完整目录臂在本次预算中可容纳，不能假定它一定更慢。

| 首轮策略 | 最终工具集合完全正确 | 模型调用 | 总 Token | 总耗时 |
| --- | ---: | ---: | ---: | ---: |
| 原词法 | 3/8 | 12 | 67,952 | 24.098 s |
| 全目录卡片扫描 | 7/8 | 38 | 177,619 | 44.605 s |
| 完整协议目录 | 8/8 | 8 | 229,469 | 15.205 s |
| 混合候选扫描 | 7/8 | 16 | 74,100 | 21.368 s |

首轮全扫描在存储题第二批返回了本批之外的身份，以 `out_of_batch` 拒绝；不是能力不足却悄悄继续。混合臂在文件指纹题错误选择 `find_archived_document`，因此即使调用协议合法也判失败。当前机制降低了扫描成本，但没有保住全扫描的召回上限；默认继续关闭，不能把同为 7/8 理解为等效替代。

第二轮独立运行保持相同配置，结果如下：

| 复测策略 | 最终工具集合完全正确 | 模型调用 | 总 Token | 总耗时 |
| --- | ---: | ---: | ---: | ---: |
| 原词法 | 3/8 | 11 | 61,095 | 22.694 s |
| 全目录卡片扫描 | 7/8 | 38 | 177,549 | 42.227 s |
| 完整协议目录 | 8/8 | 8 | 229,521 | 15.455 s |
| 混合候选扫描 | 7/8 | 16 | 74,058 | 23.345 s |

混合扫描两轮的 8 次发现请求摘要完全相同，最终仍在文件指纹题误选归档读取。全扫描两轮都在存储题触发 `out_of_batch`。所有供应商调用均返回了用量。两轮混合臂相对全扫描少约 58% Token、60% 模型调用，但不能以相同成功数量忽略不同的失败原因。

运行结果保存在忽略目录 `.weavria/capability-discovery/hybrid-retrieval-01.json` 、`hybrid-live-01.json` 与 `hybrid-live-02.json`。记录了策略参数、文件摘要、请求身份和各阶段报告，未提交模型输出或本地认证。首轮后仅收紧了报告字段校验并补充故障测试，没有改排名、候选数、提示词或数据集。收尾还补充了当前任务显式 constraints 的查询拼接及回归测试；冻结任务均无 constraints，因此本次测得的查询与模型请求不变。

## 启用与复现

先安装已有的可选本地编码依赖，模型文件由宿主明确提供，不自动下载：

```bash
uv sync --extra local-memory
uv run --no-sync python -m examples.hybrid_capabilities \
  --model /absolute/path/model.onnx \
  --tokenizer /absolute/path/tokenizer.json \
  --output .weavria/capability-discovery/new-retrieval.json
```

添加 `--live --repeats 1` 运行四路模型对照；使用已配置的 `WEAVRIA_MODEL_BASE_URL`、`WEAVRIA_MODEL_NAME`、`WEAVRIA_MODEL_API_KEY` 和可选 `WEAVRIA_MODEL_REASONING_EFFORT`。输出路径必须不存在，避免覆盖失败记录。

接入 Harness 时，先在 `async with OnnxE5MemoryEncoder(...)` 内构造 `HybridCapabilityIndex(encoder)`，再把它作为 `AgentHarness.from_config(..., capability_index=index)` 传入，同时配置 `HarnessConfig.semantic_discovery=CapabilityDiscoveryConfig(...)`。Harness 必须在编码器关闭前退出。直接构造发现器时使用 `ModelCapabilityDiscovery(..., candidate_index=index)`。

```bash
uv run pytest tests/harness/test_capability_index.py tests/harness/test_semantic_discovery.py
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
```

本轮全量测试 **1,968 通过、24 跳过**（跳过项需显式配置 Docker 镜像），发现/索引定向测试 **47 通过**。全仓 Ruff、格式和 Pyright 检查通过。

定向测试覆盖增量更新、目录移除、Schema 身份变化、长说明尾部、稳定排名、版本漂移、非法向量、容量、超时/取消、并发排队、失败后重试、报告兼容性以及真实 Harness 装配链路。确定性替身只证明这些执行不变量，无法证明语言召回质量。

## 当前局限与下一步

尚未处理任务执行中的主动搜索/查看协议、Skill 组合、对话查询重写、漏召回后的有界补搜或分布式索引。Dense 的片段最大值可能偏向长描述；RRF 可能让词法干扰挤压语义候选；本次证书题 Dense 第 1 名在融合后降到第 5 名，虽未丢失，也说明融合不是单调改善。

下一步优先研究“候选能力是否真的实现了请求动作”的适用性检查与有界补搜：解释器看到归档读取工具，不应把它当成计算内容指纹的替代。需要用未参与本轮设计的任务、真实不同输入前提和输出 Schema，验证何时拒绝当前候选、如何形成补搜查询及何时停止；不能只把 top-k 调大便宣称问题解决。
