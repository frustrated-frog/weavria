# 能力组合检查与协议引用

本轮增加可选的能力组合检查：模型判断候选工具能提供什么数据，再描述这些数据如何支持请求产出，宿主检查依赖闭合并决定是否补搜。它解决上一轮发现的“已有两版全文，却因没有专用比较工具而拒绝”的问题。设计见 [ADR 0128](decisions/0128-基于数据依赖的能力组合检查.md)，执行与答案验收沿用[本地执行实验](能力发现的本地执行与独立验收.md)。

## 能力与边界

配置保持显式启用，旧检查与默认发现行为不变：

```python
from weavria.harness import CapabilityDiscoveryConfig, CapabilityFitConfig

discovery = CapabilityDiscoveryConfig(
    fit=CapabilityFitConfig(composition=True, max_repairs=2),
)
```

`composition=True` 改变发现阶段的适用性检查协议；它不把图变成执行计划，不生成工具实参，不授权调用。只有发现通过，后续任务解释器、动态工具视图与 Runtime 才继续各自的工作。最终交付仍需通过原有 Completion Policy 和独立结果验收。

## 一次请求如何流转

以比较归档记录的两版内容为例：

1. `ModelCapabilityDiscovery` 仍先通过混合索引召回卡片，再由模型提名工具。没有向模型提供正确工具或预设工作流。
2. `composition_request` 展开候选完整协议，同时从实际说明叶子生成引用目录。模型提交每个候选的适用性判断，以及一个小型数据依赖图。
3. 模型可以提出 `tool(read_document_history) → derive(compare)`，表明比较所需内容可由历史工具取得。图只表达潜在的数据供给，尚未读到任何版本正文。
4. `validate_composition` 校验请求引文、协议引用、候选完整分区、图结构和工具覆盖。没有缺口且需要工具则得到 `ready`；没有工具和缺口则得到 `no_tools`。
5. 如果缺少真正的外部操作，模型提交 `missing` 节点与补搜查询。宿主沿依赖传播不可行性，使用原有索引排除已扫描能力并补搜；下一轮保留已支持工具，联合新候选重新检查。调用、Token 和期限共用发现器的账本。
6. 通过后按原链路解释、执行、读取 Artifact 与验收。图中的可行性不能当作执行成功的证据。

## 数据结构与不变量

| 节点 | 含义 | 主要约束 |
| --- | --- | --- |
| `tool` | 外部观察或操作 | 名称必须等于受支持候选名称；依赖可供应未来实参 |
| `given` | 请求中已经给出的数据 | 引用实际输入，无依赖；读文件指令不等于文件内容 |
| `derive` | 比较、摘要、提取、格式化或解释 | 除概念解释外必须有输入依赖 |
| `missing` | 缺失或不确定的外部能力 | 绑定请求锚点和补搜查询 |

宿主验证节点 ID 唯一、依赖存在、没有重复依赖或环、所有节点都服务于 `deliverables`，以及工具节点集合恰好等于已支持工具集合。使用确定性的拓扑扫描，以 `missing=false`、其他节点取所有父节点可行性的合取进行归约。缺口必然影响一个产出，不能藏在无用分支中。归档反序列化时也重新核对结构、深度和派生状态，不能修改 `feasible` 就伪造完成。

每图最多 32 个节点，每节点最多 16 条依赖，深度最多 16。拓扑归约在此小范围内按名称排序并直接扫描，复杂度上界为 O(V²·log V + V·E)，空间 O(V+E)；无需引入图依赖库。图规模扩大且测量表明扫描成本明显时，再使用入度队列。

这些都是结构保证。`given` 引文存在不能证明那段话真是输入数据；`derive` 枚举不能形式化证明操作属于普通推理；模型也可能漏掉用户要求。提示词明确禁止用普通推理替代文件内容获取、密码学计算保证和发送、删除等外部操作，但语义正确性仍须通过任务负例和真实执行验证。

## 协议引用为何单独处理

旧检查要求模型复制 JSON Pointer 和正文。带 `$defs` 的 Schema 容易被模型想象成已经展开的路径。本轮由宿主遍历描述符的 `description`、`input_schema`、`output_schema`，仅对其中实际存在的说明字符串叶子建立引用。保留真实 `$defs` 与数组路径，正确转义 `/` 和 `~`；不展开远程引用，不用 `title` 或 `type` 冒充操作承诺。

引用标签由完整描述符摘要、路径和正文生成，形式为 `r` 加 16 位十六进制摘要。它是请求内标签，不是授权凭据；同表碰撞直接失败。模型只能选择当前工具目录内的标签，宿主随后还原原路径和正文，交给原有严格引用验证。过期、跨工具、伪造引用不会被模糊匹配或自动纠正。

每工具最多 256 条引用，全部候选最多 2048 条；遍历深度最多 64，正文最多 4096 字符，路径最多 1024 字符。超限在检查调用前报告上下文容量失败，不截断后宣称检查完成。完整 Schema 与引用目录都计入请求 Token/字节预算，重复展示会增加成本，这是当前保留可检查协议信息的取舍。

## 版本、失败和持久化

组合子报告使用 v2，发现报告使用 v4，`TaskUnderstandingRecord` 使用 v5。旧配置关闭组合时不序列化新字段，旧报告保持原形状；新报告不能降级为旧版本。发现策略摘要绑定组合提示词、模型提议 Schema、引用格式和配置。

报告保存图结构、可行性、工具名称和来源/支持摘要，不保存任务引文、协议正文、补搜查询全文或私有推理。节点名、依赖和产出在校验后按拓扑位置统一替换为 `n0`、`n1` 等宿主编号，避免模型把私人对象标识编码进节点名。这不改变依赖关系，也不返回给模型。非法图、错误引用和模型 Schema 错误停止本次准备；不为它们新增自动重试。只有合法 `missing` 图能进入原有有界补搜。模型校验异常不复制原始异常正文到失败码，避免把模型文本写入诊断。

取消向上传播并清理在途调用；超时进入已有准备失败边界。补搜、图检查和模型调用都没有额外后台任务或独立预算。

## 如何运行

无需模型即可校验两套冻结任务：

```bash
uv run python -m examples.live_capability_execution
uv run python -m examples.live_capability_execution \
  --dataset examples/fixtures/capability_composition.json
```

配置既有 `WEAVRIA_MODEL_*` 环境变量和本地 E5 模型后，显式执行四臂对照；输出路径必须尚不存在：

```bash
uv sync --extra local-memory
uv run python -m examples.live_capability_execution --live --repeats 2 \
  --variants hybrid fit_repair composition all_tools \
  --model /absolute/path/to/model.onnx \
  --tokenizer /absolute/path/to/tokenizer.json \
  --output .weavria/capability-discovery/composition-repeat.json
```

加 `--dataset examples/fixtures/capability_composition.json` 可运行新增的四项任务：两个文件大小比较、仅比较已提供记录、归档正文与文件指纹联合请求、发送邀请能力缺失。任务答案在调用前冻结，工具闭包不读取答案；大小比较要求两次对应参数的实际元数据调用，联合请求要求两项真实数据证据。它们来自相同本地环境，属于新增组合验证，不能视为独立领域或开放场景泛化证明。

确定性验证入口为 `uv run pytest tests/harness/test_capability_composition.py`，覆盖图闭合、缺口传播、参数依赖、真实 Schema 叶子、引用版本、容量、共享预算、补搜、旧记录兼容、超时与取消清理。真实收益另由下述实验观察。

本轮最终 `ruff check .`、`ruff format --check .`、`pyright` 全部通过；全量 `pytest` 为 2041 passed、24 skipped（未配置本地 Docker 测试镜像）。离线任务清单校验确认新增四项任务仍绑定原环境和 91 项目录。

## 实验结果与限制

2026-11-16，使用 `deepseek-flash`，temperature=0，reasoning_effort=none，窗口 64000、输出上限 4096、请求字节上限 256000；准备期限 60 秒，父 Run 180 秒，执行模型和工具调用各最多 12 次。所有臂使用相同任务、工具环境、结果验收与模型配置，每项两次，轮换执行顺序。原八项任务的答案、环境和 91 项目录未修改。

原任务结果如下，每臂 16 次。Token 与耗时包含准备和执行，各行是总量：

| 策略 | 正确交付 | 正确交付或安全停止 | 模型调用 | Token | 秒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 混合发现 `hybrid` | 16/16 | 16/16 | 62 | 229835 | 77.358 |
| 旧检查与补搜 `fit_repair` | 9/16 | 13/16 | 83 | 279857 | 99.756 |
| 组合检查 `composition` | 12/16 | 14/16 | 82 | 304419 | 108.838 |
| 完整目录 `all_tools` | 16/16 | 16/16 | 28 | 200655 | 28.912 |

旧检查的两次归档比较均补搜耗尽；组合检查两次都完成。旧检查一次日历任务引用了不存在的 Schema 路径；组合检查的两次日历任务均完成，本次最终试验没有引用标签错误。组合检查没有在这些任务上超过混合发现与完整目录，且比旧检查消耗更多 Token，不能据此推荐默认启用。

组合检查的四次未交付均在能力缺失任务：删除任务两次正确停止但未答复；本地正文读取任务两次生成无用图节点，被 `composition_unused_node` 拒绝。这两次属于协议失败，不能算安全停止，也不能为了提高分数删掉校验。旧检查在四次缺失能力任务上均停止。完整目录和混合发现交付了正确的 unavailable，因此它们的“正确交付”包括这些答复，并不表示实际完成了删除或读取。

| --- | ---: | ---: | ---: | ---: | ---: |
| 混合发现 | 8/8 | 8/8 | 28 | 101799 | 36.264 |
| 旧检查与补搜 | 5/8 | 7/8 | 44 | 146762 | 53.614 |

组合检查完成了全部六次可执行/无需工具任务；两次发送邀请请求均因真实能力缺失停止，没有调用其他工具冒充发送。旧检查还在一次文件大小比较中以 `catalogue_examined` 停止。新增任务没有改变最终模型协议，仍只有同一目录下的有限组合证据。

实验保留了协议开发阶段的失败，不与最终冻结结果混在一起：首版完整 64 次对照中，组合检查 0/16 正确行为，主要是模型将 `deliverables` 写成描述而非节点 ID，另有引用标签错误；第二版运行了 61 条记录（其中一条主动取消），组合检查已执行的 15 次中正确交付 5 次、含安全停止 6 次，又暴露工具名称与 `capability_id` 混用。修正是明确字段 Schema 与提示语、缩短请求内引用标签并拒绝碰撞，没有修改原任务答案、自动猜测节点、放松引用或图结构校验。最终四臂从头重跑，新增任务在最终协议冻结后运行；不能把经历调试的旧任务当作未见测试集。

原任务 SHA-256 为 `8dab70fd2f481c10a52d54ef4cad8f76fbe0a31b3afe2478ddccb24043f3b9c5`，新增任务为 `df6029d01a55a443f5998c5f30e2ad3b5407e8791c4cd95f34238e20589303f4`。原始逐条结果保留在忽略目录 `.weavria/capability-discovery/` 下的 `composition-execution-01.json`、`composition-execution-02.json`、`composition-execution-03.json` 和 `composition-holdout-02.json`；不把模型输出提交到 Git。报告另有环境、目录、模型、配置及全包实现摘要，运行入口禁止覆盖已有文件。上述实测之后仅增加了归档节点名脱敏和注释修正，发现提示词、模型提议 Schema、选择与补搜逻辑均未改变；记录中的实现摘要对应实测源码，当前脱敏行为由回归测试另行覆盖。

这是单模型、两次重复的公开合成本地任务，模板干扰项与真实企业目录差别很大，且完整目录臂没有发现/解释阶段。结果只能说明当前组合检查在这些任务上的行为和成本，不能当作纯检索算法消融或生产收益结论。

## 下一小步

优先分析真实失败中“能力确实缺失但用户允许替代答复”的表达：目前缺失外部操作会阻断准备，可能只安全停止而没有交付 unavailable。需要把原操作可行性、允许的替代交付和执行证据要求分开研究，再决定如何接入 Task Frame。不能简单删除 `missing`、放宽图校验或把格式化节点当作已经完成外部操作。
