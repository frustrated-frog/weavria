# 条件依赖与局部修复选择

## 本阶段新增的能力

2026-11-06，成果诊断增加可选的 `dependency_frontier` 选择策略。验收器独立检查当前成果，给出未满足条件与前置关系；Harness 计算当前可修复的条件，并在固定反馈字节预算内选择一组。旧 `prefix` 策略仍是默认值。

这解决两个具体问题：下游报告依赖上游统计时，反馈不应同时催促模型先改报告；某条诊断过长时，也不应挡住能够放入预算的独立问题。机制选择反馈内容，不替模型生成修复程序。条件及其逻辑依赖仍由可信验收器提供，没有实现任意任务的自动根因发现。

## 一次请求如何流转

以 `examples/sandbox_execution.py` 的源码统计任务为例：

1. `VerifyWorkspace.diagnose` 经受控 Artifact 读取检查已接受的工作区。统计值错误、没有报告阶段、报告内容不正确，是三个可观察的未满足条件。无法检查的父版本保留关系不被伪装成内容错误。
2. 本轮三个条件分别为 `statistics_content`、`report_stage`、`report_content`。报告阶段依赖正确统计；报告内容依赖前两项。验收器只返回当前仍未满足的节点。
3. `CapabilityOutcomeResolver` 先检查所有条目的来源引用，包括之后不会展示的条目，再调用 `select_repair_issues`。当前只有统计条件没有未满足的前置节点，所以只向模型展示它，`deferred_issues=2`。
4. 模型自行决定代码和工具调用。生成正确统计后，验收器重新读取成果，移除统计条件及相关边。当前可修复条件变成报告阶段。
5. 如果第二阶段执行成功但报告总数错误，当前反馈变成报告内容。Python 的 `completed` 不等于任务完成。
6. 只有独立验收确认完整成果正确，状态才变成 `verified`，清空依赖图和诊断，允许原有能力策略移除计算工具。这里没有新增自动重试或放宽 Finish 门槛。

七种真实 Docker 回归中的新增场景实际经过这条链路，并在关闭和重开 SQLite 后检查完整拓扑、最终验收及文件父版本。动作由测试替身提供，证明执行契约，不证明真实模型必然选择正确修复。

## 算法与数据结构

`OutcomeRepairIssue.depends_on` 引用同轮的稳定条件码。只有依赖模式要求码唯一，最多八个节点。`repair_graph.py` 在完整图上检查重复父节点、自环、缺失节点与环，再计算没有未满足前置条件的根节点。缺失节点不能被默认视为通过。必须先验证整个图再做预算选择。

`repair_selection.py` 对根节点子集做精确枚举。八个根最多有 256 个子集，不需要近似背包算法或通用调度器。对每个集合：

1. 计算每个根及其后继的闭包，再取并集；共享下游只计一次。
2. 用模型实际接收的 JSON 形状、`ensure_ascii=False` 和 UTF-8 编码计量字节，保留完整条目。
3. 在预算内按以下字典序最大化：可能影响的不同条件数、选中的独立入口数、负的编码字节数。同分按稳定条件码打破平局，不依赖验收器返回次序。

例如，a 与 b 都关联下游 x，c 关联下游 y。预算只能容纳两个根时，a+c 影响四个不同节点，a+b 只影响三个，所以选择 a+c。测试遍历这五个节点的全部 120 种输入排列，结果不变。

“可能影响”不是“立即全部解锁”或“已经修好”。一个下游可以同时依赖多个根，修复其中一个并不足以通过。当前评分不估计修复成功率、实际工具成本、问题严重程度，也没有跨轮公平配额；这些是未来策略需要独立证据支持的取舍。复杂度有八节点硬上限，不能直接用于数千节点的任务调度。

## 持久化与执行不变量

`CapabilityOutcome` v3 保存完整紧凑拓扑、选中的根诊断、原有容量和省略计数。拓扑中的条件代码不包含原文内容；未展示节点仍能在账本回读时区分。详细诊断文本只保存预算内部分，需要下一轮重新检查才能重新生成。

模型反馈继续使用 `issues` 和 `omitted_issues`，v3 增加：

- `deferred_issues`：仍依赖其他未满足条件的节点数。
- `ready_issues`：全部根节点数，包括因预算未展示的根。预算省略的根数为 `ready_issues - len(issues)`。

预算包含这些字段以及 JSON 标点。空集合也占容量；256 字节下限始终容纳空反馈和计数，但未必容纳一条长诊断。没有可放入的根时仍保持 repair，不展示阻塞中的子条件凑数，也不把省略当成通过。

初始 pending 槽位就声明 v3 和固定容量，`TaskModelViewProjector` 从第一轮加入固定依赖语义说明。repair、verified 与任务修订不会让同一任务的容量临时膨胀。诊断、拓扑及选择结果不参与 `NeedLedger.progress_sha256()`；换图或改措辞不能制造进展奖励、重置动作指纹或取消幂等保护。

v1/v2 原有 JSON 不增加依赖字段，旧条目没有依赖时也不输出 `depends_on`。NeedLedger 保持 v7，嵌套成果类型升级为 v3。Resolver 配置版本升为 `capability-outcomes/3`，Task Model View 投影器版本升为普通 `/10`、紧凑 `/11`，让变化可识别。错误图是宿主契约错误，显式拒绝；上下文在图选择之前已关闭，不能因校验失败泄漏读取权限。取消、超时与来源校验沿用原有受控边界。

## 如何接入与验证

验收器声明 `repair_feedback_bytes` 和 `repair_strategy = "dependency_frontier"`，仍通过 `HarnessEvidence(outcome_verifiers=(verifier,))` 装配。图必须来自当前验收结果；已通过节点及对应边要由验收器重新检查后删除，不从上一轮 feedback 猜测。

```bash
uv run pytest tests/harness/test_repair_selection.py tests/harness/test_capability_outcomes.py -q
WEAVRIA_TEST_DOCKER_IMAGE="$SANDBOX_IMAGE" uv run pytest tests/sandbox/test_workspace_docker.py -q
uv run python -m examples.sandbox_execution --workspace --capabilities repair \
  --repair-strategy prefix --run --image "$SANDBOX_IMAGE" \
  --env-file .env.finscope-debug --output /tmp/dependency-prefix.json
uv run python -m examples.sandbox_execution --workspace --capabilities repair \
  --repair-strategy dependency_frontier --run --image "$SANDBOX_IMAGE" \
  --env-file .env.finscope-debug --output /tmp/dependency-frontier.json
```

输出文件必须尚不存在。源码、图选择及协议回读测试覆盖非法图、共享后继、超长首项、Unicode 精确预算、前沿推进、未展示条目的来源校验、固定模型容量、任务修订和无进展摘要。没有新增 Runtime 依赖。

本轮全仓测试 1673 项通过、20 项 Docker 用例默认跳过；随后补充的三项图与来源边界回归已随 35 项定向测试通过。显式工作区 Docker 七项通过。Ruff 检查、全仓格式检查、Pyright 均通过。
