# 主动上下文恢复与预算闭环

本切片解决一个具体缺口：联合编译器可以完全省略低相关来源，普通 `read_artifact` 又只能读取当前已接受上下文的证据闭包；模型发现新信息缺口时，需要一条有预算、可审计的重新纳入路径。实现限定为**当前 Run 已接受工具成果的原文恢复**，不扩展 Memory 或跨 Session 权限。

## 如何启用

在已经配置联合编译器与真实请求 Token 计数器的 `SessionEngine` 上添加：

```python
from weavria.core import RecoveryLimits

engine = SessionEngine(
    path,
    model=model,
    tools=tools,
    context_compiler=compiler_config,
    token_counter=counter,
    context_recovery=RecoveryLimits(
        max_rounds=4,
        max_ranges=4,
        max_bytes_per_round=4096,
        max_total_bytes=16384,
    ),
)
```

其余对象沿用宿主配置。不配置 `context_recovery` 时保留原协议；配置它但没有编译器会立即报错。裸 `AgentLoop` 还要求实现 `RecoveryContextBuilder` 的上下文构建器，以保证能够对完整模型请求执行预演。不能把只有旧 `build_control` 的构建器当成恢复实现。

模型可提出独立查询：

```json
{"schema_version":2,"decision":{"kind":"recover_context","query":"Aurora rollback protocol"}}
```

也可用 `call_id`、`source_sha256`、JSON Pointer、`start`、`length` 指定原文位置。两种形式互斥，恢复不能与工具批次混在同一决策里。`start/end` 是 Unicode 字符偏移，字节账本按 JSON 编码后的实际值计费；结构化值按完整编码大小限制，不按元素数量估计。

## 一次请求怎样流转

对应的运行示例是 `tests/sessions/test_context_recovery.py` 中的完整集成测试：

1. `read(archive)` 产生不可变成果，包含较远处的 rollback 原文；随后 `read(work)` 成为最新工具反馈。任务关注 work，archive 在下一次编译中被完全省略。
2. 模型提出查询。`models/provider.py` 只在 ControlRequest v4 下接受 ModelTurn v2；`runtime/agent.py` 接受 TurnDecided，进入 RECOVERY。
3. `context/recovery.py` 从权威 ToolRecord 构建来源集合，用共享 SourceIndex 访问原始 Artifact。模型无需知道被省略的调用 ID；精确请求的未知身份在读取存储之前被拒绝。
4. 规划器产出带来源摘要、字段地址、字符范围、值摘要和编码字节数的 RecoveryRange。正文不复制进恢复事件。
5. Runtime 用恢复回执和这些区间预演完整 Session 请求。`compiler_sources.py` 把对应来源的最低表示改为包含精确片段的 excerpt；其他候选也必须包含它，祖先至少保留 receipt。既有分配器继续在 BPE、字节、控制反馈和依赖预算内选择其余内容。
6. 通过后接受 RecoveryResolved；SQLite 在同一接受事务中重新检查来源和原文。下一次编译、ContextSelected 和持久化发送快照都核验同一范围集合。发送的实际内容也必须覆盖这些范围，不能以一份正确报告代替正文。
7. 模型现在可看到 archive，并提出普通 `read_artifact`。其准入与读权限仍走 EvidenceAccessView 和原有反馈预留。测试验证成功回读，并确认只有三次真正工具执行；恢复没有伪造 ToolRecorded。
8. 接受这次同修订的模型响应时，解除临时保留。后续正常选择可以再次压缩或省略来源。接受的来源、正文和执行事实一直保留在原存储中。

## 搜索、去重和额度

搜索复用 Unicode 规范化、英文词项和中文 bigram，以及 IDF 加权的查询覆盖。对每个原始片段计算查询特征；每轮选择剩余字节能容纳、对已覆盖特征有正边际收益的片段，稳定按来源顺序打破平局。无查询命中的内容不会为了凑满范围数而加入。当前是词项检索，不包含 embedding 或模型摘要。恢复查询搜索被接受成果的完整字段；`context_paths` 只是被动编译的评分提示，不是授权边界，不能把它当成恢复的搜索禁区。

来源总字节、候选来源数、索引片段数、索引字节和评分工作量受 ContextCompilerConfig 限制；评分与候选扫描定期让出事件循环。最多八个选择回合，每回合扫描有界候选；查询长度上限 2048，精确字符串读取长度上限 4000。

去重有两层：

- 同一任务修订下，`请求摘要 + 当前接受来源集合摘要` 相同就不重复搜索；有新 ToolRecord 后允许重新查询。无命中、无效来源和预算拒绝也会留下尝试记录。
- 对已成功恢复的同一 `call_id/source_sha256/pointer`，字符串区间做集合差；结构化值按地址去重。重叠请求只计入未恢复的区间，事件归约器再次拒绝与此前成功范围重叠的结果。

这个账本记录**显式恢复过的范围**，不声称追踪模型所有被动看到的内容。累计字节计算显式恢复值的 JSON 编码；编译器主动选择的额外原文由完整请求预算约束，不重复算入恢复值账本。范围元数据、请求头、反馈和祖先回执全部进入请求 Token/字节预算。

`max_rounds` 限制可处理的恢复请求轮次，重复请求也消耗轮次；超过后返回 limit，不执行搜索。继续提出恢复仍消耗普通模型调用额度，不能形成无预算循环。跨任务修订保留总轮数和累计字节，清空旧修订的保留期、范围去重和查询缓存。

## 失败与生命周期

| 状态 | 含义 |
| --- | --- |
| recovered | 精确范围已通过来源与完整请求预算检查 |
| no_match | 没有词项命中 |
| redundant | 请求或对应范围已经处理/恢复过 |
| invalid_source | 精确身份、来源摘要、Pointer 或字符范围无效 |
| budget | 来源准备额度、值字节、完整请求 Token/字节或必需闭包放不下；不记成功字节 |
| limit | 恢复轮数或累计字节已耗尽；不再搜索 |
| stale | 规划期间任务已修订；不发布原文，不污染新修订 |

任务修订可以赢在规划或预演期间，也可以赢在恢复后模型响应仍在飞行时。旧修订结果只能结算 stale，旧模型响应走既有 DecisionDiscarded。一次同修订的响应被接受才消费保留期；运行终止也解除保留。

规划、编译、存储都由父 Run 直接等待；没有脱离任务。取消向上传播并等待资源清理；总 Deadline 耗尽产生预算终态。来源损坏、内部不变量错误及持久化失败不会伪装成普通“未命中”。接受事件失败时不发布成功恢复。与现有 Session 一样，崩溃后可读已提交事实，尚不支持自动继续执行的 Resume。

## 协议演进

| 类型 | 启用恢复后的版本 |
| --- | --- |
| ModelTurn | 恢复动作要求 v2；普通 ToolBatch/Finish 仍可用 v1 |
| ControlRequest / ControlEvent | v4，一个 Run 内不能混合事件版本 |
| RunStarted / ContextSelected | v2，分别绑定额度配置和保留范围摘要 |
| ContextCompilation / 编译策略 | v4，新增 recovery_ranges |
| SessionRequest / SessionEvent / SQLite | 外层结构仍为 v5 / v4 / v6，内部类型独立版本化 |

旧 RunStarted、ContextSelected 和 ContextCompilation 序列化不增加新字段，旧 Journal 拒绝恢复载荷。恢复自己的 `TurnDecided → RecoveryResolved` 事实对承担结算，不把它错误归类为工具派发或完成候选的 TurnResolution。

## 可复现实验

```bash
uv run python examples/context_recovery.py
uv run pytest tests/context/test_recovery.py tests/sessions/test_context_recovery.py tests/test_context_recovery_experiment.py
```

数据集 `examples/data/context_recovery/cases.json` 冻结 `45f819b` 的四份真实源码及六个问题，文件 SHA-256 为 `225c6e7696a70ab7ad4c047b0e6ac60fd0a04e4fb02bc58e62765746b31bcbf9`。每份原文另带内容摘要，运行时检查。资料预置为接受成果，不评估初始工具读取策略；来源标签只在最后评分时检查原始来源归属，回读成果沿已接受的 ToolRecord.dependencies 核验，不提供给搜索与选择。问题包含路径转义、结构化读取大小、依赖闭包、取消让步、可读来源约束和终态校验。

固定窗口 3500 Token，输出预留 256，安全预留 128，请求上限 12000 字节；使用 tiktoken 0.14.0 的 cl100k_base 和供应商请求编码计数。缺口查询由实验预先编写，答案片段仅进入最后评分；改变评分标签不改变请求摘要、成本和来源选择，有独立测试约束。

| 策略 | 目标片段送达 | 六次末轮请求输入 Token 合计 |
| --- | ---: | ---: |
| 被动上下文 | 2 / 12 | 11423 |
| 可见来源回读 | 6 / 12 | 17063 |
| 主动恢复 | 7 / 12 | 15195 |

可见来源回读是乐观基线：允许用相同查询搜索已可见 ID 的原始内容，再通过有来源作用域的 ToolExecutor 真正回读；不会获知隐藏 ID 或评分标签。它不包含完整 Runtime 的模型决策和批次准入成本，不能据此推算整次 Agent 延迟或费用。主动恢复执行规划与完整请求重编译；本实验也不调用模型。表中 Token 只统计末次请求，不是累计多轮消耗。

一次本机运行中，六个用例的准备与编译耗时合计约为被动 249 ms、可见回读 1051 ms、主动恢复 645 ms；这些墙钟值含缓存建立及本机负载，重复运行会变化，不作为性能门禁。

失败同样保留：主动恢复在两项读取校验问题上未送达评分行，在可读来源约束问题上只送达两个片段中的一个。当前词项覆盖和 320 UTF-8 字节分块会选到相关位置，但不保证解释所需的相邻校验行完整。不能把“recovered”解释为找到正确答案。已送达的终态问题没有额外信息收益。

## 已解决与下一步

已验证的是独立恢复控制动作、原文范围与去重、完整请求准入、临时保留和原权限体系的衔接。测试覆盖预算拒绝、未知来源、Unicode/转义、依赖闭包、重复请求、取消、Deadline、两种任务修订窗口、持久化失败、伪造摘要、事件回放及默认关闭。

仍未验证真实模型能否识别缺口、形成有效查询、克服错误检索并提高最终任务完成率。当前也不包含语义检索、生成摘要、历史 Run 的主动恢复、长期 Memory 或自动 Resume。下一步应在冻结任务、模型、预算下运行显式启用的真实模型评测，记录整个轨迹成本；对已经暴露的分块边界和查询不匹配，比较相邻区间扩展、词项检索改进与多轮精确读取，避免按几个成功示例宣称能力成熟。
