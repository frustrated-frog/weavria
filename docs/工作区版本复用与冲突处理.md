# 工作区版本复用与冲突处理

后续阶段已加入[工作区清单与按需正文恢复](工作区清单与按需正文恢复.md)。本文保留完整快照模式的设计与历史实验；当前示例 `--workspace` 默认使用清单，复现本文模式时增加 `--full-workspace`。

## 能力与问题

本阶段让 Agent 从已接受成果继续处理文件。`execute_workspace_python` 支持基线版本、自动保留未修改文件和显式删除；并发调用形成独立子版本，`merge_workspace` 在同一基线的两个直接子版本之间合并独立改动、拒绝冲突。原来的 `execute_python` v1 保持兼容。

例如第一轮生成 `statistics.json`，第二轮只输出 `report.txt`。第二轮版本同时保留统计文件和报告；若第二轮 Python 报错，它返回诊断但不发布版本，下一轮仍能选择第一轮成果继续。每次调用都使用新容器，文件状态由 Artifact 承载。

## 状态、算法与调用链

1. 模型用 `base={artifact_id, revision}` 指定基线。`ToolContext.read_artifact` 校验当前 Run 和已接受视图，登记来源调用依赖。存过但未被接受的 Artifact 不自动获得使用权。
2. `WorkspaceSnapshot` 保存排序后的文件表、父版本和 revision。revision 是完整内容与父版本的 SHA-256；重排、篡改和版本不匹配会被拒绝。哈希是完整性检查，不是身份授权或业务真实性证明。
3. 工具把基线文件自动映射到 `/workspace/inputs/<path>`。额外 `inputs` 只传新资料，不能与基线重叠。复用既有 Python 执行实现，保持一个 Runtime 工具调用、一次沙箱执行，没有隐藏模型调用。
4. 模型把改动写到 `/workspace/outputs` 并声明 `outputs`；宿主将这些导出文件替换到基线中，保留其余文件，应用显式 `deletes`。全部路径、文件数量与容量合法才生成新快照。删改同一路径、删除不存在文件均被拒绝。
5. 工具返回 `computation`、`workspace` 和 `issue`。代码失败时 workspace 为空；进程成功但版本超容量时 workspace 仍为空，issue 描述发布失败。运行成功不能代替业务 CompletionPolicy 验收。
6. 原 ToolExecutor 和 Runtime 负责 Artifact 存储与 ToolRecorded 接受。此模块不提前更新数据库里的可变 HEAD，因此取消、异常、事件接受失败不会污染一个共享最新版本。

源码阅读顺序：[版本与合并](../src/weavria/sandbox/workspace.py) → [工具装配](../src/weavria/tools/workspace.py) → [既有 Python 执行](../src/weavria/tools/python_execution.py) → [两阶段示例](../examples/sandbox_execution.py)。设计理由见 [ADR 0105](decisions/0105-不可变工作区版本与分支合并.md)。

三方合并逐路径比较 base、left、right，缺失文件与空文件严格区分：

| 两侧状态 | 决策 |
| --- | --- |
| 两侧相同 | 接受共同结果，含共同删除 |
| 一侧等于基线 | 接受另一侧改动 |
| 两侧不同，且都改变 | 返回冲突路径，不发布部分版本 |
| 合并后出现 `a` 与 `a/b` | 返回文件与目录冲突 |
| 合并后总容量或数量超限 | 返回 capacity，不发布部分版本 |

同一文件的不同内容一律冲突，不猜测文本行或 JSON 字段合并。模型可以基于某个分支重新计算冲突文件，再明确选择成果。合并成功版本记录两个父 revision；内容一致的分支只保留一个父身份。没有可变分支指针，也没有隐含“最后完成者获胜”。

## 使用与容量

```python
compute = workspace_execution_tool(backend, workspace_bytes=8192)
merge = workspace_merge_tool(workspace_bytes=8192)
registry = ToolRegistry((compute, merge))
policy = SandboxToolPolicy(
    versions={tool.descriptor.name: tool.descriptor.version for tool in (compute, merge)}
)
```

两个工具都需要宿主明确授权。默认只读策略拒绝它们；能力发现和执行授权仍是独立边界。Artifact 内文件与来源为低信任数据。工作区限 8 个 UTF-8 文件，默认 8 KiB、可配置至 64 KiB；额外输入与基线合计也最多 8 个文件。每次新版本保存完整快照，存储与恢复时间为 O(文件总字节)，当前并未做块级去重。

完整反馈包含计算日志、导出文件和新工作区，须为最坏 JSON 转义预留预算。不能只看到实际文件很小就绕过反馈准入。两阶段示例选择 2 KiB 工作区、262144 字节请求上限、131072 Token 窗口；不同 TokenCounter 和模型窗口仍须独立检查是否足够。

显式运行真实模型与已安装镜像：

```bash
SANDBOX_IMAGE=$(docker image inspect python:3.12-slim --format '{{.Id}}')
uv run python -m examples.sandbox_execution --workspace --run \
  --image "$SANDBOX_IMAGE" --env-file .env.finscope-debug \
  --output /tmp/workspace-report.json
```

输出文件须尚不存在。示例报告升级为 schema_version 2，增加 stderr 与拒绝诊断，便于区分代码失败、参数失败、预算拒绝和终态。报告是本地诊断材料，不应直接发布含真实私有任务的版本；示例使用冻结公开源码。环境文件只用于模型适配器，不传入容器。

```bash
uv run pytest tests/sandbox/test_workspace_versions.py -q

  uv run pytest tests/sandbox -q
```

离线测试枚举三方合并的 27 种缺失/空文件/修改组合，并验证并发分支、目录冲突、容量、版本篡改、未接受 Artifact、失败不发布、取消和可操作的参数纠错反馈。Docker 集成在正式 Harness 中注入第二阶段代码错误，验证旧版本复用、最终成果验收和 SQLite 重开后文件恢复到新容器。模型替身只证明执行契约，不证明智能收益。

真实实验使用与上一阶段相同的两份冻结源码，任务扩展为先统计再生成汇总报告，保持统计原文不变；独立宿主 AST 解析器逐字段核验统计和汇总，也检查最终成果的父版本。

2026-11-05 的前两次真实运行分别为：

- 首次：10 次模型调用、96882 Token，预算耗尽；生成统计文件但未完成报告。这次旧诊断报告没有记录后续拒绝细节，不能推断为某个已确认根因。

基于第二次轨迹，工具已把基线重复输入的反馈改为明确的“文件已挂载、移除额外输入或改名”，并增加“拒绝前不执行容器 → 修正参数后成功”的回归测试。所有原校验保留。真实任务结果的波动说明该能力仍需要更多任务和重复实验；不能用单次成功宣称普遍提升规划或纠错能力。

## 当前边界与下一步

没有持久解释器、运行中进程恢复、跨 Run 授权复用、任意祖先搜索、行级合并、二进制文件和工作区垃圾回收。SQLite 重开恢复的是已保存文件状态，不是 Durable Execution。既有只读 resume/跨会话限制保持不变。

下一步优先减少完整快照重复交付：将文件内容留在 Artifact，通过有来源的文件清单按需恢复，并验证上下文压缩后版本选择是否可靠。只有出现共享主分支需求时，再把工作区指针 CAS 接到事件接受事务；不得在工具内部偷偷维护全局最新版本。
