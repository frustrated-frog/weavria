# 动态工具工作集的选择机制与实验

大目录在进入本工作集之前的候选发现，新增显式启用的语义卡扫描，见[大目录语义发现的实现与验证](大目录语义发现的实现与验证.md)。该机制作用于任务准备，不替换本页的执行期覆盖选择。

本轮解决一个执行中的问题：工具目录已经有单次召回限制，但多个回合持续取并集，导致已完成任务的工具仍占据模型窗口，而某一个需求的相似工具挤占其他需求的位置。

现在统一 `AgentHarness` 在启用任务理解时默认使用 `AdaptiveCapabilityPolicy`。它每轮根据 TaskFrame、NeedLedger 和已接受的 ToolRecord 重算工具工作集，不增加规划模型调用，不引入新的 Runtime。

2026-11-05 的 v4 后续实现改用 Runtime 实际展示条目计费，并为任务显式声明的隔离计算保留可重复使用的覆盖目标。工作区接入与包含准备成本的真实实验见[工作区动态工具接入与成本验证](工作区动态工具接入与成本验证.md)。下文 2026-11-01 的表格保留原计费口径的历史结果。

## 数据与决策过程

`harness/working_set.py` 的 `select` 接收同一工作修订的需求定义、需求状态、实际执行记录、原始工具目录与上一轮工具名称。返回本轮名称、工具描述总字节、估计覆盖效用和未覆盖目标。结果是短期选择值；正式持久化的是原有 SemanticSnapshot 的工具名称、capability epoch 和工作状态，未增加持久化 Schema。

第一步计算需求权重。`harness/context.py` 的 `need_priority_weights` 解析依赖图，用传递前驱集合计算一个需求能解除多少未完成下游需求的阻塞；不重复计算菱形图中的相同祖先。冲突/过期需求的基础权重为 3，部分完成为 2，待处理为 1，已满足为 0.5；可选需求乘 0.5，仍缺少前置条件的需求乘 0.25，解锁价值采用 `1 + 0.5 × min(4, 下游数)`，最终上限为 8。依赖关系只改变软优先级，不强制模型执行固定 DAG。

第二步按尚未满足的外部需求分别调用已有 CapabilityResolver，合并候选。部分完成需求使用尚缺的 JSON Pointer 字段进行发现，而不是一直按完整旧字段查询。初次准备只在理解器明确选择的工具中分配预算；运行中的刷新允许发现新的只读候选。已有的发现策略仍负责可见性过滤，副作用工具只能来自当前解释明确声明的集合。

第三步构建需求—工具覆盖矩阵。声明映射的基础质量为 1，发现器判断可以覆盖需求的候选为 0.6，仅有目标词法相关性为 0.2。这些数字是可以审查的启发式系数，**不是事实可信度或成功概率**。实际结果仍由原有工具反馈、证据绑定与完成策略检查。

第四步加入失败反馈。同一个需求下，当前运行中已观察到的每次可重试失败增加 0.25 惩罚，其他失败增加 1，质量除以 `1 + 惩罚和`。只有与同一需求关联的后续成功才能清除之前的失败折扣；其他运行的失败不直接污染当前选择。失败不会让质量归零：只有一个候选时仍然可以选择它，备用路径也失败后可以重新考虑旧工具的新参数。框架不把一次失败扩大成永久禁用整项能力。

第五步在数量与字节预算下做递减覆盖选择。对集合 S 的效用定义为：

```text
F(S) = Σ需求 权重 × (1 − Π已选工具 (1 − 覆盖质量))
```

同一需求已经被一个质量为 1 的工具覆盖后，添加另一个重复工具没有边际收益，因此位置会让给其他需求。每步按边际收益/描述字节选择，上一轮可见工具有 5% 的密度偏好来减少无意义抖动；零增益工具不因为“曾经出现过”而保留。最后与最佳可容纳单工具解比较，避免密度贪心选了小工具后错过一个能够覆盖更多需求的大工具。它是有界贪心，不宣称双预算条件下全局最优。

没有信息需求但存在独立 capability_result 完成义务的动作，使用独立覆盖目标，避免被空 Need 集清掉。已完成需求从工具选择目标中退出，后续发生新缺口时可以重新激活；它们的证据和来源锚点仍可由 ContextCompiler 选择。

## 在统一执行链中如何发生

`AgentHarness → TaskAwareSessionPreparer.prepare → 初始工作集 → AgentLoop`。

工具执行后，`settle_turn → refresh → EvidenceResolver → 新工作集 → 新 SemanticSnapshot`。新快照同时影响下一轮模型展示的工具与 ContextFocus。旧工具集合不再永久累积，未解决需求的变化同时影响两个模块。

集合收缩、替换与重新激活都会推进 capability epoch。仅规范化后的工具顺序相同不会产生无意义的新 epoch。用户 steering 即使保留了相同的声明工具，也可能改变需求权重；这种情况同样推进实际视图版本。进展评估只把新增名称视为“新能力出现”，不会把退休工具误判为能力扩展。

Runtime 仍校验模型提出的工具调用是否属于本轮视图，ToolPolicy 仍决定调用是否被授权。工具退休不删除原始注册表、历史记录或成果。整个策略无内部运行状态、无外部 I/O；接受事实仍由原来的 Session/Runtime 生命周期管理。

## 配置与观察

```python
from weavria.harness import AdaptiveCapabilityPolicy

# 传给 AgentHarness(..., understanding=..., working_set=policy)
policy = AdaptiveCapabilityPolicy(max_tools=4, max_descriptor_bytes=12000)
```

默认最多 8 个业务工具、16000 字节描述。v4 按 `model_tool_bytes` 统计名称、描述与输入 Schema 的紧凑 JSON 字节，不计未展示的输出 Schema；不包括数组分隔符和框架提供的成果/会话回取工具，也不是 Token 预算。最终完整请求仍必须经过 ContextCompiler 的字节和 Token 检查，不能凭工作集预算通过就认定一定能发送。

低层直接构造 TaskAwareSessionPreparer 且不配置 working_set 时，保留原有单调并集基线。统一入口的策略可替换；配置 working_set 必须同时配置任务理解。选择报告可通过策略公开 `select` 复现；会话事件中的 SemanticSnapshot 可以检查实际名称与 epoch。

## 固定轨迹实验

运行：

```bash
uv run python -m examples.capability_working_set
uv run pytest -q tests/harness/test_working_set.py
```

实验固定四个需求、每个需求两个候选，依次提供 0 至 4 个需求已经满足的状态，共五个阶段。每轮工具数量预算为 2，描述预算为 16000 字节。比较原来的永久并集、固定两个工具菜单和动态工作集；关闭额外发现以隔离选择算法本身，覆盖关系来自合成声明。

2026-11-01 本地结果：

| 策略 | 累计未覆盖的未完成需求 | 五阶段累计描述字节 | 超出数量预算的阶段 |
| --- | ---: | ---: | ---: |
| 永久并集 | 0 | 21280 | 5 |
| 固定两个工具 | 9 | 5320 | 0 |
| 动态工作集 | 3 | 3724 | 0 |

动态策略的五次选择约 0.032–0.154 毫秒，单次本地测量，不作为性能保证。该数字不含词法召回、模型、存储与工具执行。真实发现阶段按未解决需求分别扫描目录，比单次全局召回更贵；大目录需要后续索引复用和候选召回性能研究。

结果证明这组受控条件下动态分配减少了展示缺口和描述成本，**不证明真实模型知道如何使用备用工具，也不证明自然语言任务规划或整体成功率改善**。回归另外运行真实 SessionEngine 与统一 AgentHarness，验证首选工具失败、备用工具执行成功、工作状态满足和工具退休；还覆盖 steering、重新激活、失败恢复、独立动作义务、描述预算和单例回退。

## 当前限制与下一步

权重与覆盖系数是固定策略，不是学习到的策略。候选发现仍受词法和 Schema 匹配限制；一个替代工具被展示出来，不等于其输出能够满足原来源约束。数据依赖来自接受的任务解释，框架不会凭空发明正确依赖。

描述预算过小时可能没有工具入选，报告保留未覆盖目标，不自动提高宿主预算。尚未实现由模型显式请求扩大能力目录，也未新增主动摘要或自动回取新算法；已有 ContextFocus、成果读取和 RecoverContext 继续工作。

下一步应针对真实长任务中“知道缺什么，但不知道该去哪里找”的失败，深化语义能力发现与有目标的上下文回取，并比较实际任务收益和新增成本。
