# 完整反馈执行前预算证明

## 1. 本次新增了什么能力

Weavria 现在把“工具可以执行”和“工具结果可以交付给下一轮模型”合并为同一个执行前决定。完整反馈工具为已校验输入提供可验证的输出上界；Runtime 为每个调用生成反馈信封，整批计算下一轮最坏合法请求大小，只有全部结果能够共同交付时才派发工具。

对应架构决策见 [0037 完整反馈的执行前预算证明](decisions/0037-完整反馈的执行前预算证明.md)。

## 2. 它在 Agent 系统中解决什么问题

之前的链路已经能保证受控读取结果不会被上下文选择器二次裁剪，但准入阶段仍只为 Artifact 引用预留空间。结果是：批次在执行前看似合法，所有工具也成功，下一轮才发现完整结果装不下。此时模型没有重规划机会，工具调用与时间预算已经消耗，Run 只能以 `context_bytes` 结束。

新机制将交付能力提升为执行前不变量：完整反馈不是执行成功后的愿望，而是工具启动前必须完成的预算证明。

## 3. 一次请求在代码中如何流转

1. `ToolRegistry.action_identity` 用工具输入 Schema 规范化模型动作，生成稳定动作摘要。
2. `ToolRegistry.feedback_envelope` 调用可信的版本化输出估算器，并由框架补齐完整 `ToolExchange` 的协议开销。
3. `reserve_feedback` 把全部新调用的信封、已授权来源引用、轮次状态和控制通道一起计入下一步预算。
4. 总上界超限时，Runtime 接受 `BatchRejected`，向模型返回 `feedback_budget`、所需字节与可用字节；没有任何 `ToolStarted`。
5. 总上界满足时，`BatchAdmitted` v3 持久化每个反馈信封。
6. `ToolExecutor` 在执行前复核信封与动作、工具版本一致，在输出通过 Schema 后复核真实大小。
7. `Context Compiler` 使用与执行器相同的 `complete_exchange` 构造函数交付完整结果，避免两个模块的序列化格式漂移。
8. 状态重放再次验证信封顺序、调用身份、工具版本和交付策略。

## 4. 为什么采用当前设计

完整反馈的大小通常与参数相关：读取 500 字节与读取 3,000 字节不能共用一个全局最坏值。把估算器放在工具注册边界，既允许工具理解自身输出结构，又把动作、Artifact 和协议开销留给框架统一计算。

估算器不读取真实成果，因此准入仍是纯决策过程，不会绕过 Policy 或制造隐藏副作用。执行后复核则把“可信插件”与“不可验证插件”区分开：插件可以提供承诺，但 Runtime 决定承诺是否被遵守。

内置 `read_artifact` v4 把字符串、结构化值和标量的 `length` 统一成 JSON 载荷字节预算。这让上界足够紧，不必按每个 Unicode 字符的理论最坏转义长度过度预留；`start/end` 仍是字符位置或直属子节点位置，不会变成不可解释的原始字节偏移。

## 5. 如何运行测试或观察结果

```bash
uv run pytest tests/tools/test_execution.py -q
uv run pytest tests/context/test_compiler.py -q
uv run pytest tests/runtime/test_control_loop.py -q
uv run pytest tests/sessions/test_evidence_access.py -q
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
```

运行证据中可以观察：

- 完整反馈工具使用 `ToolDescriptor` v4，并携带 `feedback_bound_version`；
- 新准入事实使用 `BatchAdmitted` v3，并按调用顺序记录 `feedback_envelopes`；
- 超限批次产生 `BatchRejected.notice.reason=feedback_budget`，且对应调用没有 `ToolStarted`；
- 合法批次的成功记录仍为 `ToolRecord` v2，下一轮表示为 `representation=full`；
- 估算器低报不会变成普通工具失败，而会作为 Runtime 不变量缺陷显式终止。

## 6. 当前刻意没有实现什么

- 没有识别 FinScope、市场、日期或任何应用字段；
- 没有为 `read_artifact` 工具名在 Runtime 或 Context 中写特殊判断；
- 没有自动增加上下文、模型调用或工具调用预算；
- 没有在超限时擅自执行批次前缀；
- 没有把完整结果静默截断成摘录；
- 没有实现跨轮交付清单或自然语言不可用声明核验；
- 没有把本次确定性正确性测试宣称为真实模型能力收益。

## 7. 下一小步建议

下一步应建立领域无关的 `EvidenceDeliveryManifest`：明确区分“已执行”“已保存”“已在某次模型请求中完整交付”“只交付引用”和“从未交付”。Completion Policy 再基于该清单校验候选答案中的可用性声明。这样可以继续解决“结果虽然存在，但模型是否实际获得并正确声明其可用性”的跨轮问题，而不把应用业务知识写入框架。
