## 评分规则

每次运行同时检查三件事：

1. **结果**：最后答案必须是任务约定的 JSON，要求的字段与冻结值一致，引用包含要求的原文件路径。无序字段按集合内容比较，关闭顺序等有序字段保留顺序语义。布尔值不接受整数代替。英文/中文等预先列出的别名不会跨旧值和修订后的值混用。
2. **真实执行行为**：引用的资料确实被工具读取；多步任务至少读取两项来源；长上下文任务发生原文回取并形成工作记录；澄清继续同一工作；修订进入新 revision；记忆任务有实际准入与跨会话召回；故障任务经历主库失败并成功读取镜像。
3. **完成与重试**：相关 Run 完成，同 input_id 重试复用结果且不重跑理解和执行模型。超时、预算耗尽、异常、错误结果和缺失场景行为均计为失败。

不以 Runtime 的 COMPLETED 独立判定任务成功，不以测试通过次数充当真实模型结果。评分器自身覆盖错误字段、缺失引用、旧记忆与新记忆混淆、资料散列变化及镜像故障等回归。

这些任务验证明确指定的接入与分析行为。澄清任务包含用户要求先确认的意图；不能据此推断模型能够普遍自主估计澄清价值。源码和文档都来自 Weavria，两个场景说明接入方式独立，不代表广泛领域泛化。

## 模型与预算

使用已有本地配置指定的 `deepseek-flash`，温度 0，JSON mode，reasoning_effort=none。模型标识是请求标识；报告另外记录供应商响应中的模型名称，不能假设可变服务别名等价于固定权重版本。

| 参数 | 固定值 |
| --- | --- |
| 声明窗口 / 输出预留 / 安全预留 | 16384 / 4096 / 1024 Token |
| 可用输入窗口 | 11264 Token |
| 单次请求字节上限 | 96000 |
| 每次 send 父期限 / Run 局部上限 | 240 / 180 秒 |
| 模型调用 / 理解 / 记忆阶段期限 | 60 / 60 / 45 秒 |
| 执行模型调用 / 工具调用上限 | 16 / 20，含 2 次收尾模型预留 |
| 单项完整多会话任务上限 | 1200 秒 |
| 并发实验数 | 2；每项内部均为单 Agent |

计量使用现有 `cl100k_base` 计量器，实际供应商 Token 用量单独报告，不宣称二者完全一致。文档和源码集合分别为 34074、39747 个声明计量 Token，均超过可用输入窗口两倍。长上下文需要在实际轨迹上发生回取，不能仅凭资料体量通过。

所有场景启用相同的工作记录与 basic 记忆形成配置。记忆任务由四次独立会话组成：写入约定、首次查询、修订约定、再次查询。每项重复实验从干净的数据库开始，避免上一项成功污染下一项。

朴素基线只将 `ContextCompilerConfig.policy` 从 coverage 改为 recent，配置标识随之改变；其他能力、模型、预算和任务保持一致。每个任务各运行 3 次，共 36 次推荐配置与 36 次基线，交错调度。基线结果无论好坏均保留。

## 运行与结果保存

```bash
uv sync
# 离线校验资料、任务数量、散列和长上下文体量；不调用模型。
uv run python -m examples.m1_harness

# 需要设置 WEAVRIA_MODEL_BASE_URL、WEAVRIA_MODEL_NAME、WEAVRIA_MODEL_API_KEY。
# 也可用 --env-file 指定本地配置，只解析这三个变量，不执行 shell。
uv run python -m examples.m1_harness --run --out .weavria/m1/batch-0

# 可选单项诊断，每项仍保留三次重复和两个配置，不能代替完整验收。
uv run python -m examples.m1_harness --run --case documents_multistep \
  --out .weavria/m1/diagnostic-0
```

输出目录必须不存在，禁止覆盖旧结果。每次任务完成立即保存独立 JSON、会话数据库和记忆数据库。manifest 固定任务/资料散列、实际执行源码散列、依赖版本、模型参数与预算；结果按执行、理解、形成三个角色分别记录调用和供应商用量。结果报告不保存凭据或隐藏推理；包含最终答案的本地结果不提交 Git。

全量 summary 的 `task_gate_passed` 需要 12 个任务都完成三次推荐配置运行，成功至少 30/36，每项至少 2/3。单项诊断永不标记通过完整门槛。此字段仅表示任务门槛，不自动宣称 M1 的源码说明、独立示例与交付条件已经全部完成。

## 修复与停止

真实运行前的脚本和资料校验属于第一项交付。首次完整真实运行结束后，只按里程碑处理实际失败：最多两轮针对性修复与完整复测。任何评分器修订须单独记录原因、原结果和新版本，不能悄悄放宽成功条件。新增任务、模块或算法研究不自动进入本阶段。
