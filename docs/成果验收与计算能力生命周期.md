# 成果验收与计算能力生命周期

## 本次能力与问题

2026-11-06，本阶段把“已有中间资料”“计算成果需要修正”“完整成果通过验收”接回同一条 Harness 决策链。新增能力只影响显式声明的隔离计算：中间结果不触发退休，独立验收通过后可以退出工具视图，目标或证据变化后重新开放。

此前的信息账本区分 ACQUIRED 与 SATISFIED，但计算的完成条件会关联同一工具的信息需求。例如第一阶段需要取得 statistics.json 和版本号，第二阶段还要从该版本生成 report.txt。即使第一阶段需求已经 SATISFIED，也不能证明第二阶段完成。因此不能用一次 ToolSucceeded 或“所有关联信息需求满足”代替完整成果验收。

本次使用宿主注册的 `CapabilityOutcomeVerifier` 验证原始任务、能力目的和完成条件。它是可信策略扩展，和既有 CompletionPolicy 一样需要宿主正确实现；不是模型自动生成的自我评分。通用框架不认识 Python AST、工作区或文件名，这些只存在于示例验收器。

## 一次请求如何流转

1. `AgentHarness.from_config` 通过 `HarnessEvidence(outcome_verifiers=(verifier,))` 装配验收器，要求同时开启任务理解和动态能力。初始账本按实际配置登记 `outcome_not_checked` 槽位，没有配置时维持原来的保守保留策略且不增加验收预算。
2. `TaskAwareSessionPreparer.refresh` 先按接受的工具记录更新资料账本，再调用 `CapabilityOutcomeResolver`。每轮使用当前原始 TaskInput、TaskFrame 与已接受成果重新判断，不沿用旧 verified 缓存。
3. 验收器只返回 `verified / repair / unverifiable` 与有界原因码。框架自动记录验收器版本、能力版本、范围摘要和实际读取的 ArtifactRef；验收器不能自报一组未读取的证据。
4. 投影写入 `NeedLedger` v7 的 `capability_outcomes`。资料状态保持原义，不把验收通过改写成所有信息需求已满足。旧 v5/v6 读取、序列化和历史摘要保持兼容；重新归约才产生新判断。
5. `AdaptiveCapabilityPolicy` 检查完整范围、当前工具版本、精确接受引用与资料缺口。条件都成立才移除该计算工具的覆盖收益；声明外计算仍不会通过发现器被自动激活，ToolPolicy 仍独立授权。
6. 进度判断优先使用成果验收，repair 不会被“工具用过”覆盖。模型的进度视图包含简短验收状态；主动收尾仍需成果就绪。最终候选遇到明确 repair 会被拒绝，verified 只证明能力成果，最终自然语言答案仍受原 CompletionPolicy 约束。unverifiable 不会被宣称为成果已验证。

入口文件为 `src/weavria/harness/outcomes.py`；持久化契约在 `outcome_contracts.py` 与 `requirements.py`；消费端分别位于 `working_set.py`、`progress.py`、`finalization.py`、`completion.py` 和 `task_view.py`。示例 `VerifyWorkspaceOutcome` 与最终交付校验复用 `VerifyWorkspace.is_complete`，避免两套标准逐渐分歧。

## 数据结构与关键不变量

每份验收记录包含能力名称/版本、验收器名称/版本、状态、原因码、范围 SHA256 与最多 64 个实际读取的根 ArtifactRef。范围摘要覆盖请求锚点、完整任务规格、信息需求和完成义务；不包含由证据和菜单推进的 Frame 版本。否则验收推动一次菜单更新就会让自身过期。任务目标、约束或要求改变则必须失效。

退休条件可写为：独立 verified ∧ 范围相同 ∧ 工具版本相同 ∧ 所有引用仍为接受事实 ∧ 关联必需资料不存在缺口。ACQUIRED 可以与成果 verified 并存，它们回答不同问题。对本工具仍 pending、stale 或 contradicted 的资料要求会阻止退出。

上下文只能读取本 Run 已接受的根结果，以及通过根结果中精确引用访问的同一生产者附件。附件不能凭 ID 直接读取，读取后也不会获得通用访问权限。父子摘要均校验，持久化根摘要承诺附件地址与摘要。每个验收器默认最多 64 次读取、累计 4,000,000 字节、5 秒，最多注册 16 个能力；运行仍受父请求总期限约束。

超时、读取越界或预算耗尽产生 unverifiable，保留计算入口；普通验收器缺陷继续抛出，不伪装成业务失败。取消不被转换为普通失败，上下文在成功、异常、超时与取消后关闭。超时取消即使被外部验收器误吞，也不会生成 verified。异步期限不能抢占阻塞的 Python CPU 代码，宿主验收器本身仍需有界实现。

结果是不可变成果的存在性证明，不自动引入“最后一个版本才有效”的全局 HEAD。后续失败不会抹掉此前仍然满足完整任务的交付版本；需要最新版本语义的应用必须明确写入自己的验收条件。

## 集成故障与修复

初次接线在第一轮反馈后触发 `task model definition or capacity changed without a task revision`。原因是验收状态首次出现时才增加模型进度容量，违背同一任务的固定预算承诺。第二轮全量回归又揭示：若给全部声明能力预留验收空间，会挤占未启用验收的紧窗口任务的原文预算。最终修复是在初始账本只登记实际配置的验收槽位，按这些固定槽位、最长状态和有界原因码预留空间，后续只改变内容。没有降低 Session 校验或扩大运行预算。

回归覆盖：信息满足但中间成果不足、完整验收退出、缺失/篡改引用、工具版本变化、任务修订、读到另一个生产者附件、无读取却声称 verified、字节预算、超时、误吞超时、外层取消、验收器异常、同事实重复刷新无版本抖动、v5/v6 线协议、v7 与来源失败状态共存、模型视图容量固定、主动收尾与最终候选拒绝。

真实 Docker 用例使用正式 Harness 与 SQLite：读取源码、生成统计、读取文件、注入 NameError、修正并生成报告、验收退出、关闭重开后读取结论和恢复文件。原动态模式的固定替身需要 8 次执行模型请求；验收模式需要 6 次，因为中间结果不会再触发一次过早的完成建议与拒绝往返。动作由测试编排，此差异只证明控制契约，不是模型智能或总体性能结论。

## 边界与下一步

本阶段完成的是有界、可追溯的成果验收如何驱动能力保留、释放、进度与交付，不是开放领域通用自动验收。未实现跨 Run 自动继承证明、任意任务的语义验收器生成、事实依赖变更下的增量验收或大型成果的验证索引。当前每轮重读相关事实，成本随已接受历史增长，超出读取预算会保守退回 unverifiable。

下一步优先把验收器的原因与具体未满足条件形成更精确的修复反馈，支持模型定位哪份成果的哪个条件失败；再用多个领域的冻结任务验证其是否减少无效重试。先改善反馈的决策价值，再考虑缓存和增量验收。
