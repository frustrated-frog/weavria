# 局部工作补丁的执行机制与实验

本轮针对上一轮真实执行中的具体失败：模型为了修正一条笔记，必须重发整组工作记录，容易丢失身份、误写父版本或原文地址。新增显式 `work_updates="patch"`，把局部意图编译到既有工作提案，保留证据失效、前沿重验与完成门禁。设计见 [ADR 0130](decisions/0130-局部工作补丁与宿主版本绑定.md)。

## 能力与接入

```python
config = HarnessConfig(
    configuration_id="my-agent",
    context=ContextCompilerConfig(window_tokens=64000, output_tokens=4096),
    working_records=True,
    work_recheck=True,
    work_updates="patch",
)
```

默认仍为 `replace`。补丁必须显式开启工作记录；它不自动启用证据重验。若需要 Ledger 驱动失效与语义重验，应同时启用 `work_recheck`。

工具仍叫 `propose_work`，但模型看到的是局部操作 Schema：

| 字段 | 语义 |
| --- | --- |
| `upsert` | 按稳定 `note_id` 新增或修改；已有笔记省略的字段保留，新笔记必须声明 `kind`、`summary` |
| `remove` | 显式撤回已有笔记；不静默删除未提及的记录 |
| `review` | 选择已有笔记重验；适用于结论文字不变、证据版本变化的失效根 |
| `depends_on` | 父笔记 ID 列表，宿主填写当前绑定视图中的版本 |
| `sources` | 已授权 `artifact_id` 和精确 `quote`；可选 `pointer` 用于消歧 |
| `next_need_ids` / `next_query` | 省略保留，空数组或空串显式清空 |

可选字段的 `null` 按未提供处理。每类操作内部 ID 必须唯一，删除不能与修改或重验相交。修改本来就包含按需重验，因此同一 ID 同时出现在 upsert/review 会合并为一次意图；未知删除/重验 ID、重复修改、环、非法来源及超限均拒绝。活跃工作集仍最多六条笔记，每条最多五个父节点、两个来源、四个需求。原始补丁和展开后的 WorkUpdate 都受 4000 UTF-8 字节上限约束；最终工作状态保留 8 KiB 上限，不能把小补丁当作无限增长存储。

## 一次请求如何流转

假设工作集已有 `capacity`、依赖它的 `recommendation`，以及独立的 `audit`。新证据使前两条失效。

1. 模型向 `propose_work` 发送 `upsert=[{note_id:"capacity", summary:"容量变为 8", sources:[...]}]`。`work_patch.compile_work_patch` 从 ToolContext 中本次请求绑定的 TaskModelView 读取旧笔记与版本，保留其他笔记、下一查询和未修改字段。
2. 对省略 pointer 的来源，只通过 `ToolContext.read_artifact` 读取已授权原文。`locate_quote` 在 JSON 字符串叶子中寻找唯一精确短句，生成规范 JSON Pointer；原 `work_tool` 再检查该地址与引文，计算字符区间并绑定 Artifact 身份。
3. 编译器输出 WorkDraft，交给原工作工具的公开 `invoke` 路径，生成 WorkUpdate v4。版本号不由模型提供，宿主也不读取更新后的隐藏状态来修改模型看到的事实。
4. `ModelWorkRechecker` 只审查本次涉及的失效结果。审查收据仍绑定任务、旧工作修订号、原笔记版本和完整候选提案摘要；来源支持仍须匹配当前 NeedLedger。
5. 原 `reduce_work` 接受工具事实并进行 CAS，提交完整工作集。成功修正 `capacity` 后，`recommendation` 保持失效，`audit` 的内容与版本不变；完成门禁仍拒绝旧建议。
6. 下一次模型只提交 `recommendation` 的新判断。宿主绑定已接受的 `capacity` 版本，经原文重验后更新后继。原文、收据、提案和语义快照沿既有事件与 SQLite 事务保存；重开和回放不调用模型重做补丁。

新图允许同一补丁声明多个新节点，父版本统一绑定本次候选修订号，随后由既有 DAG 校验器检查环。对于已有图，不能在一个补丁中同时编辑或重验父节点及其后继，也不能先换绑仍失效的父节点。这个限制保持“先确认前提，再复核结论”的执行顺序。

删除父节点时，未触及的子节点保留旧边并进入 `missing` 失效状态；不会自动断边。两个来自同一旧视图的补丁即使修改不同笔记，也只有首个 CAS 能被接受，后一个收到旧修订诊断并需基于新视图重提；本轮没有实现并发语义合并。

## 关键设计取舍

`WorkUpdate.recheck_note_ids` 是 v4 新增的宿主字段。旧 v1/v2/v3 省略它，保留原自动根重验行为；补丁写入显式选择，避免只更新独立计划时顺带重验并恢复未触及的失效结果。改变、降级或删除失效结果仍必然进入原重验目标，空选择不能绕过检查。全量工具的模型输入不暴露该宿主字段，并拒绝模型手工提交；输出 Schema、提案摘要和持久化数据完整保留它。

没有新增 Patch 持久化事件、表或第二套状态归约器。`propose_work` 的输入操作留在原 ToolRecord，接受后的权威结果仍是完整 WorkProposal。这让回放不需要重新编译旧补丁，保持“事件记录接受事实”的边界。WorkingState 不因此升级；新 WorkUpdate 可读取，已有 Run 是否能继续执行仍由配置和策略兼容检查决定。

定位算法使用栈遍历 JSON 值，正确转义 `~` 和 `/`。最多遍历 1024 个节点、32 层、累计 65536 字节字符串；容器宽度在入栈前检查。跨字段重复和同一字段内重叠重复都拒绝；达到容量上限也拒绝，不能只扫描前半份材料便宣称唯一。指明 pointer 后走原来的精确字段引用路径。它只解决位置，不判断引文是否支持结论。

编译开销为工作节点与边的线性扫描，加每份需要自动定位的 Artifact 有界遍历。同一次编译缓存已读取文档，原工具仍独立复核来源。所有 I/O 都在原 ToolExecutor 的超时、取消和权限边界内；失败不提交部分工作状态，不创建后台任务。验证异常不回显完整模型输入。

逐条检查确认同一 ID 同时出现在 upsert/review 的拒绝属于协议多余负担。最终 patch/2 将两者合并；修改后重新固定实现，从头执行完整对照。没有修改题目、答案、模型或预算，也没有放宽语义审查、删除冲突或父子前沿限制。最终版原资料对照为 replace 2/6、patch 2/6 正确完成。单次工作输入中位数分别为 1689、928 字节；模型调用分别为 56、68，总 Token 为 528615、734434，总时间为 167.38、273.61 秒。两组各有一次在证据失效后经过重验正确交付，均发生于未变化契约材料，不能据此证明修正错误结论的能力提高。补丁完成的一条运行保留陈旧 plan，但没有陈旧 result；计划不增加交付义务，不能与陈旧结果混为一谈。

本轮补丁没有出现引用地址/字符区间或冗余 upsert/review 拒绝。原资料仍有 14 次工作工具失败，集中在六笔记/提案容量、未知父节点和前沿限制；两条文档修订任务都未完成。因此最终版并未证明整体任务收益，仍保持可选实验配置。短材料最终版两组仍均为 0/4；replace/patch 分别调用 57/35 次，使用 487001/237872 Token，耗时 133.83/61.42 秒，工作输入中位数为 1179/557 字节。补丁组四次最终都没有陈旧笔记，但 Ledger 都仍有 `$freshness` 缺口；本组没有观察到证据驱动失效。较少调用也可能来自较早停止，不能等同于有效任务效率改善。

两轮共 40 次真实运行均保留；同设置的 replace 原资料结果也从 4/6 波动到 2/6。样本量小且任务由模型自行构建起点，不能用前后两轮结果证明冗余意图合并的统计收益。重复意图只执行一次由确定性测试保证，任务收益需要后续固定起点、多模型实验。

原始记录位于忽略目录 `.weavria/work-recheck/`：首版 `local-patch-sources-01.json`、`local-patch-short-01.json`，最终版 `local-patch-sources-02.json`、`local-patch-short-02.json` 及对应 trace。每套分别包含 12/8 条运行；保存失败和未进入机制的成员，不只保留成功轨迹。

## 当前边界与下一步

当前补丁新增或替换来源只接受文本精确引文；纯数值、对象等非文本来源的新引用仍需全量模式，已有结构化引用可随未修改字段保留。这一输入范围尚未扩展为所有 Artifact 类型的通用选择器。

局部协议不会自动发现漏掉的依赖，不保证模型选择正确来源，也不保证它遵守先记录旧资料、再修复新资料的任务顺序。唯一短句不等于蕴含，审查模型仍可能误判；宿主现有来源门禁只提供其明确定义的保证。原文定位、省略字段保留和版本绑定降低机械负担，不能单独证明长任务能力提升。

本次已看到两种需要分开深入的问题：一是工作集达到容量后，模型需要可操作的整理与修复反馈；二是完成门禁中的证据缺口。首版短材料四条补丁轨迹都出现 `missing_evidence`，其中三条最终没有陈旧笔记。对 `capacity_unchanged` 第一次运行的最终 Ledger 检查显示，`/text` 已匹配，剩余缺口是 `$freshness`，当前版本材料没有提供结构提取器认可的时效证明。这说明“选到了 current 文档”与“满足实际时效要求”在当前链路中尚未一致解决，不能把失败一概归因于笔记修复。

下一步应先给这些失败建立固定起点，研究相对资料版本、实际时效要求及证据绑定的语义，再完善容量约束下可执行的修复反馈。不能通过删掉时效要求、移除失效结论或放宽完成门禁来制造成功率。
