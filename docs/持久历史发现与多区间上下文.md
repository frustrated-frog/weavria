# 持久历史发现与多区间上下文

本切片让上下文编译器发现最近 64 次交互之外的历史，并在一个文本字段中交付多个不相邻的原文区间。实现位于当前 `codex/context-compiler-v1` 分支，接续 ADR 0030；只建设 Context，不引入 Memory。

## 1. 新能力与解决的问题

此前 Session 编译器只能在最近 64 次已结束交互内选择，单个字段主要提供完整内容、前缀和一个连续片段。它面临两个独立问题：窗口外的来源根本不能参与选择；即使找到来源，连续片段也可能无法同时容纳相距很远的事实。

现在先用持久倒排索引发现有限候选，再让现有联合分配器选择表示。检索负责“从哪里找”，多区间表示负责“交付哪些原文”，全请求 Token 核算负责“能否放得下”。近期反馈和当前 Run 的工具依赖闭包继续由编译器保护。

覆盖范围是同一 Session 内已经结束或中断的交互，包括用户文本、助手文本和用户追加要求。原交互的工具成果目录仍随候选保留。历史 Artifact 正文继续通过 `read_session_source` 读取，本次不建立其全文索引，也不把历史来源伪造成当前 Run 的 `ToolRecorded`。

## 2. 一次请求如何流转

以第 73 次请求“找出 Aurora password 和 Zephyr deadline”为例，两条信息位于第一次交互的同一长文本中，中间隔着大量附录。

1. `SQLiteSessionStore._append` 接受终态时，将最终 `ConversationTurn` 的身份、摘要、大小、ordinal 和接受位置登记到 `history_catalog`。这些记录与终态处于同一事务。这里只登记目录，不进行全文索引。
2. `_SessionAdapter.prepare_turn` 记录当前 Session 截止位置和历史数量。启用检索时，不再预读最近 64 份完整交互。
3. `build_control` 将当前目标、约束和 `ContextFocus` 中的需求交给 `retrieve_history`。索引按额度补建至截止位置；每份交互的来源、片段、词项、前缀统计和水位一起提交。
4. 搜索从片段级 BM25 得分生成交互候选，保留至少最近两份交互，再分配显式锚点、近期窗口和词项命中名额。候选数量还受到编译器剩余单元容量约束。只有入选候选才加载完整原文，并核对目录摘要。
5. 编译器从候选原文发现片段。多区间候选按新增覆盖收益与片段成本生成，随后与单区间、完整内容和当前 Run 工具证据一起参加联合分配。
6. 完整 `SessionRequest` 再次经过实际适配器 BPE 计量、字节预算和控制反馈预留检查。`prepare_request` 在提交事务中核对检索边界、候选身份、实际交付的原文区间及原交互元数据，随后一起保存请求快照与 `ContextCompilation` v3。
7. 模型只接收已提交的请求。检索期间若用户追加要求，旧修订计划会被丢弃，按新需求重新检索；派生索引可以复用。

检索报告中的候选不等于实际交付。查看 `retrieval.candidates` 可以知道发现了什么；查看编译报告的 `choices` 和请求快照，可以知道哪些来源及区间最终进入了模型上下文。

## 3. 数据结构与算法

### 持久索引

SQLite Schema 从 v5 升级到 v6，新增六张表：

| 表 | 内容 |
| --- | --- |
| `history_catalog` | 已接受交互的身份、ordinal、接受位置、投影 SHA-256 和字节大小 |
| `history_index_state` | 分词策略版本、重建代次、已提交的 ordinal 与 Session 位置 |
| `history_sources` | 用户、助手或追加要求的原字段身份与 SHA-256 |
| `history_passages` | 原文字符区间、片段词项数 |
| `history_postings` | Session、词项、片段 ID 与词频 |
| `history_turn_stats` | 按交互累计的片段数与词项数 |

目录与原始投影保持一致；其余五张表是可重建的派生数据。前缀统计与水位一起更新，按历史截止位置选取即可得到 BM25 的语料大小和平均片段长度，避免每次查询都扫描全体片段。倒排表同时具有词项查询索引和按片段删除索引，清理重建不会逐片段重扫整个倒排表。

首次迁移扫描旧事件与投影，为已有终态登记目录。终态位置一次聚合后关联投影，避免每份历史重复扫描事件。迁移保持已接受事件、请求快照与 v5 原文投影的字节不变；更早版本按原迁移规则先升级投影。全文索引随后才按查询额度补建。

片段限制为最多 320 个 UTF-8 字节，地址始终是原文的 Unicode 字符位置。优先在邻近空白处切分，连续中文边界重叠一个字符，以保留跨边界双字词项。分词沿用 NFKC、大小写归一化、英文词与中文双字词项，不增加运行时依赖。超长且没有分隔符的单个标识仍可能被分割。

BM25 固定 `k1=1.2`、`b=0.75`，每个需求的词项贡献按其查询词项数归一化并乘以需求权重。片段分数按需求聚合到交互：同一需求取该交互最好的片段分数，再对需求求和，避免一份长交互仅靠重复相同事实不断累积得分。查询优先访问低文档频率词项；预算耗尽时只能得到明确标记的部分结果。

所有命中、词项频率和前缀统计都约束到同一 Session、`ordinal < before_ordinal`、`accepted_sequence <= through_sequence`。索引已经包含后续交互时，较早截止位置的查询也不能使用后续语料统计或命中。这里的 Session 范围是现有本地所有权模型的读取边界，不扩展为多租户认证。

### 多区间候选

新增 `MultiRangeTextView` v3，携带完整原文 SHA-256、字符总数和 `ranges`。每个区间包含 `start`、`end`、`text`，必须有序、非空、不重叠；相邻区间应合并。v1 前缀、v2 连续区间保持原来的序列化。v3 的展示用 `.text` 属性会插入省略标记，它不会序列化成一段冒充连续原文的文本。

候选生成先计算各片段的需求覆盖特征，然后反复选择“新增覆盖 / 片段编码成本”最高的片段。每步取覆盖特征的最大值，已覆盖的重复事实不会再次获得相同收益；在 1、2、4、8 及配置上限等规模产生少量组合。区间随后按字段归并，保留一份来源元数据。

这只是来源内部的候选生成。最终选择继续由既有联合分配器承担，包括依赖闭包、两条初始贪心路径、有限交换和完整请求成本复核。该方法不保证全局最优，也不理解事实的真假、冲突或语义等价。

## 4. 工作额度、取消与失败

`HistoryRetrievalConfig` 默认值：最多 32 个候选，近期窗口 8 个；每次补建最多 256 份交互、8 MiB 原文、65,536 个片段；最多检查 20,000 条命中 posting、128 个查询词项；SQL 总工作额度约 200 万条 VM 指令，搜索准备时间 5 秒；候选原文合计最多 8 MiB。

补建与查询分别受到片段/字节和 posting/词项额度约束，同时共享 SQL 和时间上限。SQLite progress handler 大约每 1,000 条 VM 指令检查一次，因此 SQL 工作计数是近似上界，并非精确 CPU 时间。额度停止后仍需有限的近期候选装载和报告收尾，`max_duration` 不代表完整 API 的严格墙钟时限；父 Run 的 deadline 仍通过取消约束全过程。

- 索引补建按整份交互提交。当前交互中途超限、异常或取消时整体回滚，之前提交的交互继续有效。
- 超限报告区分 `index_budget`、`query_budget`、`query_terms`、`time_budget` 和 `candidate_budget`；`index_complete` 与 `search_complete` 分开记录。部分搜索不能解释成全历史不存在相关内容。
- 单份交互超出补建额度时，水位会停在它之前，后续查询不会静默跳过。需要显式提高额度才能继续，不会自动无限重试。
- 最近两份必要交互无法装入原文容量时，抛出 `ContextCapacityError`，不静默删除必要上下文。
- 取消设置线程事件，经 Python 片段检查和 SQLite progress handler 中断工作；异步调用等待所属线程结束，再传播 `CancelledError`。回调在清理前移除，避免它干扰回滚。并发存储异常保留为取消的原因。
- 原文或候选身份不一致时拒绝发布。`rebuild_history_index` 只清理派生索引并增加代次，不能修复被篡改的原始投影，也不宣称自动发现所有派生分数损坏。

## 5. 使用与观察

已有 `SessionEngine` 配置可以显式增加：

```python
from weavria.context import ContextCompilerConfig, HistoryRetrievalConfig

engine = SessionEngine(
    path,
    model=model,
    tools=tools,
    context_compiler=ContextCompilerConfig(
        window_tokens=16000,
        output_tokens=1024,
        max_history_spans=4,
    ),
    token_counter=counter,
    history_retrieval=HistoryRetrievalConfig(
        max_candidates=32,
        recent_turns=8,
    ),
)
```

`counter` 必须计量实际供应商请求，其输出上限不能超过编译器预留。未配置 `history_retrieval` 时保留原历史窗口；`max_history_spans` 默认 1。仅启用新表示或新检索就使用编译策略/报告 v3 与运行配置 v3；外层 `SessionRequest` 仍为 v5，`ConversationView` 仍为 v2，其嵌套文本通过独立版本区分。旧报告不会额外序列化 `retrieval: null`。

公开诊断入口是 `SQLiteSessionStore.retrieve_history`，返回不可变序列化快照 `RetrievedHistory`；访问 `.turns` 和 `.report` 会解析出独立对象。显式重建使用：

```python
await engine.store.rebuild_history_index(session_id)
```

重建后下一次查询按额度补建，不在调用中同步扫描全部原文。

源码入口：`sessions/engine.py` 接入决策边界；`sessions/history_index.py` 负责目录、事务索引和水位；`sessions/history_search.py` 负责有界检索；`context/spans.py` 负责互补片段；`context/compiler.py` 负责全局分配；`sessions/history_validation.py` 负责请求提交时的原文核验。

## 6. 冻结对照实验与证据强度

运行：

```bash
uv run python examples/history_context.py
uv run pytest tests/context/test_history_spans.py tests/sessions/test_history_retrieval.py tests/evaluation/test_history_context_experiment.py
```

数据版本 `history-delivery/1`，文件 SHA-256 为 `6b447998a70a02a1964fa3e42162a739835895ae7385da526d8cec6f3f7f5bb2`。每个场景经过 72 次真实 Session 接受、关闭与重开，再执行三种策略。六个场景为合成压力数据，另一个来自仓库冻结版本 `bb17ea0` 的会话协议文档。正确短语只进入评测器；改变答案标签不会改变候选、请求摘要和 Token 数，测试对此做了验证。

2026-10-23 本地运行使用 `tiktoken 0.14.0 / cl100k_base`、窗口 5,000 Token、输出预留 256、安全预留 256、请求上限 9,000 字节。没有调用模型 API。表格中的分数表示交付给模型输入的目标短语数，不是回答准确率。

| 场景 | 最近 64 轮 | 检索 + 单区间 | 检索 + 多区间 |
| --- | ---: | ---: | ---: |
| 英文远距离事实 | 0/2 | 1/2 | 2/2 |
| 大量重复片段 | 0/2 | 2/2 | 2/2 |
| 中文远距离事实 | 0/2 | 1/2 | 2/2 |
| 近期事实对照 | 1/1 | 1/1 | 1/1 |
| 词面不匹配的改写查询 | 0/2 | 0/2 | 0/2 |
| 冻结仓库协议问答 | 0/2 | 0/2 | 2/2 |
| 无词项命中对照 | 0/0 | 0/0 | 0/0 |
| 合计 | 1/11 | 5/11 | 9/11 |

21 次编译的来源区间与原文全部一致，均满足预算；完整检索范围内的未命中对照没有词项命中。三种策略总输入 Token 分别为 4,243、5,673、6,053。重复片段场景中，单区间已经交付两条事实，多区间仍增加了 61 Token，说明覆盖优化不会保证每个场景都更省成本。

实验先单独记录首次补建加检索，再测量两种已建索引策略，避免混淆冷、热状态。此次首次准备为约 15–42 ms；热检索中位数约 0.61/0.62 ms；单区间/多区间编译中位数约 4.99/5.94 ms。窗口基线加载 64 份候选，编译中位数约 68.24 ms；检索方案最多 6 份。这些是当前小语料和本机的观测值，不是容量承诺。

契约验证还覆盖：跨 Session 与历史截止隔离、旧库迁移、中文边界、区间伪造、分批补建、故障回滚、取消后的水位与连接可用性、显式重建、已接受成果锚点、用户追加要求、检索期间修订，以及请求提交前丢弃旧计划。

## 7. 尚未解决的问题与下一步

这一步完成了有界历史发现和多区间原文交付的闭环，但没有证明真实模型任务成功率提升。词面完全不同的查询仍会漏召回；局部词项覆盖无法判断事实冲突、时效性或语义上必要的邻接内容；候选上限、首次索引额度和高频词 SQL 工作额度也会降低召回。大规模、高并发生产负载未在本轮验收。

后续仍沿 Context 主线：先用固定模型与领域无关任务验证遗漏如何导致失败，再建设有明确预算和来源身份的主动恢复，以及恢复结果进入当前 Run 上下文的重新准入机制。历史 Artifact 正文索引、语义混合检索、生成式压缩和 Memory 都没有在本切片中实现。
