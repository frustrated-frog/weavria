# 当前可承诺库存的双向验收

2026-11-19。相同的问题、模型和执行预算下，有有效 ATP 发布单时，正式批三次都交付了正确件数；只有历史归档时，三次都没有交付。默认任务解释和完成策略继续沿用现有版本。本轮将两种材料和独立判据保留为回归用例。

## 同一个问题，两种证据

用户问 S4 在核验时刻能向客户承诺多少件。东、西两仓各须给一个整数或 null，`status` 说明能否确认，`needed` 说明还缺哪类来源。

| 来源或判据 | 有发布单 | 仅有历史归档 |
| --- | --- | --- |
| 两边共用 | D17 结账表、结账口径、东仓更正单 | 完全相同 |
| 可查的来源 | 完整来源清单另列出分配系统的 ATP 发布单 | 完整来源清单只有三份历史材料 |
| 独立预期 | `confirmed`，东 0、西 31，`needed=none` | `insufficient_evidence`，两仓均为 null，`needed=current_atp` |
| 来源回执 | 本 Run 获准读到有效发布单原文 | 本 Run 获准读到完整来源清单原文 |

仓储材料是合成夹具。该例将“现在”固定在 2026-05-14 10:00 UTC。适配器在装配时校验预先固定的发布单摘要、发行方、SKU 和有效区间 [09:55, 10:05)。执行时，只有匹配实际工具版本、获准的读取路径与相同 Artifact 摘要的原文才有时效证明。命中镜像也有效，改动正文后重新计算的文件摘要不能替代固定摘要。结构提取仍逐项校验声明的字段。清单给出本次材料的范围，不含当前件数。

两臂使用相同的公开 Harness、归档搜索和主备读取工具、证据适配器和任务理解器 `/16`。每臂从独立空会话开始，三对交替顺序，准备失败也进入分母。开启覆盖审计、工作记录和重验；模型为 `deepseek-flash`，温度 0，推理选项 `none`，输出上限 4,096 Token。每轮执行最多 16 次模型调用、24 次工具调用、150 秒，总请求限时 210 秒。

## 实际交付

首批问题列出了 `needed` 的取值，未明确它表示“仍缺少”的来源。三个有发布单的会话都报出东 0、西 31，其中两个同时给出 `needed=current_atp`。正式批仅澄清该字段的含义。两批使用相同的材料、冻结答案、独立评分器与预算，首批记录单独保留。

| 批次与分支 | 通过内容、交付和来源检查 | 失败位置 | 供应商调用 / 总 Token |
| --- | ---: | --- | ---: |
| 首批，有发布单 | 1/3 | 2 次交付中 `needed` 与独立答案不同 | 17 / 84,002 |
| 首批，仅历史归档 | 0/3 | 2 次完成验收拒绝，1 次准备失败 | 16 / 76,516 |
| 正式，有发布单 | 3/3 | 三次均有有效原文回执，四个字段均正确 | 15 / 73,229 |
| 正式，仅历史归档 | 0/3 | 第 1、3 组完成验收拒绝，第 2 组准备失败 | 24 / 119,163 |

正式批第 1、3 组都读到了本臂完整来源清单。第 1 组的三个“无法确认”候选内容均正确，但首次提交早于清单读取，后两次才具备所需回执。第 3 组的两次正确候选都已有清单回执。对应任务帧把两仓的当前数值列为必需项，且使用 `positive_value_required`。即使另有 `report_findings` 项解释资料不足，两个数值项仍须各自通过。最后留下的缺口是 `$freshness`，宿主每次都返回 `missing_evidence`。第 2 组记录为 `CoverageNoProgress:missing_selector=2`，未进入取证和验收。三次有发布单的宿主决策均为 `accept(unverified)`，数值和剩余来源由离线评分器独立核对。

## 固定证据后交换候选

确定性测试固定一条“需要当前数值”的需求解释，通过真实的 Tool 执行、Artifact 存储、证据解析和完成策略做以下对照。Fake Model 只提供固定任务解释。每行中交换候选，宿主看到的来源完全相同。

| 已读证据 | 候选报出 0、31 | 候选说明无法确认 |
| --- | --- | --- |
| 有效发布单和清单 | 宿主接受，独立评分正确 | 宿主接受，独立评分错误 |
| 只有历史材料的清单 | 宿主要求补证，独立评分错误 | 宿主要求补证，独立评分正确 |

这个对照定位了具体边界。现有判据能区分是否取到了有效数值来源，却不能仅凭同一项必需数值义务判断“无法确认”这个结论是否有据。直接放过 `$freshness` 会让无依据的肯定候选失去这道检查，仅凭候选填了 null 又会误收有数时的回避回答。后续若改变完成策略，应同时验证四格，确认清单只证明指定范围内资料不足，赋予数量的证明仍绑定发布单。此次只有一个任务、一个模型，正式批每臂各三次，无法据此判断自然语言回答、开放来源或真实库存服务的效果。

## 离线与真实运行

```sh
uv run pytest -q tests/evaluation/test_inventory_atp.py
uv run python -m examples.inventory_atp
uv run python -m examples.inventory_atp --live --repeats 3
```

默认输出配置和材料、请求、答案的摘要。显式真实运行沿用现有模型环境变量，每轮结束即保存结果。任一分支未通过，命令返回非零。可用 `--pilot` 重跑首批问题。首批本地证据为 `.weavria/inventory-atp/run-4ktknacb/`，正式批为 `.weavria/inventory-atp/run-06w913ss/`。数据库和模型输出保留在本地。两批的 12 个会话已逐一与只读回放核对。

```sh
uv run python -m examples.inventory_atp --replay .weavria/inventory-atp/run-06w913ss/1-published.db --branch published
uv run python -m examples.inventory_atp --replay .weavria/inventory-atp/run-06w913ss/1-archive.db --branch archive
```

第一条返回 0，第二条返回 1。回放按 run ID 和候选摘要核对宿主决策。`candidate_errors=[]` 说明候选内容正确，`candidate_source_errors=[]` 表示提交该候选前已有所需回执，`source_errors=[]` 说明已获取本分支所需原文，`delivery_errors=[]` 才说明实际交付正确。准备失败时，缺失的记录保留为空值。
