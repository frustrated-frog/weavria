# 任务修订与整体验收复测

## 验收问题

用户已经拿到首版，此时改变目标，或提供一项使旧结论失效的依据。单 Agent 能否根据改动交出完整修订版，同时保留依然正确的判断？本轮从两个方向考察这个问题，先冻结原有 M1 全矩阵，再在独立的两轮任务中记录相同输入预算下的交付与开销。

| 任务 | 两轮之间的变化 | 应保留的结论 |
| --- | --- | --- |
| W17 双组件升级 | 新增 QA 复核单，撤销一个组件的旧回执 | 另一个组件的全部字段，以及受影响组件的版本和兼容性 |
| 安装组合迁移 | 冻结资料不变，用户把目标中的 tokenization 换为 openai-compatible，安装起点不变 | snowballstemmer 的新增分类，以及 numpy、onnxruntime、tokenizers 的移除分类和精确版本 |

升级资料来自既有的独立编写案例。迁移资料取自项目提交 `d02a743` 的真实清单和锁文件，两份原件分别验证散列，所有包按相同规则投影。迁移判据人工核对。两者共享只读工具、任务理解、证据审计、工作记录、预算和统一入口，因而覆盖了两种变化形态，但只覆盖一种工具环境。

每次先用空数据库交付首版。续接在重开 Harness 后调用同一会话的 `send`，保留真实历史。对照另开数据库，只收到原始请求、追问和同一份修订时资料，从头重做。宿主不提供首版答案、差异清单、工作图或读文件顺序。每项重复三次，交替安排续接与重做的先后。两臂共享冻结的 Luna medium 请求配置，每次 send 的执行模型调用上限为 16，工具调用上限为 20。

整对通过要求两轮均由宿主完成且独立内容评分通过。首轮未完成保留在分母内，跳过无法发生的续接，冷重做仍照常运行。结论保留只在首版相应结论正确、修订版实际交付时评判。重读统计两轮均成功读取的同路径、同内容文件，包括镜像与重复调用。该数字表示读取次数，独立评分不以读取少为通过条件。供应商调用数包括准备阶段和失败调用；缺少 usage 时将总 Token 标为未知。

## 同一候选的证据重放

对升级与迁移各自的首个失败会话，逐个回到 `CompletionChecked` 之前。核对先前 `Finish` 的摘要，从该 Run 的 SQLite 事件与 Artifact 重建当时已经发生的工具回执，将同一份输入送入两个证据归约器。两个正确候选各提交过两次。普通提取器每次留下一个 `$scope`，核对过授权全集的提取器每次都消除该缺口。这个对照证明了两次独立失败的局部成因，没有执行后续模型决策。[机制与证明边界](decisions/0151-区分目录字段覆盖与完整范围证明.md)
