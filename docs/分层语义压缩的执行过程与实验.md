# 分层语义压缩的执行过程与实验

## 能力与当前成熟度

Context 可以显式启用模型生成的、带原文地址的分层摘要。模型可以压缩已经读取的资料，也可以合并先前摘要；系统从已接受的工具记录重建层级，让摘要、原文和摘录竞争同一请求预算，并复用原文恢复协议。

当前交付达到机制实现和确定性契约验证层面。真实模型的长任务收益尚未通过验收，默认保持关闭。本次真实实验也没有证明默认启用能提高任务质量。设计来源与重要取舍见 [ADR 0099](decisions/0099-带来源的分层语义压缩与原文展开.md)。

## 入口与调用过程

```python
from weavria.context import ContextCompilerConfig
from weavria.harness import HarnessConfig

config = HarnessConfig(
    configuration_id="source-summary/1",
    context=ContextCompilerConfig(
        window_tokens=32768,
        output_tokens=4096,
        semantic_compaction=True,
    ),
    context_recovery=True,
)
# 将 config 传给既有 AgentHarness.from_config；模型和计量器仍由宿主提供。
```

`AgentHarness` 自动注册 `weavria.tools.context_summary_tool()`，它使用普通工具的 Policy、期限、取消、参数指纹、调用预算、结果持久化和依赖记录。没有后台摘要任务，也没有预算之外的模型调用。可以同时开启 `extractive_compaction` 和 `work_summary_compaction`，三者分别负责短摘录、工作状态表示和分层来源摘要。

一次请求的路径如下。

1. 模型读取资料，从实际模型上下文取得 Artifact ID、原始 JSON Pointer 和可选的字符区间。
2. 模型调用 `compact_context`，提供当前任务版本、来源数组和陈述数组。每条陈述有 `finding`、`condition`、`counterexample` 或 `open_question` 类型，以及从零开始的来源下标。它记录可公开的工作内容，不收集隐藏推理。
3. `tools/summarize.py` 通过 `ToolContext.read_artifact` 读取当前 Run 有权访问的已接受成果，核验区间，计算实际内容摘要，产出 `ContextSummaryNode`。来源不存在、越界、过大或整体无压缩收益时返回具体反馈。来源错误不会被静默猜测修正。
4. Runtime 接受普通 `ToolRecord` 和不可变 Artifact。只有此后，新节点才能被下一次压缩引用；同批尚未接受的结果不可作为父节点。
5. `context/summaries.py` 按接受顺序构建摘要图，展开父节点的来源，重映射陈述下标，再将候选交给 `SessionContextCompiler`。
6. 编译器测量包含摘要的完整请求，分配器决定交付原文、摘录、摘要还是引用。会话适配器保存相同的摘要包络，存储层核验生产调用身份，并将请求和报告一并提交。
7. 模型需要精确证据时，用摘要叶子里的 `artifact.call_id`、`artifact.sha256`、`address.pointer` 和字符位置发出 `recover_context`。真正交付的原文进入证据清单，摘要本身不提供原文交付证明。

合并摘要时，来源指向先前摘要的整个 Artifact，即空 Pointer 且不带字符区间。不能只引用父摘要的一句话而丢弃其来源表。查看完整中间节点也可以使用已有 `read_artifact`；`recover_context` 只处理非摘要的原始工具成果。

## 图和选择算法

持久节点只保存直接边，不在每次合并时复制所有祖先。编译器按记录顺序维护 Artifact 索引和已验证节点表，每条边必须指向更早、身份一致、实际读取过的成果。这个顺序保证图无环。

普通来源成为叶子；已知摘要来源展开为该节点的叶子。相同来源地址和内容绑定去重，陈述下标映射到展开后的数组。每个节点最多 8 条直接边、8 条陈述，图深度最多 8，展开后最多 64 个不同叶子。一次编译只构建局部投影，不依赖跨请求的隐藏可变状态。缓存丢失后可从接受记录重建。

摘要候选复用现有覆盖分配器。当前任务和需求账本提供需求特征；摘要仅按实际可见文字评分，其需求特征权重是原文的 0.7，并移除因换措辞产生的片段新颖性奖励。相同需求特征采用最大覆盖值，减少重复摘要占用空间。原文和摘要都参与两路贪心与有限局部交换，候选成本使用完整请求的 Token 与字节计量。0.7 是显式启发式，不是置信概率，也尚未通过收益实验调优。

父节点与子节点并非强制互斥：如果子节点保留了父节点丢失的细节，它仍可产生额外效用。来源依赖至少保留引用闭包。当前反馈预留仍采用既有保守上界，深层节点和很大的生成参数可能使后续工具准入提前收紧；不能用摘要压缩比声称消除了全部上下文容量限制。

## 正确性与兼容边界

- 摘要内容是 `model_inference`。地址与哈希校验只证明引用绑定，不能证明陈述由来源语义蕴含，也不能证明模型确实理解了全部材料。
- 当前任务版本变化后，旧节点以及依赖旧节点的新提议退出活跃摘要内容。原文保留，仍可按新需求检索。
- 已消费的摘要调用以专门的摘要视图交付，不重复复制生成参数；最新一轮反馈保留真实动作—结果配对。旧执行事实不会被伪造成当前结论。
- 格式正确但来源内容摘要伪造、父节点部分引用、层级超限等情况，候选显示为 `invalid`；版本不适用显示为 `stale`。它们不替代原文。
- `SessionRequest` 新增 v8，`ContextCompilation` 新增 v14；旧版序列化保持原样，旧记录无需重写。v14 记录候选、有效、失效、拒绝、选择数量和字节规模。
- 这一版处理当前 Run 已接受的工具成果，不自动压缩用户指令，不跨会话继承旧摘要，不写入长期 Memory。
- 阶段结论与任务笔记仍由 `WorkingState` 负责；此能力补充来源材料的多层表示，不取代需求账本或完成验收。

## 2026-11-04 的实验结果

模型配置为 `deepseek-flash`，temperature 0，窗口 16384，输出 4096，最多 14 次模型调用。复用 M1 冻结资料，来源提交为 `f026796054a10132561faa4f2e7225a6e23390d4`。每个任务每组只运行一次，样本很小。此入口关闭任务理解与 Memory，以隔离 Context 能力，不代表完整 M1 配置。

自主对照结果如下。Token 是供应商报告的输入和输出总量，时间包含本地运行。

| 任务 | 配置 | 模型调用 | 总 Token | 秒 | 结果 |
| --- | --- | ---: | ---: | ---: | --- |
| 文档 | 摘录基线 | 3 | 9294 | 3.600 | 数值正确，漏一处要求的引用 |
| 文档 | 开启分层摘要 | 3 | 10131 | 2.829 | 数值正确，漏同一处引用；未调用摘要 |
| 源码 | 摘录基线 | 12 | 66358 | 20.385 | 两个字段错误 |
| 源码 | 开启分层摘要 | 9 | 48326 | 13.599 | 同样两个字段错误；未调用摘要 |

两组均未通过完整评分，且分层组未使用摘要，因此成本差异不能归因于分层压缩。

第一次显式功能验证中，文档任务发起 5 次摘要调用，全部因错误 Pointer、越界或无压缩收益失败；源码任务未发起摘要。这暴露了纠错反馈缺少具体结构信息的问题。实现随后补充原始根字段、实际范围长度和输入/摘要字节数；保持原有校验。

修正反馈后的第二次显式验证中，文档任务发起 2 次摘要调用，其中 1 次成功接受。最终字段正确，但仍缺引用；摘要未被分配器选为正文，现有原文表示仍被采用。源码任务耗尽 14 次调用，未生成摘要。该轮仅说明真实模型能够按反馈修正一次范围错误并创建合法节点，不能证明主动触发、层级合并、按摘要导航或任务质量改善。

这轮研究没有达到真实任务收益验收。下一步应研究何种任务压力和信息缺口需要触发压缩，以及生成摘要如何保留条件并带来新增覆盖；同时补充确实需要多轮压缩的任务。当前保持显式启用，保留失败结论，不将单个成功节点或确定性测试数包装为成熟 Context Engine。


## 后续实现：压力建议与联合选择

进一步设置 `summary_guidance=True` 可启用压力建议和多来源联合替换，仍须同时开启 `semantic_compaction`。旧配置保持原有策略。机制与不变量详见 [ADR 0100](decisions/0100-上下文压力建议与多来源联合替换.md)。

调用链增加两处：`context/summary_pressure.py` 在普通分配之后，用实际交付范围生成 `summary_advice`；`context/allocation.py` 在贪心之后尝试把一组祖先降级为引用并插入摘要，再用腾出的空间补入新需求。请求适配器保存完全相同的建议，存储层同时验证其交付范围和报告绑定。v9 请求/v15 报告不会改变 v8/v14 的历史序列化。

这一步的确定性实验能复现旧选择算法效用 22、新算法 25.4 且与穷举解一致的案例；这些数字是人工构造的特征效用，不是准确率。Harness 测试包含两层摘要后展开原文及重开数据库的幂等返回。完整的多层执行测试关闭任务理解以隔离协议；启用任务理解的测试验证单层摘要与恢复，已经满足完成条件后的额外合并仍受到收尾策略约束。

压力策略目前只建议已显示的足够长范围。它不会要求模型压缩未读内容，也不会通过降低反馈预留来争取一次摘要调用。建议协议在分配前计量，并预留 1024 字节/保守 Token 空间；最终按实际内容释放预留。具体来源放不下时降级为压力提示，提示仍放不下才撤回。这个成本会减少可选正文空间，不能声称无成本。对于已被切成许多短片段的材料，这种保守边界可能导致有压力却没有候选；对深层节点暂不主动推荐再合并。

新增的真实资料审阅任务要求逐篇提供条件/例外、精确引句和综合判断，覆盖冻结 corpus 全部文档或源码。工具与资料不包含预设操作顺序。评分只自动核验原句和出处，`evidence_passed` 不能当作语义验收通过。

```bash
uv run python -m examples.context_summary_experiment --run --audit --case documents --arm guided --env-file YOUR_ENV_FILE --output NEW_REPORT.jsonl
```

`--arm both` 为保留已有 CLI 的名称，加入后续阅读准备策略后运行 extractive、hierarchical、guided、prepared 四组；各组共享相同预算和任务。`--window` 可以选择至少 12000 的窗口，默认 16384。报告额外记录压力轮数、建议轮数、摘要采用轮数与最大深度。


### 本轮真实任务与失败诊断（2026-11-04）

冻结的多资料审阅任务使用全部 8 份文档，`deepseek-flash`、temperature 0、16384 窗口、14 次调用上限，三组各运行一次。三组实现摘要与实验入口摘要均一致；另一次开发中预跑因代码有变更，不纳入以下对照。

| 配置 | 模型调用 | 总 Token | 执行结果 | 摘要调用 |
| --- | ---: | ---: | --- | ---: |
| 摘录基线 | 10 | 52123 | 上下文预算错误 | 0 |
| 被动分层摘要 | 14 | 75110 | 调用预算耗尽 | 0 |
| 压力建议（后加建议版本） | 14 | 79295 | 调用预算耗尽 | 0 |

这些结果没有证明任务收益，任务均未交付可评分答案。时间包含本地开销且样本仅一次，不用于性能排序。

增加“建议因预算撤回轮数”诊断后，单独复测 guided 组：14 次模型调用、77317 Token、11 次读取成功、0 次摘要调用、10 轮建议被预算撤回。这直接暴露了“正文已经分满，再附加控制提示”的自我挤出问题。后续实现改为在分配前计入协议和有界预留，仍保留原有最低反馈、恢复保护和硬预算，不通过放松准入解决它。


预留控制空间后的单组复测：14 次模型调用、72883 Token，13 轮实际交付压力提示、0 轮提示被预算撤回，0 次具体摘要建议和摘要调用，最终仍耗尽调用预算。这验证了控制提示不再被挤掉，没有验证摘要收益。调用与任务路径具有模型非确定性，不能把单次 Token 下降归因于质量改善。下一项研究应定位可见材料范围、具体建议的容量与后续阅读选择之间的交互；不能仅调高摘要权重或绕过恢复/反馈预算。

## 后续实现：先补读，再决定压缩

设置三个开关可启用阅读准备策略：

```python
ContextCompilerConfig(
    semantic_compaction=True,
    summary_guidance=True,
    summary_preparation=True,
)
```

一次请求沿以下路径流转。编译器先按普通规则交付原文或摘录，`summary_pressure.py` 收集确实显示的地址。`summary_preparation.py` 测量真实来源元数据成本，枚举最多 162 个组合；只要能留出至少 512 字节陈述和 64 字节节省，就可以建议压缩，不再强制合计达到 4 KiB。该预算是建议，实际摘要仍须通过工具的完整尺寸校验。

如果可见片段太小，准备器用现有覆盖评分找一个已接受原文窗口。编译器预演“恢复后的一轮请求”，包括受保护证据和后续反馈预留；放不下就缩窗，最多三次。只有预演可放入且下一轮建议覆盖目标窗口，才向模型交付 `recover`。模型选择后，Runtime 正常检查累计配额和重复范围并提交恢复事实；下一轮真实正文到达，才会交付 `compact` 建议。准备过程没有隐式模型调用，也没有提前把未读内容标成证据。

这条链路用 `SummaryAdvice` v2、请求 v10、报告 v16 记录。`reason` 让“无压力”“材料不足”“恢复失败/耗尽”“完整请求放不下”“建议自身放不下”可被区分。报告另记录每轮实际可见范围的字节数，排查时不必输出原文。完整算法、边界和版本规则见 [ADR 0101](decisions/0101-压缩前的有界阅读规划与容量预检.md)。

确定性测试中的例子：单个大 Artifact 先只交付短摘录，编译器建议一个不超过 3072 个 JSON 字节的原文窗口；恢复后建议压缩这个不足 4 KiB 的范围；工具接受摘要；再次编译保留原文恢复保护，并排除重复压缩建议。SQLite Harness 测试将读取、恢复、压缩、回答作为四次显式模型决策，重开后同一 input_id 返回原有结果，不增加调用。它证明执行与持久化契约，不证明模型会自主选择这条路径。

```bash
uv run pytest -q tests/context/test_semantic_compaction.py tests/context/test_phase_budget.py tests/harness/test_summary_harness.py tests/test_context_summary_experiment.py
uv run python -m examples.context_summary_experiment --run --audit --case documents --arm prepared --env-file YOUR_ENV_FILE --output NEW_PREPARED_REPORT.jsonl
```

### 阅读准备的诊断结果（2026-11-04）

保持 8 份冻结文档、16384 窗口、4096 输出、14 次调用预算及 `deepseek-flash`。未加完整请求预检的开发版本发出 4 轮补读建议，模型尝试后被上下文预算拒绝，最终停滞失败，0 次摘要调用。这个失败说明“原文载荷小于 3 KiB”不是完整请求可放入的证明。

增加预检后的单次诊断中，6 轮记录为 `recovery_budget`，没有发出不可容纳的补读建议；后段原文读取产生较长可见范围，出现 3 轮具体压缩建议。模型仍未压缩，最终调用预算耗尽。这些开发中不同代码版本的运行用于定位断点，不作为策略收益的受控对照。

代码固定后的 guided/prepared 对照各执行一次，来源文件摘要、实验入口摘要、corpus 与任务摘要一致；两组配置只相差准备开关及 configuration_id。表中调用数是供应商 HTTP 调用数，并非 Runtime 尝试预算的计数。

| 配置 | HTTP 调用 | 总 Token | 补读建议轮数 | 具体压缩建议轮数 | 摘要调用 | 结果 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| guided | 4 | 12212 | 0 | 0 | 0 | 调用预算耗尽，无有效交付 |
| prepared | 14 | 75128 | 1 | 7 | 0 | 调用预算耗尽，无有效交付 |

prepared 另外有 5 轮因恢复容量不足而撤回补读建议，5 份编译报告携带恢复保护范围；这些报告数不能当作 5 次独立恢复。建议出现并未带来摘要采纳，任务也没有完成，因此这轮没有证据支持成功率或成本改善。两组调用路径差异很大、各仅一个样本，不比较性能优劣。报告包含逐文件源码摘要与实验入口摘要，可据其检查复现版本；开发中的单组诊断不混入本表。

本阶段全仓 `pytest` 为 1527 项通过。测试数反映回归覆盖，不代表自主能力提升。下一小步应针对这些轨迹研究阅读、压缩与直接交付之间的决策价值，并用保留条件/例外的摘要质量评测约束它；不能为了让摘要调用数变多而强制调用。

后续已加入独立的[摘要保真与压缩成本实验](摘要保真与压缩成本实验.md)：用冻结探针对比原文、首尾摘录与真实摘要视图，区分信息损失和原文阅读失败，记录供应商 Token 与理论摊销点。它为决策研究补充证据，尚不改变生产压缩策略。
