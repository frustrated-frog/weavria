# 真实文档问答与引用交付实验

本轮把真实文档检索接到了材料审查、带来源的答案生成与逐条复核，并补上最终回答的独立评分入口。它能区分材料不足、错误草稿与调用失败，但实验**尚不支持将多轮审查设为默认**：额外调用改善了一个词法补证请求，也造成协议失败和误拒，Hybrid 的实际交付率仍较低。设计边界见 [ADR 0120](decisions/0120-记忆答案的引用定位与交付审查.md)。

## 新增能力及调用过程

`ModelMemoryAnswerer` 消费已有 `ContextSupply`，不重新检索，也不创建另一套任务状态。一次请求依次经过：

1. `MemoryContextSource.retrieve` 从同一 SQLite 快照选择完整事实族，按配置执行联合审查和一次缺口补证。
2. `answer` 重新校验原问题与供给摘要。只有所有需求均为 supported 才继续；未审查与模型失败返回 unverified，缺失、冲突或条件不明返回 abstained。
3. 生成器只接收原问题和获准事实族的完整文本，返回有限的声明、成员序号和引文。宿主把序号解析为 bundle、memory ID、revision、source IDs，并定位原文字符区间。
4. 另一轮模型调用同时读取原问题、原文和草稿，逐条判断支持关系、逐个检查引用贡献，并判断是否答全。完整原文用于发现限定与例外，不能替一个不支持声明的引文补充依据。
5. 全部通过才返回 accepted 及答案；其余结果保留原因、摘要和已得到的复核向量，不发布草稿。输入错误抛出异常，取消传播；容量和模型故障显式返回失败。

核心实现位于 `src/weavria/harness/memory_answers.py`，原文定位位于 `memory_quotes.py`。`MemoryAnswerDraft` 与 `MemoryAnswerResult` 分开，避免把“引用能找到”误当作“回答已通过”。结果可以序列化审计，但当前没有自动写入 Runtime Trace、Artifact 或会话最终答案；宿主需通过公开 API 显式接入。

```python
# supply 和 demands 必须来自同一原问题及同一轮供给。
answerer = ModelMemoryAnswerer(provider, configuration_id=model_config_sha256)
result = await answerer.answer(supply, demands)
if result.answer is not None:  # 结果契约要求此时必为 accepted。
    for claim in result.answer.claims:
        print(claim.text, claim.citations)
```

可以另外配置 `reviewer` 和 `reviewer_configuration_id`。本实验生成、复核、评分使用同一模型的分开调用，没有共享聊天历史，但仍存在模型偏差相关性，不能称为独立真值判断。

## 冻结条件与指标

沿用前轮 CPython `v3.12.8` 四份完整 RST：178 段、231199 字节；开发、验证各 12 道正例及 2 道语料外负例。没有通过题目标注筛选检索输入。新评分要点在首轮模型实验前冻结于 `examples/fixtures/document_memory_answers.json`，绑定旧检索清单 SHA；每道正例写明必须回答的事实，负例要点为空。

本轮统一最多 3 个完整事实族、32768 字节供给，使用英文 Snowball 词形分析；Hybrid 同时使用 contextual_windows 和真实 multilingual-e5-small。相较前轮检索实验的 20000 字节，这里是新的固定供给预算，不能跨两轮直接归因比较。三个交付方案为：

| 方案 | 执行路径 |
| --- | --- |
| raw | 检索 → 生成来源已定位、语义未批准的草稿 |
| reviewed | 检索 → 联合证据审查 → 生成 → 逐条答案复核 |
| refined | 检索 → 联合审查 → 必要时一次查询扩展及补证、重审 → 生成 → 逐条复核 |

raw 仍要求原文定位，也允许主动不答；它并非完全无约束生成。补证复用既有单次预算、完整事实族和已有证据保护机制，没有增加多轮循环。答案生成/复核共用 120 秒期限；模型为 deepseek-flash，temperature=0、max_output_tokens=10000、reasoning_effort=none。温度为零仍不保证重复调用逐字一致。

盲评调用只看到原问题、人工冻结要点、标注原文及待评分声明，不看到策略标签，且不把评分回流给系统。指标分别计算：

- **答案正确**：所有要求事实都明确答对，且没有被评分器判为无依据的附加声明。
- **正确且引用支持**：答案正确，并且每条声明的实际引文能够支持它。
- **负例拒答**：系统主动返回 abstained；unverified、rejected 和评分失败都不算成功拒答。
- **成本**：交付链实际模型尝试次数，另列评分调用，不把评测开销混入系统调用。

评分器也可能出错。其结构化输出必须覆盖所有要点与声明，索引有效且不重复。最终脚本把已知维度写入可见 Schema；不合法结果标为 grade_failure，不中断后续案例、不自动重试，也不算答对或正确拒答。输出含计划问题、策略、是否完整执行的标记，禁止把中途结果当作完整分母。

## 首轮验证集结果

以下为 2026-11-11 至 12 日完成的第一次验证运行，共 84 行，全部策略使用同一冻结条件。没有按验证结果改提示、标签、融合权重或语义接纳规则。验证时评分维度已由宿主检查，尚未增加后续的可见 Schema 维度提示；本次 84 行没有评分维度失败。

| 检索与方案 | 正确且引用支持 / 正例 | 非空交付 | 正例 unverified | 负例主动拒答 | 交付调用 / 评分调用 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Lexical raw | 8/12 | 9 | 1 | 2/2 | 14 / 9 |
| Lexical reviewed | 8/12 | 8 | 2 | 2/2 | 30 / 8 |
| Lexical refined | 9/12 | 9 | 2 | 2/2 | 39 / 9 |
| Hybrid raw | 7/12 | 7 | 4 | 2/2 | 14 / 7 |
| Hybrid reviewed | 6/12 | 6 | 5 | 2/2 | 28 / 6 |
| Hybrid refined | 6/12 | 6 | 5 | 2/2 | 34 / 6 |

本次“答案正确”与“正确且引用支持”计数恰好相同，不能由此把两项合并成同一概念。Lexical raw 的第九个非空答案被评分器拒绝，其余非空答案均通过该模型评分。所有方案在两个负例上都能主动拒答，新增审查并未证明拒答提升。

三个值得继续追查的具体问题：

1. `l4` 中文询问日志系统退出时的缓冲写出和处理器关闭。Lexical refined 通过一次扩展补到了答案，raw/reviewed 没有；Hybrid refined 仍缺证据。扩展和通道融合的交互比“再多加一轮判断”更值得研究。
2. `a5` 在 shield 相关原文的引号上出现重复转义；`s6` 联合审查对同一成员返回两段引文，违反现有一成员一引文契约。两者显式失败，没有把模型字符串硬改成想要的事实，也没有为通过验证临时放宽协议。
3. Lexical raw 的 `s6` 附加了 Windows/SIGTERM 声明。源文确有相似句，但它处于 `send_signal` 的 API 上下文；脱离方法范围容易造成歧义。盲评判为无依据，这是需人工复核的语义边界案例，不能仅凭模型裁判宣称已获得绝对真值。审查分支在更早的协议阶段失败，因此该案例也不能用来宣称答案复核器成功拦截了此错误。

Hybrid 分支另有多次 unavailable，不能把整体交付率差异全部归因于检索算法。原始传输记录在请求失败后未占记录位置，导致后续按调用下标切片的 Token 观察错位；**本报告不使用该批逐题 Token 总量作成本结论**。已修复记录为每次尝试先占一行，并用连接失败、取消后继续成功的测试验证对齐。调用次数在发请求前累加，以上调用计数不受这个日志问题影响。没有为了得到更好成绩删除故障案例或只统计成功调用。

## 开发过程中的失败与修复

第一轮 Hybrid 开发集 raw 为 12/12，reviewed 为 9/12，refined 为 10/12；调用分别 14、34、37。不能只报告改进后的数字。失败包括换行/字面量 `\n` 定位错误、把附近不同 API 的行为误判为冲突、以及引用缺少方法指代背景。

本轮修复只将引文定位扩展为唯一的源文空白/控制字符匹配，返回并哈希原文切片；大小写、标点、词语和语义判定仍保持严格。对应真实 `a1` 清理与取消传播请求，以及 `l1` 日志方法请求，修复后能够继续交付。

之后一次开发重跑在第 31 行评分时收到维度不符结果而中止，30 行已完成结果保留为中途产物，不作为 12 题完整成绩。最终脚本将评分失败隔离，并重新运行完整开发集，没有用重复运行挑选每题最好结果：

| Hybrid 开发方案 | 正确且引用支持 | 负例主动拒答 | 交付调用 |
| --- | ---: | ---: | ---: |
| raw | 12/12 | 2/2 | 14 |
| reviewed | 11/12 | 2/2 | 36 |
| refined | 10/12 | 2/2 | 40 |

最终 42 行完整运行没有评分失败。reviewed/refined 均在 `s2` 上将附近 API 行为判断为冲突；refined 的 `a1` 这次通过原文定位，却在后续语义复核中被拒绝。因此定位错误确实消除了，但不能宣称该题从此稳定完成。补证分支也不保证比不补证更好，模型波动和附加声明仍会改变交付结果。

`a1` 的具体拒绝点是：声明同时写了“通常不应调用 uncancel”与“确需抑制时调用 uncancel”，引文只覆盖后半句。复核保留了完整问题覆盖为 true，但将该声明判为 unsupported，最终不发布整个草稿。这说明本次检查确实触及了声明与引用的关系；还没有实现自动补齐引用或缩减附加声明，因此正确的核心回答也可能随草稿一起被拒绝。

开发记录分别保留于本机 `/tmp/weavria-doc-answers-development.json`、`development-final.json` 和 `development-complete.json`（后两者也使用 `weavria-doc-answers-` 前缀），验证记录为 `/tmp/weavria-doc-answers-validation.json`。临时目录不是永久归档；可用上述冻结清单和脚本重新生成独立记录。完整开发复跑之后另补了重复引文识别和传输观察对齐的确定性回归，没有据此改写已运行的模型成绩。

## 当前边界与下一步

没有实现自动修复答案、遇到失败反复重生成、通用最终交付策略替换、多模型集成投票或来源事实真伪鉴定。一个小型真实文档集、同模型评分和单次验证，不足以证明普遍能力提升。协议正确性与语义可靠性必须分开看。

下一步应优先研究**按 API/段落范围组织证据，以及一个事实成员内多段支持如何表达**，同时保留原文地址和失败诊断。先用独立新增文档冻结引用范围、否定和条件对照题，再比较分段引用与当前连续引文基线，检查误拒、漏拦与调用成本；不能通过持续放宽匹配规则掩盖证据粒度问题。
