# 双组件升级建议的修订验收

2026-11-19。结论：同一个单 Agent 在三个独立会话中都交对了首版，但只有一个会话交对了修订版。两个未交付案例停在不同阶段；本轮保留回归用例，没有新增 Planner、重开覆盖审计专题或放宽完成条件。

## 冻结的任务和答案

W17 是一组专为验收编写的小型发布材料，不是生产发布记录。首轮提供三份文件：发布清单确定两个目标构建和生产环境；兼容性表按构建和环境匹配；测试登记同时含正确门禁和其他环境、构建、测试套件的干扰记录。模型须给每个组件四个字段：候选版本、是否兼容、适用的测试回执、升级或暂缓的建议。

交付首版后，QA 在归档中追加一份复核单，仅撤销一条回执并给出替代记录。旧文件保持原样。第二轮用户要求修订上一版并交付两个组件的完整报告，不复述首版格式。两轮通过同一 SQLite 会话衔接；两轮间重开 Harness、更换只读快照，工具名称和契约保持不变。首轮搜索或读取任意路径都不可能得到复核单。没有向模型提供预填解释、工作图、工具顺序或评分答案。

| 组件 | 首版 | 修订版 |
| --- | --- | --- |
| ferrite | 2.4.1，兼容，T-641，升级 | 四个字段都不变 |
| linden | 7.3.0，兼容，T-643，暂缓 | 7.3.0，仍兼容，T-697，升级 |

独立验收器比较交付内容与预先人工标注的答案。顺序、空白不计分，重复键、错类型、漏组件、旧回执或改错另一个组件均不通过。首版与修订版都须达到 completed 且内容正确，才算整对通过。首版没完成的会话仍计入分母。工作笔记数量、工具调用次数和模型自称完成都不是通过条件。

## 冷启动结果

使用现有统一 Harness，任务理解和覆盖审计开启，工作记录、局部工作补丁和证据变化重验开启。三次从独立空会话开始，运行中没有调提示、换模型或追加成功样本。模型 deepseek-flash，温度 0，reasoning_effort=none，输出上限 4096 Token。每轮请求限时 210 秒，准备阶段至多 60 秒，执行阶段至多 150 秒、16 次模型调用、24 次工具调用。

| 会话 | 首版 | 修订时发生了什么 | 两轮供应商调用 / 总 Token |
| --- | --- | --- | ---: |
| 1 | 正确交付 | 两次覆盖声明均因义务来源不合法被拒；未进入执行，没有修订候选 | 8 / 36,278 |
| 2 | 正确交付 | 正确的修订候选提交两次；两次都收到 missing_evidence，最后未交付 | 15 / 83,273 |
| 3 | 正确交付 | 正确更新 linden，完整保留 ferrite，宿主接受 | 10 / 49,311 |

会话 2 的最终账本只剩 `$freshness` 缺口：准备阶段把新增复核单解释成需要验证现实时效的需求。只读归档能证明文件里的内容，却没有提供现实时间有效性证明。候选与标准答案一致不能推翻宿主当时的约束，因而不计任务成功。会话 1 记录的是 `invalid_obligation_source`；仅凭这个不含原文的错误类别，无法确定模型引用了哪句话。

进入修订执行的两次都读取了复核单，也都重读了三份首轮资料。它们都生成了内容正确的修订候选，但只交付了一份。**结果说明有能力正确更新一项并保持另一项，不说明模型做了增量推理或避免了重复工作。** 这组小样本没有显示反复改坏未受影响组件，也没有在不同会话复现同一种交付阻断。当前不为这一个样本调整框架行为。以后如果独立任务重复卡在同一位置，应沿相应的准备或验收轨迹定位。

## 复现与诊断

```sh
uv run python -m examples.upgrade_review
uv run pytest -q tests/evaluation/test_upgrade_review.py
uv run python -m examples.upgrade_review --live --repeats 3
```

默认离线输出任务、材料、独立答案的 SHA-256 及配置。真实调用使用现有 `WEAVRIA_MODEL_BASE_URL`、`WEAVRIA_MODEL_NAME` 和供应商凭据；每批独立建目录，每轮结束立即保存结果。完整会话有失败时返回非零。首批本地留证目录为 `.weavria/upgrade-review/run-se2da9qw/`，包含 `results.json` 及三个会话数据库，不进入版本控制。

```sh
uv run python -m examples.upgrade_review --replay .weavria/upgrade-review/run-se2da9qw/2.db
```

回放以只读方式逐条解析持久事件，不请求模型、不更改会话。通过 input_id、任务原文和 run_id 区分两轮，按 Run 与候选摘要对应 Finish 和宿主验收。输出中 `candidate_errors=[]` 表示候选内容正确；`delivery_errors=[]` 才表示该轮交付通过。没有候选或终态时保留未知，不从其他轮借用成功记录。回放得到的两轮结果分别与首批三个数据库核对过。
