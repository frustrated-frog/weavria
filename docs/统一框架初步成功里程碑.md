# 统一框架初步成功里程碑

制定日期：2026-11-01。代码基线：`f026796`，分支 `codex/unified-harness-lifecycle`。

## 目标与终点

**M1：可独立使用的单 Agent 框架 Alpha。**

开发者只通过公开入口提供模型、工具、存储和授权，就能让真实模型完成多步任务；任务、工具、上下文、工作记录、记忆和反馈在同一个执行生命周期内协作。既能演示和解释源码，也能在固定任务上复现成功与失败。

本里程碑约束当前“把已有模块串联起来”的阶段，不修改或降低《长期研发宪章》。达到 M1 后停止本阶段功能开发，交付 Alpha 候选版本。它不代表所有子系统都已成熟或已适用于生产。

## 五项验收条件

### 一、一次接入即可运行

- 独立示例仅通过 Weavria 公开 API 接入，不导入框架私有模块，不依赖 FinScope 服务。
- 应用提供模型及计量器、工具、路径和授权；不手动消费事件形成记忆、不替框架更新工作状态、不逐轮重建工具和上下文。
- 同一入口支持两种场景：项目文档研究、代码仓库只读分析。二者使用各自材料与工具，核心不出现案例名称、答案、固定调用顺序或领域分支。
- 接入说明提供依赖安装、环境变量名称、完整运行命令和读取结果的方法。凭据不进入仓库。

### 二、已有模块形成真实闭环

冻结六类场景，验收实际行为：

| 场景 | 必须成立的行为 |
| --- | --- |
| 多步任务 | 模型根据原始目标选择行动，工具结果更新任务进展，最终结果满足任务要求 |
| 长上下文任务 | 原始材料总量超过声明的可用输入窗口至少两倍；上下文选择与原文回取仍能支持正确结果 |
| 澄清续接 | 模型识别阻塞任务的歧义，用户补充后继续同一工作，不丢失已接受结果 |
| 中途修订 | 新目标影响下一轮任务视图、工具与上下文；旧工作记录按依赖保留或失效，最终回答符合新目标 |
| 跨会话记忆 | 约定从真实用户输入形成，在新会话被使用；用户明确修订后正确使用更新后的约定 |
| 失败后继续 | 一个来源失败后仍能使用其他可用来源或修正行动，成功结果保留，最终完成或明确说明无法完成 |

不要求所有任务都调用所有模块。简单请求允许直接回答，工作记录按需更新，没有可复用信息时允许不形成长期记忆。

模型必须接收自然语言目标并实际决策；工具、宿主或测试不得预填正确 Task Frame、Need Ledger、答案、工作笔记或记忆。故障和用户修订可以按固定外部事件触发，但不能替模型指定解决路径。

### 三、真实模型达到小规模可用门槛

- 冻结 **12 个任务**：两种场景各覆盖上表六类；每个任务独立运行 **3 次，共 36 次**。
- 在首次运行前固定材料版本、初始环境、用户澄清与修订内容、评分规则、模型配置和所有阶段预算。每次从干净状态开始；记忆任务内部保留必要的多会话顺序。
- **至少 30/36 次任务成功，且每个任务至少 2/3 次成功。** 未完成、超时、超预算、结果错误均计入失败，不通过增加尝试挑最好结果。
- 成功必须同时满足预先声明的结果要求和场景行为要求；Runtime 返回 COMPLETED 或模型自称完成不算独立验收。结果检查优先用可核对事实、文件/符号位置和任务特定断言，需要语义判断时保留人工复核依据。
- 任务失败必须保留；不得看到结果后删除困难任务、放宽评分或单独提高某个任务预算。确认评分器缺陷时先记录修订理由与版本，再完整重跑受影响的比较组。

这是自定的 Alpha 验收门槛，样本规模有限，不据此宣称泛化成功率或成熟框架水平。

### 四、工程行为与机制代价可解释

- 相同 input_id 重试已完成输入，不重复执行模型任务或工具；记忆失败可单独续接。
- 用户取消、工具失败、形成超时和请求期限耗尽均有明确结果，清理完成，无遗留任务；已经完成的回答不因后置形成故障被改成执行失败。
- 澄清、修订、工作记录、来源与完成结果的版本保持一致；不接受过时结果冒充新目标成功。
- 以上承诺以现有契约测试和必要的组合回归验证，相关质量检查全部通过。只补覆盖缺口，不以增加测试数量作为交付目标。
- 报告每次任务的结果、模型调用、工具调用、各阶段 Token、耗时和失败原因。总量统计不冒充框架尚未实现的跨阶段强制 Token 预算。
- 同一冻结任务集额外运行一组朴素上下文基线：只把公开的 ContextCompilerConfig.policy 改为 `recent`，其余模块、材料、模型和预算保持一致。比较任务表现和代价，完整记录负收益；无需新增评测平台。基线是否更差不决定“接通可用”是否成立，但没有正向证据时不得宣称选择机制带来任务收益。
- 源码说明能沿一项任务讲清需求账本、工作记录归约、需求覆盖工具选择、上下文分配、来源回取及记忆形成如何交互。工厂和类型包装本身不算技术深度证明。

### 五、形成可交付版本

- 提供固定代码提交、推荐配置、两个独立示例、任务清单、完整验收报告及已知限制。
- 已有公开行为和持久化格式保持兼容；必要变更有明确说明。
- 本阶段所有验收项完成后，标记 M1 达成并交付 Alpha 候选。进入新阶段须有用户选择的新目标，不自动把可改进点追加到 M1。

## 固定的三项剩余交付

1. **链路收口。** 映射上述六类场景到当前代码和测试，补足推荐入口的必要组合覆盖；复现断点才修改。冻结 12 个真实任务及评分规则，完成后停止增加场景。
2. **真实运行与有限修复。** 执行冻结任务和朴素基线。按失败结果修复影响 M1 的问题，最多进行两轮“明确问题清单 → 修复 → 回归 → 完整复测”。不因某个模块仍有研究空间另开专题。
3. **版本交付。** 整理独立接入示例、源码流程和验收结果。达标就结束 M1；未达标则交付具体阻塞与结果，明确标记“未达成”，停止自动追加开发轮次，由用户决定继续、调整目标或暂存。

## 停止扩张的规则

只有能明确对应上述验收失败的修改才进入 M1。重构必须是修复该失败所必要的，不以代码更优雅为由展开全仓调整。已有能力通过验收就复用，不重新实现。

本阶段不新增自动崩溃续跑、后台记忆 Worker、Skills 系统、多 Agent、分布式运行、Control Plane、向量数据库、新摘要算法或跨阶段总 Token 强制预算，也不进行 FinScope 联调。它们保留在长期研发方向，不作为本阶段完成前提。

任何新的能力、验收类别或“下一步”建议都先进入后续候选清单，不能静默延长 M1。发现已有能力存在严重正确性问题仍必须如实处理和报告，不能为按期收口隐瞒；超过两轮修复仍不达标时按未达成收口。

**初步成功的判据：能独立接入、真实模型能完成固定任务、已有模块共同参与执行、失败可解释、别人能复现；五项全部成立就停止本阶段。**
