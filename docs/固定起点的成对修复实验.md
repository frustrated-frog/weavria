# 固定起点的成对修复实验

## 本阶段解决的问题

上一阶段两组真实运行分别生成任务解释和初始代码，观察到的成本差额无法单独归因于依赖反馈。本阶段增加可重复的修复实验入口：固定任务解释，通过正式工具链构造相同的工作区，再把后续行动交给模型。默认不联网，显式 `--run` 才调用模型与 Docker。

这次完善的是反馈机制的验证能力，没有调整生产默认策略。固定解释和初始化程序只用于控制实验起点，不能据此宣称框架具备更好的自主理解、根因发现或端到端规划能力。

## 场景与控制变量

四个场景共享冻结 Python 源码、原始任务、TaskSpecification 和独立验收器。任务解释只描述资料、计算能力与交付目标，不告诉模型发生了哪种错误。

| 场景 | 初始化状态 | 要观察的问题 |
| --- | --- | --- |
| statistics | 每个文件的函数数多算 1，没有第二阶段报告 | 上游条件与两个下游缺口并存时能否有效修复 |
| report_format | 统计正确，报告总数正确但分隔符为冒号 | 只有一个内容问题时，依赖选择是否增加无用成本 |
| preservation | 子工作区重排统计 JSON 的缩进，同时报告格式错误 | 是否回到正确父版本，保持原始统计字节并修复报告 |
| clean | 两阶段成果已正确 | 无需修复时能否直接完成，避免多余计算 |

`RepairSeed` 包含初始化程序和独立计算的预期工作区版本。版本摘要同时覆盖文件内容、路径及父版本；只比较最终文本不够，因为不同父版本会改变合法修复操作。每个场景的两组使用同一个 seed。初始化失败或摘要不同，不能进入有效配对。

模型配置、Runtime 预算、任务原文、规范化解释、数据摘要、Sandbox Profile、场景摘要及当前实际运行源码摘要组成 `comparison_sha256`。源码摘要包含工作区已有修改，不假定 HEAD 等于执行版本；凭据和环境变量文件不参与摘要或报告。场景和重复编号组成配对键。重复成员、缺少策略成员、配置不一致会拒绝比较。

## 一次实验如何执行

1. `examples/repair_cases.py` 创建固定解释与场景。预期成果由宿主独立解析原文得到；初始化程序在容器中重新计算，不直接把预期答案写入执行结果。
2. `SeededRepairModel` 先提出读取源码、计算统计及必要的报告工具调用。这些动作经过原有 Runtime、Policy、预算与 Artifact 接受流程，没有直接改写账本或伪造工具成功。
3. 最后一个初始化结果到达时，包装器核对预期工作区摘要，然后将后续请求原样交给真实模型。初始化历史及当前诊断对模型可见，但包装器不提供下一步修复代码。
4. `examples/repair_feedback.py` 调用原有 `run_task`，两组只选择 `prefix` 或 `dependency_frontier`。为避免总由某个策略先运行，按场景和重复编号交替顺序；没有并发共享 Session 或可变模型包装器。
5. 结束或取消后，重新打开 SQLite，从接受的 ToolRecord 读取完整成果及受控附件，使用同一个 `VerifyWorkspace.diagnose` 独立检查每次自主计算后的全部条件，不拿截断后的模型反馈打分。
6. `RepairTrial` 立即追加到 `runs.jsonl` 并 flush。完整配对才生成 `comparison.json`。每个成员的 SQLite 保留在本地 `sessions/`，可以沿真实接受事实检查失败。

初始化占用 Runtime 的真实调用预算：statistics 有两次初始化工具调用，其他场景三次；同场景两种策略完全一致。模型调用指标只统计交接之后的调用，Token 采用真实供应商 usage，其中包含初始化历史被送入模型的成本。不能把脚本初始化轮次算成模型自主行动。

## 指标与失败语义

`RepairStep` 保存一次自主计算的执行状态、工作区摘要及完整未满足条件集合。`unchanged_repairs` 统计与前一次相比，条件集合未变的计算次数。这只是描述性指标：数值部分改善可能仍对应同一个条件，不能直接把它当成无进展停止策略。

`verified` 同时要求初始化有效、Runtime 完成、独立验收确认没有未满足条件。单次 Python 的 completed、模型说完成、没有展示诊断，均不能替代这三个条件。

保留模型失败、预算耗尽、取消与框架异常成员，不只汇总成功样本。未知 usage 保持 `null`，不填零；任一成员 Token 未知，配对 Token 差值也未知。所有差值为依赖策略减前缀策略。`comparable` 说明控制变量成立，不表示任务成功或策略具有统计显著收益。

Provider 状态只记录调用次数、HTTP 状态及 finish reason，不记录认证信息或响应正文。遇到 HTTP 401/402，保存当前成员及 `interruption.json`，停止后续批次。这样的成员被标记 `provider_unavailable`，不能作为能力比较证据。部分批次不会产生伪装完整的 comparison 文件。

取消在记录后继续向上传播；若诊断或写报告本身失败，仍传播原始取消并保留错误原因链，不把取消变成普通评测失败。统一 Harness 负责工具和存储关闭，Transport 在 `finally` 中关闭。并未提供跨进程实验自动恢复或从部分批次继续计分。重新运行需使用新目录，原有结果保留。

## 运行与观察

```bash
# 只检查四个初始化版本，不联网、不启动容器。
uv run python -m examples.repair_feedback

uv run pytest tests/evaluation/test_repair_feedback.py -q
WEAVRIA_TEST_DOCKER_IMAGE="$SANDBOX_IMAGE" \
  uv run pytest tests/evaluation/test_repair_feedback.py -m docker -q

# 明确启用模型与容器；输出目录必须不存在。
uv run python -m examples.repair_feedback --run --repeats 2 \
  --image "$SANDBOX_IMAGE" --env-file .env.finscope-debug \
  --output /tmp/weavria-repair-paired-new
```

配置文件是 `configuration.json`，逐次记录是 `runs.jsonl`，完整配对结果是 `comparison.json`。中断时另有 `interruption.json`，SQLite 位于 `sessions/`。这些都是本地运行数据，不应提交 Git。环境变量文件只是本机已有模型配置，不依赖 FinScope 服务或业务数据。

## 本轮验证与尚未完成的实验

2026-11-06，全仓测试 1689 项通过、24 项显式 Docker 测试默认跳过。新增四个真实 Docker 初始化场景均通过；随后补充 Provider 停止与取消期间落盘失败校验，最终 15 项定向回归通过。类型、Lint 和格式检查通过。

真实实验曾启动四场景、两策略、每组两次，共 16 个成员。所有初始化摘要匹配，但全部在首次真实模型调用发生 `HTTPStatusError`，没有自主修复工具调用，usage 未知。一次后续诊断明确返回 HTTP 402 `insufficient_balance_error`。因此**这轮没有取得可用的真实修复收益证据**，不能写成功率对照或声称依赖策略更省 Token。

原始失败记录保留在 `/tmp/weavria-repair-paired-20261106/`。该批发生在新增 HTTP 状态记录和遇 401/402 停止逻辑之前，旧报告没有逐成员 HTTP 状态，不能把诊断请求的 402 回填成每一项的已观察状态，也不将旧 comparison 的控制变量通过视为模型效果可比较。新版入口已用离线注入验证遇余额错误只执行一个成员、保留部分记录、不生成总体比较。

模型额度恢复后可按上面的命令重跑。当前仍只覆盖一个源码任务的四个错误位置，尚未覆盖多个独立任务、复杂依赖图和不同模型；需要增加有效样本后再决定是否调整默认策略。没有引入论文算法、生产自动纠错调度或跨能力图。
